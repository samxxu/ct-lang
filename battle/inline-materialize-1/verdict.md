# battle/inline-materialize-1 判决

> **状态：`closed`**（2026-11-19；裁判 EDITOR；1 轮 claim/counter/evidence）。
> **结论：B 胜（就当前提案与当前语法）；A 的“inline 物化”方向不被永久否决，但 `.m()$name` 这一稿不进入实现。**

## 1 逐项判决

| J | 结论 | 依据 |
| --- | --- | --- |
| J-1 真实价值 | **B 胜** | 935 个 `.ct` / 67,771 行中，A 形态仅 4 处；每处只省 1 行、8–13 字符；`238` 中 A/B 同为 3 行，A 还要 2 个未初始化声明。没有证据表明这是普遍痛点。 |
| J-2 语法歧义 | **A 通过（但成本存在）** | `$` 只从 `T_PUNCT` 回退产生，标识符分支不接受 `$`；现有 `$ident` 0 处，range/into/errdefer 的 `$` 后跟 ID 会报错，无合法程序歧义。但 `$` 增加第 4 个义项，文档/诊断负担真实。 |

## 2 采纳：B（当前稿不实现）

1. **不新增 `.m(args)$name` 语法。**
2. 现有写法：
   ```ct
   HttpRequest req = "...".method("GET");
   req.header(...).send();
   ```
3. 兄弟方法仍用：
   ```ct
   a into {
       .m();
       .n();
   }
   ```
4. 文档需补 `into` 的教程入口；目前只有 spec §4.52、examples/29、55 个测试，tutorial/README 缺失。
5. **SH-73 不是本提案前置依赖**；它仍是动态派发临时值接收者的有意限制。

## 3 A 的方向：保留，但另立提案

用户提出的“CT 鼓励链式，缺少 inline 物化会显得僵化”是**产品方向**，不被本判决否定。  
A 若重启，必须满足：

- C1：至少 3 个**外部真实代码**站点，证明两行拆分造成实质负担（当前仓内 4 处单跳，不足以证明）；
- C2：只允许**已声明变量**，删除“`T x = <call>`”这种声明形态；不引入 `?.m()$x`，直到 L53-7 落地；
- C3：明确 definite-assignment 规则；没有该检查前，不承诺“未初始化使用报错”；
- C4：明确 `$` 第 4 义项的 lexer/parser/诊断边界；不宣称“零新分支”；
- C5：明确 own/接口/容器/`into`/range/尾随块的禁用矩阵；
- C6：重新跑真实语料与全量门禁，不能只靠 4 个构造样例。

在这些条件满足前，`$name` 只是“少写一行的语法糖”，不足以进入 phase。

## 4 不采纳

- 把 `$name` 说成 SH-73 的语法糖或前置依赖；
- 说 `$name` 能修 `a.m().n()` 的 SH-73 限制；
- 用 `into` 替代所有链式；`into` 不能换类型、不能接接口/own 接收者；
- 用 `$name` 替代 `into` 处理兄弟方法；
- 在无 definite-assignment 的情况下承诺未初始化诊断。

## 5 证据限制

- A 未实现，无法验证其新诊断/生成物。
- 外部 `ct-http` 语料按 DB-3 未访问；外部需求无法独立复核。
- 全量测试有 4 个并发/环境噪声失败；单独复跑全绿，不能宣称干净全绿。
