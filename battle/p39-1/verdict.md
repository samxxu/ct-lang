## 0 判决摘要

1. **J-1 不成立**：A/A′ 的导出面定义（`docs/design/phase39-draft.md:37`）没有任何「只导出子集」的输入；主张席在 `claim-r2.md:56` 自认这一点。f1 夹具通过（V15）不能改变判据整体。
2. **J-2 不成立**：「不改一行即可构成 `--lib` 库」在 5 个单元上失败（A），A′ 下仍有 2 个 trait 值单元 + `Str.h.ct` 作根失败（V5/V6/V8）。
3. **J-3、J-4、J-5 成立**：零新语法（V1）、成本估算双方相容（`claim.md:355-362` 对 `counter.md:189-197`）、硬错路径天然带 `file:line:col`（V11 + 本席复核 `Diag.h.ct:85`）。
4. **按 §7.9 判 `rejected`**：判据未被满足，且反证清单 C2、C3 被证据证实。
5. **证据席「`--lib`/L39-1 未实现，E3 预测无法执行」是正当的无法判定理由**：所有「A / A′ 落地后应得到什么」的断言（含 exit≠0、不写产物；`claim.md:335-347`、`claim-r2.md:205-219`、`counter.md:174-181`）一律记为无法判定（§4 U-1），**不作为任何一方的胜证**；本判决不建立在这些预测上。
6. **卡面自相矛盾 C3 成立，必须修**：`:45`（泛型跳过）与 `:60/:102/:134/:194`（泛型硬错、负例 `p39_export_generic/`）对同一对象给出相反处置。修法进 C 方案（§6），本席不改卡。

## 2 逐条判定

### 2.1 J-1 意图一致 —— **不成立**

**判据原文**（`question.md:18`）：用三个夹具（纯 C 兼容库 / 含泛型 `pub` helper 的库 / 含 trait 类型 `pub` 方法的库）分别构建，方案能否只导出作者要的、**且不把其余判死**。

**已出证的做法与结果**：
- f1 纯 C 兼容：`.abi.h` 恰 2 个原型（2/2），V15；主张席 `claim.md` E1-6 与证据席一致 → 这一格通过。
- f2 含泛型 helper：今天的 `--emit-c` 只声明 `from_lib`、`id` 一字不出且零诊断（V2，`claim.md` E1-2 逐字复现）；纯 C 消费者今天就能 `#include "lib.h"` 链接运行（V4，`counter-r2.md` §2 复现）。泛型实例是 `t`（local），`from_lib` 是 `T`（V3、V10）。
- f3 含 trait 值：`sink_open` 是 `T`（V10），生成头把 `*_iface`/`*_vtbl` 当导出类型发出（V12 的 bound 形态同理）。
- 结构性事实：仓库内 53 个顶层 `pub` 函数里 12 个非 C 兼容、分散 5 个单元（V5/V6）；`selfhost/ct-ast` 72 个顶层 `pub` 函数声明（V13）。

**为什么不成立**：
1. **判据的核心句「只导出作者要的」没有实现输入。** 导出面定义是「本次构建所有非内建 `.h.ct` 单元的有定义 `pub` 函数」（`:37`，verify.json anchors 已核），逐字没有任何清单/标记/白名单。主张席自己在 `claim-r2.md:56`（§1 Q5）写：「A/A′ 确实没有『只导出 C 兼容 `pub` 的真子集』的输入；这是 A 的公开定价。」这是**自认**，不需要任何未实现的编译器行为即可成立。
2. **`pub` 不是「C ABI 意图」的充分信号。** `docs/language-spec.md:617`（anchors 已核）：「`pub` 只表示导出：未标 `pub` 的全局仍只属于本单元」；`test/modules/p34_pub_generic/main.ct:9`（anchors 已核）用 `id<int>(3)` 证明同一个 `pub` 的服务对象是 CT 消费方（`counter-r2.md` §3）。因此「导出集合 = 作者意图」在 `pub` 这一层无法成立——除非把 `pub` 重定义为「对 C 的承诺」，那是语义变更，不是判据满足（`counter.md` §1 C4）。
3. **f3 仍被判死，且是用户已定的处置。** D39-6（`:60`，用户 2026-11-13 批准三项决策之一）逐字含「trait 值、泛型……一律 L39-1」；`claim-r2.md` §4 J-1 自己把 f3 的失败记为残留风险。这一半是「判据要求」与「用户已定黑名单」的冲突：本庭**不能**替用户改 D39-6（生效范围见 §6），但判据文本仍未满足——如实记 `不成立`，并在 C 里把「f3 类单元能否成库」列为**需用户批准**的项。

**本席不采用的两条论证**：
- 「A 会在 f2/f3 上整建失败、不写产物」——`--lib` 不存在（V1），这是规则推演 + 预测，执行层无法判定（§4 U-1）。本席只用规则文本（`:102/:104/:134`）说明「按卡面 A 会中止」，不用它作为 J-1 的独立失败证据；J-1 的失败已由第 1 点（无子集输入、自认）独立成立。
- 反对席「72 个全部进 `.abi.h`」（`counter.md` §1 C2）——V13 计的是 `pub` **声明**；本席只读复核 `Symbols.h.ct:423` 是 `pub` 原型、定义在 `:1825` 且定义行不带 `pub`。是否在 AST 层继承 `is_pub` 未出证，故本席**不**以 72 条为据（见 §4 U-4）。C2 的成立依据只取「无子集输入」这一条，它与 72 条无关。

### 2.2 J-2 既有代码零语法改动 —— **不成立**

**判据原文**（`question.md:19`）：`lib/std/**/*.h.ct`、`test/modules/**/*.h.ct` **不改一行即可构成 `--lib` 库**；统计其中「非 C 兼容 `pub` 函数」的数量与位置。

**已出证的数量与位置**（V5/V6 逐行可审计）：53 个顶层 `pub` 函数声明、12 个非 C 兼容（`lib/std/Str.h.ct:33,51,63,70,80,99,117` 七个按值 `Str`；`p34_pub_bound/lib.h.ct:21,26` 与 `p34_pub_generic/lib.h.ct:3` 三个泛型；`ns_types/hal/uart.h.ct:22`、`xunit_box/net.h.ct:22` 两个 trait 值），3 个 `Point` 按值原型待定，69 个 `.h.ct`。V7 证明反对席的 54 只多一条 `test/modules/extern_decl/lib.h.ct:6 pub extern int lib_fn(int x);`，按 D39-2 不进导出面，分母应为 53；其 `scan.py` 只标 10 条（缺 trait 返回值判据）。

**为什么不成立**：
- 硬错版 A：5 个单元（`lib/std/Str.h.ct` 作根、`p34_pub_generic`、`p34_pub_bound`、`ns_types`、`xunit_box`）在不改一行的前提下不能成库——这正是 `claim.md:49` 自认的「5 个单元 12 个 `pub` 做不了 `--lib` 根」，也是 `counter-r2.md` §1 Q1 对判据文本的读法（分号后的统计只有在「要能成库」时才有意义）。
- A′：3 个泛型站点可按「跳过 + 诊断」转好（`claim-r2.md` §4 J-2），但 2 个 trait 值单元与 `Str.h.ct` 作根仍按 D39-6 硬错 → 「不改一行即可构成」仍不成立。
- 残余失败的归因：A′ 剩下的失败全部由 D39-6（用户已批）造成，**不是选择机制本身的缺陷**。本席因此把 J-2 判为不成立（判据文本未满足），同时把「这 2 个单元要不要能成库」移交 C 的需批准清单，不据此否定任何机制方向。

**本席对双方口径的更正（都影响证据强度）**：
- 主张席 A-1（`claim.md:319`）「`lib/std/Str.h.ct` 的 7 个 `pub` 会让 std 不能做 `--lib` 根」是**无条件表述错误**：V8 实测，根在别处时 `find_builtin` 载入 4 个内建单元（`Str` 是内建 → 按规则 1「非内建」不进导出面）；只有 `Str.h.ct` 自身作根时才是普通单元（3 个内建）。verify.json 的 unreproduced 第 2 条已记。
- 反对席 C5-1（`counter.md:48-52`）「`vendor/std` 是普通单元 → 7 条 L39-1」按默认路径**不成立**：V9 显示 `import std::str` 直接报 `cannot resolve import 'std/str'`，`vendor/std` 从不被读（`Driver.h.ct:432` 注释），只有加 `-I vendor` 才成立。verify.json 的 unreproduced 第 4 条已记。故 C5-1 只作**条件成立**，不作全称论据。

### 2.3 J-3 语言面最小 —— **成立**

- 主张：`claim.md` §2 J-3（:50）与 §7 回应 5（:383）——A 只新增 `--lib` 一个已立项 CLI 选项，无关键字、无清单、无 `pub export`。
- 反证：`counter-r2.md` §4（:95）主动撤回该质疑：「J-3 成立……B 的 `pub export` 撞 `AGENTS.md:469` 且本庭无批准证据」；`counter.md` §7（:221）自承 B 至少要一次用户批准。
- 出证：V1（`--lib` 在 HEAD 不存在，`unknown option`，exit 1；`git grep -- '--lib' HEAD -- selfhost/` 零命中）；锚点 `phase39-draft.md:16`（目标已立项）、`:3`（用户批准并冻卡）、`AGENTS.md:469`（新增语法/改 CLI 须先确认）。
- 判定成立。注意：**成立的是 A 的「语言面成本」**，不是 A 的「可行」。B 的 J-3 不成立（无批准），但 `rejected` 不等于 B 成立（§7.9）。

### 2.4 J-4 实现成本 —— **成立（设计层）**

- 主张：`claim.md` §2 J-4（:51）与 §6 E4（:355-362）——2 文件（`Module.h.ct` + `Driver.h.ct`）、机制增量 ≤80 行；`check-ast.sh` 只增 p39 段，G1/G3/G4 判据零改动；回退是单提交 `git revert`。
- 反证：`counter.md` §5（:189-197）独立估 50–70 行（`--export` 清单）/ 100–160 行（`pub export`），与主张席 ≤80 相容；`counter-r2.md` §4（:97）明写「我不质疑 2 文件 / ≤80 行的估算」。
- 出证：V1（HEAD 无任何实现，沉没成本为 0）。
- 判定成立（限「选择机制」切片，不含 `.a`/`ar`/visibility）。**限制**：行数是设计估算，不可实测（§4 U-3）；R2 落地时按 G8 复核，超出即在收口对照表记一次偏差。

### 2.5 J-5 可诊断 —— **成立**

- 主张：`claim.md` §2 J-5（:52）与 E1-5（:202-210）——拒绝是硬错 `'<name>' cannot be exported: <reason>`，位置在声明行；`claim-r2.md` E1-r2-b（:125-153）补出「`ct check` 能给 `file:line:col`」的通道。
- 反证：`counter-r2.md` §4（:96）「J-5 成立（限硬错版 A）」；并据 `claim.md:347` 否掉「静默跳过」——「得到静默省略 `id`/`max2` 的 `.abi.h` 则 A 没有成立」。
- 出证：V11（`ct check` 的 sig_mismatch 输出 `test/modules/sig_mismatch/prog.ct:4:10: error: …`；leak 只有 `prog.ct:6:`，因 `w->col == 0`）；V2（今天 `--emit-c` 省略 `id` 时零诊断——要被修掉的现状）。
- 本席只读复核（非 verify.json 证据，仅校锚点）：`Diag.h.ct:85` 的 `sem_error` 无条件写 `"%s:%d:%d: error: %s\n"`，**硬错天然带列**；`:388` 的警告路径才受 `self->strict && w->col > 0` 限制。故 L39-1 走硬错即满足 J-5；C 方案里的「跳过 + 诊断」（L39-1w）走警告路径，需让 `--lib` 进入带列集合（约 3 行），这一项属未实现、记为 §4 U-2。
- 判定成立，但**列号来源是实现风险，不是已出证事实**：`struct Fn`（`Symbols.h.ct`）与 `struct Node`（`Arena.h.ct`）都只存 `line`、不存 `col`，而 `sem_error` 的列号是解析时从词法器位置传入的。导出扫描若在解析之后运行，列号需另行取得（回读声明行定位函数名，或给 `Fn` 加 `col` 字段）。C 方案在 §5 给出留在 2 文件内的做法；若 R2 拿不到列号，J-5 在该轮转为不成立，须按 §7.10 回到单方案评审，**不得**静默降级为 `file:line:`。

## 5 §7.9 推导与 §7.10 出口

**§7.9 第二行**：「判据未被满足，或反证清单中至少一条失效条件被证据证实 → 主张不成立 → `rejected`」。

- J-1 未被满足（无子集输入，自认）；J-2 未被满足（5 个单元 / A′ 下 2 个单元 + Str 作根）。
- 反证清单 C2、C3 被证据证实。
- 故 `verdict: rejected`。`rejected` 不等于「B 成立」：B 在本庭没有主张书、没有 E1–E5，且其 `pub export` / `--export` 撞 `AGENTS.md:469` 而记录中没有用户批准 → B 不能满足全部判据（至少 J-3 不成立）。

**为什么 A′ 不能直接作为 A 的补丁被采纳**（三条独立理由）：
1. 主张席自己划的界：`claim.md:347`（E3）把「得到一个静默省略 `id`/`max2` 的 `.abi.h`」判为「A 没有成立」；A′ 是「跳过 + 诊断」，属 `counter-r2.md` §5(b) 明确命名的**新机制**，不是本庭 A。
2. 它要改用户已批的 D39-6（`:60` 逐字含「泛型……一律 L39-1」）与 `:3`「禁用构造硬错」，还要改冻结的 8 条负例（`:194` 的 `p39_export_generic/`）——本庭无权替用户改，需用户批准。
3. 即便批准，J-1 的通用情形仍失败：`counter-r2.md` §5(b) 的「C 兼容内部 helper 仍被强制导出」，`claim-r2.md:56` 自认「只修无符号的泛型模板，不承诺解决有符号的内部 helper」。

**§7.10 二选一：选第 1 项（产出 C 方案）**，理由：
- C 的可定义性充分：双方最强约束（A 的零新语法/可诊断/低成本 + B 的作者可控导出集/不静默丢弃）可以在**不新增任何语法、不新增任何 CLI 选项**的前提下同时逼近，做法是把导出面绑到既有的「根单元」上（C 方案 §1）。
