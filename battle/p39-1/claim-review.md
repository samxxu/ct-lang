## 0 结论摘要

C **建议采纳，附条件**。它把 A 的失败面从 5 个单元缩到「2 个 trait 值单元 + `Str.h.ct` 作根」，且残余全部由用户已批的 D39-6 造成，不是选择机制缺陷。C 的 J-3/J-4 无条件成立，J-1/J-2/J-5 成立带条件（B1、B3、列号回读）。必须用户批准：B1（泛型跳过硬错）、B3（冻结卡变更）；**不建议 B2**（trait 值/按值 struct 不降为跳过）。

## 1 C-1 是否解决我在 `claim-r2.md:56` 自认的「没有子集输入」

**成立（文件级），但不解决函数级。**

- 我在 `claim-r2.md:56` 写的是「A/A′ 没有『只导出 C 兼容 `pub` 的真子集』的输入」。C-1 把候选面收窄到根单元、非根单元不进候选，作者于是有两个既有输入：**把哪个单元当根**、**把哪个 `pub` 放进非根单元**。这是零新语法下能得到的最强子集控制，正面回答 `counter.md:29-34`（C2）。
- **不成立的部分**：同一根单元内仍不能逐个选；C 兼容的内部 helper 在根里就会被导出，只能靠搬到非根单元（C-4′）。反向代价 C 没写进卡面：**非根单元里想导出的函数进不了 `.abi.h`**，多单元公开 API 必须再造一个 wrapper 根。C §9 只列了缺口①（同根 helper），应补缺口③（多单元超集）。
- 因此我的自认缺口从「无任何输入」缩小为「无函数级输入」；这是零语法上限，我接受。**需要的输出**：P-C3 实测（根 import 含 `pub int helper` 的单元 → helper 不在 `.abi.h`、有 C-5 汇总行、exit 0）。

## 2 C-3 是否等价于今天 `--emit-c` 对 `p34_pub_generic` 的符号面（V2/V3/V10）

**符号面等价；诊断面不等价，且这正是 J-5 要的。**

- V3/V10 已证：实例是 `t _id__ct1`（local/static，无外部符号），`from_lib` 是 `T`。C-3 跳过的是模板，不碰实例化与 `from_lib`，所以 `nm -g` 的 external 集合不变，`.abi.h` 原型集合 = 今天生成头里的 `{from_lib}`（V2）。等价成立。
- V2 的今天行为是**零诊断静默省略**；C-3 改为 `file:line:col` 的 L39-1w。若 C-3 只是「跳过」而无诊断，它就和 V2 一样违反 J-5；C 明确加了诊断，方向正确。
- **J-5 是条件成立**：L39-1w 必须带列。C §5(b) 的回读方案可行——E1-r3 在 HEAD 夹具上机械得到 `line=3 col=7`（见 §4）。`struct Fn` 只有 `line` 没有 `col`（E2-r3），所以回读是**唯一**不破 2 文件的路；C §5 已写死「拿不到列号不得降级为 `file:line:`，回单方案评审」，这条必须保留。若 R2 拿不到列号，J-5 转不成立。

## 3 C-4 保留 D39-6，f3 仍不能成库：是否可接受的残留

**可接受，条件是接受 C-4′ 的文件级重排。**

- f3 的 `sink_open` 是 `T` 外部符号（V10）；跳过它会在归档里留下「C 可手写声明调用、但 `.abi.h` 不承诺」的符号，比硬错更难守边界。D39-6 是用户 2026-11-13 批准的黑名单（`phase39-draft.md:60`），本庭不该改；我上一轮已把 f3 的失败记为残留，本轮维持。
- 但「f3 类库被整死」不成立：把 `sink_open` 放进被根 `import` 的单元（C-4′），根只留 C 兼容函数，库照样成，trait 函数保持 CT 包级可见、只是不进 `.abi.h`——这正是 D39-6 的本意。**若评审要求「f3 原样作根且成库」，则需 B2**；我不建议 B2：它把「可手写调用的半 ABI 符号」合法化，且比 B1 更偏离用户的「禁用构造硬错」。
- 建议加一条 errata（不新增批准）：L39-1 的 trait 值文案附一句 `move it to an imported unit (C-4′)`；否则作者看不到零语法出口，会把 C-4 误读成「这个库做不了」。

## 5 C 在 J-1…J-5 上的成立情况

| 判据 | C 下 | 理由 / 条件 |
| --- | --- | --- |
| **J-1 意图一致** | **成立（条件 B1）** | f1 2/2；f2 导出 `{from_lib}`、`id` 跳过 + L39-1w → 导出集 = 作者 C 面；f3 经 C-4′ 重排后库可成、trait 函数不导出（D39-6）。若要求 f3 原样成库 → 不成立，需 B2 |
| **J-2 零语法改动** | **成立 3/5（B1），非全绿** | 3 个泛型站点零改动成库；`xunit_box`/`ns_types` 与 `Str.h.ct` 作根仍硬错（D39-6）→ 需 B2 或「接受不做根」；`vendor/std` 因 C-1 根限定不再进候选（C5-1 消解），这是 C 相对 A′ 的实质改进 |
| **J-3 语言面最小** | **成立** | 零关键字、零语法、零新 CLI；只改卡面语义（B3 是冻结变更，不是语法批准） |
| **J-4 实现成本** | **成立** | 2 文件、约 55–75 行（含回读 8–12），≤80；G1/G3/G4 判据零改动；单提交可 revert |

**总评**：C 在 J-1/J-2 上不是无条件全绿，但它把失败面压到用户已批的 D39-6 残余；这正是可采纳的形态——**机制不再制造失败，剩下的失败是用户选择**。

## 6 是否建议采纳（附条件）

**建议采纳 C，须同时满足：**

1. **B1 + B3 必须**：B1 把泛型从 D39-6 的硬错改为「跳过 + L39-1w」，并同步 `:45` 与负例 `p39_export_generic/`；B3 为 O2/§3.1/L39-2/R2/R3/E39-3/负例台账的冻结变更签字。缺 B1，C 退回 A 的失败面。
2. **不批准 B2**：保留 D39-6 对 trait 值/按值 struct/std 的硬错；f3 的出口是 C-4′ 重排，不是降级。
3. **C-1 补卡面纪律**：写明「根单元 = 公开 ABI 头；多单元公开 API 需 wrapper 根；同根 C 兼容 helper 仍会导出」——把 C §9 缺口①与新增缺口③写成限制，别留给实现者自由发挥。
4. **C-5 列单元名**：只给计数无法行动；一行列出「N 个单元的 pub 不进 ABI」即可，行数不变。
5. **L39-1 文案附 C-4′ 提示**（errata，不改判据）。
6. **C-6 纳入 B3**：L39-2 的「没有可导出函数」改为「没有候选」，否则只剩泛型的根会被 L39-2 吃掉。
7. **J-5 的 R2 红证**：必须断言 L39-1w 的列号等于源码列，且禁止 `file:line:` 降级（C §5 已写，验收要落成断言）。
8. **p39-2 边界**：C §1.1 的「不裁归档符号面」我接受；E39-2 的快照按 D-002 处理，不在本方案里预判。

**一句话**：C 的机制（根单元 + 符号类别分级）是 A 的可实现版本；它的两个格子（f3、2 个 trait 单元）是用户已定的 D39-6 残余，不该由机制背锅。若 B1 未批，C 不可落地；若 B1 批，C 是三方里唯一同时保住零新语法与作者可控导出集的方案。
