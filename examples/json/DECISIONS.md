# json 设计决策记录

本文件记录 `examples/json/` 在实现前后的取舍。凡是有两种做法都说得通、且会
影响公开 API 或可验收性的点，都在这里给出选项、代价和最终裁决；裁决由实现侧与
一个独立的对手评审（红队）来回辩论后定稿，题目不重复讨论。

前提约束（不参与辩论）：

- 纯 CT，无第三方 C 源码，不改 `selfhost/**`；
- 生成 C 必须在 `-Wall -Wextra -std=c99` 下零警告；
- 既有门禁把 `examples/*/*.ct` 当单文件程序编译、运行并与 `.expected.out`
  比对，所以库、演示和自测必须在同一个 `json.ct` 里。

## 1. 视图 vs DOM

- **选项 A（采纳）零分配只读视图**：`parse` 只做一次全量校验，文档只保存源文本
  指针、长度、首个错误偏移；`JsonView` 是 `{start, len}` 的字节区间，访问时按需
  重扫容器。
- **选项 B DOM**：解析时建树，节点用堆分配，读取 O(1)，但必须引入所有权、释放
  与错误中途回滚。

裁决 A。代价是每次查找 O(n)，但换来与 CT 栈上模型一致的零分配、可直接指向只读
字面量、无生命周期问题。README 的「限制」一节明确写出 O(n) 与适用场景。

## 2. 视图内容：只存区间，还是缓存 kind / 元素计数

- **选项 A（采纳）只存 `{start, len}`**：`kind` 用首字节 O(1) 判断，元素计数与
  成员查找重扫。
- **选项 B 缓存 `kind`**：省一次判断，但视图变大，且 `kind` 本来就能从首字节
  得出，缓存没有信息增量。
- **选项 C 缓存元素边界表**：`at` 变 O(1)，但需要额外内存，与零分配冲突。

裁决 A。对手评审同意：真正贵的不是 `kind`，是元素查找；缓存计数救不了成员访问。

## 3. 错误模型：错误码 + 偏移 / 解析时记录行列 / 错误字符串

- **选项 A（采纳）`enum 码 + 字节偏移`**，行列由同一套扫描按需计算（从 1 开始，
  列按字节，`\n` 换行）。
- **选项 B 解析时同时记录行列**：省一次扫描，但两处逻辑要同步，容易不一致。
- **选项 C 存错误字符串**：调用方最省事，但绑定文案、吃固定缓冲，且错误码仍不
  可避免。

裁决 A。对外只承诺「码 + 偏移 + 1-based 行列」，文案由 `json_message` 单独提供，
不属于 ABI。

## 4. 序列化 API：追写器 / 递归整树写 / 两者

- **选项 A（采纳）单个追写器 `JsonOut`**：深度栈与每层状态放在结构体里，调用方
  给缓冲区，`cap = 0` 量长度，`finish` 返回所需长度。
- **选项 B 递归 `write(view, buf, cap)`**：实现短，但只能整树输出，无法边算边写，
  且和追写器并存会维护两套转义与格式化逻辑。
- **选项 C 两者都提供**：能力强，但两份实现迟早分叉。

裁决 A。整树复制用 `JsonDoc.emit`（把一个视图的原始字节交给追写器）解决，
不再另开递归入口。对手评审指出 `emit` 名为 `copy` 更贴切，但仓库已有 `copy`
语义偏向「深拷贝」；最终保留 `emit`，并在 README 写明它是「原字节搬运」。

## 5. 重复键：first-wins / last-wins / 报错

- **选项 A first-wins**：`member` 可提前返回。
- **选项 B（采纳）last-wins**：与 JavaScript / Python 的行为一致，用户心智负担
  最小；代价是 `member` 必须扫完整个对象。
- **选项 C 报错**：最严格，但会拒掉现实里常见的带重复键配置；且「已见键」索引
  与无 DOM 的设计直接冲突。

裁决 B。`member` 本来就要处理多个键，扫完的增量成本可忽略；README 与测试都
覆盖了「最后一个值生效」。

## 6. 可变 API

- **选项 A（采纳）不提供**：视图不可变；修改一律用 `JsonOut` 重新构造。
- **选项 B 提供 setter**：一旦原地改值，`{start, len}` 立即失效，必须引入缓冲区
  重排、增长与所有权，等于第二个库。

裁决 A。与零分配的目标不可兼得，明确写进 README 的「限制」。

## 7. 数字精度与原文访问

- **选项 A（采纳）整数严格 int64，实数近似并在文档中声明**：整数拒绝
  `1.0` / `1e3`，越界报 `JSON_READ_RANGE`；实数最多取 19 位有效数字，手写十进制
  缩放（不用 `strtod`，避免 locale），末位可能有差异；需要精确原文时用
  `offset_of` / `len_of` 取原词。
- **选项 B 正确舍入**：要引入大整数或 `strtod`；前者超出示例规模，后者把
  locale 依赖带进来（`%.17g` 输出同理，但本程序不调用 `setlocale`，固定 C
  locale）。

裁决 A。对手评审提出的「`%.17g` 也可能受 locale 影响」成立，但只在宿主主动改
locale 时发生；README 已写明该前提。序列化对非有限值直接报 `JSON_EMIT_FINITE`。

## 8. 深嵌套：递归下降 / 显式栈

- **选项 A（采纳）递归下降 + 深度上限**：校验、跳过、迭代共用同一套扫描；默认
  上限 64 层容器，保证 C 栈有界。
- **选项 B 显式栈数组**：不依赖 C 栈，但扫描函数要拆成状态机，可读性明显变差。

裁决 A。对手评审建议「每层 2 bit 状态 + 局部数组」，功能等价；在 C 栈帧可控的
前提下，递归下降更短、更容易核对 RFC 8259 的每一条产生式。

## 9. 输入边界：UTF-8 校验与 UTF-8 BOM

- **选项 A（采纳）不校验 UTF-8，不跳过 BOM**：只保证结构合法、字符串内无未转义
  的控制字节；`0x7F` 以上原样透传。BOM 视为非法字符，由调用方剥离。
- **选项 B 全量 UTF-8 校验并接受 BOM**：更友好，但校验器和错误码都要扩大，且
  与「JSON 文本是字节序列」的定位不一致。

裁决 A，写进 README 的「限制」。

## 已实测的 CT 语言约束（实现层面，不是设计取舍）

这些不是「两种做法」的问题，而是编译器当前的硬约束，实现已绕开并在注释中标注：

1. trait 方法参数里出现「与实现该 trait 的结构体相同」的类型时，需要先用
   `struct X;` 前向声明；否则生成 C 引用未声明类型。本文件因此把 `JsonView`、
   `JsonOut` 定义成**不带 trait** 的普通 struct，由 `JsonDoc` 的 trait 方法接收
   它们的指针。
2. trait 方法体内局部定义「带 `use` 的结构体」变量会生成对尚未声明的 vtable 的
   引用，编译失败；本文件只在 `main` 与普通函数里定义 `JsonDoc` / `JsonOut`，
   在方法内只定义无 trait 的 `JsonView`。
3. 方法体没有引用 `self` 时，生成的 `_self` 参数触发 `-Wunused-variable`；本
   文件所有方法都通过 `self` 访问源文本或输出缓冲，没有「纯静态」方法。
4. 示例由 L0 与 ct-ast 各编译一次，因此只用两边都支持的结构：`#define`、
   `struct`、`trait`、`impl`、`static` 函数与 C99 语句，没有使用 `enum`、
   `namespace`、`map`。

## 测试策略

门禁只认「单文件程序 + `.expected.out`」，因此自测写在 `main` 里，按
`-- demo --` / `-- reader --` / `-- writer --` / `-- errors --` 分段输出确定
文本；任何断言失败都会打印 `FAIL` 并最终以非零退出。负例覆盖空输入、截断、
尾逗号、缺冒号、非法字面量、前导零、`1.`、`.5`、`+1`、控制字符、坏转义、
坏 `\u`、孤立代理项、尾随数据、65 层嵌套，并逐一核对错误码、偏移、行、列。
