# AGENTS.md — 项目规约（面向 AI 编码代理）

> 中文 · [English](#english)

本文件是 `ctc` 仓库的**唯一行为规约**。任何 AI 编码代理在本仓库动手之前，必须先读完本文件；
它与代码冲突时以代码为准，但**修改代码前必须先跟用户确认**。

### 2. 文件职责与改动边界

| 文件 | 性质 | 可否修改 |
| --- | --- | --- |
| `selfhost/l0/ctc.c` | 源码，全部实现（L0 C 种子） | ✅ 唯一需要改的实现文件 |
| `examples/**` | 源码：可运行示例（`<name>.ct` + `<name>.expected.out`） | ✅ 新增语法时同步扩充；生成物不入库 |
| `test/**` | 测试：用例、golden 基线、runner | ✅ 可改；`*.expected.*` 只能用 `./ctc` 重新生成 |
| `editors/**` | 编辑器插件：`editors/vscode/`（VS Code，纯 JSON） | ✅ 可改；见下方硬性边界 |
| `selfhost/**` | 源码：自举编译器 —— **L0 C 种子** `selfhost/l0/ctc.c` ＋ 冻结种子 `selfhost/l1/ctc.ct`（L1，能力停在 Phase 2）＋ **开发主线** `selfhost/ct-ast/**`（`main.ct` = driver + 编译核心，`runtime/arena/` = 节点池 + 字面量池（`namespace runtime::arena`），`frontend/lex/` = 词法器（源码游标 + 当前 token，`namespace frontend::lex`），`frontend/module/` = 单元表与 `map` 记录的取值类型（`namespace frontend::module`），`frontend/sym/` = 符号表（函数/变量/作用域/类型/trait/struct，`namespace frontend::sym`），`frontend/type/` = 类型推断与装箱判定（`namespace frontend::type`），`tool/diag/` = 告警存储（`namespace tool::diag`），`tool/cache/` = 增量缓存（`namespace tool::cache`），`tool/pkg/` = 包管理器（`namespace tool::pkg`），`backend/mem/` = AutoDrop 与泄漏分析（`namespace backend::mem`），`backend/emit/` = 代码发射器（`.c`/`.h`/map JSON，`namespace backend::emit`）；Phase 9 的 AST 版编译器，ct-ast）＋ **冻结归档** `selfhost/l2/**`（`core.ct` + `driver.ct`，Phase 3–8 的旧管线 L2；只修 bug，不再加能力） | ✅ Phase 1 起新增；放编译器源码（含 L0 C 种子）与门禁脚本，生成物不入库 |
| `bindings/**` | 源码：C 库的**声明式 binding**（Phase 12 起）—— 直通 `#include "<lib>.h"` ＋ 镜像 `trait` / `struct` ＋ 已声明全局实例 ＋ `map`；仓库内假 HAL 自带其头与实现 | ✅ Phase 12 起新增；只放 binding 源与（假 HAL 的）最小 C 头 / 实现，**不 vendored、不下载**、不成为编译器构建步骤；生成物不入库 |
| `LICENSE`、`LICENSE.EXCEPTION` | 许可全文与输出例外 | ❌ 仅限用户明确要求时修改 |
| `README.md`、`AGENTS.md`、`docs/*` | 文档 | ✅ |
| `ctc`、生成的 `.c`/`.h`、`.o` | 编译产物 | ❌ 不入库 |

硬性边界：

- 生成的 `.c` 必须**自包含**（不 `#include` 生成的 `.h`），保证生成物可单独编译。
- 生成的头文件只放类型（trait vtable、struct 定义），不放 `static` 函数/变量。
- 不引入任何第三方库、构建系统、代码生成脚本。**例外（Phase 6.6 方言）**：方言展开器是**仓库外**的
  独立脚本（bash / Python / awk 均可，作者自选语言），`ctc` 对它**零感知**——编译器只见纯 CT，且
  **永不**调用展开器、**永不**内置任何方言；本禁令只约束**仓库内的编译器构建管线**。仓库内**只允许**
  在 `examples/**`（演示）与 `test/**`（测试）下携带方言源与方言插件，且必须满足：插件放在约定目录
  `ct-dialects/`、按 `//@ct-dialect: <名字>` 路由、文件名 `<名字>.sh`（`/` 换 `-`）；**不得**成为编译器的
  构建步骤——`gcc selfhost/l0/ctc.c`、`./test/run.sh` 的编译相关层与 CT 线全部关卡都不得依赖它，方言演示只由
  `test/run.sh` 的 `dialect` 层驱动。方言所需的符号信息由编译器已产出的 map JSON（`--emit-map`）
  提供，不在仓库内另造一套。
- **例外（Phase 8 包管理）**：`ct get` / `ct install` 可调用**系统 `git`** 获取 git 源包，并可把**本地目录源**同步进
  `vendor/`。这是包管理子命令的受控例外——编译器核（`ct compile` / `ct build`）仍**零网络、零子进程**，
  且不得内置 HTTP 客户端。无 `git` 时 git 源硬报错并提示，本地源照常可用。见
  [design/phase8.md](docs/design/phase8.md)（D22 / D26）。
- **例外（Phase 12 bindings）**：仓库内新增顶层 `bindings/**`，承载对既有 C 库的**声明式 binding**
  （`selfhost` 之外的第二类源码目录）。binding 只是 CT 源——直通 `#include` ＋ 镜像声明 ＋ `map`，
  **只声明外部符号，不 vendored、不下载、不链接**；仓库内假 HAL 的 C 头 / 实现仅作**演示与测试**，
  **绝不**成为编译器构建步骤（`gcc selfhost/l0/ctc.c`、`./test/run.sh` 的编译相关层与 CT 线关卡都不得依赖它）。
  见 [roadmap](docs/roadmap.md) 的 Phase 12 与 [design/phase12.md](docs/design/phase12.md)。
- `editors/**` 必须保持**纯声明式 JSON**：无构建步骤、无 npm 依赖、无需打包器，改完可直接
  `npx @vscode/vsce package`。插件只负责高亮与编辑体验，不做语法校验、**不调用 `ctc`**（方言亦不例外：
  插件不代跑展开器，`--watch` / 后台自动展开推迟；消费映射信息只能读编译器已产出的 map JSON）。
- 不改变已发布产物的命名规则（`<Trait>_vtbl`、`__<trait>_vptr`、`<Struct>_<Trait>_<method>`、`<Struct>_<Trait>_vtable`），除非用户明确要求。
- `docs/design/` 下是**未实现的设计草案**（如自举的目标目录结构），不是实现依据；不要照着草案创建目录或文件。
- **`ctc.c` 在自举启动后冻结**：Phase 0.3 剥离完成后**只接受 bug 修复**，**不再新增任何能力**（2026-10-15 用户明确重申：bug 修复可以接受，其他一律不行）。自举要求 `ctc.c` 的 `main` 加 `#ifndef CTC_NO_MAIN` 守卫——这是冻结期**唯一**允许的结构性改造。判据如下，**含混时按「不允许」处理**：
  - **允许**：修正既有行为中的缺陷（错判、错发射、崩溃、越界、状态未还原等）。出口是**既有语料产物不动**——改完 `./test/run.sh` 与 `bash selfhost/check-goldens.sh` 仍须全绿，且**不得重新生成任何 `*.expected.*`**；必须是一个独立的 `fix(...)` 提交，正文写明缺陷、触发条件与验证方式，并登记进下面的清单。
  - **不允许**：新增或加回任何语言特性 / CLI 选项 / 诊断；放宽或绕开任何 `MAX_*` 上限（含为了让 L1 过 `MAX_FUNCS` / `MAX_METHOD` 而改 `ctc.c`）；改动产物命名规则、banner 或 `CTC_VERSION`；重构、重命名、重排既有符号；新增 `#include` 或改变生成物结构。这些一律只能做在 **CT 侧**（L1 及以后）。
  - **冻结期改动登记**（至今两次个别改动；版本 bump 见下一条）：
    1. `1bdb93b fix(codegen): keep file-scope vars in emit_body`（2026-10-15）——`emit_body` 退出时只还原变量表的**条目数**、不还原**内容**，会覆盖外层文件作用域已登记的条目；补进/出各一次内容快照与拷回。产物不变，无 golden 重生成。此后 Phase 1 期间 `ctc.c` **再无任何改动**。
    2. **Phase 7.3 banner 改名**（2026-10-17，**用户显式授权的一次性解冻例外**）——生成物 banner 由 `Generated by ctc …` / `re-run ctc` 改为 `Generated by ct …` / `re-run ct`，L0（`ctc.c`）、L1（`selfhost/l1/ctc.ct`）与 L2（`selfhost/l2/core.ct`）**三层同步**；map JSON 的 `compiler` 字段同步改为 `ct v…`。全部 `test/cases/**` 与 `test/modules/**` golden 已重生成（仅 banner 一行变化），归档 oracle 仍写 `ctc`，由 `check-archive.sh` 的 `same_modulo_version` 归一化兼容。除 banner 文案外，三层**无任何行为变更**。
  - **版本 bump 另行登记**：`CTC_VERSION` 的推进（v0.4.0 / v0.5.0 / v0.6.0 / v0.7.0 / v0.8.0 / v0.9.0 / v0.10.0 / v0.11.0 / v0.11.1，以及 Phase 12 收口时的 v0.12.x）同样属用户显式授权的冻结期例外，但**不逐条列入上表**——逐次记录见 [roadmap](docs/roadmap.md) 的「版本记录」与对应 `v*` tag 注释。每次 bump 都同时改动 `ctc.c`、L1（`selfhost/l1/ctc.ct`）、`selfhost/l2/{core,driver}.ct` 与 `selfhost/ct-ast/main.ct`，并重生成全部 golden；上表只逐条登记**与版本推进无关**的个别改动。

- **L1 必须是 CT OO 风格**：`selfhost/l1/ctc.ct` 的数据模型层与管线层须用 `struct` + `use` + `impl` 书写，**不得**退回 plain-C 直通；仅设施层（`Buf` / 分配器 / `die` / 扫描原语）保持 plain-C 透传。注意管线层由**两个** trait 承载（`PipeOps` 主流程 + `RewriteOps` 行重写层，`struct Pipe` 同时 `use` 二者）——新增方法请放进对应的那一半，别往单侧堆到 `MAX_METHOD`。见 roadmap Phase 1 开工决策 5。

### 3. 代码风格

- 缩进 4 空格，K&R 花括号；**函数定义**的左花括号另起一行。
- 所有内部函数一律 `static`；不使用非 `static` 的全局函数。
- 命名：
  - 全局变量 `g_` 前缀 + `snake_case`（`g_src`、`g_ntraits`）
  - 函数 `snake_case`（`parse_impl`、`transform_calls`）；「动作」动词开头（`parse_` / `emit_` / `try_` / `find_` / `skip_`）
  - 宏与上限常量 `UPPER_SNAKE`（`MAX_TRAITS`、`MAX_VARS`）
  - 类型 `typedef struct { … } Name;`，**不加** `_t` 后缀（`Trait`、`Struct`、`Method`）
- 注释：**英文**，`/* … */` 风格；只解释「为什么」，不复述代码。
- 内存：一律走 `xmalloc` / `xstrndup`（失败即 `exit(1)`）；拼接字符串用 `Buf`（`buf_puts` / `buf_putc` / `buf_putn`），不要写 `strcat`。
- 上限：所有固定容量常量集中在文件头部，越界一律 `die()` 报错，不允许静默截断。
- 逐个函数按「工具 → 源扫描 → 符号表 → 签名解析 → 生成器 → 解析器 → 行重写 → main」的顺序摆放，新增函数放进对应分区，不要乱序插入。

### 4. 错误处理约定

- 唯一入口是 `die(pos, fmt, ...)`：`pos` 是 `g_src` 中的字节偏移，由它换算出 `行:列`。
- 报错格式固定为 `文件:行:列: error: 描述`，描述小写、不加句号、标识符用单引号包裹。
- 遇到无法解析的 trait / struct / impl 语法，或引用未定义的 trait / struct，**必须 `die` 并 `exit(1)`**，不允许「跳过继续」。
- 不允许生成明知编译不过的 C 代码来「糊过去」——能静态判定的错误就要在 `ctc` 阶段报出来。
- 不做错误恢复（Phase 0）：一个错误即终止。

### 5. 修改流程

1. **先读后改**：改任何函数前，先读 `ctc.c` 中相关分区，确认数据流与副作用。
2. **先确认后动手**：涉及行为变更（新增语法、改变命名、改变 CLI）必须先向用户说明方案并获得确认。
3. **最小改动**：只改与任务直接相关的代码，不顺手重构、不调整无关格式、不重命名既有符号。
4. **同步文档**：改动**核心语法**（L0 与 L2 共有）或产物命名时，必须同步更新 `docs/language-spec.md` 与 `README.md` 中的语法表；改动 **L2 独有**语法（`namespace` / `import` / `pub` / `Drop` / `#line` / 诊断 / AutoDrop）时，必须同步更新 `docs/roadmap.md` 对应阶段与 `docs/design/**`，并在 `README.md` 标明适用编译器。
5. **重新生成基线**：生成器有任何变化，都要重跑 `./test/run.sh`（其中的 examples 层会端到端校验 `examples/**` 的展开与运行结果），并确认 `test/cases/**` 的 golden 差异符合预期。
6. **改版本号**：`CTC_VERSION` 会进入生成物注释，改它必须重新生成 `test/cases/**` 的全部 golden、同步 `README.md` 与 `docs/roadmap.md` 的版本记录，并跑完整套验证。

### 6. 验证（Definition of Done）

任何改动完成后，必须完整跑通下面三条，并把结果贴给用户：

```bash
# 1) 编译器本身：零警告
gcc -Wall -Wextra -std=c99 selfhost/l0/ctc.c -o ctc

# 2) 代码生成：应无输出（无报错）。产物写临时目录，避免污染仓库
./ctc examples/01_greeter/greeter.ct -o /tmp/greeter.c

# 3) 产物：必须编译并输出两行
gcc -Wall -Wextra /tmp/greeter.c -o /tmp/greeter && /tmp/greeter
# Hello, I'm Tom, age 36
# Hello Jerry, I'm Tom
```

补充要求：

- **自动化测试**：`./test/run.sh` 必须全绿（退出码 0）。**八层覆盖**：ctc 自身零警告构建、
  `test/unit` 白盒单测、`test/cases` golden 快照（生成 → 比对 → 编译 → 运行）、
  `examples/**` 端到端（生成 → 构建 → 运行 → 与 `.expected.out` 比对）、
  `dialect` 方言演示（`ct-dialects/` 插件展开 → 同一套生成 / 构建 / 运行 → 与 `.expected.out` 比对，
  并断言未展开的源不可直接编译）、
  `test/errors` 负例诊断（必须非 0 退出，且带 `文件:行:列: error:` 前缀）、
  `known limitations` 特征化断言、`cli` 参数与驱动分支。`CC=gcc ./test/run.sh` 可换编译器。
- **CT 线关卡同样必跑**（`run.sh` 只驱动 L0）：一条命令 `bash selfhost/check-all.sh` 依次跑
  `./test/run.sh`、`selfhost/check-goldens.sh`（L1 对 golden + L1′ 自举闭环 + L1/L2 不动点）、
  `selfhost/check-archive.sh`（L2 对归档 oracle 的棘轮）、`selfhost/check-m2a.sh`、
  `selfhost/ct-tour.sh`、`editors/vscode/test/check-grammar.py`、`test/pkg/run.sh`（Phase 8.1–8.3
  包管理器：本地目录源、git 源与 `install` 校验）与 `selfhost/check-ast.sh`（Phase 9.1–9.7 + 10.x
  AST 编译器的行为用例、CLI 错误分支、自编不动点与全量语料等价；任一失败即整体非零）；
  `bash test/acceptance/run.sh` 单独报告（其 PENDING 属预期，不阻断）。改动 `selfhost/**` 后必须跑一遍。
- **ct-ast 是分组多单元树**：各分组（`runtime/`、`frontend/`、`tool/`）按全路径互相 `import`，
  构建时必须带 `-I selfhost/ct-ast`（门禁脚本与 README 的安装命令已内置；手工构建同样要加）。
- **手工三件套不可省**：套件内部的路径与你手工敲的不完全相同，改完必须按上面三条命令亲自跑一次并贴结果。

  因此**不进** `./test/run.sh`；反过来它也不能替代手工三件套。
- **诚实报告**：验证失败就如实说失败并贴原始输出，不允许把「没跑」说成「通过」；
  更不允许靠改 golden 基线或 `.expected.out` 来「修」失败——只有在确认编译器行为变更是有意为之之后，才重新生成它们。

### 7. 禁止事项

- 禁止在 `ctc.c` 中引入类型检查、语义分析、优化（Phase 0 范围外）。
- **禁止把非 bug 修复的改动混进 `ctc.c`**：冻结期只接受「不改变既有语料产物」的缺陷修复（判据与登记清单见第 2 节）；**禁止放宽任何 `MAX_*` 上限**，**禁止为了让 L1 过某个关卡而改 `ctc.c`**，**禁止打着「修 bug」的旗号改既有行为**（若产物确实变了，那就不是 bug 修复，必须走用户确认 + 重新生成 golden 的流程）。
- 禁止把 namespace / 多文件 / import / Drop / `#line` / 诊断在 **C 侧**新增或加回（Phase 0.3 已把它们移出 `ctc.c`；Phase 2–5 改用 **CT** 重做）；禁止新增泛型、继承，除非用户明确把对应阶段指派给你。
- 禁止把 `examples/**` 下生成的 `.c` / `.h` 入库或手工编辑（生成物一律不入库）。
- 禁止为了让示例通过而修改 `examples/**/*.ct` 的语义（可以扩充，不可以削弱）。
- 禁止吞掉错误、禁止静默截断、禁止 `TODO` 空实现留在主路径上。
- 禁止把项目名 `ct`、入口命令 `ct`（`ctc` 为兼容别名）或后缀 `.ct` 改成 `ct-lang` / `ctlang` / `.ctlang`（`ct-lang` 只是仓库名）。唯一被认可的演进是 roadmap 里已定的「单入口 `ct` + `ctc` 兼容别名」，不得自行发明其它名字。
- 禁止删除或改写生成物 banner 里的许可声明行，也禁止移除 `ctc.c` 顶部的 SPDX / 版权 / 例外说明——输出例外必须**随产物走**（见 `LICENSE.EXCEPTION`）。
- 禁止给 `editors/**` 引入构建步骤、npm 依赖或打包器（见第 2 节硬性边界）。
- 禁止提交二进制文件、`.o`、临时文件。

Hard boundaries:

- The generated `.c` must stay self-contained (it must not `#include` the generated `.h`) so that it
  compiles on its own.
- The generated header carries types only (trait vtables, struct definitions) — no `static` code.
- No third-party libraries, build systems, or code-generation scripts. **Exception (Phase 6.6 dialects)**:
  a dialect expander is a standalone script **outside the repository** (bash / Python / awk — the author
  picks the language); `ctc` stays **unaware** of it — the compiler only ever sees plain CT, **never**
  invokes an expander and **never** ships a dialect. The ban covers the **in-repo compiler build
  pipeline** only. Inside the repo, dialect sources and plugins are allowed **only** under `examples/**`
  (demos) and `test/**` (tests), and must satisfy: a plugin lives in the conventional `ct-dialects/`
  directory and is routed by `//@ct-dialect: <name>`, its file being `<name>.sh` (`/` → `-`); it must
  **not** become a compiler build step — `gcc selfhost/l0/ctc.c`, the compilation-related layers of `./test/run.sh`
  and every CT-line gate must not depend on it, and the dialect demo is driven by the `dialect` layer of
  `test/run.sh` alone. The symbols a dialect needs come from the map JSON the compiler already emits
  (`--emit-map`); nothing parallel is built in the repo.
- **Exception (Phase 8 package management)**: `ct get` / `ct install` may invoke the **system `git`** to
  fetch git-sourced packages and may sync **local directory sources** into `vendor/`. This is a
  controlled exception for the package subcommands only — the compiler core (`ct compile` /
  `ct build`) stays **network-free and process-free**, and no HTTP client may be built in. Without
  `git`, git sources fail hard with a hint while local sources keep working. See
  [design/phase8.md](docs/design/phase8.md) (D22 / D26).
- **Exception (Phase 12 bindings)**: a new top-level `bindings/**` carries **declarative bindings** to
  existing C libraries (a second source area beside `selfhost`). A binding is CT source only —
  pass-through `#include` + mirrored declarations + `map` — and **declares external symbols without
  vendoring, downloading or linking** them; the in-repo fake HAL's C header / implementation exists for
  **demos and tests only** and **never** becomes a compiler build step (`gcc selfhost/l0/ctc.c`, the
  compilation-related layers of `./test/run.sh` and every CT-line gate must not depend on it). See the
  Phase 12 section of [roadmap](docs/roadmap.md) and [design/phase12.md](docs/design/phase12.md).

    v0.6.0 / v0.7.0 / v0.8.0 / v0.9.0 / v0.10.0 / v0.11.0 / v0.11.1 / v0.12.0) are likewise user-authorised freeze exceptions, but they are **not listed one
    by one above** — each is recorded in the roadmap's "Version record" and in the matching `v*` tag
    message. Every bump touches `ctc.c`, L1 (`selfhost/l1/ctc.ct`), `selfhost/l2/{core,driver}.ct` and
    `selfhost/ct-ast/main.ct` in lockstep and regenerates every golden; the table above lists only
    individual changes that are **not** version advances.
- **L1 (`selfhost/l1/ctc.ct`) reuses nothing**: it must **not** `#include ctc.c` and carries its own
  facilities. It must be written in the OO subset L0 supports (single file, one statement per line,
  declarations before use, no interface arrays) and its exit is a **byte-identical** match with L0
  (banner included). **That exit is met**: milestone M2 completed with `test/cases/**` fully green
  (25/25, 0 regressions), and the L1′ that L1 builds reproduces the same corpus byte for byte. Check
  it with `bash selfhost/check-goldens.sh` instead of hand-rolling loops. See the Phase 1 kick-off
  decisions in the roadmap. **Phase 2 split exit**: L1 builds the multi-unit tree
  `selfhost/l2/**` (`core.ct` + `driver.ct`) with its own `build` (multi-file + `import`) into
  **L2**, and L2 must match L1 byte-for-byte on `test/cases/**` (25/25) — the split's exit criterion.
  Cross-unit access goes only through the 10 scalar `pub` wrappers (`ct_read_file` &c.); data, macros
  and the singleton stay inside `core.ct` (land in `core.c`), and **no language feature may be added**
  to help the split. Gates: `check-goldens.sh` steps 6/7, `check-archive.sh` 3b, `check-m2a.sh` step 7,
  `ct-tour.sh` step 6. See Phase 2 in the roadmap.
- **`selfhost/l1/ctc.ct` (L1) is frozen from Phase 3 on**: L1 has become a **frozen seed** — its
  capability stops where Phase 2 left it and it gains **no new capability** (comments included,
  registered the same way as `ctc.c`). The reason mirrors the level above: once `ctc.c` froze,
  development moved to L1; now that L1 has frozen, development moves to **`selfhost/l2/**`**
  (`core.ct` + `driver.ct`, the source of L2). **From Phase 3 on every new capability lands in
  `l2/**` only.** (From Phase 9.7 on the mainline moves again, to `selfhost/ct-ast/**` — see the next
  bullet.)
  - **The gates change meaning with it**: `check-archive.sh`'s ratchet now runs **L2** (which L1
    builds from `l2/**`), not L1; `check-goldens.sh` step 7 is a **fixpoint** — L2 compiles
    `l2/**` too and its output must be **byte-identical** with L1's, because the two compilers must
    agree on the very subset the compiler is written in.
  - **The signature ceiling is a real constraint**: `MAX_FUNCS` (64) **counts every top-level
    plain-C signature, `static` included**, and `l2/**` has almost no headroom left. New helpers
    **must** go into an `impl` block (impl methods do not count), minding `MAX_METHOD` (32) —
    `PipeOps` already uses 31. See Phase 3 in the roadmap.
- **`selfhost/l2/**` is frozen and archived from Phase 9.7 on** (D36): the Phase 9 AST compiler
  `selfhost/ct-ast/main.ct` is the **only development mainline** (ct-ast self-compiles and is
  behaviourally equivalent over the whole corpus); `l2/**` takes **bug fixes only, no new
  capability**, with `pre-ast-mainline` as the archive reference tag (the 2026-10-17 frozen boundary;
  Phase 9 starts at the `v0.8.0` close). The old gates (`check-goldens.sh` /
  `check-archive.sh` / `check-m2a.sh` / `ct-tour.sh` / `test/pkg/run.sh`) keep running `l2/**` as a
  **regression oracle**, unchanged in the dual-track period; new capabilities and every slice after
  9.x land in `selfhost/ct-ast/**` only, bound by `check-ast.sh` (the self-compile fixpoint plus the
  whole-corpus equivalence section).
- **L1 must be written in CT OO style**: `selfhost/l1/ctc.ct`'s data-model and pipeline layers use
  `struct` + `use` + `impl` and must not fall back to plain-C passthrough; only the facilities layer
  (`Buf` / allocators / `die` / the scanning primitives) stays plain-C. Note the pipeline is carried by
  **two** traits (`PipeOps` for the main flow, `RewriteOps` for the line-rewriting layer; `struct Pipe`
  uses both) — put a new method in the half it belongs to rather than piling one side up to
  `MAX_METHOD`. See Phase 1 kick-off decision 5 in the roadmap.

### 3. Code style

- 4-space indent, K&R braces; the opening brace of a **function definition** goes on its own line.
- Every internal function is `static`.
- Naming: globals `g_snake_case`, functions `snake_case` with a verb prefix
  (`parse_`, `emit_`, `try_`, `find_`, `skip_`), constants `UPPER_SNAKE`, types
  `typedef struct { … } Name;` (no `_t` suffix).
- Comments in **English**, `/* … */` style, explaining *why*, not *what*.
- Memory goes through `xmalloc` / `xstrndup` (fail fast), string building through `Buf`.
- All fixed capacities live as `MAX_*` constants at the top of the file; overflow must `die()`, never
  silently truncate.
- Keep functions grouped in the existing order: utilities → source scanning → symbol tables →
  signature parsing → emitters → construct parsers → line rewriting → `main`.

### 4. Error handling

- The only reporting entry point is `die(pos, fmt, ...)`, where `pos` is a byte offset used to derive
  `line:column`.
- Format: `file:line:col: error: message`; lowercase message, no trailing period, identifiers in
  single quotes.
- Unparsable trait/struct/impl syntax, or references to undefined traits/structs, **must** `die` and
  `exit(1)` — never skip and continue.
- Never emit C that is known not to compile. If it can be detected statically, report it in `ctc`.
- Phase 0 has no error recovery: the first error terminates.

### 5. Change workflow

1. **Read before writing.** Inspect the relevant section of `ctc.c` and confirm the data flow.
2. **Confirm before implementing.** Behaviour changes (new syntax, naming, CLI) require user sign-off.
3. **Minimal diff.** No opportunistic refactors, reformatting, or renames.
4. **Update the docs.** A **core-grammar** change (shared by L0 and L2) or a naming change must be
   mirrored in `docs/language-spec.md` and the syntax table in `README.md`; an **L2-only** syntax
   change (`namespace` / `import` / `pub` / `Drop` / `#line` / diagnostics / AutoDrop) must update
   the matching phase in `docs/roadmap.md` and `docs/design/**`, and state the applicable compiler
   in `README.md`.
5. **Regenerate the baseline.** After any generator change, re-run `./test/run.sh` (its examples
   layer re-checks `examples/**` end to end) and review any golden diffs under `test/cases/**`.
6. **Version bumps.** `CTC_VERSION` is embedded in the generated comments, so bumping it means
   regenerating every golden under `test/cases/**`, updating the version records in `README.md` and
   `docs/roadmap.md`, and re-running the full suite.

### 6. Definition of done

```bash
gcc -Wall -Wextra -std=c99 selfhost/l0/ctc.c -o ctc                # zero warnings
./ctc examples/01_greeter/greeter.ct -o /tmp/greeter.c         # silent (no errors)
gcc -Wall -Wextra /tmp/greeter.c -o /tmp/greeter && /tmp/greeter   # prints two lines
```

Also required:

- **Automated tests**: `./test/run.sh` must be green (exit 0). **Eight layers**: a warning-free build
  of `ctc`, white-box unit tests in `test/unit`, golden snapshots in `test/cases`
  (generate → diff → compile → run), end-to-end examples in `examples/**`
  (generate → build → run → compare with `.expected.out`), the `dialect` demo (expanded by its
  `ct-dialects/` plugin, then the same generate / build / run path compared with `.expected.out`, plus
  an assertion that the unexpanded source does not compile), negative diagnostics in `test/errors`
  (must exit non-zero with a `file:line:col: error:` prefix), characterisation assertions under
  `known limitations`, and the `cli` argument/driver branches. `CC=gcc ./test/run.sh` selects a compiler.
- **The CT-line gates are required too** (`run.sh` only drives L0): one command,
  `bash selfhost/check-all.sh`, runs `./test/run.sh`, `selfhost/check-goldens.sh` (L1 against the
  goldens, the L1′ bootstrap loop, and the L1/L2 fixpoint), `selfhost/check-archive.sh` (the L2
  ratchet against the archived oracle), `selfhost/check-m2a.sh`, `selfhost/ct-tour.sh`,
  `editors/vscode/test/check-grammar.py`, `test/pkg/run.sh` (the Phase 8.1–8.3 package manager:
  local directory sources, git sources and `install` verification) and `selfhost/check-ast.sh`
  (the Phase 9.1–9.7 + 10.x AST compiler's behavioural cases, CLI error branches, the self-compile
  fixpoint and whole-corpus equivalence) — any
  failure makes the whole run non-zero; `bash test/acceptance/run.sh` reports
  separately (its PENDING entries are expected and do not block). Run it after touching
  `selfhost/**`.
- **ct-ast is a grouped multi-unit tree**: the groups (`runtime/`, `frontend/`, `tool/`) `import` each
  other by full path, so a build needs `-I selfhost/ct-ast` (the gate scripts and the README install
  recipe already pass it; a hand-rolled build must too).
- **The manual three-step check stays required** — the suite's internal paths differ from the commands
  you type, so run the three commands above yourself and paste the output.
- **New or changed syntax needs new cases** — see the checklist in §9.
- **Editor side**: a syntax change must be mirrored in `editors/vscode/syntaxes/ct.tmLanguage.json`,
  and `python3 editors/vscode/test/check-grammar.py` (21 assertions) must be green. It checks the
  extension, not the compiler, so it stays **out** of `./test/run.sh` — and it never replaces the
  manual three-step check.
- **Report honestly**: never claim an unrun check passed, and never "fix" a failure by editing a
  golden baseline or an `.expected.out`. Regenerate them only after confirming the behaviour change
  was intended.

### 7. Prohibited

- No type checking, semantic analysis, or optimisation in `ctc.c` (outside Phase 0 scope).
- **Never slip a non-bug-fix into `ctc.c`**: while frozen, only defect fixes that do **not move the
  existing corpus output** are accepted (criteria and register in §2). Never relax a `MAX_*` ceiling,
  never edit `ctc.c` to make an L1 gate pass, and never change existing behaviour under the label of a
  "bug fix" — if the output really does move, it is not a bug fix and must go through user sign-off
  plus golden regeneration instead.
- No adding or re-adding namespaces / multi-file / import / Drop / `#line` / diagnostics on the **C
  side** (Phase 0.3 moved them out of `ctc.c`; they are redone in **CT** in Phases 2–5). No generics
  or inheritance unless the user assigns that phase explicitly.
- No committing or hand-editing the `.c` / `.h` generated under `examples/**` (generated files are
  never committed).
- No weakening of `examples/**/*.ct` to make output pass (extending them is fine).
- No swallowed errors, silent truncation, or `TODO` stubs on the main path.
- Never rename the project `ct`, the entry command `ct` (`ctc` is the compatibility alias) or the `.ct` extension to `ct-lang` /
  `ctlang` / `.ctlang` (`ct-lang` is only the repository name). The one sanctioned evolution is the
  decided "single-entry `ct` with `ctc` as a compatibility alias" recorded in the roadmap — do not
  invent other names.
- Never delete or reword the license line in the generated banner, and never strip the SPDX /
  copyright / exception notice at the top of `ctc.c` — the output exception must **travel with the
  output** (see `LICENSE.EXCEPTION`).
- No build step, npm dependencies, or bundler under `editors/**` (see the hard boundaries in §2).
- No committing binaries, object files, or temporary files.

### 8. Commits

`<type>(<scope>): <subject>` with an English imperative subject ≤ 50 chars; `type` ∈
`feat|fix|docs|refactor|test|chore`; `scope` ∈ `parser|codegen|rewrite|cli|selfhost|docs|example`. Explain the
*why* and the verification steps in the body (Chinese is fine). One concern per commit.

### 9. Checklist for new syntax features

- [ ] Lexing uses `word_at()` word-boundary checks, not bare `strncmp`
- [ ] Incomplete/invalid input produces a positional error
- [ ] New naming rules documented in `docs/language-spec.md`
- [ ] The "never rewrite inside strings / chars / **single-line** comments" guarantee still holds (the
      **continuation line** of a multi-line block comment is not covered: it is treated as ordinary
      code, a known limitation recorded in [language-spec](docs/language-spec.md) §6.2)
- [ ] `examples/**` extended or updated, regenerated and reviewed, `.expected.out` refreshed
- [ ] `test/cases` extended with golden cases (regenerate baselines with `./ctc <case>.ct -o <case>.expected.c` and review them — never hand-write them); negative cases go to `test/errors`
- [ ] The three-step verification passes **and** `./test/run.sh` is green
- [ ] `editors/vscode/syntaxes/ct.tmLanguage.json` covers the new construct and
      `python3 editors/vscode/test/check-grammar.py` is green
- [ ] `README.md` and `docs/language-spec.md` updated
