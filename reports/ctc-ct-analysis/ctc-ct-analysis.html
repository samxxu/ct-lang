01一分钟速读

它做的事只有一件：把 CT 语法糖展开成纯 C。没有任何类型检查、优化或错误恢复——能静态判定的错误就 die() 退出，其余原样透传。

读整文件
一次性读入 g_src/g_len，CRLF 归一化
单趟扫描
compile_range 只跑一遍；边扫边写两个流
按行分派
trait/struct/impl 走构造解析器，其余走逐行重写
收尾补构造器
文件作用域对象的 vptr 攒进 g_unit_init，末尾发 __ct_init
先记住这三条，通读会快很多 ① 一切都是偏移量扫描。 全文件用 size_t p 在 g_src 上走，没有 token/AST。
② 两个 trait 是同一对象的两半。 struct Pipe 同时 use PipeOps, RewriteOps，两半可经 self-> 互相调用；拆成两个只为绕开 MAX_METHOD。
③ 方法体看不到文件作用域对象。 所以符号表一律以 struct SymTab *sym 参数显式传下去（这正是 emit_body 那个快照/还原 bug 的由来）。
物化约束 编译器源码本身必须遵守 CT 的「一行一语句、声明先于使用、单文件」纪律——否则重写器认不出来，产物编译不过。这条约束贯穿全文。

03主流程：从 argv 到 .c/.h

顶层是单趟的：compile_file 只调用一次 compile_range，扫描过程中直接往两个流写；文件作用域对象的 vptr 写入不是靠第二趟，而是攒进 g_unit_init，末尾一次性发成 __ct_init 构造函数。

04逐行重写管线（核心）

普通行进入 emit_raw_line 后：先试 parse_func_sig（是不是函数签名/定义），否则交给 transform_line。transform_line 按固定优先级依次尝试四个识别器，任一命中即返回；全部不命中时才走通用兜底 transform_calls。

try_var_decl 的三条分支

  • 指针形态（Struct *p）：检测 RHS 是否 malloc/calloc → 判 isheap；是堆对象且该 struct（含嵌套）需要 vptr 时，换行补 put_heap_vpts（用 -> 写 vptr）。
  • 数组形态（Struct a[n];）：需要 vptr 时强制成带长度的裸声明形式（否则 die）；按作用域分流——文件作用域把逐元素 vptr 攒进 g_unit_init，函数内则追加到本行之后。
  • 值对象形态（Struct x）：= { … } 时在 } 前用 put_own_vptr 插入 vptr 指示符（多行初始化式 die）；裸声明补 = { …vptr }；还需嵌套初始化时同样按作用域分流。
作用域分流的判据 就是 g_nscope == 0——0 表示文件作用域。文件作用域没有任何语句能安放赋值，所以只能攒进 g_unit_init 交给 __ct_init。

05接收者形态与 transform_calls

transform_calls 是全文最长的扫描器（约 300 行）。它逐字符走一行，遇标识符就取 token 并查 find_var，然后按 A → B → C → D 四分支尝试改写；字面量与注释逐字拷贝，保证「字符串/注释内不重写」。

hoist 机制（rvalue 提升） g_hoist 是一个「下一行之前要先输出的声明」缓冲。emit_raw_line / emit_body 在写被重写行之前调用 emit_hoisted() 把它 flush 出去，于是接收者只求值一次、且次序正确。临时量命名 __ct_tmp<N>，N 来自全局单调计数 g_ntmp（全文件唯一）。

两个 walker

walk_method（2688）与 walk_to_iface_field（2735）是同构的：从一个 struct 接收者出发，循环按 isptr 要求 . 或 ->，读成员名；命中目标（方法 / 接口字段）就回填出参并返回 1，否则用 find_field_ex 往下一层走——跨过指针字段时翻转 isptr，这决定了最终是取 &recv 还是 recv、用 .__ 还是 ->__。

出参含义：out_tr 命中方法所属 trait；out_cur 最终接收者 struct 下标（rvalue 提升要写回）；out_need_amp = !isptr；out_rend 接收者文本结束位置；mp 实参左括号位置；memb 方法名。

06数据结构与符号表

关键字段语义

  • Var：s = struct 表索引（接口值时为 -1）；ptr 指针；arr 数组；iface 是否接口值；tr 接口对应的 trait 索引。这六个字段决定了 transform_calls 里选哪个分支。
  • FuncSig：retstruct/retptr 让 rvalue 接收者知道临时量该声明成值还是指针；rettrait 让 box_to_iface 认出「返回接口的函数」；ptrait[] 决定哪些实参要装箱。
  • SymTabOps 的 8 个方法全部是线性查找（名字 + 计数），find_func 是从后往前找最近同名（允许重声明）。

07impl 的展开：方法与 vtable

为什么 emit_body 要快照/还原 进入方法体前 sym->nvars = 0 并重新登记 self 与参数；退出时必须把 sym->vars 的内容（而不只是条目数）还原回文件作用域的状态。冻结期唯一那次 ctc.c 修复（1bdb93b）修的就是这里只还原计数、不还原内容导致覆盖外层条目的缺陷；L1 同步保持同一行为。

方法体里的两条行级特例

  • replace_self（1802）：把 self 改写为 _self——只在 self 是完整单词、且前一字符不是 . 或 -> 时替换。所以 g.self、字符串里的 "self"、注释里的 self 都不动。
  • scope_track（2794）：扫本行的 {/} 压弹 g_scope[] 并回滚 sym->nvars，让局部变量只在自己的作用域可见；函数体入口那个 { 用 g_body_pre 快照对齐。

08实例：一份 .ct 到 .c

以仓库里被测试套件校验的样例为准：examples/01_greeter/ —— ./test/run.sh 的 examples 层会生成 → 构建 → 运行 → 与 greeter.expected.out 比对，所以左右两侧的内容可自行核对。左边是你写的 CT，右边是它展开出的 C。

输入：greeter.ct

trait Greeter {
    void greet();
    void greet_name(char *name);
}

struct Person {
    char *name;
    int age;
} use Greeter;

impl Greeter for Person {
    void greet() {
        printf("Hello, I'm %s, age %d\n",
               self->name, self->age);
    }
    void greet_name(char *name) {
        printf("Hello %s, I'm %s\n", name, self->name);
    }
}

int main() {
    Person p = { .name = "Tom", .age = 36 };
    p.greet();
    p.greet_name("Jerry");
    return 0;
}

09错误路径地图（die）

全文只有 die(pos, fmt, ...) 一个报错口（设施层，208 行）：由偏移换算出 文件:行:列: error: 描述，随即 exit(1)。不做错误恢复——第一个错误就终止。唯一例外是 read_file 的 I/O 失败走 fprintf + exit(1)。

这些「不支持」是刻意的 namespace/import/pub（模块系统）、#line、诊断、Drop 都属 Phase 2–5 —— 要么用 CT 侧重做，要么已被归档为 oracle。ctc.c 冻结期不得在 C 侧加回。L1 对它们报错而不是硬编。

其他已知边界

  • 接口数组声明即 die：AST 子节点只能用「接口指针 + 链表」。
  • 多行初始化式（= { 找不到配对 }）die；数组只支持 Type name[n]; 形态。
  • 接口指针字段：装箱/接收者分发会被放弃（返回 NULL，留给用户或报错）。
  • rvalue 接收者只允许出现在语句头或初始化式首位。

10最短阅读路线

如果只想用一小时建立骨架认知，按这个顺序读约 300 行就够：

  1.  1–64 行 — 头注释。作者自己的能力清单与 OO 结构说明，读完就有地图。
  2. 72–153 行 — 常量与数据模型。看懂 Struct 的四张字段表和 Var 六个字段。
  3. 631–690 行 — 两个管线 trait 的声明 + struct Pipe。39 个方法签名（另加符号表层 SymTabOps 的 8 个，全文共 47 个）。
  4. 3010–3041 行 — main。32 行，看它怎么落到一次 compile_file。
  5. 1580–1629 行 — compile_file。重置 → 读文件 → 开流 → guard/banner → 扫描 → 构造器 → 收尾。
  6. 1425–1475 行 — compile_range。单趟扫描与四种分派（含「不支持」的报错）。
  7. 1390–1422 行 — emit_raw_line。每行如何进 parse_func_sig 或 transform_line。
  8. 2084–2106 行 — transform_line。四识别器的优先级链。
  9. 2378–2680 行 — transform_calls。最长的核心扫描器，配合 A/B/C/D 四分支读。
  10. 2688–2770 行 — 两个 walker。接收者沿字段链行走的规则。

之后再按需展开：parse_trait(1090) / parse_struct(1177) / parse_impl(1248)、try_var_decl(2109)、box_to_iface(1846)、parse_func_sig(2826)。

配合跑一遍 bash selfhost/ct-tour.sh 会现场演示 L0→L1→L1′ 与「逐字节一致」；bash selfhost/check-goldens.sh 是常驻关卡（L1 vs golden、L1′ vs golden）。边读边跑，理解最快。

MAX_FUNCS 是「健康约束」 它逼着 L1 把逻辑搬进 impl 方法而不是散落的自由函数——这正是「L1 必须写 OO」的机械保障。不得为绕过它而改冻结的 ctc.c。

L1 源码自身的硬约束

  • 单文件：L0 已无 namespace / 多文件，所以 L1 无法分文件组织。
  • 一行一语句、函数体不用单行写法：否则按行重写器认不出来，产物静默不变、编不过。
  • 声明先于使用、单趟扫描：trait/struct 需人工拓扑排序；相互递归只能经接口指针。
  • 零复用：不得 #include ctc.c，设施自带（否则自举与差分验证都变成同义反复）。
