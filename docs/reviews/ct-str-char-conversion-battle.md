## 1 主张席

### 1.1 主张与可验证判据

| # | 主张 | 可验证判据（实现后） | 依据 |
| --- | --- | --- | --- |
| C1 | `Str` 在需要裸指针的实参位置可直接传，取内部起始地址，不分配 | 同一调用分别用 `str_c_str` 与自动转换，对分配计数/自定义 allocator 观测：自动转换路径分配次数为 0，C 侧读到的字节一致 | `Str` 布局与结尾 NUL：[Str.h.ct:18-21](../../lib/std/Str.h.ct#L18-L21)、[:39-46](../../lib/std/Str.h.ct#L39-L46) |
| C2 | 借用指针只在 `Str` 存活期内有效 | 调用返回后释放 `Str`，再用旧指针应被编译期拒绝；运行期 ASAN 无 use-after-free | 需要新的生命周期/逃逸规则（现行规范无对应条目） |
| C3 | `char *` → `Str` 在声明处深拷贝 | `Str s = p;` 后改 `p[0]`，`s` 字节不变；`s` 的缓冲区地址与 `p` 不同 | `str_from` 现状：[Str.h.ct:51-60](../../lib/std/Str.h.ct#L51-L60) |
| C4 | 赋值处深拷贝且旧缓冲区只释放一次 | `s = p;` 后旧 `s` 被 `Drop` 释放；ASAN 无 double-free；新 `s` 与原串无别名 | `Drop`：[Str.h.ct:23-29](../../lib/std/Str.h.ct#L23-L29) |
| C5 | 传参位置等价于显式 `str_from` | `f(p)` 与 `f(str_from(p))` 生成物行为一致；实参为 `NULL` 时行为按最终裁定固定 | 现行 `char *` → `Str` 形参是硬错：[language-spec.md:2000-2005](../language-spec.md#L2000-L2005) |
| C6 | 只在这三处转换，其他位置不静默拷贝 | 返回值、字段初值、容器字面量、三目位置各一条负例，均给出固定诊断，不生成拷贝 | 提案 §2.2 |
| C7 | 自动深拷贝分配失败终止程序 | 用注入失败的 allocator 运行，进程以固定退出码终止，不返回释放态；诊断含分配字节数 | 与现状不同：`str_from_len` 返回 `len = -1`（[Str.h.ct:40-43](../../lib/std/Str.h.ct#L40-L43)） |
| C8 | 既有显式写法零回归 | `str_from` / `str_c_str` 调用点、ABI、`ct check --types` 既有硬错用例全部保持 | 提案 §5 |

### 1.2 主张席结论

两条转换的**方向**成立：`Str` 拥有连续缓冲区且以 NUL 结尾，借出起始地址在实现上直接可得；
`char *` → `Str` 也有现成的深拷贝实现。提案能把「取地址再 `free`」「显式 `str_from`」两类纯搬运
从调用点移除，收益是真实的。C1–C8 足以构成一轮可执行的验收面。

## 2 反证席

### 2.1 逐条反证

| # | 针对 | 反例 / 边界 | 代价与判定 |
| --- | --- | --- | --- |
| R1 | C3 / C4 的「三处」 | 声明、赋值、传参在语法上都是**表达式位置**，不是三种独立语句；`f(cond ? p : q)`、`f(g(p))`、嵌套调用都落在「传参」里，转换点是按**期望类型**判定，不是按语法位置 | 需要类型定向转换与更精确的上下文定义；仅靠 parser 切不了。判 C3/C4 **方向成立，边界未定** |
| R2 | C3 的开销可见性 | `loop 1000000 { Str s = p; }` 每次隐式 `malloc`+拷贝，调用点没有任何标记；与显式 `str_from` 相比，读者无法从语法看出分配 | 隐藏 O(n) 拷贝是真实代价；至少要提供诊断/统计手段，或在规范里写明「这三处一律分配」。判 **代价可见性不足** |
| R3 | C2 的借用生命周期 | `char *q = s;` 若允许，`s` 释放后 `q` 悬空；`c_fn(make_str())` 借用临时值，若临时值在调用前被释放则悬空；C 函数若保存指针，返回后仍悬空 | 必须限制为「立即实参、非临时左值、不得逃逸」；这需要逃逸分析或语法限制。判 **需加约束** |
| R4 | C1 的可写性 | `Str` 内部缓冲区可写；借出 `char *` 后，被调方可以写坏字节或提前写 `\0`，破坏 `len` 契约；只借 `const char *` 又覆盖不了大量 C 接口 | `const` 正确性与兼容面二选一。判 **需项目组定 `const` 规则** |
| R5 | C5 的重载/歧义 | 同一点同时存在 `f(char *)` 与 `f(Str)` 时，`f(s)` 精确匹配 `Str`，`f(p)` 精确匹配 `char *`；但 `f(0)`、`f(NULL)`、`f("literal")` 会同时可转，可能从「唯一候选」变成二义 | 需要「精确匹配优先、转换次之、仍二义则报错」的规则；现有规范无此条。判 **需补解析规则** |
| R6 | C5 与 trait/方法解析 | 若 `char *` 上已有方法层 trait；`char *` 可隐式转 `Str` 后，`p.len()` 这类调用可能改走 `Str` 侧方法，既有调用点语义漂移 | 方法解析优先级要重定；属于跨特性的交互成本。判 **高风险，需先做影响清单** |
| R7 | C7 的失败即终止 | 库代码调用 `f(p)` 时隐式分配失败会直接杀进程；嵌入式/长驻进程无法恢复；现有 `str_from` 明确返回释放态，两种语义并存会让「同一转换」有两种失败行为 | 终止策略与现行错误处理约定冲突；测试也难以稳定注入 OOM。判 **暂不接受为默认** |
| R8 | 与 v0.53.2 硬错的关系 | `char *` 传给 `Str` 形参在默认路径是**硬错**，这是 v0.53.2 为拦截 C 无法转换的按值 struct 不一致而加的；自动转换等于撤销这条拦截 | 需要过渡方案与诊断分层，不能静默翻转。判 **需单独立项，不宜夹带** |
| R9 | 「消除两种写法」的动机 | 事实澄清（§5）：转换函数保留，编译器只插入调用；不是「新增第三种写法」，也不是要废弃函数。真正要驳回的是「消灭函数/写法」的表述 | 驳回结论不变；理由改为「函数保留，只是不让调用者手写那一步」；动机应写成「减少纯搬运」 |
| R10 | C1 的数据完整性 | `Str` 允许内嵌 `\0`，C 读者按 NUL 截断；自动转换会让「传 `Str`」看起来与「传 `char *`」等价，实际可能丢尾部字节 | `str_c_str` 已在注释里写明截断；隐式化后这个警告消失。判 **需诊断或文档硬约束** |

### 2.2 反证席结论

提案的**实现可行性**成立，但**规则边界**不成立为「两条一句话规则」：

- `char *` → `Str` 的「三处」实际是类型定向转换，必须定义期望类型、重载优先级、临时值与 `NULL`；
- `Str` → `char *` 的借用必须限制逃逸，否则是悬空指针；
- 失败即终止与现行 `str_from` 的释放态语义冲突，且与「库不杀进程」的常识冲突；
- 撤销 v0.53.2 的硬错需要独立过渡，不应由本提案顺带完成。

## 3 对冲

两席在事实层面无分歧：两条转换都能实现，收益存在；分歧在**代价与边界由谁承担**。
主张席的 C1–C8 可以作为验收面，但必须先补齐反证席指出的四类约束（生命周期、`const`、重载、失败语义），
否则「能跑」不等于「可安全交付」。

## 4 裁判席

### 4.1 结论：**部分受理**

不是整条驳回，也不按提案原文整条受理。受理的是方向与受限形态；驳回的是把未定边界直接写成规则。

**受理（有条件）**

1. `Str` → `char *` 的**借用视图**方向受理，但限为：
   - 只出现在**立即实参**位置；
   - 实参必须是**非临时左值** `Str`；
   - 只借 `const char *`，除非项目组另行裁定可写借用；
   - 不得赋给指针变量、不得返回、不得存入字段；
   - 违反任一条给出固定诊断。
2. `char *` → `Str` 的**三处深拷贝**方向受理，但限为：
   - 由**期望类型**触发，不按语句形状识别；
   - 精确匹配优先；仍二义则报错，不静默选一个；
   - `NULL` 行为单独立条（建议：拒绝并要求显式 `str_from`，避免「空指针=空串」的隐式约定）；
   - 只覆盖声明、赋值、传参；其余位置保持硬错。

**驳回 / 暂缓**

1. **失败即终止**：暂不受理为默认语义。它与 `str_from` 的释放态、项目的错误处理约定冲突；
   若项目要引入 OOM 终止政策，应单独立项，并同时定义显式与隐式两条路径的一致性。
2. **立即撤销 v0.53.2 的硬错**：暂不受理。该硬错是已发布行为，需要过渡期、诊断分层与兼容说明；
   不能由本提案静默翻转。
3. **「消除两种写法」的表述**：驳回。显式 `str_from` / `str_c_str` 仍需保留；动机应改写为
   「减少纯搬运」，而不是「只剩一种写法」（理由见 §5 澄清）。

### 4.2 仍需项目组决定的事项

1. 借用视图的生命周期模型：语法限制（只许立即实参）还是引入借用标注/逃逸分析。
2. `const char *` 与 `char *` 的边界：是否允许可写借用，以及写坏 `len` 契约的责任归属。
3. 重载与方法解析优先级：`char *` / `Str` 双候选、既有方法层 trait、`NULL` 字面量的处理。
4. `NULL` → `Str` 的语义：拒绝、空串、还是终止。
5. OOM 政策：是否引入终止语义；若引入，`str_from` / `str_from_len` 是否同步。
6. 内嵌 `\0` 的诊断：自动转换时是否给 warning，还是只在文档里声明截断。
7. 与 v0.53.2 硬错的过渡：先加 warning 再转自动转换，还是一次性切换。

### 4.3 裁判附注

本记录只给设计结论，不构成排期或 phase 分配；是否落成施工卡、何时做，由项目组另行决定。
提案方不再就上述已驳回项重复主张，除非项目组先改需求或错误处理约定。

## 5 对抗后事实澄清（2026-11-16，负责人）

本节只澄清事实前提，**不改写裁判结论**；与上文冲突时，以本节的事实陈述为准，结论仍按 §4.1。

1. **隐式转换函数必须保留。** `str_from` 等转换函数是公开、可显式调用的能力，不得因引入自动转换
   而删除或私有化。编译器只是在适用位置自动插入对它的调用：源码字面不出现转换调用，
   底层仍由该函数完成转换（与 C++ 的转换函数同理）。
2. **`Str` → `char *` 的底层能力也必须是函数。** 借用视图需要一个公开函数（提案暂记
   `str_view`，最终名字由项目组定），返回内部起始地址、不分配；`str_c_str` 保持「分配副本」语义，
   两者并存。编译器在适用位置插入的是这个借用函数，不是 `str_c_str`。
3. **对 R9 的影响。** 驳回结论成立，但理由修正为：我们不是要消灭函数或写法，而是不让调用者
   手写那一步；显式场景（把借用视图存进变量、返回、存字段、需要明确副本）仍直接调用公开函数。
4. **对裁判 §4.1 第 3 条的影响。** 结论（驳回「只剩一种写法」的动机表述）不变，理由以本节为准。
5. **适用位置按裁判口径收窄**（详见提案 §2.1 / §2.2）：
   - `Str` → `char *` 只允许立即实参，且实参为非临时左值；不得赋给指针变量、返回、存字段；
   - `char *` → `Str` 只允许声明、赋值、传参三处，由期望类型触发；精确匹配优先，二义报错。
6. **未改变的事项。** 失败即终止仍为暂缓；v0.53.2 硬错的过渡仍需单独立项；§4.2 的待决事项
   继续留给项目组。

## 6 对抗后补充事实：目标类型与归属（2026-11-16，负责人）

本节是 §5 之后的补充事实，**不改写裁判结论**；§4.1 仍为「部分受理」。三条规则是**通用机制**，
不限于 `Str` / `char *`；任何「产出型操作 + 两种表示」都按同一口径处理。

1. **结果类型由目标类型决定（target typing）。** 产出型操作（字符串拼接、构造、转换等）不固定
   返回类型；结果类型由接收它的声明、赋值目标或形参类型决定：目标 `char *` 就给 `char *`，
   目标 `Str` 就给 `Str`，编译器负责把产出转成目标类型。同一句 `a.concat(b)` 在
   `Str s = ...` 与 `char *p = ...` 两处得到不同类型。没有目标类型的上下文（独立表达式语句、
   条件表达式）退回默认返回类型或固定诊断，不能静默改变归属。
2. **不产出新值的位置退回最易表示。** `a == b` 直接比较内容，不分配、不拷贝；一方 `Str`、
   一方 `char *` 时用能同时看到字节与长度的表示比较。边界事实：`Str` 允许内嵌 `\0`，
   按 `data` + `len` 比较；只用 NUL 结尾视图（`strcmp`）会把尾部截断，违反 §1.1 的 `len` 契约。
3. **内存归属随目标类型变化。** 目标 `char *`：被调方分配、调用方 `free`（C 的 `malloc`/`free`
   规矩）；目标 `Str`：拥有型、由 `Drop` 回收。同一条调用，归属随目标类型变化，必须在调用点
   文档与诊断里写清；临时值的归属随其最终目标类型确定。
4. **对裁判的影响。** 受理/驳回项不变；新增的是机制层规则，仍受 §4.2 待决事项约束：
   target typing 在嵌套、条件分支、无目标上下文中的传播；`==` 的统一比较协议与内嵌 `\0` 判定；
   `char *` 产出的 `free` 责任与临时值释放点；同一操作为不同目标类型生成签名时的 ABI 安排。
