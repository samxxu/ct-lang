## 0 结论（可单独摘出）

提案指出的方向是对的：CT 要支撑 JSON 的自然访问，语言层确实只差「自定义下标」和「链式短路」两块，其余可以在包层解决。但这份提案的**证据链不能直接用于决策**：它引用的 `phase40-draft.md` 是已完成的 `errdefer` 相，不是下标草案；真实的 L1 草案是 `docs/proposals/custom-index-protocol.md`，其状态是「提案 / 未立项 / 未过分析，不作数」，判据编号是 `RL1-D*` / `RL1-L*` / `RL1-E*`；`container_index_check` 的行号与职责都写错了；`q_suffix_ahead` 不是 Result 传播后缀；`Trait` 并非没有 `tparam`；`lib/std/utf8` 不存在。

**裁定**：

1. **L1 接受立项**，但只按 `custom-index-protocol.md` 的 `RL1-E1..E10` 验收；提案的 C1 可映射到 `RL1-E1`，C2 映射到 `RL1-L1`，C3–C5 属于全新的 `?.` 相，C6 引用的 `E40-1..E40-10` 与 L1 无关。
2. **L1 只能解决单层下标**。草案 `RL1-D8` 明确：`p[k]`（`p: struct X *`）仍是 C 指针算术，不进入协议；而 JSON 的 `get` 必然返回 `JsonValue *`。因此 `v["a"]["b"]` 在草案下不成立——字符键会落成 C 下标报错，数字键会变成指针算术且**不报错**。要么包层把 `get` 改成返回值类型（`JsonRef`）并给 `JsonRef` 也实现 `get`，要么另立「指针接收者 + 连写下标」需求。建议前者先做，语言侧不扩。
3. **`?.` 当前形态驳回**：`a?.b → (a ? a->b : 0)` 只在「接收者是指针、结果是标量或指针」时成立；结构体值接收者/结果会被 `cc` 拒绝（实测）。`a?[k] → (a ? a.get(k) : 0)` 两种接收者都不合法（值不能作条件，指针不能用 `.`）。此外 `?.` 作为独立 token 会破坏今天合法的 `c?.5 : 1.0`。JSON 真正需要的是**可选方法调用**（`data?.get("server")`）而不是可选字段访问，提案没有覆盖。
4. **`a.get("b").get("c")` 的前提也不成立**：CT 对指针接收者用 `.` 调用方法时发射 `S_f(&p)`（传 `struct S **`），`cc` 报 incompatible pointer types，非空时结果就已经错，不只是「中间为 0 段错误」。这是独立缺陷，建议单独立项，先于任何链式语法。

## 2 「不需要语言动」表复核

抽查结论：**大部分成立，两处硬错、一处缺件、一处引用失真**。

- **硬错**：「泛型 trait 未实现（Trait 无 tparam）」不成立。`Trait` 自 Phase 35 起就是模板行（`ntparams`/`tparam`/`bound`）。「JSON 不需要」这个取舍可能仍成立，但事实前提不能这么写。
- **缺件**：「UTF-8 `lib/std/utf8`」在仓库里不存在。要么是外部依赖/尚未落地的包，要么是记忆中的旧版本；照此写进依赖表会误导排期。
- **引用失真**：union 的规范锚点 `:715-728` 实为函数指针节；union 在 `:828-840`。
- **成立**：`Vec`/`Map` 内置、`Map` key 白名单、`foreach item.key/value`、方法级 `pub`、`err:`/`errdefer`、浮点字面量。
- **规范空白（不是事实错误）**：`JsonValue` 作为 `Map` 的 key、`==` 重载、`foreach` 直接遍历用户类型——提案把它们推给 JSON 组，但规范里没有对应条款，属未定义区，不能当作「包层可解」的既成事实。

## 3 L1 判定

**接，按 `custom-index-protocol.md` 立项，不接受提案的 phase40 依据。**

理由三点：

1. **JSON 的真实需要**：`v["server"]` 只是第一步；JSON 访问的常态是连写。草案 `RL1-D8` 把 `p[k]`（指针接收者）留给 C 指针算术，而 `JsonValue::get` 返回 `JsonValue *`，于是第二次下标不再进入协议：
   - `v["a"]["b"]`（字符串键）→ 发射 C 指针下标，`cc` 报 `array subscript is not an integer`；
   - `v[0][1]`（数字键）→ 合法的 C 指针算术，**不报错、指向错误对象**。
   因此「L1 一落地，`v["server"]["port"]` 就可用」的推论不成立。两条出路：
   - **包层优先（推荐）**：`get` 返回值类型（如 `JsonRef`），并给 `JsonRef` 也实现 `get`，这样每一跳的接收者都是值，连写自然成立，语言不动；
   - **语言扩展**：另立「指针接收者进入协议 + 连写」的需求，涉及“值/指针同一协议”的接收者语义与自动解引用，成本远高于 L1 本身，不应塞进 L1。
2. **实现成本**：草案已把工作拆成 T-1..T-7（读形态、写形态、守卫、泛型还原、双模式、文档、收口），每项可独立验收；这是现成的、可排期的路径。提案的 A/B 只是其中 `RL1-D3` 的一个取值，不需要重写草案。
3. **对既有语义与生成物的风险**：草案 `RL1-D8` 冻结 C 数组 / 指针 / `Vec` / `Map` 的既有行为，`RL1-E5`/`E6` 要求逐字不变；新增分支只对 `struct` 且解析成功的接收者生效。风险可控。

**方案 A 还是 B**：**MVP 选 A**（方法名 + 参数个数 + 非 static，`RL1-D3` 不动）。理由：

- 方案 B 要在调用点按实参类型选方法，这是表达式类型系统的一部分，仓库今天只在 `static_ctype` 这一层做保守推断（草案自己写了「本仓没有完整表达式类型系统」）。把重载解析塞进 L1，会让同一个 `[]` 糖在 `Vec`/`Map`/用户类型上出现三套匹配规则，回归面远大于收益。
- 代价是 `v[0]` 与 `v["k"]` 不能同时用 `get`。JSON 包已接受 `get_idx` 分名，这个代价可控。
- **但**：如果 JSON 组坚持 `v[0]` 也要糖，那就是方案 B 的独立需求，应单独立项（重载解析 + 诊断），不要借 L1 的壳。

**验收条目够不够撑 C1–C6**：

- C1 → `RL1-E1`（非泛型 struct + `int get(int)`）基本对应，但 C1 的 `impl J { int get(int i) }` 是固有 impl，符合 `RL1-D2`；fixture 名不同不算冲突。
- C2 → `RL1-L1`，文案「指名类型」已覆盖；但提案引用 `E40-4` 是错的。
- C3–C5（`?.`）**草案完全没有**，不能算在 L1 的验收里；应另立阶段与 `D/E` 编号。
- C6 引用的 E40 条目与 L1 无关，**作废**；L1 的全量证据应是 `RL1-E8/E9`（fixpoint、四门禁）与 `RL1-E4`（负例逐字）。
- 还缺一条：**指针接收者与连写下标的明确“不做”判据**。建议在草案中补 `RL1-E11`：`p["k"]`（`p: struct X *`）保持 C 语义并给出文档/诊断口径，避免实现后用户以为可用。

## 4 `?.` 判定

**驳回当前形态。** 不是方向错，是展开式与 token 方案都不可实现为所述语义。

1. **`a?.b → (a ? a->b : 0)` 只在窄条件下成立**：
   - `a` 必须是指针或标量；`a` 是 struct 值时，`ct-ast` 会照发 `(y ? y.n : 0)`，`cc` 直接拒绝：`used type 'struct X' where arithmetic or pointer type is required`（实测）。
   - `a->b` 必须是标量或指针；字段是 struct 值时，`0` 不能作为另一分支，C 三元要求两分支可转换。
   - 若要通用，展开必须由编译器按结果类型给出零值（`(T){0}` / `(void *)0`），不再是「纯语法糖」；这需要类型信息，影响 `static_ctype` 与发射器。
2. **`a?[k] → (a ? a.get(k) : 0)` 两种接收者都不合法**：`a` 是指针时 `a.get` 不是 C；`a` 是值时 `a ?` 不是 C。正确形态至少要 `(a ? (a)->get(k) : <零值>)`，同样需要类型导向。
3. **独立 token 会破坏既有合法代码**：今天 `c?.5 : 1.0`（无空格）合法，`ct-ast` rc=0，生成 `(c ? .5 : 1.0)`（实测）。若 `?.` 按最长匹配成一个 token，`c?.5` 会被切成 `?.` + `5`，语义破坏。词法必须对「`.` 后跟数字」让位，这条约束提案没有写。
4. **与 Phase 44 后缀 `?` 的关系**：`?` 是后缀消歧，靠「`?` 后能否开始表达式」判断；`.` 不在“不能开始”的集合里，所以 `x?.y` 今天被当三目并最终语法错误，没有既有语义可保。但 `?.` 与 `? .5` 的冲突是实打实的（上一条）。
5. **优先级前提不成立**：规范优先级表（`language-spec.md:95-112`）只列一元/二元/三目/赋值，**没有后缀运算符行**；`. -> [] ?` 都在后缀链里解析。因此不存在「高于一元 `?`、低于成员 `.`」的插入位置，也没有「一元 `?`」。正确说法是：`?.` 属于后缀链，左结合，与 `.` / `->` / `[]` / 后缀 `?` 同层。
6. **JSON 需要的不是字段可选访问**：`data.server` 在 JSON 里不是 C 字段，而是 `get("server")`。`a?.b` 只覆盖字段，覆盖不到 `data?.get("server")`。若要 JS 式体验，需要的是**可选方法调用/可选下标**（`a?.get(k)` / `a?["k"]`），且结果类型必须可空。提案的 `a?[k]` 是这个方向，但展开式写错（见第 2 条）。
7. **贯彻影响面**：新增 token 要改词法、语法、语法检查器（`check-grammar.py` 的 168/169 计数）、编辑器高亮与规范 §；`.5` 冲突要在词法层加特判；既有 fixture 没有 `?.`（`grep` 无命中），生成 C 对不含 `?.` 的程序不变。但「可选调用」若要做，还要定义空结果、类型与诊断，成本高于 L1。

**建议**：`?.` 不按现稿立项。若要满足 JSON，重写为：

- 形态：**可选后缀调用/下标**，接收者必须是指针（或显式可空句柄），结果为指针或标量；
- 展开：`(a ? (a)->get(k) : (T){0})`，零值由编译器按结果类型给出；结构体值接收者/结果给出硬错；
- 词法：**不做独立 token**，在 parser 的后缀链里识别 `?` + `.`，且 `.` 后必须是标识符（排除数字字面量），避免破坏 `c?.5`；
- 优先级：并入后缀链，不新增优先级层；
- 边界：只判 NULL，不判 `tag == TAG_NULL`——这条同意提案（见 Q4），但它不足以让 `{"a":null}` 自动短路，包层仍需判 tag。

## 5 示例可行性逐条

| 示例 | 结论 | 依据 |
| --- | --- | --- |
| `data?.server?.port` | **不成立**（需额外能力：可选调用） | `server` / `port` 不是 C 字段，而是 JSON key；`?.` 只展开字段访问。要写成 `data?.get("server")?.get("port")`，而当前 `?.` 不支持方法调用；且 `get` 返回指针时 `.` 调用本身有缺陷（见下条） |
| `items?[0]?.name` | **不成立** | `a?[k] → (a ? a.get(k) : 0)` 的接收者形态两种都不合法；`items` 是指针时还要处理 `->`；`name` 同样不是字段。需要「可选下标 + 可选调用 + 类型导向零值」三件套 |
| `v["server"]["port"]` | **不成立（L1 草案下）**；包层改造后**成立** | 第一跳后接收者是 `JsonValue *`，`RL1-D8` 把 `p[...]` 留给 C 指针算术：字符键 `cc` 报错，数字键静默算错。若 `get` 返回 `JsonRef` 值并给 `JsonRef` 实现 `get`，则每跳接收者都是值，可连写——不需要语言再动 |
| `a?.b` 展开为 `(a ? a->b : 0)` | **部分成立**（仅指针接收者 + 指针/标量结果） | 指针 + `int` 字段实测 rc=0 且 `cc` 通过；struct 值接收者实测 `ct-ast` rc=0 但 `cc` 报 `used type 'struct X' where arithmetic or pointer type is required`；struct 值字段同样不成立 |
| `a.get("b").get("c")` | **不成立** | 第一个 `get` 返回 `V *`；对指针接收者用 `.` 调用时，`ct-ast` 发射 `get_...(&p)`（传 `struct S **`），`cc` 报 incompatible pointer types，**非空时结果已错**（实测 `S_f(&p)`）；「只在中间为 0 时崩溃」的前提不成立 |

| Q1 L1 签名匹配 A/B | **A**（MVP），B 另立需求 | 见 §3；B 需要调用点重载解析，超出 `RL1-D3` 的「本仓没有完整表达式类型系统」前提 |
| Q2 `?.` 独立 token 还是 parser 组合 | **parser 组合**（反对独立 token） | 独立 token 按最长匹配会破坏今天合法的 `c?.5 : 1.0`（实测 rc=0）；parser 在后缀链里识别 `?` + `.` 且要求后随标识符即可，词法、编辑器、`.5` 都不受影响 |
| Q3 `?.` 优先级「高于一元 `?`、低于 `.`」 | **前提不成立**，无法按此插入 | 规范优先级表没有后缀行；没有一元 `?`（Phase 44 的 `?` 是后缀）；`?.` 应并入后缀链，左结合 |
| Q4 `?.` 只判 NULL、不判 `TAG_NULL` | **同意边界**，但**不足以支撑 JSON** | 与 `Map.get` 返回 0 的契约一致；`{"a":null}` 的 `get` 返回非空 `TAG_NULL`，包层仍需 `v && !v.is_null()`；提案自己的 §2.2 已承认这一点 |

## 7 若采纳的最小落地顺序与主要风险

1. **先重立 L1 的依据**（文档改动，不写代码）：把提案中的 `phase40-draft.md` / `D40` / `E40-4` 全部换成 `docs/proposals/custom-index-protocol.md` 的 `RL1-*`；确认 `REQ-L1` 仍为 open，但草案状态是「不作数」，需先过分析、补 S0 基线（草案 §2.1 要求 `baseline: <sha>`）。
2. **按草案 T-1→T-4 落地 L1**：读形态、写形态、守卫（`RL1-L1..L9`）、泛型还原；每步先红后绿，门禁用 `RL1-E1..E10`，不要用 E40。
3. **补一条 L1 判据**：指针接收者 `p[k]` 的「不做」口径（`RL1-E11`），避免 JSON 组按 `v["a"]["b"]` 排期。
4. **JSON 侧先走包层解法**：`get` 返回值类型 `JsonRef`，`JsonRef` 实现 `get`/`is_null`；`json_get(root, "a.b.c")` 过渡。这样 L1 一落地，`v["a"]["b"]` 就成立，不必等指针协议。
5. **修 `.` 对指针接收者的发射缺陷**（独立 issue，建议 P0/P1）：`p.f()` → `S_f(&p)` 是静默错值，`cc` 只给 warning；任何链式方案都会踩到。
6. **`?.` 重写后再立项**：可选调用/下标、类型导向零值、parser 组合、只判 NULL；不要与 L1 绑定排期。

**主要风险**：

- 把 `?.` 当纯语法糖，会低估「结果类型决定零值」的实现量（要动 `static_ctype` 与发射器），并可能与 Phase 44 后缀 `?` 的消歧互相干扰。
- 把 `v["a"]["b"]` 写进验收而不同时解决接收者形态，会在 L1 收口时才发现连写不成立，返工在验收阶段。
- 独立 `?.` token 的 `.5` 冲突是兼容性回归，不是新语法问题；必须在词法层明确让位规则。
- 提案里的行号/编号体系若原样进入需求池，会让后续实现与门禁对不上号；先对齐编号再排期。
