## 2 PH-46 — `Map` 元素完整性

### 2.1 目标是否单一

**是。** 一句话：让 `Map<K, 用户 struct>`（按值元素）在 `ct build` 下可编译。
证据：`docs/proposals/ct-json-capability-blockers.md:82-86` 的 `field has incomplete type` 与
`:100-106` 的四种形态对照表，只有 `Map<char *, JsonRef>` 失败。

### 2.2 范围边界

| 本卡做 | 本卡不做 | 归属 |
| --- | --- | --- |
| `MapEntry` 的**定义位置/可见性** | 键白名单、键比较、键所有权 | PH-47 |
| 按值用户 struct 元素的 build 模式完整性 | `Map` API 与 `MapEntry` 字段布局 | 本卡 D46-1 冻结 |
| `--lib` 导出面不回归 | 跨单元 Drop / 指针字段胶水 | PH-48 |
| 四种既有形态零漂移 | 新增「元素必须完整类型」的语言限制 | 明确不引入 |

补一条边界（卡里没有）：**只对「按值存储的用户 struct 元素」改归属**；`Map<char *, US *>`、
`Map<char *, void *>`、`Map<char *, int>` 必须零变化。理由见 §2.5 风险。

### 2.3 验收判据是否可执行

| ID | 现写法的问题 | 替换写法（可执行） |
| --- | --- | --- |
| E46-1 | 「输出与单文件模式一致」没有命令 | `"$work/ct-ast" main.ct -o a.c && cc -std=c99 a.c -o a && ./a > a.out`；`"$work/ct-ast" build main.ct -o out && cc out/*.c -o b && ./b > b.out`；`cmp a.out b.out` |
| E46-2 | `check-goldens 82/82` 是魔法数，且该脚本只覆盖 L1（§1.2） | 按 §1.2 的 `/tmp/p46-base` 快照 `cmp` 四种形态产物；再用 `bash selfhost/check-ast.sh \| tail -1` = `0 failed` |
| E46-3 | 「`nm -g` 面与第 39 相口径一致」不是命令；且 PH-46 §8.2 「新增 `MapEntry_*` 符号」说法错误 | 用 [phase39-draft.md](../design/phase39-draft.md):142 的归一化符号集（导出集合 ∪ `expected.internal`）做 diff；**不**允许新增符号（C 的 struct 定义不产生符号，见 §9 F2） |
| E46-4 | `grep -c 'struct MapEntry_'` 没写目标文件；多实例下 `= 1` 不成立 | 对示例实例断言：`grep -c 'struct MapEntry_char_p_JsonRef {' out/Vec.h` = 0；`grep -l 'struct MapEntry_char_p_JsonRef {' out/*.c \| wc -l` = 1 |
| E46-5 | 「无新增告警」没有基线数字 | `bash selfhost/check-warnings.sh \| tail -1` = `0 failed`，并把编译总数写成「基线 N + 本相新增数」 |
| E46-6 | 可执行 | 保留 |

### 2.4 依赖与顺序

- 46 → 47 → 50 串行成立：三者都动 `Map` 生成物与 `lib/std/Vec.h.ct`（总计划 §3）。
- 46 之前只差 PH-45 收口（§1.1），不是功能依赖。
- **必须调整的一点**：47 的 `Map<Str, 用户 struct>` 夹具只有在 46 收口后才能同时覆盖「Str 键 + 按值元素」；
  否则 47 只能退到指针元素（47 卡 §8 已写，但应提升为收口条件而不是可选项）。

### 2.5 工作量与风险

**量级：小（≤50 行）**，不是卡上的 150–280。证据：现成机制已经存在——
`Emitter.h.ct:1981-2016` 的 `inst_elem_foreign` 已把「外单元元素」的实例下沉到命名它的单元，
`Emitter.h.ct:1609-1625` 已在 header 模式用 `if (inst_elem_foreign(...)) continue;` 跳过共享头。
缺口只是 `inst_elem_foreign` 的模板白名单：

```c
/* Emitter.h.ct:1994-1997 */
if (strcmp(ins[ii].tmpl, "Vec") != 0 && strcmp(ins[ii].tmpl, "Map") != 0
    && strcmp(ins[ii].tmpl, "Option") != 0 && strcmp(ins[ii].tmpl, "Result") != 0)
    return 0;
```

`MapEntry` 不在其中，于是它按 `via_hdr` 进了共享头（`Emitter.h.ct:1609-1615`、`Stmt.h.ct:955` 命名）。

主要风险（都指向具体形态）：

1. **误伤指针元素**：若把 `MapEntry` 无条件纳入，`Map<char*, US*>` 的条目也可能被搬走，违反 O3。
   必须先用 `elem_plain_owner` 判「按值 plain struct」——该函数对 `"struct X *"` 返回 -1
   （`Emitter.h.ct:1967-1976`，`find_struct` 按基名匹配），正好可以当条件。
2. **两个单元各写一份 `MapEntry`**：`emit_struct_insts` 的非 header 分支只让
   `insts[i].owner` 写（`Emitter.h.ct:1621-1625`），但 `MapEntry` 的 owner 与 `Map` 的 owner 是否同一，
   S0 必须确认；冻结「同一个实例的 Map 方法与 MapEntry 定义必须同单元」。
3. **`map_brace_target` 的名字依赖**：`Stmt.h.ct:955` 用 `MapEntry_%s` 拼名，定义搬走后
   结构体字面量仍在同一单元，安全；但 S3 必须加一条 `Map<char*, US>{...}` 的 build 夹具。

### 2.6 定稿建议

**可定稿。** 需冻结的条目：

1. 修法冻结为「扩展 `inst_elem_foreign` 覆盖 `MapEntry`，条件为按值 plain struct 元素」。
2. O3 增加限定语「按值元素才搬，指针元素零变化」。
3. 采用 §2.3 的 E46-1…E46-5 替换写法。
4. baseline 按 §1.1 改。
5. 工量改为「小（编译器 ≤50 行 + 夹具 50–100）」。
6. 在 S0 交付物里点名 `Emitter.h.ct:1981-2016` 与 `:1609-1625`。

## 3 PH-47 — 容器键协议与键所有权

### 3.1 目标是否单一

**否，卡里是两条能力**：`Str` 键（内容比较）与 `put_owned`（复制键 + 释放）。
两条可以分别回滚（S2 / S3），但**共用同一份 `Map` 生成物**，所以放在一相可接受；
不可接受的是 `put_owned` 的所有权载体在卡里不存在（§3.5）。

### 3.2 范围边界

| 本卡做 | 本卡不做 | 归属 |
| --- | --- | --- |
| `Map<Str, V>` 按「长度 + 字节」比较 | 任意用户类型键协议 | D47-1 已冻结 |
| 键所有权契约（借用 / 复制 / 释放） | 哈希表 / 改线性扫描 | 不做 |
| 白名单文案更新 | `get` 返回形态、越界/缺键语义 | PH-50 |
| `Map<char*, V>` 零迁移 | 键的排序 / foreach 排序 | PH-29 契约 |

### 3.3 验收判据是否可执行

| ID | 现写法的问题 | 替换写法 |
| --- | --- | --- |
| E47-2 | `ASAN 无 leak` 与 §1.3 冲突；且 `put_owned` 的释放路径没有定义（§3.5） | 改成「UAF / double-free 为 0」+「显式释放计数器」：夹具里给 `Str` 分配打计数，`release()` 后计数归零；命令 `p47_str_ownership && bash selfhost/check-sanitizers.sh` |
| E47-3 | 「既有 125 条 golden」无出处；`check-goldens` 不覆盖 ct-ast（§1.2） | `/tmp/p47-base` 快照 `cmp`；+ `bash selfhost/check-ast.sh \| tail -1` = `0 failed` |
| E47-4 | 「`p47_errors.sh` 两条负例」没点名既有断言 | 点名 `selfhost/check-ast.sh:6964`（`L31_nested_map_key`）与 `:7128`（`map_key_bad`），断言只改这两条的键类型清单 |
| E47-5 | 「既有 Map 遍历夹具继续绿」是形容词 | 点名夹具：`test/ast/` 内含 `foreach` + `Map` 的用例（S0 列清单）逐个 `grep -F "ok    <name>"` |
| E47-1 / E47-6 / E47-7 | 基本可执行 | 保留 |

### 3.4 依赖与顺序

46 → 47 → 50 正确，理由同 §2.4。47 的 `Str` 键入口是 50 `E50-5` 的前置；50 的 `Vec` 部分不依赖 47，
卡里已写，可接受。

### 3.5 工作量与风险

**量级：中偏大。** 主要风险全部指向代码形态：

1. **`put_owned` 没有所有权位可放**。`MapEntry` 只有 `key` / `value`
   （`lib/std/Vec.h.ct:47-50`），`ct_buf` 只有 `refs/len/cap/data`（`:30-35`）。要区分「借用键」与
   「拥有键」，必须有每条目的一位信息；现有结构没有位置。卡里 S3「只加入口，不改 `put`」无法落地。
2. **泛型 `memcmp` 对 `Str` 比的是 16 字节**。通用 `Map<K,V>::put` 用
   `memcmp(&es[i].key, &k, sizeof(k))`（`Vec.h.ct:371`、`:406`），而 `Str` 是
   `{ char *data; int len; }`（`lib/std/Str.h.ct:19-22`）。本机实测该布局
   `sizeof=16 offset_len=8 pad=4`（`cc` 探针，`/tmp/strprobe.c`），即比较会读进 4 字节填充。
   因此「只放开白名单」必然得到不确定结果，D47-5 的判断是对的，但卡里没写清必须整段特化。
3. **`foreach item.key` 的借用语义**：`Map<Str,V>` 若深拷贝键，`item.key` 若按值给出，用户对副本
   `release()` 会释放容器仍持有的 buffer（`Str` 的 `impl Drop` 见 `Str.h.ct:24-30`）。必须在卡里
   定义：`foreach` 暴露的 `key` 是**借用**，禁止释放；并用一条负例/夹具锁住。

**主张（battle 裁定）D47-3′**：v1 不做 `put_owned`，改为按**键类型二分所有权**：

- `char *` 键：维持借用，零迁移（现有 125+ 形态与 golden 不动）。
- `Str` 键：`put` 即**深拷贝字节**（新建 buffer），`release` / `remove` / `clear` 释放该 buffer；
  `Str` 是值句柄，调用方的临时 `Str` 到期被 Drop 也不会留下悬空键。
- 因为 `Map<Str,V>` 是本相新增实例，没有历史语义要保，所以「全拥有」不需要每条目标志位，
  也就不需要改 `MapEntry` / `ct_buf` 布局。

这样 D47-4 的「只复制 struct 等于没复制」风险消失，R47-2 的「独立字节缓冲」自然成立，
E47-2 的「改源缓冲仍可查」仍然成立（而且更强：源 `Str` 被释放也可查）。

### 3.6 定稿建议

**有条件定稿。** 条件：

1. 采纳 D47-3′：删除 `put_owned`（不保留别名），O2 / O3 / E47-2 / L47-2 同步改写。
2. 冻结 `Str` 键特化范围：`put` / `get` / `remove` / `clear` / `release` / `foreach` 六处同一比较函数。
3. 加一条契约：`foreach item.key` 是借用，禁止 `release()`；加负例或夹具。
4. 采用 §3.3 的 4 条替换判据。
5. 工量按「`Map` 特化 100–180 + 夹具 80–160 + 文档 40–80」重估（去掉 `put_owned` 后仍在中档）。

## 4 PH-48 — Drop 语义闭环

### 4.1 目标是否单一

**是（一个症状、两个成因）**：`delete` / AutoDrop 必须执行定义单元的真实 Drop 体，且指针字段的胶水
必须指向子对象。两个成因共享「Drop 出口」这一条链路，合在一相可接受。

### 4.2 范围边界

| 本卡做 | 本卡不做 | 归属 |
| --- | --- | --- |
| 指针字段胶水改传子对象（判空、不取址，`Emitter.h.ct:3132`） | 自动 `free` 子指针 | D48-1 冻结 |
| 跨单元 `delete` 调真实体（非 `static` + `extern`） | Drop 顺序 / `defer` / `errdefer` / `own` 相对顺序 | PH-38 / 40 |
| 不可见即硬错（L48-2），不发空桩 | Drop 体进 `.abi.h` | 不做 |
| `try_release_payload` 本相不碰 | 容器 `release` 是否跑元素 Drop | PH-50 |

### 4.3 验收判据是否可执行

| ID | 现写法的问题 | 替换写法 |
| --- | --- | --- |
| E48-3 | 含 `leak`，与 §1.3 冲突 | 只断言 ASAN 无 UAF / double-free：`p48_drop_asan.sh` rc=0 |
| E48-4 | 「既有 Drop 夹具继续绿」是形容词 | 点名 `check-ast.sh` 中现存的 Drop 夹具（S0 列清单）逐个 `grep -F "ok    <name>"` |
| E48-6 | 「两处胶水点同判据」与代码事实不符（§4.5） | 收缩为只锁 `Emitter.h.ct:3132`：生成 C 的指针字段胶水含判空、不取址；`try_release_payload` 不在本相断言面（如需纳入，须先定义借用指针的释放权，另立卡） |
| E48-2 | 「输出 `res drop 7` + `done`」可执行，但顺序未锁 | `printf '%s\n' "$(./d4)"` 与 `printf 'res drop 7\ndone\n'` 逐字比较（`cmp`） |

### 4.4 依赖与顺序

- 48 → 49 成立：49 的 AutoDrop 依赖 48 修好的 Drop 体与跨单元符号。
- 48 与 46 只共享发射器，可并行开发、门禁串行；总计划 §8 的排法可接受。
- 与 PH-42 方法可见性的冲突由 D48-2 单独一档链接性解决，方向正确。

### 4.5 工作量与风险

**量级：中。** 三个具体风险：

1. **卡里说的「第二处同类胶水」不是同类**。`Emitter.h.ct:5800-5801` 属于
   `try_release_payload`（Phase 44，`?` 丢弃载荷时的释放），该函数在 `Emitter.h.ct:5764-5770`
   对含 `*` 的类型**直接 `return 0`**，根本不会发指针字段的胶水。也就是说：
   - 它现在不会读错值，只是**不做**指针字段释放；
   - 若本相要「同判据」，得先定义「临时载荷里的指针字段是拥有还是借用」。
     `try_release_payload` 的注释写的是「临时量拥有唯一副本」（`Emitter.h.ct:5749-5753`），
     但指针字段指向的子对象是否唯一，代码里没有依据；贸然补上会引入 double-free。
   **主张**：v1 明确**排除**该点（写进非目标），E48-6 改为只锁 `:3132`；把 `try_release_payload`
   的指针字段释放单列为「未立项项」。
2. **漏了原型发射点**。跨单元修法只改函数体不够：`Emitter.h.ct:2615-2619` 会给每个
   `uses_drop` 结构体发 `static ... <S>_Drop_drop(void *self);` 原型，消费单元还发空桩
   （`Emitter.h.ct:3114-3139`）。若不改这里，定义单元即使非 `static`，消费单元的 `static` 声明
   仍会造成「声明为 static 但无定义」或冲突。S0 必须把该点写进「定位」表。
3. **`--lib` 可见性**：`--lib` 下非 `pub` 顶层函数/全局发 `static`
   （`docs/language-spec.md:2339`）。Drop 胶水不在 `.abi.h`，但必须绕过该规则；D48-2 已写，
   E48-2 的 build 夹具要覆盖 `--lib` 与非 `--lib` 两种。

### 4.6 定稿建议

**有条件定稿。** 条件：

1. 裁定「`try_release_payload` 本相不碰」并写进非目标；E48-6 相应收缩。
2. 在 S0 锚点表补 `Emitter.h.ct:2615-2619`。

4. 冻结 L48-2 文案与「不发空桩」的边界：只有「无 Drop 字段」的合法空体保留。

### 8.5 工作量与风险

**量级：中偏大。** 五个具体风险：

1. **方案 A 与「`v[0]` 硬错」互相矛盾**。方案 A 的匹配条件是「方法名 + 参数个数 + 非 `static`」
   （[custom-index-protocol.md](../proposals/custom-index-protocol.md):47-48、:106-115），**不看参数类型**。

   字面量 `0` 在 C 里是空指针常量，`cc` 不诊断（变量整数下标才给 int-to-pointer warning）；
   运行到 `Map::get` 的 `k == 0` 分支返回 0
   （`lib/std/Vec.h.ct:260-269`）。也就是说：**`v[0]` 不是硬错，而是静默返回空**——正是本波要消灭的形态。

   `grep` 无实现），不可能靠九条 `RL1-L*` 实现。
2. **未解析接收者的行为自相矛盾**：D52-5 说「缺协议是硬错，不回退 C 下标」，R52-2 说
   「`static_ctype` 推不出时不静默（硬错而非回退）」，但草案 `RL1-R1` 说「失败保持 C 语义」
   （[custom-index-protocol.md](../proposals/custom-index-protocol.md):222）。现状也是「推不出就保留
   C 下标」（`Expr.h.ct:4101-4158`）。三者只能留一个。
3. **`static_ctype` 的覆盖面**：`f().box[k]`、字段链、union 成员等形态可能推不出；若选「硬错」，
   会把今天合法的 C 下标（如宏/`#ct-raw` 里的数组）误杀。
4. **写形态的 AST 改写**：提案 §3.2 把右值挂到下标节点的 `next`（`:127-129`），若下标子表达式共享会
   改到别处（草案 `RL1-R4` 已登记）；S2 需夹具 `x[f()] = v` 断言 `f()` 只出现一次。
5. **泛型类型名还原**：`RL1-D6` 要求先 `ct_inst_find` 还原 `Box<int>`，失败才退回 `Box_int`
   （草案 `:51`、`:226`）；S4 要有负例。

**主张（battle 裁定）**：

- 采用「已解析为 `struct` / 泛型实例且无匹配 `get` → 硬错；`static_ctype` 无法解析 → 保持 C 语义」。
  这与今天的实现边界一致，也是唯一不误杀 C 代码的选项；R52-2 的「硬错而非回退」改写为
  「**已判定**无协议时硬错；**未判定**时保持 C 语义并在文档写明」。
- `v[0]` 从验收里删除；JSON 包的数字索引用显式 `get_idx(i)` 方法调用，不承诺下标糖。
  这符合「挂不进现有门禁的能力就不主张」的原则，不靠 skip 假装覆盖。

### 8.6 定稿建议

**有条件定稿。** 条件：

1. 采纳 §8.5 的两条裁定：未解析接收者保持 C 语义；`v[0]` 本期不主张。
2. 删除 RL1-E10；按 §8.3 重写 E11 / E12 / E4。
3. 冻结「诊断集仍是 RL1-L1–L1-L9」，不新增 `get_idx` 提示类文案。
4. S0 锚点改用实测行号：`container_index_check` 在 `Expr.h.ct:3867-3883`，
   `[` 后缀在 `Expr.h.ct:4083-4162`（卡里引的 `:3957-4007` 实际是 `container_addr_check` /
   `brace_arg_ok`）。
5. E11 明确夹具接收者：`JsonValue` **值**（`struct X x;`），不是指针；指针接收者按 E11 仍是 C 语义。
