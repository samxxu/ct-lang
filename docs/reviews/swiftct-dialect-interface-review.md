# SwiftCT 方言接口评估：CT 应提供什么

> 中文
>
> **对象**：外部设计提案《CT 方言语义导出与 SwiftUI 三方资产组方案》（自述基线 v0.12.0）。
> **核对基线**：本仓 `v0.53.0`（`ct-ast v0.53.0`，HEAD `267cb5eb`）。
> **定位口径**（负责人补充）：SwiftCT 是 ct-pkg 下的**第三方开源包**，内含 PHP 生成器、CT 侧模型与事件机制、生成的胶水与 SwiftUI 代码；CT 的职责是提供**足够的方言编写能力**，即一套跨进程、语言无关的固定接口。
> **性质**：只评估、只给接口清单。不排 phase、不预排相号、不改实现。
> **实测方式**：按 `selfhost/check-ast.sh` 的链路在 `/tmp` 重建探针编译器（L0→L1→L2→ct-ast），探针与产物全部在 `/tmp/ctprobe`，未改仓库实现。

---

## 0. 结论：两半

**部分采纳。** 提案的分层目标成立（人只写声明 + 业务逻辑；生成物入库；包自持运行时），但它对现行方言的三条现状判断与 v0.53.0 全部不符，据此推导出的九项改进里有四项在解决已经不存在的问题；同时它把「env 数据面」「编译器 fork 插件」设计成 CT 侧机制，与 D20 及 `AGENTS.md` §2 的硬边界冲突。

结论按交付形态拆成两半：**包做映射与运行时，CT 只给声明层视图与 ABI 面。** 详细证据见 §1–§11。

### 0.1 一、ct-pkg 仓库里的 SwiftCT 包

包自己决定结构，CT 不约束。建议形态（仅示意，非规范）：

```
swiftct/
├── ct.pkg                  # name/version/dep；不放产物清单
├── swiftct/                # CT 侧：模型 struct + View trait + 胶水自由函数（根单元）
├── gen/                    # PHP 生成器（入库）
│   ├── gen.php             # 读语义视图 → 写三份产物
│   └── expect.json         # 期望的 schema 版本与字段白名单
├── runtime/                # Swift 运行时：holder / 回调注册表 / 变更通知
├── templates/              # 生成模板（.ct 骨架 / .c / .h / .swift）
├── generated/              # 生成物入库，与声明同批提交
├── examples/login/         # golden 工程
└── tools/verify.php        # 漂移自检（门禁入口）
```

包自己背的责任：

| 项 | 包的责任 | 现状可依 |
|---|---|---|
| PHP 生成器 | 读视图、写三份产物、写头部戳、`--verify`、失败退出非 0 | 只能读到 §5.1 的字段（**缺字段与形参类型**） |
| 类型映射表 | CT 类型拼写 → Swift 类型；长期跟版由包承担 | 无（CT 不给映射规则） |
| SwiftUI 运行时 | holder、注册/注销、通知、`@convention(c)` 包装、`deinit` 顺序 | 需包自建；CT 无属性观察 |
| 胶水 | bridging header / modulemap、`typedef` 包装层、`_new`/`_free` 模板 | `.abi.h` 不发射 typedef，包可自建 `swiftct_glue.h` |
| golden 与入库 | 三份同批入库、同批比对；「手改任一份」「只重生成一份」必须红 | 需包自建 `--verify`；CT 不提供跨产物一致性检查 |
| 资产组布局 | 文件类型、命名、路径、生成区位置 | 无（CT 无资产概念） |
| 状态绑定方案 | `@State` / `$binding` ↔ CT 状态结构的读写路径 | 无（CT 无绑定语义） |

CT 侧**不背**以上任何一项。特别地：不背 SwiftUI 组件映射表跟版、不背运行时、不背绑定方案。

### 0.2 二、CT 项目提供的能力

| # | 能力 | v0.53.0 现状 | 最小要求 |
|---|---|---|---|
| 1 | **语义出口** | 部分有：`--emit-map` 给模型名 / `use` / 方法名 / 返回类型 / 形参**个数** / `line` | 补字段名与类型、形参类型、`col`、`namespace`、`schema` 版本号 |
| 2 | **资产组契约** | 从未存在 | **CT 只固定三条红线**（见下），文件类型/命名/路径交给包 |
| 3 | **回指** | 有 `file:line`，无 `col` | 视图带列号；生成物头部带来源戳 |
| 4 | **失败语义** | 有：`file:line:col: error:` + rc=1（重复声明、空导出均实测 rc=1） | 补「视图/schema 不兼容」由生成器判定，CT 只保证版本可见 |
| 5 | **schema 版本化** | 无 | `schema` 整数 + 只追加不删改 + 不兼容即失败 |
| 6 | **C ABI 面** | 有：`--lib` 产 `.abi.h`（不透明前置声明 + 导出函数 + `ABI_VERSION`/`ABI_HASH`） | 保持；建议补签名级指纹 |

资产组在 CT 侧的三条红线（这是「CT 提供资产组契约」的最小可实现形态）：

1. 生成的 `.ct` 骨架必须是**合法编译单元**，`ct build` 能吃（已成立，多单元可用）。
2. `--lib` 的 `<base>.abi.h` 是**唯一** ABI 承诺；`nm` 面可以更大（既有判据）。
3. 生成物与用户声明必须能**按单元分开**（否则 §0.5.1 判据无法机械检查）。

文件类型清单、命名规约、路径布局、bridging header 是否自动维护——**不固定**。理由：这些跟随 Swift 工具链，固定即替包跟版，与提案 §7 自己的判据相反。

### 0.3 依赖顺序

| 阶段 | 谁先行 | 能做什么 | 不能做什么 |
|---|---|---|---|
| ① CT 侧先 | 语义出口字段集与 `schema` 冻结 | 包按 §5.3 的视图写消费层；用**手写 JSON fixture** 驱动 PHP 开发 | — |
| ② 包侧跟进 | 包不等 CT 全量 | `ct.pkg` 骨架、Swift 运行时、holder、模板、golden 框架、`--verify` | 不得读 `.ct` 文本、不得读 `.h` 布局、不得依赖 mangling |
| ③ 联调 | 两侧都可跑 | 全链路 golden 与联调门禁 | — |

关键分界：**视图字段集冻结之前，PHP 只准消费「今天已存在的字段」**（模型名、方法名、返回类型、`line`、`uses`），字段级代码生成必须由 fixture 驱动。否则 PHP 会先按自己的猜测写死一套解析，等视图出来再返工，等于把 CT 内部结构写进包。

CT 侧可独立交付、不阻塞包的顺序建议：① schema 字段集 → ② `col` → ③ 签名级指纹。②③ 可以晚于包的第一版（包可用 `view_hash` 兜住），① 不能晚。

### 0.4 缺口回退

| CT 缺口 | 包的自补方式 | 代价 | 会不会变永久分叉 |
|---|---|---|---|
| 视图缺字段与类型 | 解析 `.ct` 文本；或解析生成的 `.h` | 文本解析要追语言演进（v0.12→v0.53 已变三次：namespace 形态、`use` 子句、impl 可见性）；`.h` 拿不到 `line`/`use`，且随 `--lib` 改变形态 | **会**（读内部结构即分叉） |
| 缺 `col` | 回指只到文件:行 | 低 | 不会 |
| `ABI_HASH` 不含签名 | 用视图 JSON 的 `view_hash` 覆盖 | 低 | 不会 |
| 无显式标记 | 目录 / 生成区约定 | 低 | 不会 |
| 无注记语法 | 元数据编码进字段名或 `//@` 注释 | 中；命名即协议，后续难改 | **半永久**（约定固化） |
| 无资产组概念 | 包内 manifest + `--verify` | 低 | 不会 |
| `.abi.h` 无 typedef | 包内 `swiftct_glue.h` 包一层并 `#include` | 低 | 不会 |

总则：**凡是「包去读 CT 内部结构」的回退都会永久分叉；凡是「包读公开视图 + 自己算法」的回退不会。**

### 0.5 验证点

**CT 侧单侧**：
1. 固定 fixture 单元 → `--emit-map` 逐字段断言（`schema`、字段名/类型、形参类型、`col`）。
2. `--lib` → `.abi.h` 逐符号断言（不透明前置声明在前、导出原型逐个匹配）。
3. 负例：重复声明、空导出、不兼容 schema → 生成器/编译器都必须 rc≠0。

**包侧单侧**：
1. golden 工程：生成 → `ct build` rc=0 → 运行输出比对。
2. `--verify` 在两种注入下必须失败：手改一份产物、改字段类型但不重生成。

**联调（必须一起验，只验单侧不算）**：

| # | 联调用例 | 单侧无法替代的理由 |
|---|---|---|
| 1 | 同一份 `.ct` → 三份产物 → 编译运行 | 两侧各自绿仍可能接缝错位 |
| 2 | 改字段类型 → 重生成 → 三份同步变 → `--verify` 绿 | 只有跨两侧才能证明「视图驱动」成立 |
| 3 | 只重生成一份 → `--verify` 红 | 漂移检测只在两侧合起来时才有意义 |
| 4 | 手改 `.swift` / `.c` → `--verify` 红 | 同上 |
| 5 | 用户源码黑名单零命中（见 §0.5.1） | 验收口径本身就是端到端的 |
| 6 | 无 ct 编译器的机器上仍能构建 | 「生成物入库」的价值只能整链路验证 |

#### 0.5.1 目标验收口径（待实现验证）

负责人给出的目标是：**开发者在 CT 里直接写 UI 逻辑，不管对接；前后代码与配合由 SwiftUI 包负责。**
本节把它当验收口径用，不当愿景写。

> **状态：目标口径（待实现验证）。** SwiftCT 包尚不存在，本节判据**均未验证**，不得在任何结论里当作已成立。

**正例（满足）**：一个只含 `.ct` 声明与逻辑的工程，加上包提供的生成与构建步骤后能跑起来；用户写的 `.ct` 里**不出现**胶水样板——不出现 `set_on_*` 之类的注册调用、不出现 `void *ctx`、不出现注销顺序、不出现 bridging header 声明、不出现 `@convention(c)`。

**反例（任一命中即不满足）**：
1. 用户需要手写 bridging header；
2. 用户需要手写 class holder；
3. 用户需要自己安排「先注销再释放」的顺序；
4. 必须手改生成物才能跑通（改了才编译过 → 生成物不完整）；
5. 用户在 `.ct` 里自己写回调注册 / `void *ctx` / 生命周期函数。

**边界（防止口径被夸大）**：
- `@main`、App 生命周期、平台适配仍在 Swift 侧；包承诺**把 Swift 缩到最薄**，不是「不需要 Swift」。
- 生成物本身也是 `.swift`，因此「用户不写 Swift」≠「工程里没有 Swift」。
- 包内部胶水、生成物不计入「用户写的代码」。

**这条口径对接口取舍的硬约束**：
- 生成物必须与用户声明**物理可分**（独立文件或明确生成区），否则判据 1–5 无法机械检查。这是「资产组」真正的需求，不是文件类型清单。
- 生成器必须只消费**声明层视图**：判据 5 要求用户源码里没有胶水语义，视图缺字段时生成器只能回头读源码，等于把胶水需求转嫁回用户。
- 验证方式（包落地后）：对新工程执行生成 + 构建，要求 rc=0 且可运行；再对用户源码目录跑黑名单检查（`set_on_`、`void *ctx`、`@convention(c)`、`bridging`、holder 类），零命中才算通过。

## 1. 前提核对（逐条，含实测）

| # | 提案前提 | 判定 | 证据 |
|---|---|---|---|
| 1 | 方言靠注释注记匹配 | **成立** | `//@ct-dialect: <名>` 路由，`selfhost/../test/run.sh:315-385`；`examples/07_dialect/registry.ct:24-32` |
| 2 | 方言「只吐 C 编译单元」 | **已不成立** | 插件产出是**纯 CT 源**并插回原文件；编译器对插件零感知（`docs/history/design/dialect.md:62-66`、`test/run.sh:286-291`）。且插件**只拥有自己那块**，外来块必须逐字节透传（`docs/history/design/dialect.md:168-172`） |
| 3 | 语义参数走 env | **从未存在** | 现行契约是 argv + stdout（`test/run.sh:298-313`）；`CT_FILE` / `CT_LINE` / `CT_NS` 只活在归档草案 `docs/history/design/dialect.md:246-252`，代码零引用 |
| 4 | 无公共语义出口 | **部分有，形态不同** | `--emit-map` 已是正式出口，实测见 §5.1。缺字段与形参类型、缺列号、缺注记 |
| 5 | `trait View` | **从未存在** | 全仓 `trait View` / `use View` 零命中。但 `use` 子句真实存在（`docs/language-spec.md:72-73`、§4.2），`struct Login use View;` 可当显式标记——代价是**追加 vptr 字段**（`docs/language-spec.md:131-148`） |
| 6 | P22 的 `loop` / `..` / `Range` / `each` | **一半成立、一半从未存在** | `loop(n)` §4.45、`loop(a..b)` §4.46、`a..b($)` §4.47 均在；但 `Range` **不是 trait**、`..` 只是这两处语法；`each` **不是关键字**（`foreach` 才是 §4.49），`each` 仅作方法名出现（`docs/language-spec.md:579`） |
| 7 | asset group（资产组） | **从未存在** | 全仓零命中；`ct.pkg` 只有 `name/version/dep/cflags/ldflags/requires/licence`（`docs/package-guide.md:70-80`），无产物清单概念 |
| 8 | `borrow` 阶段一 | **成立（有边界）** | `borrow` + 内建 `Handback`，明写「阶段一：参数注解，代码生成零变化」（`docs/language-spec.md:1530-1544`）。边界：`impl Handback` 必须与借用点同单元（`issues/selfhost/sh38-borrow-cross-unit.md`） |
| 9 | 闭包档① / 档② | **成立** | 档① 手写 `(fn, env)`、档② `=>` 栈闭包（`docs/closure-conventions.md`、`examples/09_callback/callback_tier2.ct`）。档② 是**绑定不是值**，不可拷贝/存字段/逃逸（同文档约定 #3） |
| 10 | `set_on_*` 回调约定 | **从未存在** | 全仓 `set_on_` 零命中；示例只有 `ring_each` 这类命名 |
| 11 | 不透明句柄 + `Type_method(self,…)` | **部分有** | `ct build --lib` 实测产出 `Lib.abi.h`：`struct Lib_Conn;` + `int Lib_conn_open(struct Lib_Conn *, char *);`。导出面**仅根单元 `pub` 自由函数**（`docs/design/phase39-draft.md:37-48`、`docs/language-spec.md:2366`）；固有方法不进导出面，trait impl 符号是 `static` |

### 1.1 顺带撞到的语法漂移（实测报错）

提案没有给出可编译的 CT 代码，但它假设的写法在 v0.53.0 均已失效：

| 写法 | v0.53.0 实际 |
|---|---|
| `namespace A { … }` 块式 | `error: a namespace is file-scoped: write 'namespace A::B;'` |
| `impl T for S { void m(self) {…} }` | `error: expected a parameter name`（须写 `void m(S *self)`） |
| `pub impl S { … }` 块 | `error: a pub impl block is not supported; mark methods`（只能逐方法 `pub`） |

结论：提案的示例不可直接照抄，成本估算也不能按「已核实的写法」来折算。

## 2. 逐节判定

| 提案章节 | 判定 | 理由 |
|---|---|---|
| §1 目标与结论（人只写声明 + 逻辑） | **采纳** | 与「包持有生成链路」不冲突，是合理分工 |
| §2 #1 接前端符号结果 | **采纳** | 正是本评估的核心需求，但载体应是 `--emit-map` 的扩充，不是新造通道 |
| §2 #2 产出改 asset group | **驳回（转包内）** | 资产组是包的内部概念；CT 只需保证「生成的 `.ct` 能被 `ct build` 吃、`.c/.h` 是正常编译单元」，这两条今天已成立 |
| §2 #3 导出 schema v1 | **部分采纳** | 方向对，但「无公共语义出口」判断错误：`--emit-map` 已在。应是**扩字段 + 定版本**，不是新建出口 |
| §2 #4 env 控制面 + 结构化数据面 | **驳回** | 要让编译器 fork/exec 插件并注入 env，与 D20「编译器零感知、永不调用展开器」直接冲突（`AGENTS.md:402-410`）。跨进程接口应由**生成器调用 `ct`** 形成两段式，而不是编译器调用生成器 |
| §2 #5 `// @ct Login.ct:7` 回指 | **采纳（有条件）** | 前提是视图带行列；当前只有 `line`，无 `col` |
| §2 #6 三方 golden 一起验 | **部分采纳** | 作为包的 CI 可，作为 CT 仓门禁不可：依赖 PHP/Swift 工具链，`docs/language-spec.md` 门禁体系不承接 |
| §2 #7 自动维护 bridging header | **驳回（转包内）** | CT 不产 Swift 侧胶水，bridging header 属包内生成物 |
| §2 #8 生成物入库 + 可选 make target | **采纳（转包内）** | 与 CT 无关，纯包策略；不能落在 CT 的构建入口 |
| §2 #9 `trait View` 后端可替换 | **驳回** | `trait View` 不存在；且「后端可替换」是生成器多后端（同一份视图 → 不同 `.swift`），属包设计，不需要语言级 trait。提案把它类比「自定义 `use Range`」——`use Range` 根本不存在 |
| §3 三方同源符号表 | **部分采纳** | 「同一份视图派生三份产物」成立；但「`.h` 就是 CT 产物里那张头」不成立：普通 `.h` **含完整 struct 布局**，只有 `.abi.h` 是不透明前置声明（实测 §5.2） |
| §4 所有权纪律进模板 | **采纳（转包内）** | 模板属生成器；CT 侧唯一能加的保险是 `_free` 内清回调槽（见 §4 生命周期） |
| §5 三边所有权边界 | **采纳** | 与 CT 价值语义一致：CT 不 malloc 视图对象、C 侧只借用 |
| §6 与既有机制的关系 | **大部过时** | `use Range`、asset group、`borrow` 与 `each`/`set_on_*` 共用实现——三条均无对应物；闭包档② 可以做回调但**不能做持久回调**（non-escaping），提案这一句方向可用、语义需改 |
| §7 官方给四样 / 不给三样 | **部分采纳** | 「跟版成本在谁那边」判据成立。但「给 asset group 契约」应删；「给 schema v1」应改为「给语义视图 + 版本规则」 |
| §8 留给实现方 11 条 | **部分过时** | 第 1/2/3/4/5/10 条在「包内解决」框架下大半不需要 CT 参与；第 11 条（对照 0.13–0.15）已无意义，应对照 v0.53.0 |
| §9 Golden 9 条 | **部分采纳** | 1/2/3/4/5/9 可在包 CI 落地；6/7/8 依赖无编译器 CI、Xcode 跳转、后端切换，不能当门禁 |
| §10 口径与边界 | **部分过时** | `..` 按上下文分派成立；「`Range` 是 trait、默认实现内置」不成立 |

## 3. 「一份声明 → 三份产物」的四组对应关系

每组写清「靠什么固定住」。四组的共同前提：**CT 侧只提供声明层视图与 C ABI 面，映射规则由包定义并随包版本化。**

### 3.1 类型映射

`CT struct / 字段类型` ↔ `C 不透明句柄 + setter/getter` ↔ `Swift 类型 + class holder`

| 环节 | 靠什么固定 |
|---|---|
| CT → 视图 | 视图字段 `models[].fields[{name, type, kind}]`；`type` 是规范化拼写（见 §5.3），`kind` 区分标量 / 指针 / 数组 / 函数指针 |
| CT → C | `ct build --lib` 的 `<base>.abi.h`；导出面只允许标量与指针（`docs/design/phase39-draft.md:60`），**按值 struct 不可导出** |
| C → Swift | 包内的固定类型表（`char *` → `UnsafeMutablePointer<CChar>?`，`T *` → `OpaquePointer?`）。**必须由包维护**，CT 不提供 |
| holder | 包模板：holder 只存 `OpaquePointer`，不存 struct 值 |

关键约束（实测）：`.abi.h` 里只有 `struct X;` 前置声明，Swift 只能拿到 `OpaquePointer`；要构造/释放必须由 CT 侧提供 `pub X *x_new(void)` / `pub void x_free(X *)`，这两个自由函数实测可进导出面。**固有方法（`impl X { pub … }`）不进导出面**——实测只报 `no exported functions`。因此胶水只能写成根单元里的自由函数，不能写成方法。

另有一处命名漂移：实测导出名是 `<namespace>_<func>`（`UI_login_set_name`），不是提案写的 `ct_login_set_on_login` 形态；`Type_method` 只在 namespace 为空时逐字成立。

### 3.2 事件机制

`CT 回调 typedef + 分发钩子` ↔ `C 函数指针 + void *ctx` ↔ `Swift @convention(c) + 被捕获对象`

| 环节 | 靠什么固定 |
|---|---|
| CT → C | 实测可导出：`void UI_login_set_on_login(struct UI_Login *, void (*)(void *, int), void *);`。**CT 不发射 typedef**，`.abi.h` 内联函数指针类型 |
| 注册/注销 | 包内约定：`x_set_on_<event>(self, cb, ctx)`，`cb == NULL` 即注销。这是命名约定，不是语言能力 |
| ctx 语义 | 沿用闭包档①约定：`env` 是回调**第一个**形参，`fn`/`env` 相邻（`docs/closure-conventions.md`）。Swift 侧传 `Unmanaged.passUnretained(holder).toOpaque()` |
| 为什么不能用档② | 档② 是 non-escaping 绑定，不可存、不可跨调用存活（约定 #3）；事件回调是持久回调，只能用档① 手写对接 |

**无法固定的一条**：`void *ctx` 被 CT 侧保存后，编译器不检查（`docs/language-spec.md:1829` 明确把「env 以 `void *` 交给不透明接收方后被保存」列为未防护面）。协议只能靠模板纪律，不能靠编译期。

### 3.3 生命周期

| 环节 | 靠什么固定 |
|---|---|
| 谁持有 | Swift 侧 class holder 唯一持有 `OpaquePointer`；CT 不持有视图对象 |
| 谁释放 | CT 侧 `pub void x_free(X *)`；Swift 在 `deinit` 调用 |
| 先后顺序 | 生成器模板写死「先 `x_set_on_*(h, NULL, NULL)` 再 `x_free(h)`」。**建议**：`x_free` 自己在 CT 侧把回调槽清空，这样即使 Swift 侧漏注销也不会回调到已释放 ctx——这是 CT 侧可落地、不需要新语法的保险 |
| 跨语言借用边界 | 回调内 `ctx` 只在本调用内有效；CT 不保存、Swift 不释放 |

**无法固定的一条**：释放顺序没有编译期检查。CT 不知道 Swift 侧是否还持 ctx，只能"清槽自保"。

### 3.4 状态绑定

| 环节 | 靠什么固定 |
|---|---|
| 声明 | 视图 `models[].states[{name, type}]`；生成器产出 `x_get_<s>` / `x_set_<s>` 与 Swift `@State` / `$binding` |
| 读写路径 | 生成器模板：Swift 只经 getter/setter 走 C ABI，不直接触字段 |
| 变更通知 | **必须包自己实现**：setter 内调用已注册的观察者回调。CT 无属性观察、无属性变更钩子 |
| 值语义 | CT struct 是值拷贝语义。holder 持指针意味着 Swift 侧看到的是**共享**对象，与「值拷贝」不同——这条要在包文档里写明，不能靠猜测 |

## 4. 两类契约的边界

| | CT → 生成器（外部契约） | 生成器 → 包内 Swift 运行时（内部契约） |
|---|---|---|
| 载体 | 命令行 + JSON（stdout 或文件）+ `.abi.h` | 包内 `.swift` / `.h` / `.ct` 产物，以及包自己的 manifest |
| 语言 | 无关（PHP / Python / sh 均可） | Swift + 包内约定 |
| 版本化 | schema 版本 + `ABI_VERSION` | 包版本（`ct.pkg` 的 `version`） |
| 谁改 | CT 侧，按 schema 演进规则 | 包作者 |
| 失败判定 | 进程退出码非 0 + `file:line:col` 诊断 | 包自己的校验命令 |
| **不归 CT** | — | 组件映射表跟版、运行时、状态/绑定方案、bridging header、资产组命名 |

这两类契约**不得互相引用**：包不得依赖 mangling（`<Struct>_<Trait>_<method>`）、vtable 布局、内部符号编号；CT 也不得知道 `.swift` 的存在。

## 5. 语义出口：现状、最小字段集、稳定性

### 5.1 现状（实测 `--emit-map`）

```
$ ctast --emit-map - pkgproj2/Lib.h.ct -o /tmp/x.c
{
  "compiler": "ct v0.53.0",
  "file": "pkgproj2/Lib.h.ct",
  "traits": [],
  "structs": [{"name":"Lib_Conn","cname":"Lib_Conn","file":"…","line":3,"uses":[]}],
  "functions": [{"name":"conn_open","file":"…","line":7,"ret":"int","params":2}],
  "impls": [], "calls": [], "maps": []
}
```

已能给：编译期版本、文件名、Trait 名（含 `line`、方法名/返回类型/形参**个数**）、struct 名（含 `line`、`uses` 列表）、impl 的 `symbol`、函数名（含 `ret`、形参**个数**）。
**给不了**：struct 字段名与类型、形参类型、列号、注释/注记、枚举/别名、事件语义。

### 5.2 C ABI 面（实测 `ct build --lib`）

```
#define UI_ABI_VERSION 1
#define UI_ABI_HASH 0x29dbf49f
struct UI_Login;                                        /* 只有前置声明 */
char * UI_login_name(struct UI_Login *);
void UI_login_set_name(struct UI_Login *, char *);
void UI_login_set_on_login(struct UI_Login *, void (*)(void *, int), void *);
```

普通构建的 `.h` 恰好相反：`struct Lib_Conn { int fd; };` 是**完整定义**，不是不透明句柄。因此「不透明句柄」只在 `--lib` 产物里成立，提案 §3 那句需要改写。

### 5.3 最小字段集（建议的 schema v1 形状）

只给声明层，不给函数体、表达式、控制流、内部编号：

| 组 | 字段 | 现状 |
|---|---|---|
| 版本 | `schema`（整数）、`compiler` | `compiler` 有；`schema` 无 |
| 模型 | `models[].{name, cname, namespace, use[], loc{file,line,col}}` | 有 name/cname/line；无 namespace/col；`use` 有 |
| 字段 | `fields[].{name, type, kind, loc}` | **全无** |
| 方法 | `methods[].{name, ret, params[{name,type}], loc}` | 只有 `ret` 与形参个数 |
| 事件 | `events[].{name, params[{name,type}], loc}` 或由方法签名派生 | 无独立概念；可由 `set_on_*` 方法签名派生 |
| 注记 | `annotations[].{key, value?, loc}` | 无（见 §7-4 的取舍） |
| 枚举/别名 | `enums[]` / `aliases[]` | 无（若 UI 模型用得到则需补） |

**PHP 读得到什么 / 读不到什么**（按现状）：读得到模型名、Trait 归属、方法名与返回类型、行号、C 符号名；读不到字段、形参类型、列号、注记。也就是说——**按现状，PHP 生成不出 setter/getter 与 `@State`**，因为它不知道有哪些字段、字段是什么类型。这是当前唯一真正卡住整条链的缺口。

### 5.4 稳定性约束

1. 视图语义只随 `schema` 版本变化；CT 内部改名、降级方式、内部符号编号**不得**改变视图语义。
2. `cname` 字段仅供 C 侧对接，不构成 Swift 侧依赖；包不得把 mangling 写进模板。
3. 版本不兼容时生成器必须**明确失败**（非 0 退出 + 说明期望/实际版本），不得产出半成品。
4. 新增字段只追加、不改变既有字段含义；删改字段必须 bump `schema`。

### 5.5 由谁导出、在哪一步、失败时看到什么

- **由谁**：编译器前端符号层（不是编译产物层）。理由：行号/列号与 `use` 归属只有前端有；产物层已被 mangling 与 vtable 污染。`--emit-map` 现在就是在编译前端跑完后、发射前输出。
- **在哪一步**：`ct --emit-map - <unit> -o <tmp.c>` 的**编译模式**（实测 JSON 到 stdout、rc=0）；生成器把它当独立的一次 CLI 调用，不要求编译器知道生成器存在。
- **失败时生成器看到什么**：`file:line:col: error: <msg>` 到 stderr、退出码 1（实测重复 `struct` 报 `duplicate struct 'S'`、`--lib` 空导出报 `no exported functions in '…'`，均 rc=1）。生成器应把「非 0 退出」与「JSON 解析失败」都当硬失败，不得降级为警告。

## 6. 漂移检测：改了 `.ct` 只重生成一部分 / 手改某一侧

现有可用件与缺口：

| 手段 | 现状 | 能否判定漂移 |
|---|---|---|
| `ABI_VERSION` | 有（常量 1） | 只能判「大版本」 |
| `ABI_HASH` | 有，但**只哈希导出名**（实测：把回调参数 `int` 改 `long`，`.abi.h` 变了、哈希 `0x3b8d1c83` **不变**） | **不够**：签名级漂移检测不到 |
| `--emit-map` 的 `compiler` 版本 | 有 | 只判编译器版本 |
| 生成物内戳 | 无 | 无法判「这份 `.swift` 是从哪版声明生的」 |
| `ct check` / 编译报错 | 有，`file:line:col` + rc=1 | 能判「生成物自相矛盾」，不能判「三份不同源」 |

**建议的检测链（包内可落地，不依赖 CT 新能力）**：

1. 生成器为每次导出算一个 `view_hash`（视图规范化 JSON 的哈希），连同 `schema` 版本、`ABI_HASH` 写进**每一份**产物头部（`.ct` 骨架 / `.c` / `.h` / `.swift`）。
2. 包提供 `--verify`：重新导出 → 重算 → 逐份比对头部。任一份缺失、版本不符、哈希不符 → 非 0 退出。
3. 「手改某一侧」由第 2 步覆盖；「只重生成一部分」由三份头部必须一致覆盖。
4. 「改了字段类型但没改名」这一档，**必须靠签名级指纹**；否则只能靠 `view_hash`（它包含字段类型，所以能覆盖）——结论：**`view_hash` 足够，`ABI_HASH` 不够**。

也就是说：漂移检测可以在包内自洽完成；CT 唯一值得补的是把「规范化签名串」也纳入 `ABI_HASH`，让 C 侧也能独立判漂移（见 §7-3）。

## 7. 最小固定接口（按必要性排序）

「固定」= 第三方不必读 CT 源码、不必读包源码，就能用任意语言写生成器。

### 7-1 声明层语义视图（必须）

- 内容：§5.3 的字段组，带 `schema` 版本与 `file:line:col`。
- 不提供的绕法：自己写 `.ct` 解析器；或读生成的 `.h` 反推字段。
- 绕的成本：解析器要跟随语言演进（`namespace` 形态、`use` 子句、泛型、`impl` 可见性都在变，v0.12→v0.53 已变三次以上），每个方言一套、永远追不上；读 `.h` 拿不到行号与 `use` 归属，且 `.h` 是 codegen 产物，会被 `--lib` 与否改变形态。
- 为什么该由语言侧提供：符号表只有编译器有；`AGENTS.md:410` 已经定过口径「方言所需的符号信息由 map JSON 提供，不在仓库内另造一套」。这是既有承诺的兑现，不是新增面。

### 7-2 稳定 C ABI 导出面（必须，已具备）

- 内容：`.abi.h` 的不透明前置声明 + 导出函数原型 + `ABI_VERSION`。实测已可用，且回调函数指针可导出。
- 现状缺口：固有方法不进导出面（胶水只能写自由函数）；不发射回调 `typedef`。
- 不提供的绕法：手工在 C 侧 `extern` 声明 → 依赖 mangling，一改就碎。
- 为什么该由语言侧提供：只有编译器知道最终符号名与可见性；Phase 39 已为此立过判据。

### 7-3 签名级 ABI 指纹（强建议）

- 现状：`ABI_HASH` 只到导出名。
- 不提供的绕法：包自己解析 `.abi.h` 文本做哈希。
- 绕的成本：低，但要把「规范化」规则抄一遍，且对格式变化（空格、换行、typedef 内联）脆。
- 为什么该由语言侧提供：编译器天然持有规范化签名；30 行级改动换掉一类长期漏检。

### 7-4 显式标记的语法落点（建议，可不用新语法）

- 现状：`use` 子句存在（进符号表、进视图 `uses`），但会**追加 vptr**；注记不存在。
- 两个可选方案：
  - A. 用 `struct Login use View;`——零新语法，视图里直接可见；代价是每个模型带一个 vptr 字段（8 字节 + vtable）。
  - B. 用 `//@ct-model` 注释块——零语义副作用，但**不进符号表**，生成器要二次解析注释，与「只依赖视图」的口径冲突。
- 不提供的绕法：命名约定（`*View` 后缀）或目录约定。
- 绕的成本：低，但脆弱且不可静态校验。
- 为什么该由语言侧提供：只有「进符号表」的标记才能进视图；否则 §5 的「PHP 只依赖视图」就有一个洞。
- **按 §0.1 的判据 5 修订**：验收口径要求「用户 `.ct` 里不出现胶水」，而生成器需要知道哪些声明是模型。若生成物与用户声明**物理可分**（独立目录/文件），这一项可以不在语言侧解决——生成器处理整个用户单元即可。因此本项从「建议」降为「可选」，优先级低于 7-1 / 7-2 / 7-3。

### 7-5 生成物自校验入口（必须，已具备）

- 内容：`ct check` / `ct build` 对生成的 `.ct` 骨架给 `file:line:col` + rc=1。
- 现状：已具备；重复声明实测报 `duplicate struct 'S'`（rc=1）。
- 不提供时：生成器只能靠自己的模板断言，无法发现「生成的骨架与生成器预期不符」。

### 7-6 asset group / 非 C 产物契约（**不由 CT 提供**）

- 理由：SwiftCT 是第三方包，资产组（`.ct` / `.c` / `.h` / `.swift` / bridging header）是**包的内部布局**。CT 若定义它，就要替包跟 Swift 工具链的版，与「跟版成本在谁那边」判据相反。
- 包的做法：`ct.pkg` 只有 `name/version/…`，**不放产物清单**；另用包内 manifest（如 `swiftct.json`）+ `--verify` 自管。
- CT 唯一要保证的：生成的 `.ct` 能被 `ct build` 正常编译、`.h/.c` 是普通 C 单元——两条今天都成立。

### 7-7 env 数据面 / 编译器调用插件（**驳回**）

- 与 D20 冲突：`AGENTS.md:402-410` 明确 `ctc` 对展开器零感知、永不调用；把语义塞进 env 要求编译器 fork/exec 并把符号表序列化给子进程，等于让编译器当驱动器。
- 正确形态：**生成器调用 `ct`**（两段式：先 `--emit-map` 拿视图，再由生成器写产物），通信是命令行 + 文件，天然跨进程、跨语言、可版本化。

|---|---|---|

| 不改 CT 的部分 | — | PHP 生成器、Swift 运行时、类型映射表、bridging header、资产组布局、状态绑定方案 |

## 9. 风险

### 9.1 来自提案本身

1. **成本严重低估**：把「读取声明层语义」算成「一个序列化器」，但真正的工作是**类型拼写规范化**与**注记语法**；后者是语言级改动。
2. **架构方向与既有边界冲突**：env 数据面 + 编译器 fork 插件，与 D20 / `AGENTS.md` §2 正面冲突；落地前必须先改规约，等于先撕一条已冻结边界。
3. **「三方 golden 逐字一致」不可当门禁**：PHP 版本、Swift 工具链版本都会让产物文本漂移；正确判据是「结构化等价 + 头部哈希一致」，不是逐字。
4. **把可替换后端做成语言级 trait**：`trait View` 把包的设计问题上升为语言机制，收益不明、成本在核心。
5. **不透明句柄的前提写错**：普通 `.h` 是全定义，只有 `--lib` 才是前置声明；提案 §3 的「C 胶水就是 CT 编译产物里那张 .h」会把包作者引到错误路径。
6. **验收口径尚不可验证**：§0.1 的正例/反例依赖 SwiftCT 包存在。当前只能验证到「CT 侧是否提供了让判据 1–5 可被机械检查的能力」，不能宣称「用户确实不用管对接」。

### 9.2 来自版本漂移（v0.12 → v0.53，40 个版本）

1. 三条现状判断全错（只吐 C / env 传参 / 无公共出口），导致 §2 九项里 #2/#3/#4/#9 在解决不存在的问题。
2. 提案依赖的五个概念**从未存在**：`trait View`、`use Range` / `Range` trait、`asset group`、`each` 关键字、`set_on_*` 约定。
3. 示例语法在 v0.53.0 全部报错（namespace 块式、`void m(self)`、`pub impl`），任何照抄都会先撞语法墙。
4. 期间已落地的能力反而让部分目标提前达成：`--emit-map`（视图雏形）、Phase 39 `.abi.h`（不透明句柄 + 导出面）、`use` 子句（显式标记锚点）、`borrow`/`Handback`（借用纪律）、泛型与 `foreach`（模型迭代）。**这些必须先核，再谈新建。**

## 10. 需要负责人拍板的点

1. **显式标记**：`struct Login use View;`（零新语法、多一个 vptr）还是 `//@ct-model` 注释块（零副作用、不进符号表）？
2. **注记是否进语言**：若坚持「PHP 只依赖视图」，标记必须进符号表 → 需要语言级注记，成本远超「几百行」；是否接受这个成本，或用 `use` 折中？
3. **`schema` 定在哪一侧**：CT 定字段名与演进规则（包跟着 CT 走），还是 CT 只保证「不删字段、只追加」、语义由包定？
4. **签名级 `ABI_HASH` 是否改**：改动涉及 Phase 39 的 D39-12 口径（只哈希名字），需要确认是否值得为方言链改这条已收口判据。
5. **`_free` 是否强清回调槽**：把「先注销再 free」做成 CT 侧模板保险（`_free` 内置清槽），还是完全交给生成器模板？
6. **`.abi.h` 是否允许包加包装层**：包内自建 `swiftct_glue.h`（`typedef` 回调 + `#include <base>.abi.h`）是当前唯一可行路径；是否认可「CT 不产 typedef」这一分工。
