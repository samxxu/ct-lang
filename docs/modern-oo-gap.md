## 1. 判据

### 1.1 参照系

用四组参照系来「提问」，不是逐条对齐：

| 参照 | 取什么 | 不取什么 |
| --- | --- | --- |
| Java / C# / Kotlin / Swift | 名义类型、封装、接口多态、构造与不变量、有界泛型、空安全、结构化错误 | 继承层级、GC、运行时反射、异常展开 |
| Rust / Swift 协议 | trait 约束、关联类型、组合优于继承、值语义、所有权 | 借用检查器的全部复杂度、生命周期标注语法 |
| ML 家族（OCaml/Haskell） | 代数数据类型、穷尽模式匹配、`Option`/`Result` | 惰性求值、类型类推导 |
| 现代工程基线 | 模块/包、依赖锁定、诊断、LSP/formatter | 具体工具实现 |

### 1.2 CT 的既定约束

（作为筛选器，不是可选项）

- **Z1 零运行时**：不引入 GC、RTTI、异常展开、异步调度器、装箱迭代器。
- **Z2 零第三方依赖**：标准库自包含，容器与协议不能依赖外部运行时。
- **Z3 C 超集**：生成的 C 必须可被普通 C 编译器消费，ABI 与 `#ct-raw` 是逃生口。
- **Z4 编译期单态化**：泛型不产生运行时类型信息或动态分派（除非显式 `impl` 接口值）。
- **Z5 类型检查是设计取舍**：编译路径默认不做，`ct check` 只覆盖有限几类（`../README.md:58`、`language-spec.md:1968`）。
- **Z6 1.0 兼容冻结**：已发布语法不轻易破坏。

### 1.3 判定规则

| 规则 | 内容 |
| --- | --- |
| N1 表达力 | 没有它，OO 的核心范式（抽象、封装、多态、复用）是否**根本无法表达**？ |
| N2 替代性 | 现有特性（trait + impl、组合、默认方法、函数指针、`#ct-raw`、工厂函数）能否以**有界成本**表达？有界 = 模板代码不超过约 30%，且不引入新的安全检查缺口 |
| N3 约束冲突 | 是否必须引入运行时对象、GC/RTTI/异常展开、或破坏 C ABI？ |
| N4 成本 | 单相（约 ≤ 400 行、一个 Phase）还是多相（> 1,000 行或跨单元格式变更）？ |
| N5 前置 | 是否是其他必须项的前置（缺它则后续无法开工）？ |

- **必须补**：N1 成立且 N2 不成立且 N3 不成立；或 N5 成立且已排期。
- **值得补**：N1 不完全成立，但 N2 的替代成本高（易错、冗长、性能损失），且 N3 不成立。
- **明确不做**：N3 成立；或 N2 成立且替代成本低、收益不随规模增长；或与项目目标（C 超集 / 零运行时 / 系统语言）不匹配。

### 1.4 规模口径

行数为**量级估计**，按 Phase 19（+881 行 / 11 文件）、Phase 21（+1,245 / 9）、Phase 25（+304 / 3）、Phase 26（+303 / 6）的实际 delta 校准，误差约 ±40%；不是工期承诺。标「立项卡」的项以 `phase28.md` / `phase29.md` 的切片为准。

## 3. Battle 记录

### B1 继承 vs 组合 + trait 默认方法

- **正方**：实现继承能复用具体状态与 `protected` 行为，`super` 调用是框架基类的常见写法；Kotlin/Swift 之外的主流 OO 都默认提供。
- **反方**：CT 的零运行时与 C ABI 不支持虚基类/菱形继承；trait 对象已提供接口多态，默认方法已提供方法级复用；继承会把“实现复用”和“子类型”绑死，反而限制组合。
- **判据**：若真实需求是“子类型可替换”，trait 对象已满足；若是“复用字段与受保护实现”，组合 + 默认方法可替代。只有当 3 个以上真实包必须依赖 `protected` 状态或 `super` 链时，才重新评估。
- **裁决**：明确不做。理由不是偏好，而是 N2 成立（组合可替代）且 N3 成立（会引入运行时/ABI 复杂度）。

### B2 GC / 引用计数 vs `own`/`borrow`

- **正方**：共享所有权、图结构、循环引用在 GC/RC 下更自然；现代语言默认有其一。
- **反方**：Z1 零运行时；RC 的原子计数与头开销会污染所有结构体布局，GC 需要调度器与根扫描。
- **判据**：若目标包含“长生命周期共享图”或“高并发服务”，GC/RC 才有必要；CT 的定位是 C 超集与系统级零开销，arena/池/`Handback` 已覆盖主要模式。
- **裁决**：明确不做。替代路径成本有界（arena/池），且不会随项目规模恶化。

### B3 异常 vs `Result`

- **正方**：异常让错误传播不侵入签名，跨层代码更短；Java/C#/Kotlin 默认。
- **反方**：Z1 禁止 unwind；C ABI 无异常表；异常与 `own`/`Drop` 的交互复杂。
- **判据**：若“错误必须跨多层且调用方无法逐个转发”，异常有优势；但 CT 的 C 互操作要求错误可被 C 调用方处理，返回码/`Result` 更合适。
- **裁决**：不做异常；`Result` 作为“值得补”（依赖 ADT/泛型 struct），并保留返回码作为 C 边界契约。

### B4 语言级线程 / `async` vs 外部运行时

- **正方**：现代 OO 语言普遍提供 `async`/线程池；并发是服务端刚需。
- **反方**：Z1 需要调度器、状态机、跨平台线程抽象；CT 没有运行时库，标准库也刻意自包含。
- **判据**：若 CT 的目标包含“直接写高并发服务”，语言级并发是必须；但 `vision.md` 的核心价值与 roadmap 的非目标清单都没有并发，且 `pthread`/C11 可透传。
- **裁决**：明确不做语言级线程/`async`；std 可提供薄封装（P2），不改变语言语义。

### B5 运算符重载 vs 命名方法

- **正方**：`v[i]`、`a + b` 对容器/数值类型是基本体验；C++/Kotlin/Swift 都支持某种形式。
- **反方**：全量重载需要重载解析、隐式转换、优先级规则，和“可读的 C”冲突；`design/phase29.md:380` 已明确不做 `v[i]`。
- **判据**：若容器是 Phase 29 的核心交付，`v[i]` 的缺失会直接影响体验；但全量重载成本高，窄口（只做索引 `[]`）成本可控。
- **裁决**：全量运算符重载明确不做；**索引运算符**作为窄口列入“值得补”（P2），前提是 29 落地后容器使用频率证明其必要。

### B6 空安全 vs C 指针

- **正方**：空解引用是 C 系语言最大的运行时风险之一；Kotlin/Swift 的非空类型是现代化标志。
- **反方**：Z3 要求指针与 C 一致；引入 `Option<T>` 需要泛型 struct（29）与额外布局；非空注解需要类型检查。
- **判据**：若“现代化 OO”包含类型安全，空安全应补；但可以分两步：先做编译期非空检查（不改变布局），再做 `Option`（依赖 29）。
- **裁决**：值得补（P1），优先“编译期非空检查 + `Option` 标准库”，不改变 C 指针语义。

### B7 类型推导 vs 显式类型

- **正方**：`var`/泛型实参推导减少样板，现代语言默认。
- **反方**：CT 目前没有规范类型表示（字符串类型），推导会放大误报；Phase 26 明确不做泛型推导（`design/phase26.md:46`）。
- **判据**：类型推导的前提是类型检查档 2 与规范类型表；在二者之前做推导，收益低、误报高。
- **裁决**：值得补（P2），但排在静态类型检查（P0）之后；先做局部 `var`，再做泛型实参推导。

### B8 属性 vs `get`/`set` 方法

- **正方**：属性让封装不污染调用点；C#/Kotlin/Swift 默认。
- **反方**：C 字段布局与 ABI 要求直接访问；属性需要 getter/setter 展开与命名约定；`pub readonly` 已被明确不支持。
- **判据**：若痛点是“字段级校验/只读”，方法已能表达；若痛点是“调用点冗长”，属性是纯语法糖。
- **裁决**：值得补（P2），以编译期展开的 getter/setter 实现，不改变字段布局；`readonly` 优先于 setter。

## 4. 分层结论

### 4.1 必须补（否则“现代 OO”名不副实）

排序按**依赖关系**，不是偏好：

| 顺序 | 项 | 判据 | 规模 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | 静态类型检查（档 1） | N1：类型安全是现代化基线；N2：`ct check` 只覆盖 4 类，替代不足 | 350–900 行 | 不改变发射；是推导/空安全的前置 |
| 2 | Phase 28 泛型约束 | N5：29 的泛型 impl 与容器算法依赖约束；N1：无约束的泛型只是“类型占位” | 190–395 行 | 已立项，按卡执行 |
| 3 | Phase 29 泛型 struct + 内置 `Vec`/`Map` + 容器 `foreach` | N1：没有泛型 struct 就没有通用容器，OO 的数据建模不完整；N5：`foreach` 容器协议依赖 29 | 见 29 立项卡 | 已立项，按卡执行 |
| 4 | SH-65 闭包作方法实参 | N1：`.each(closure)` 是容器迭代的主路径；当前只能用自由函数绕路 | 50–150 行 | 独立 bug，不依赖 28/29 |

### 4.2 值得补（显著提升表达力，但不阻塞“现代 OO”成立）

按**杠杆率**（前置依赖少、影响面大）排序：

| 顺序 | 项 | 判据 | 规模 | 依赖 |
| --- | --- | --- | --- | --- |
| 1 | 参数化 trait / 关联类型 | 统一容器/迭代器抽象，减少每容器一套 impl | 800–1,300 行 | 28/29 |
| 2 | 可空 / 空安全 | 消除最大类运行时崩溃；可先做编译期非空检查 | 800–2,000 行 | 类型检查、29 |
| 3 | `Result` + ADT/模式匹配 | 错误处理可组合、状态机可穷尽 | 800–2,000 行 | 29 |
| 4 | 构造语义 | 初始化不变量与失败返回 | 300–700 行 | 无 |
| 5 | 成员级可见性 / `readonly` | 封装粒度从“文件”细化到“字段” | 200–500 行 | 无 |

### 4.3 明确不做（判据，不是偏好）

| 项 | 判据 |
| --- | --- |
| 继承 | N2 成立（trait + 组合 + 默认方法可替代）；N3 成立（虚基类/菱形/ABI 复杂度）；仅当 3+ 真实包依赖 `protected`/`super` 再评估 |
| GC / 引用计数 | N3 成立（Z1 零运行时；RC 污染布局，GC 需调度器）；arena/池/`Handback` 已覆盖 |
| 异常 | N3 成立（unwind 与 C ABI/`Drop` 冲突）；返回码/`Result` 足够 |
| 语言级线程 / `async` | N3 成立（需运行时/调度器）；目标不含并发服务；`pthread`/C11 可透传 |
| 反射 / 注解 | N3 成立（RTTI 与零运行时冲突）；代码生成可替代 |
| 宏 / 条件编译 | N3 成立（与 C 超集简化冲突）；`#ct-raw` 已是逃生口 |
| 生命周期标注 | N3 成立（语法与 C 兼容成本高）；`own`/`borrow` 已覆盖主要场景；若做逃逸闭包再局部评估 |
| 全量运算符重载 | N2 成立（命名方法可替代）；仅保留索引运算符窄口 |
