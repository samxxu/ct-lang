## 0. 结论先行

Phase 30 收口后，CT 的 OO 骨架已经闭合：trait 动态派发 + 默认方法 + 泛型 struct + 泛型函数（显式实例化）+ 有界泛型函数 + 引用计数容器 + `foreach` 协议 + `own`/`Drop` + `into` 接收者块。

**仍然差三样东西，性质各不相同：**

| 类别 | 内容 | 性质 |
| --- | --- | --- |
| 表达力缺口 | 容器装不了接口值、装不了容器；泛型 trait / supertrait / 泛型 struct 约束 / 非泛型固有方法缺失 | 多数是**没做**，不是**不做** |
| 语义缺口 | 元素没有所有权（`retain`/`release` 只管缓冲）、泛型 `Drop` 缺失、接口值浅拷贝、无 RTTI | 一半是 Z1（无 GC/无隐藏运行时）的直接后果 |
| 安全网缺口 | 赋值/返回类型不匹配不报错，推给 `cc`；诊断跨不过单元边界 | 是 Z5（类型检查 opt-in）的明确选择，但当前覆盖面偏窄 |

一句话定位：**CT 不是「缺一门 OO 语言」，而是「C + 显式单态化 + 胖指针接口」这条路线走到 Phase 30 后，被容器与安全网两处卡住了。** 前者卡住「对象集合」这个最基本的 OO 用法，后者卡住「错了能在编译期知道」。

## 1. 判据

### 1.1 参照系

取「现代优秀 OO 语言」的最小公共集（Java / C# / Kotlin / Swift / C++ / Rust / Go 的交集，而非并集）：类或等价物、接口/trait、默认方法、泛型与约束、对象集合、RTTI 或等价的下转型、闭包、错误处理、空安全、并发。**不把「必须有继承」「必须有 GC」当作判据**——这两条在 Go/Rust 上都不成立。

### 1.2 CT 的既定约束

| 约束 | 含义 | 本评估的处理 |
| --- | --- | --- |
| Z1 | 零运行时 | GC、反射、异常、async 运行时都被排除 |
| Z2 | 零第三方依赖 | 标准库只能包一层 C |
| Z3 | C 超集 | 语法糖必须能无歧义脱糖到 C |
| Z4 | 编译期单态化 | 泛型靠展开，不靠运行时字典 |
| Z5 | 类型检查 opt-in | `ct-ast check` 是可选模式 |
| Z6 | 1.0 兼容冻结 | 已发布语法不破坏 |

### 1.3 判定规则

- 被 Z1–Z6 明确排除、且**存在可用替代**（如用 `Result` 结构体替代异常）→ 记为**选择**，只写边界，不计缺陷。
- 与 Z1–Z6 无关、或虽有约束但**没有替代路径**（例如"容器装接口值"既非 Z1 排除，也没有等价写法）→ 记为**缺陷**。
- 介于两者之间 → 记**半选择**，并写清"选择的边界在哪"。

### 1.4 规模口径

见文档头。对照感受：Phase 30 的 905 行换来一个 `into` 块 + 后缀链，所以「数百行」= 一个中小 Phase，「一千行以上」= 一个大 Phase，「两千行以上」= 需要拆卡。

### 2.3 与旧评估的三处漂移（以实跑为准）

1. **`Vec<Show *>`**：旧评估判「不能」。HEAD 上**能编译、能运行**（`len=1`），但它不是「接口指针容器」，而是**只能存、不能取用**：`v.push(pa)`（`pa` 为 `struct A *`，`malloc` 或取地址均可）能过，生成 `Vec_Show__iface_p_push(&v, pa)`，`-Wall` 报 `incompatible pointer types passing 'struct A *' to parameter of type 'struct Show_iface *'`（`cc -Werror` 下直接失败）；取用侧则编译不过——`Show *got = v.get(0);` 报 `cannot infer the type to box`，`v.get(0)->area()` 与 `(*v.get(0)).area()` 报 `method receiver must be a variable, an element, a call or a field chain`。另外它不能用 `v.data = 0` 初始化（0 被当作待装箱表达式，报 `cannot box this expression`），必须 `memset(&v, 0, sizeof v)`。结论：**不是能力，是一条只能塞进去的缝**。
2. **`Vec` 初值**：不是 `{1,2,3}`，而是 range 初值 `1..4 { $ }` 或 `Vec<T>::from(items, n)`。旧文档若写「花括号初值」即为漂移。
3. **类型检查**：`ct-ast check` 只挡结构性错误（实参个数：`arity mismatch: 'f' takes 1 argument(s), 0 given`）；`int x = "s";` 与 `return "s";` 在 `check` 下**照样通过**，错误推给 `cc`。旧评估笼统写「检查点不减」，低估了这条缺口的宽度。

### 2.4 两处实跑证据（原文）

**元素所有权是浅拷贝**（§3.2 O3、§4 B3、§6.1）：`struct Holder { Vec<int> xs; }` 的句柄被 `push` 逐字节拷入容器，元素不参与引用计数；释放原句柄后，容器里的元素读到已释放内存。同一份程序连跑四次：

```text
still 766634193
still 0
still -1362230811
still 0
```

不是崩溃，是静默垃圾值。`Vec::release()` 只 `free(self->data)` 与 `free(self->h)`，不碰元素。

**`check` 与 `cc` / `build` 的诊断差异**（§4 B1、§6.1）：

```text
$ ct-ast check prog.ct
（退出码 0，无输出）

$ ct-ast prog.ct -o prog.c && cc ...
prog.c:16:9: error: incompatible pointer to integer conversion initializing 'int'
    with an expression of type 'char[2]' [-Wint-conversion]

$ ct-ast build prog.ct -o prog
prog.ct:6:9: error: incompatible pointer to integer conversion initializing 'int'
    with an expression of type 'char[2]' [-Wint-conversion]
```

单文件模式没有 `#line`，指向生成的 `.c`；`build` 模式带 `#line`，指回 `.ct`。容器实参同理：`v.push("s")` 在 `build` 下报 `prog.ct:10:22: ... passing 'char[2]' to parameter of type 'int'`。

### 3.6 错误处理

现状：无异常、无 `panic`、无 `Result` 协议；`release` 二次调用是 `abort`，容器越界是静默零值/空操作。判定：**选择**（Z1），但「静默」与「硬崩」两种策略混用是缺陷——同一套容器里 `get` 越界给零值、`release` 二次调用直接 `abort`，使用者无法从类型上区分。建议在库层统一成 `Result` 风格（D1），编译器不必动。

### 3.7 迭代与集合

现状：`foreach` 覆盖数组 / `Vec` / `Map`，`Map` 保证插入序；无迭代器协议、无 `map`/`filter`、无排序。这些都能在 `lib/std` 里用手写函数补齐（`S`，0 编译器行），不算语言缺口。

### 3.8 模块与工程

现状：`pub` 只有「导出/不导出」一档；`.h.ct` 才能被 `import`；类型别名只在头单元；跨单元泛型只能靠「泛型 struct 在 `.h.ct` 里 + 实例在消费单元用」——而这正好被 §2.2 的容器缺陷挡住（泛型电商包无法服务用户类型）。这一条是 O1/C2 的工程投影，不单独计一次工作量。

### 3.9 并发与异步

无语言级线程、原子、`async`。判定：**明确不做**（Z1、Z2）；`pthread` 走 `bindings`，与 CT 的 OO 表达力无关。

### 3.10 元编程与工具

无编译期反射、无注解、无派生宏；无 LSP / 格式化 / 包管理器（`ct.pkg` 只有清单）。判定：**明确不做或外部化**；其中「派生 `Drop`/`clone`」值得作为 O3 的副产物。

## 4. 设计取舍的两面

每条都写：这个选择买到了什么、卖掉了什么、边界在哪、判定是「选择」还是「缺陷」。

### B1 不追求完整类型检查（Z5）

- **买到**：编译器小、自举可行（`l0 → l1 → l2` 全链能自己编译自己）、C 超集成立、`cc` 的错误信息直接可用。
- **卖掉**：`int x = "s";`、`return "s";`、`f()` 少参（部分）都要等 `cc`；单文件模式没有 `#line`，错误指向生成的 `.c`，`build` 模式才有 `#line` 指回 `.ct`；诊断措辞是 C 的（`-Wint-conversion`）；跨单元只能靠 `cc` 兜底。
- **边界**：`check` 是 opt-in，不是「没有检查」——实跑 `arity mismatch` 能挡。边界在「结构 vs 类型」：结构查，类型不查。
- **判定**：**半选择**（B 档）。选择本身成立；真实差距是 `check` 不报、要等 `cc`，且措辞是 C 的，属于该补的边界内工作（§7 的 P32）。

### B2 显式实例化（Z4）

- **买到**：单态化结果确定、无推导复杂度、生成代码可预测、零运行时。
- **卖掉**：`id<int>(3)` 必须写类型；泛型函数不能 `pub` 跨单元；`impl<T> Vec<T>` 的方法体在模板所属单元展开，因此看不到消费方的类型（这就是 O1/C2 的根因）。
- **边界**：单态化换来的是「编译期可知」，不是「写法简洁」。
- **判定**：**选择**，但「跨单元泛型」这条边界已经影响到容器包生态，需要显式承认。

### B3 引用计数 + 显式 `retain`/`release`（Z1）

- **买到**：无 GC、无隐藏分配、`retain` 返回新句柄、`release` 返回到零时释放；二次释放是 `SIGABRT` 而不是静默破坏。
- **卖掉**：元素不参与计数（`Vec<Vec<int>>` 会双持有）；没有元素级 Drop；嵌套/接口容器没有所有权主体。
- **边界**：只对「缓冲」计数，不对「元素」计数——这是 V29-2 的明确切分。
- **判定**：**选择**，但元素所有权缺口是缺陷（O3）。

### B4 接口值按值拷贝（胖指针 `{self, vt}`）

- **买到**：无堆分配即可传递接口值、`use` 一句即采纳、与 C 结构布局兼容、可作字段和参数。
- **卖掉**：浅拷贝（`self` 指向原对象，源对象死了就悬垂）；`use` 过 trait 的 struct 带 vptr，被容器守卫整类拒绝；空接口值 `{0,0}` 派发即崩。
- **边界**：能放进「结构体字段」，不能放进「容器元素」——同一套值语义，两个结论，说明限制在容器侧而不是接口侧。
- **判定**：**半选择**。接口表示是选择，容器拒绝是实现缺口（O1）。

### B5 方法只归属 trait（无固有方法）

- **买到**：派发模型单一（要么 vtable，要么单态化），没有「同名方法在不同上下文含义不同」。
- **卖掉**：写一个工具结构体也得造 trait；`patterns` 这类模式包写不出「方法」，只能写自由函数；非泛型 struct 连 `impl P { … }` 都不行。
- **边界**：泛型 struct 例外（`impl<T> Vec<T>` 有固有方法），因为单态化路径清晰。
- **判定**：**缺陷**（T4），与 Z1–Z6 都不冲突，纯粹是没做。

### B6 不做继承

- **买到**：没有菱形、没有脆弱基类、没有构造链；组合 + 默认方法覆盖大部分场景。
- **卖掉**：没有 is-a 多态；没有 `protected`、没有 `super`。
- **边界**：接口值已经承担了「同一接口、多种实现」，继承剩下的主要是代码复用——而默认方法补了这块。
- **判定**：**选择**，与 Go/Rust 一致。

### B7 不做运算符重载（`into` 是唯一例外）

- **买到**：语法稳定、解析简单、生成代码与 C 一一对应。
- **卖掉**：`v[i]`、`a + b` 只能写成命名方法；下标糖要等 C1。
- **边界**：`into` 能进语言，是因为它是**纯局部脱糖**（`expr into { … }` 就地改写为 `expr->field = …` 与语句序列），不引入新类型规则；`v[i]` 不是——它要回答零值、左值、缺键三个语义问题。
- **判定**：**选择**；但「下标」可以和「运算符重载」脱钩，单独做（C1）。

### B8 不做异常

- **买到**：零运行时、与 C 完全互操作、`errno` 可用。
- **卖掉**：错误处理靠返回值 + 手工检查；没有 RAII 抱错。
- **边界**：`own`/`Drop` 只覆盖局部指针，容器里的错误无法自动冒泡。
- **判定**：**选择**（Go 同路线），但库层应统一（见 §3.6）。

### B9 `own` / `Drop` 只管局部指针

- **买到**：保守、可预测、泄漏有静态告警；`use Drop` + `delete` 可用。
- **卖掉**：`own` 作字段在 CT 侧放行、`cc` 侧报错；容器不自动析构；泛型 `Drop` 缺失，模式包只能手写 `deinit()`。
- **边界**：`own` 的对象必须是 `malloc`/`calloc` 得到的结构体指针（函数体内），不是字段、不是栈值。
- **判定**：**半选择**。字段形态是缺陷（O6），容器不析构是 O3。

### B10 闭包非逃逸（栈 env）

- **买到**：无 GC、无分配、捕获是按值快照（`__ct_cl_env_v_0 = { threshold }`），语义可预测。
- **卖掉**：闭包不能存字段、不能跨调用、不能作 trait 方法实参（SH-65）、不能当普通函数指针传。
- **边界**：`fn` + `env` 成对传递（`int (*fn)(void *, int), void *env`）是唯一形态。
- **判定**：**选择**，但 SH-65 这种「方法实参」属于漏做的边界，值得补（F3）。

## 6. 分层结论

### 6.1 必须补（A 档）与高优先项

判断标尺（本节每条都按它复核，不按形容词）：

| 档位 | 含义 | 用户感受 |
| --- | --- | --- |
| A 写不出 | 常见程序根本表达不了，只能换语言或改需求 | 卡死 |
| B 容易错 | 写得出来，但默认写法会在运行期静默出错 | 埋雷 |
| C 绕大圈 | 写得出来，但要先搭一层脚手架，且脚手架本身有代价 | 烦，但能干活 |

| 项 | 档位 | 理由 | 规模 |
| --- | --- | --- | --- |
| O1 + O3 + C2（一条链） | A | 「对象集合」与「分组 / 邻接表」是 OO 的基本用法，现在分别被 L29-13、L29-11 硬拒。O1 放开守卫、按值浅拷贝即可先用；O3 是 O1/C2 的**验收条件**，不是独立条目——元素不参与 retain/release，放开后默认就是悬垂或泄漏（证据见 §2.4）；C2 依赖 O3，且还要过 `ct_impl_matches` 无嵌套 pattern 或发射器私有分支这一关 | 900–1,600（O1 单独 320–680；O3 与 C2 共享元素助手，不重复计） |
| 安全网（B1 的边界） | B（高优先值得补） | `int x = "s"` 能过 `check`，要等 `cc` 才报；不挡程序，但措辞是 C 的，且单文件模式下位置指向生成的 `.c`（§2.4）。若目标是「看起来像现代语言」，应排在最前；按 A 档标准它不够 | 500–1,000 |

### 6.2 值得补（显著提升表达力，不阻塞）

T3 泛型 struct 约束（C 档：不挡常见程序，只挡「方法语法 + 约束」的组合；绕法是写成有界泛型自由函数，实测 `any_area<struct Circle>(&b.v)` 返回 9）、T1 泛型 trait、T2 supertrait、T4 非泛型固有方法、C1 下标糖、O4 泛型 Drop、O5 RTTI、F1 `pub` 泛型函数、F2 函数返回函数指针、F3 闭包作方法实参、T5 类型别名、D3 字符串类型、D1 `Option`/`Result` 库。

### 6.3 明确不做（判据，不是偏好）

继承、GC、异常、运行时反射、语言级并发/async、自动类型推导、逃逸闭包、运算符重载（`into` 是脱糖例外）。

## 7. 只能再做三个 Phase 的排序

### P31「容器表达力」

- **范围**：O1（接口值按值进容器）+ O3/C2（元素所有权助手 + 嵌套容器）。
- **独立交付**：`Vec<Show>`、`Map<char*, Show>`、`Vec<Vec<int>>`、`Map<char*, Vec<int>>` 能编译、能 `foreach`、`release` 级联不泄漏（ASAN 夹具）。
- **规模**：编译器 + `lib/std` **900–1,600**（O3 的助手生成与 C2 共用，不重复计）。
- **依赖**：无（可先做 O1，320–680，作为一期提前交付）。
- **风险**：接口值浅拷贝的寿命规则必须同时写进语言规范，否则放开守卫只是把 `cc` 段错误挪到运行期；`Vec<Show *>` 目前那条不兼容指针转换要一并收紧。

### P32「类型检查网」

- **范围**：`ct-ast check` 覆盖赋值、返回、字段、容器实参、`into` 块赋值。
- **独立交付**：`check` 能挡住 `int x = "s"`、`return "s"`、`v.push(错类型)`，且诊断指回 `.ct` 行号。
- **规模**：编译器 **500–1,000**。
- **依赖**：P31 的新形态（容器实参）先定，否则规则要写两遍。
- **风险**：Z5 是 opt-in，扩大检查面会暴露既有样例的类型错误；需要一次性清账，不能用「默认关闭」掩盖。

### P33「类型系统表达力」

- **范围**：T3（泛型 struct 约束）+ T4（非泛型固有方法）+ T1/T2（泛型 trait、supertrait）。
- **独立交付**：`struct Box<T: Show>` 可用；工具结构体可以写方法；`trait Iter<T>` 与 `trait Ord: Eq` 可声明。
- **规模**：编译器 **700–1,400**。
- **依赖**：无（T4 可单独 80–250 提前做）。
- **风险**：T1 会撞上 `ct_impl_matches` 只支持「具体拼写或参数名」的匹配模型（C2 也有同一问题），要么扩展匹配，要么统一走单态化；这一步需要先做原型再定卡。

**为什么是这个顺序**：P31 是用户优先级最高、且不改变语义模型的一项；P32 是 P31 的安全前提（容器一放开，错误面立刻变大）；P33 主要是「写法」问题，晚做不会挡住别人。三者的共享地基只有一处：**逐元素 copy/drop 助手**（P31 的 O3 与 C2 共用），P32/P33 不碰它，所以不能把三份估算简单相加。

## 8. 无法判定 / 待验证

- 所有行数区间是设计级估算，误差 ±40%；没有做原型，不能当承诺。
- `Vec<Show *>` 的指针转换在 `-Wall` 下是警告，`cc -Werror` 实测直接失败；`check-ast` 要求生成代码警告为零，因此这类夹具**进不了门禁**（没有跑完整门禁，但 `-Werror` 等价于该要求）。
- C2 的「扩展 `ct_impl_matches` 支持嵌套 pattern」与「发射器内置分支」两条路，我只确认了当前 pattern 无嵌套能力，没有做原型比较成本。
- `ct-ast check` 的检查清单没有系统枚举，本文只实测了赋值、返回、实参个数三点；其余检查点是否覆盖未知。
- 泛型 trait 与 `trait` 作为类型参数（`Vec<Show>` 的 trait 名解析）在 `container_vptr_type` 之后还有哪些分支会拒，我只测到第一条错误，没有逐层剥。
- 并发、逃逸闭包、模式匹配属于「明确不做/长线」，本轮没有写探针，相关判断来自语法缺失而非运行验证。
