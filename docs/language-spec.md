# .ct 语言规范（Phase 0）

> 中文 · [English](#english)

本文描述 `ctc` 在 **Phase 0** 接受的输入语法、展开规则、命名规则与诊断行为。
凡本文未写明的行为，均属未定义，不应依赖。

---

## 中文

### 1. 源文件模型

一个 `.ct` 文件是「若干顶层构造」与「原样透传的 C 代码」的混合体。
编译器**单趟顺序扫描**，按源码顺序处理：顶层构造被展开成 C，其余内容逐行透传。
因此**顺序敏感**：所有定义必须出现在使用之前。

```
program  ::= { item }
item     ::= trait-def | struct-def | impl-def | raw-text
```

顶层构造只能出现在文件的最外层（不允许嵌套），且其关键字必须位于行首（允许前置空格/制表符）。

生成物的第一行固定是溯源注释 `Generated by ctc v<版本> from <输入路径> -- do not edit; ...`（`.h` 头部也有一段等效注释），它不属于源文件内容。

### 2. 词法与书写要求

- 关键字（`trait` / `struct` / `impl` / `use` / `for`）必须成**独立单词**出现，由 `word_at()` 做词边界判断；`traitx`、`my_struct` 不会被误判。
- 空白、换行、`//` 行注释、`/* */` 块注释在构造头部可自由插入。
- trait 体内的方法声明以 `;` 分隔，允许一条声明跨多行；注释在切分前被剥离。
- struct 体内的字段原样保留、不做解析。
- 标识符为 `[A-Za-z_][A-Za-z0-9_]*`；超出 127 字符会被**静默截断**。

### 3. 语法

```ebnf
trait-def   ::= "trait" IDENT "{" { method-decl } "}" ;
method-decl ::= type-spec IDENT "(" [ param-list ] ")" ";" ;

struct-def  ::= "struct" IDENT "{" raw-text "}" [ use-clause ] [ ";" ] ;
use-clause  ::= "use" IDENT { "," IDENT } ";" ;

impl-def    ::= "impl" IDENT "for" IDENT "{" { method-def } "}";
method-def  ::= type-spec IDENT "(" [ param-list ] ")" block ;

param-list  ::= param { "," param } ;
param       ::= type-spec [ IDENT ] ;   (* type-spec 可含 *、const 等 *)

type-spec   ::= <C 类型写法，取到方法名/参数名之前的全部字符>
```

约定：

- `use` 子句可紧跟 `}` 写在同一行，也可另起一行。
- 单个参数写成 `void` 视为**无参数**。
- struct 定义后的分号可选（`};` 与 `}` 都接受）。
- `param` 的类型与名字靠**启发式**切分：取参数文本的最后一个标识符作为参数名，除非它是类型关键字（`void`/`char`/`int`/`unsigned`/`size_t` …）或参数文本以 `*` 结尾。

### 4. 展开规则

#### 4.1 trait → vtable 类型

```c
trait Greeter { void greet(); int add(int a, int b); }
```

```c
struct Greeter_vtbl {
    void (*greet)(void *);
    int (*add)(void *, int, int);
};
```

每个方法多出一个前置参数 `void *`；参数列表在 vtable 中**只保留类型、去掉参数名**。

#### 4.2 struct + use → 追加 vptr 字段

```c
struct Person {
    char *name;
    int age;
} use Greeter;
```

```c
struct Person {
    char *name;
    int age;
    struct Greeter_vtbl *__greeter_vptr;
};
```

字段体原样保留，vptr 字段按 `use` 的书写顺序追加在末尾。

#### 4.3 impl → 静态方法 + vtable 变量

```c
impl Greeter for Person {
    void greet() {
        printf("Hello, %s\n", self->name);
    }
}
```

```c
static void Person_Greeter_greet(void *self) {
    struct Person *_self = (struct Person *)self;
    printf("Hello, %s\n", _self->name);
}

static struct Greeter_vtbl Person_Greeter_vtable = {
    .greet = Person_Greeter_greet
};
```

- 生成函数的参数是「`void *self` + impl 中书写的方法参数」，函数体第一行固定为 `_self` 强转。
- 方法体的缩进按最小公共缩进去除后重新以 4 空格排版。
- vtable 初始化项按 **trait 中方法的声明顺序**排列，而不是 impl 中的书写顺序。

#### 4.4 变量声明 → 限定 `struct` + 追加 vptr 指定初始化

```c
Person p = { .name = "Tom", .age = 36 };
```

```c
struct Person p = { .name = "Tom", .age = 36, .__greeter_vptr = &Person_Greeter_vtable };
```

规则：

| 源码形态 | 处理 |
| --- | --- |
| `Person p = { … };`（全为指定初始化） | 前缀 `struct `，并在 `}` 前追加 vptr 指定初始化项 |
| `Person p = {};` / `Person p;` | 前缀 `struct `；空列表会追加 vptr，无初始化式则**不追加**（见 6.2） |
| `struct Person p = { … };` | 同上（已有限定符时不重复添加） |
| `Person p = { "Tom", 36 };`（位置式初始化） | 前缀 `struct `，其余原样输出，**不追加 vptr** |
| `Person *p = …;` | 前缀 `struct `，其余原样输出；指针变量**不登记**，`p->m()` 不重写 |
| 其它类型 | 完全不动 |

被识别为「结构体类型变量」的名字会登记进变量表，供后续方法调用重写使用。

#### 4.5 方法调用重写

```c
p.greet();
p.greet_name("Jerry");
```

```c
p.__greeter_vptr->greet(&p);
p.__greeter_vptr->greet_name(&p, "Jerry");
```

触发条件（**全部**满足才重写）：

1. 左边是一个标识符，且它在**本文件此前**已被登记为某 struct 类型的变量；
2. 紧接着是 `.`，且成员名是该变量类型的某个 trait 的**方法名**；
3. 成员名后紧跟 `(`。

方法归属的判定顺序：按该 struct `use` 子句中的 trait 顺序查找，**取第一个**声明了该名字的 trait。

重写细节：

- 形如 `x.m()` 的无参调用 → `x.__t_vptr->m(&x)`（不产生多余逗号）。
- 形如 `x.m(a)` → `x.__t_vptr->m(&x, a)`。
- 参数内部的嵌套调用会被继续处理：`q.add(1, q.add(2, 3))` → `q.__greeter_vptr->add(&q, 1, q.__greeter_vptr->add(&q, 2, 3))`。
- 字符串字面量、字符字面量、注释内的内容**永不重写**。
- `->` 形式的指针调用不识别。

### 5. 命名规则（稳定契约）

| 产物 | 规则 | 示例（trait `Greeter`，struct `Person`，方法 `greet`） |
| --- | --- | --- |
| vtable 类型 | `<Trait>_vtbl` | `struct Greeter_vtbl` |
| vptr 字段 | `__<trait 全小写>_vptr` | `__greeter_vptr` |
| 方法实现 | `<Struct>_<Trait>_<method>` | `Person_Greeter_greet` |
| vtable 变量 | `<Struct>_<Trait>_vtable` | `Person_Greeter_vtable` |
| 隐式参数 | 固定为 `self`，函数体内强转目标固定为 `_self` | — |

### 6. 语义约束与已知问题

#### 6.1 会被诊断的约束

| 约束 | 违反时 |
| --- | --- |
| `use` 引用的 trait 必须已定义（且出现在该 struct 之前） | `error: struct 'S' uses undefined trait 'T'` + `exit 1` |
| `impl` 的 trait 与 struct 必须已定义 | `error: impl for undefined trait/struct 'X'` + `exit 1` |
| struct 必须 `use` 了对应 trait 才可 `impl` | `error: struct 'S' does not use trait 'T'` |
| impl 不得出现 trait 未声明的方法 | `error: method 'm' is not declared in trait 'T'` |
| impl 必须实现 trait 的**每一个**方法 | `error: trait method 'm' is not implemented for struct 'S'` |
| 大括号/圆括号必须配对 | `error: unterminated '{'` |

**不做**的检查：方法签名是否与 trait 一致（参数类型、个数、返回类型都不比对，原样搬运）；
trait / struct 是否重名（`find_*` 取最先出现者，后者不可达，不报错）。

#### 6.2 已知限制

- 无初始化式的声明（`Person p;`）不会写入 vptr，此时调用方法会解引用空指针。
- 位置式初始化不追加 vptr，因此不要用 `Person p = { "Tom", 36 };`。
- 指针声明 `Person *p = …;` 会被正确限定为 `struct Person *p = …;`，但指针变量不登记，
  因此 `p->m()` 形式的方法调用不会被重写（`->` 形式不在 Phase 0 范围内）。
- 变量表无作用域、无类型（同名变量在后续函数中被沿用），且**登记顺序 = 源码顺序**：在变量声明之前出现的方法调用不会被重写。
- 跨行的方法调用语句不重写（按行处理）。
- `impl` 方法体内对其它方法的调用不会被重写（`self->other()` 只会变成 `_self->other()`）。
- 顶层构造不支持嵌套。

### 7. 容量上限

| 常量 | 值 | 含义 | 超限行为 |
| --- | --- | --- | --- |
| `MAX_TRAITS` | 16 | trait 数量 / 单 struct 的 `use` 数量 | 报错退出 |
| `MAX_STRUCT` | 32 | struct 数量 | 报错退出 |
| `MAX_METHOD` | 32 | 单 trait / 单 impl 的方法数 | 报错退出 |
| `MAX_PARAMS` | 16 | 单方法参数个数 | 报错退出 |
| `MAX_VARS` | 512 | 被登记的变量数 | 静默忽略（不再重写） |
| `MAX_NAME` | 128 | 标识符 / 类型名长度 | 静默截断 |
| `MAX_PARAM` | 256 | 参数字符串长度 | 静默截断 |

### 8. 明确不支持（Phase 0 范围外）

namespace、可见性修饰符（`pub` / `readonly` / `setter`）、泛型、继承、多文件编译、类型检查、
错误恢复、嵌套定义。

### 9. 诊断与退出码

- 格式：`<file>:<line>:<col>: error: <message>`，输出到 `stderr`。
- 退出码：`0` 成功；`1` 语法错误、语义错误、I/O 错误。
- 无警告机制：可疑但仍可生成代码的情况（如静默截断）不会提示。

## English

This document specifies what `ctc` accepts and emits in **Phase 0**. Anything not described here is
undefined behaviour and must not be relied upon.

### 1. Source model

A `.ct` file mixes top-level constructs with verbatim C. The compiler scans it **once, in source
order**: top-level constructs are expanded, everything else is copied line by line. Order therefore
matters — all definitions must precede their use.

Top-level constructs must sit at file scope (no nesting) and their keyword must start the line
(leading spaces and tabs are allowed). The first line of every generated `.c` is a provenance comment
`Generated by ctc v<version> from <input path> -- do not edit; ...` (the `.h` carries an equivalent
comment in its header); it is not part of the source content.

### 2. Lexical notes

- Keywords (`trait`, `struct`, `impl`, `use`, `for`) must appear as whole words (`word_at()` performs
  word-boundary matching), so `traitx` or `my_struct` are not misread.
- Whitespace, newlines, `//` comments and `/* */` comments may appear freely in construct headers.
- Method declarations inside a trait are separated by `;` and may span lines; comments are stripped
  before splitting.
- Struct bodies are preserved verbatim and not parsed.
- Identifiers are `[A-Za-z_][A-Za-z0-9_]*`; anything longer than 127 characters is **silently
  truncated**.

### 3. Grammar

```ebnf
trait-def   ::= "trait" IDENT "{" { method-decl } "}" ;
method-decl ::= type-spec IDENT "(" [ param-list ] ")" ";" ;

struct-def  ::= "struct" IDENT "{" raw-text "}" [ use-clause ] [ ";" ] ;
use-clause  ::= "use" IDENT { "," IDENT } ";" ;

impl-def    ::= "impl" IDENT "for" IDENT "{" { method-def } "}" ;
method-def  ::= type-spec IDENT "(" [ param-list ] ")" block ;

param-list  ::= param { "," param } ;
param       ::= type-spec [ IDENT ] ;   (* type-spec may contain '*' and 'const' *)

type-spec   ::= <everything up to the method/parameter name>
```

Conventions: the `use` clause may follow `}` on the same line or start a new line; a sole `void`
parameter means "no parameters"; the semicolon after a struct definition is optional. Parameter types
and names are split heuristically — the last identifier is taken as the parameter name unless it is a
type keyword or the text ends with `*`.

### 4. Expansion rules

**trait → vtable type.** Each method gains a leading `void *` parameter; the vtable keeps types only
and drops parameter names.

**struct + use → extra vptr field.** The field body is preserved and one
`struct <Trait>_vtbl *__<trait>_vptr;` member is appended per trait, in `use` order.

**impl → static functions + vtable variable.** The generated function is
`<Struct>_<Trait>_<method>` with signature `void *self` plus the written parameters, and its first
statement is always `struct <Struct> *_self = (struct <Struct> *)self;`. The body's shared
indentation is removed and re-emitted with a 4-space base. Initialisers in the vtable follow the
**trait's declaration order**, not the impl's order.

**variable declarations.** `Person p = { .a = 1 };` becomes
`struct Person p = { .a = 1, .__t_vptr = &Person_T_vtable };`, and `p` is registered as a
`Person`-typed variable for later call rewriting. Only empty or fully designated lists receive vptr
designators; positional initialisers and declarations without initialisers are emitted unchanged
(see known issues). Pointer declarations receive only the `struct` qualifier.

**method calls.** `p.greet(1)` becomes `p.__greeter_vptr->greet(&p, 1)`. Rewriting requires all of:
the left-hand identifier was previously registered as a variable of a struct type; the member name is
a method of one of that struct's traits (first match in `use` order); and the member is immediately
followed by `(`. No-argument calls produce no trailing comma, nested calls inside arguments are
rewritten recursively, and content inside strings, character literals and comments is never touched.
The `->` form is not recognised.

### 5. Naming contract

`<Trait>_vtbl`, `__<lowercase trait>_vptr`, `<Struct>_<Trait>_<method>`, `<Struct>_<Trait>_vtable`.
The implicit parameter is always `self` and its cast target inside the body is always `_self`.

### 6. Diagnosed constraints and known issues

Diagnosed with `file:line:col: error: …` and `exit 1`: undefined traits in a `use` clause; undefined
trait/struct in an `impl`; `impl` of a trait the struct does not use; methods in an impl that the trait
does not declare; trait methods not implemented; unterminated delimiters.

Not checked: signature agreement between impl and trait (types, arity and return type are copied
verbatim, never compared); duplicate trait/struct names (the first definition wins silently).

Known issues: declarations without initialisers leave the vptr unset; positional initialisers are not
extended; pointer declarations are qualified correctly (`struct Person *p`) but pointer variables are
not registered, so `p->m()` calls are never rewritten; the variable table is global, untyped and
order-sensitive, so calls appearing before the declaration are not rewritten; call statements spanning
multiple lines are not rewritten; calls between methods inside an impl body are not rewritten; nested
constructs are unsupported.

### 7. Capacity limits

| Constant | Value | Meaning | On overflow |
| --- | --- | --- | --- |
| `MAX_TRAITS` | 16 | traits / traits per `use` | error, exit |
| `MAX_STRUCT` | 32 | structs | error, exit |
| `MAX_METHOD` | 32 | methods per trait or impl | error, exit |
| `MAX_PARAMS` | 16 | parameters per method | error, exit |
| `MAX_VARS` | 512 | registered variables | silently ignored |
| `MAX_NAME` | 128 | identifier / type name length | silently truncated |
| `MAX_PARAM` | 256 | parameter string length | silently truncated |

### 8. Out of scope

Namespaces, visibility modifiers, generics, inheritance, multi-file compilation, type checking, error
recovery, nested definitions.

### 9. Diagnostics

`<file>:<line>:<col>: error: <message>` on stderr; exit code `0` on success, `1` on syntax, semantic
or I/O errors. There is no warning channel — suspicious but usable output (such as silent truncation)
is never reported.
