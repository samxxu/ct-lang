# .ct 语言规范

> 中文 · [English](#english)

> **状态**：本文描述 **ct 语言的核心语法**——L0（`ctc.c`）、CT 线（L2，`selfhost/l2/**`；冻结的回归
> oracle）与安装入口 ct-ast（`selfhost/ct-ast/main.ct`）**共同**接受与产出的部分。CT 线是 L0 的超集，额外支持 `namespace` / `import` / `pub` / 多文件 `ct build` /
> `Drop` / `#line` / 泄漏警告与 `--diagnostics`；这些**不在本文的语法章节内**，语义与落地记录见
> [roadmap](roadmap.md) 的 Phase 2–5、[design/restore.md](history/design/restore.md) 与
> [design/phase5.md](history/design/phase5.md)。AutoDrop（`own`）虽然也是 CT 线独有，但在 §4.9 一并描述。
> Phase 11.1 新增的 `map`（把 trait 方法绑定到已声明的全局实例；SH-20 起也可绑定到命名空间）**仅 ct-ast** 支持，L0 与 L2 都不接受，见 §4.10。
>
> 三者并非逐字节等价：ct-ast 是安装入口，L2 只是回归 oracle。已知分叉分两类。
>
> **有意拒绝**（设计决定，不是缺失）：
>
> | 构造 | L2 | ct-ast | 理由 |
> | --- | --- | --- | --- |
> | 块式 `namespace A::B { … }` | 接受 | 拒绝（`a namespace is file-scoped`） | 单元级前缀与目录校验都假设一个文件只声明一个命名空间 |
> | 跨命名空间裸调用 | 接受并回退到根表 | 拒绝（要求限定写法 `A::f()`） | 避免在两个同名导出之间静默选错对象 |
> | `import` 一个普通 `.ct` 单元 | 接受（附加式：普通 `.ct` 也产 `.h`） | 拒绝（`only a .h.ct unit can be imported: rename 'x.ct' to 'x.h.ct'`） | 只有 `.h.ct` 发布接口；ct-ast 下普通 `.ct` 不产 `.h`（build 与 compile 一致） |
>
> **C 形式覆盖**：`goto` / 标签、`switch` 范围、位域、匿名成员、变参、`inline`、
> `_Static_assert`（含 `static_assert` 别名）、整数字面量后缀（§4.37）、浮点字面量（§4.24）、
> `_Alignas` / `_Alignof` / `_Generic`（§4.35）与
> GNU `__attribute__((…))`（§4.36）等两侧都接受，没有已知的未实现形式，见 §4 各节。
>
> 这是两层的**能力差**，不是同一条流水线上的进度差：L0 命中上述构造仍报
> `'namespace' is not supported by this compiler`（`pub` / `import` / `ct build` 同类；
> `--line` / `--no-line` / `--diagnostics` 报 `unknown option`）。归档 fixture 见 `test/archive/`，
> 特性完整的旧实现见 git tag `overreach-oracle`。

本文描述核心语法的输入规则、展开规则、命名规则与诊断行为。凡本文未写明的行为，均属未定义，不应依赖。

## 中文

### 1. 源文件模型

一个 `.ct` 文件是「若干顶层构造」与「原样透传的 C 代码」的混合体。
编译器**单趟顺序扫描**，按源码顺序处理：顶层构造被展开成 C，其余内容逐行透传。
因此**顺序敏感**：所有定义必须出现在使用之前。

```
program  ::= { item }
item     ::= trait-def | struct-def | impl-def | raw-text
```

顶层构造只能出现在文件的最外层（不支持嵌套），且其关键字必须位于行首（允许前置空格/制表符）。

生成物的第一行固定是溯源注释 `Generated by ct v<版本> from <输入路径> -- do not edit; ...`（`.h` 头部也有一段等效注释），它不属于源文件内容。

### 2. 词法与书写要求

- 关键字（`trait` / `struct` / `impl` / `use` / `for`）必须成**独立单词**出现，由 `word_at()` 做词边界判断；`traitx`、`my_struct` 不会被误判。
- `namespace` / `pub` / `import` 已不再是关键字：这三个词现在会被编译器拒绝（见开头的状态说明）。
- 行首的 `trait` / `impl` / `struct` 只有在**完整构造头部**紧跟其后时才算构造（`trait IDENT {`、`impl IDENT for`、`struct IDENT {`），否则按原样透传。因此把 `trait` / `impl` 当作普通标识符的合法 C（如 `impl[0] = 1;`、`trait = 2;`）不会被误判。
- 重写**按行**进行：构造与普通语句写在同一行时，语句不会被重写（`int main(void){ Person p = {…}; p.greet(); }` 中的 `p.greet()` 保持原样）。
- 所有固定容量上限（标识符长度、参数个数与文本、字段 / 方法 / trait / struct 数、变量数、作用域深度等）越界一律 `die` 报错，**不静默截断**。
- 空白、换行、`//` 行注释、`/* */` 块注释在构造头部可自由插入。
- trait 体内的方法声明以 `;` 分隔，允许一条声明跨多行；注释在切分前被剥离。
- struct 体内的字段原样保留、不做解析。
- 标识符为 `[A-Za-z_][A-Za-z0-9_]*`；ct-ast 对超过 159 字符的名字**报错**
  （`identifier is too long`），不再静默截断（L0 种子的上限是 127 字符）。

### 3. 语法

```ebnf
trait-def   ::= "trait" IDENT "{" { method-decl } "}" ;
method-decl ::= type-spec IDENT "(" [ param-list ] ")" ( ";" | block ) ;

struct-def  ::= "struct" IDENT "{" raw-text "}" [ use-clause ] [ ";" ] ;
use-clause  ::= "use" IDENT { "," IDENT } ";" ;

impl-def    ::= "impl" IDENT "for" IDENT "{" { method-def } "}";
method-def  ::= type-spec IDENT "(" [ param-list ] ")" block ;

param-list  ::= param { "," param } ;
param       ::= type-spec [ IDENT ] ;   (* type-spec 可含 *、const 等 *)

type-spec   ::= <C 类型写法，取到方法名/参数名之前的全部字符>
```

约定：

- `use` 子句可紧跟 `}` 写在同一行，也可另起一行。
- 单个参数写成 `void` 视为**无参数**。
- struct 定义后的分号可选（`};` 与 `}` 都接受）。
- trait 方法以 `;` 结尾是无体的**抽象方法**；以 `{ … }` 结尾则是带**默认实现**的方法
  （ct-ast；见 §4.39）。
- `param` 的类型与名字靠**启发式**切分：取参数文本的最后一个标识符作为参数名，除非它是类型关键字（`void`/`char`/`int`/`unsigned`/`size_t` …）或参数文本以 `*` 结尾。

#### 3.1 表达式（ct-ast）

ct-ast 按 C 的优先级解析表达式，支持的运算符子集由紧到松为：

| 层级 | 运算符 |
| --- | --- |
| 一元 | `!` `~` `-` `&`（取地址） `*`（解引用）、强制转换、`sizeof` |
| 乘除 | `*` `/` `%` |
| 加减 | `+` `-` |
| 移位 | `<<` `>>` |
| 比较 | `<` `>` `<=` `>=` `==` `!=` |
| 位与 | `&` |
| 位异或 | `^` |
| 位或 | `\|` |
| 逻辑 | `&&` `\|\|` |
| 条件 | `?:` |
| 赋值 | `=` 以及复合赋值 `+=` `-=` `*=` `/=` `%=` `&=` `\|=` `^=` `<<=` `>>=` |

生成物给每个二元 / 一元运算都加括号，因此源码语义不依赖 C 侧的优先级重排。
L0 / L1 / L2 不解析表达式（按行透传），本表只约束 ct-ast。

### 4. 展开规则

#### 4.1 trait → vtable 类型

```c
trait Greeter { void greet(); int add(int a, int b); }
```

```c
struct Greeter_vtbl {
    void (*greet)(void *);
    int (*add)(void *, int, int);
};
```

每个方法多出一个前置参数 `void *`；参数列表在 vtable 中**只保留类型、去掉参数名**。

#### 4.2 struct + use → 追加 vptr 字段

```c
struct Person {
    char *name;
    int age;
} use Greeter;
```

```c
struct Person {
    char *name;
    int age;
    struct Greeter_vtbl *__greeter_vptr;
};
```

字段体原样保留，vptr 字段按 `use` 的书写顺序追加在末尾。

#### 4.3 impl → 静态方法 + vtable 变量

```c
impl Greeter for Person {
    void greet() {
        printf("Hello, %s\n", self->name);
    }
}
```

```c
static void Person_Greeter_greet(void *self) {
    struct Person *_self = (struct Person *)self;
    printf("Hello, %s\n", _self->name);
}

static struct Greeter_vtbl Person_Greeter_vtable = {
    .greet = Person_Greeter_greet
};
```

- 生成函数的参数是「`void *self` + impl 中书写的方法参数」，函数体第一行固定为 `_self` 强转。
- 方法体的缩进按最小公共缩进去除后重新以 4 空格排版。
- **方法体走与顶层代码完全相同的重写管线**：先把 `self`（指向当前 struct 的指针）与 impl 中书写的
  方法参数登记进变量表，再逐行 `transform_line`，最后把标识符 `self` 重命名为 `_self`。因此方法体内
  的各类接收者都会被派发，与顶层代码无差别：
  - 兄弟方法：`self->other()` → `_self->__<trait>_vptr->other(_self)`；
  - 字段链：`self->field->m()` → `_self->field->__<trait>_vptr->m(_self->field)`（可递归，见 §4.5）；
  - 方法参数：`o->m()` → `o->__<trait>_vptr->m(o)`、`v.m()` → `v.__<trait>_vptr->m(&v)`；
  - 方法体内局部变量：`P q; q.m();` → `q.__<trait>_vptr->m(&q)`。
  - **同名跨 trait**：宿主 `use` 的多个 trait 都声明方法 `f` 时，裸调用 `s.f()` 按 `use` 顺序**取第一个**
    匹配（`s.__<首个 trait>_vptr->f(&s)`）。顺序即语义，属**已知限制**；要调用另一个实现，需把 `s`
    装箱成目标 trait 的接口值（`struct B_iface x = B_of(&s); x->f();`）或改名。
- 只要某个方法体会产生派发，就会在方法函数之前先输出一行前向声明
  `static struct <Trait>_vtbl <Struct>_<Trait>_vtable;`，以解决 vtable 变量的前向引用
  （C 的 tentative definition，随后再带初始化式定义，合法）。
- vtable 初始化项按 **trait 中方法的声明顺序**排列，而不是 impl 中的书写顺序。
- 跨单元（ct-ast `build` 模式）：当 trait 与 struct **都标 `pub`** 时，vtable 改为外部链接——声明单元的
  头文件发射 `extern struct <Trait>_vtbl <Struct>_<Trait>_vtable;`，实现单元给出定义，消费单元可直接装箱。
  其它情况仍为 `static`，且同一对 `struct`/trait 的 `impl` 必须位于同一编译单元。

#### 4.4 变量声明 → 限定 `struct` + 追加 vptr 指定初始化

```c
Person p = { .name = "Tom", .age = 36 };
```

```c
struct Person p = { .name = "Tom", .age = 36, .__greeter_vptr = &Person_Greeter_vtable };
```

规则：

| 源码形态 | 处理 |
| --- | --- |
| `Person p = { … };`（指定初始化） | 前缀 `struct `，并在 `}` 前追加 vptr 指定初始化项 |
| `Person p = { "Tom", 36 };`（位置式初始化） | 同上：追加的 vptr 项接在位置式元素之后（C99 允许 `{ 1, .v = 0 }` 混用） |
| `Person p = {};` / `Person p;` | 前缀 `struct `；空列表追加 vptr，无初始化式则补上 `= { <vptr> }` |
| `struct Person p = { … };` | 同上（已有限定符时不重复添加） |
| `static Person p;` / `static Person ps[2];` | 前缀 `static` 原样保留，其余与非 `static` 声明相同（对象补初始化式、数组走 `__ct_init`） |
| `Person *p = …;` | 前缀 `struct `，其余原样输出；指针变量**登记为指针**，故 `p->m()` 会重写为 `p->__t_vptr->m(p, …)` |
| 其它类型 | 完全不动 |

被识别为「结构体类型变量」的名字会登记进变量表，供后续方法调用重写使用。

#### 4.5 方法调用重写

```c
p.greet();
p.greet_name("Jerry");
```

```c
p.__greeter_vptr->greet(&p);
p.__greeter_vptr->greet_name(&p, "Jerry");
```

触发条件（满足 1 或 1′，且 2–4 全满足才重写）：

1. 左边是一个标识符，且它在**本文件此前**已被登记为某 struct 类型的变量（`T x`、`T *x`、
   `T x[n]`、`T *x[n]` 均可）；**或**
1′. 左边是一次调用 `f(...)`，且 `f` 的返回类型是**此前已登记的 struct**（值返回或指针返回均可，
   如 `f().m()`、`mk()->m()`、`f().a.b.m()`）；
2. 若该变量是数组或指针，其后可先跟一个下标 `[<表达式>]`（表达式可为任意平衡内容，例如
   `ps[i]`、`ps[i + 1]`、`ps[f()]`）；
3. 之后是 `.`、`->`，或一串字段跳（每跳 `.field` / `->field`），且**最终**成员名是（跳转后那个
   struct 的）某个 trait 的**方法名**；
4. 成员名后紧跟 `(`。

方法归属的判定顺序：按该 struct `use` 子句中的 trait 顺序查找，**取第一个**声明了该名字的 trait。

重写细节：

- 形如 `x.m()` 的无参调用 → `x.__t_vptr->m(&x)`（不产生多余逗号）。
- 形如 `x.m(a)` → `x.__t_vptr->m(&x, a)`。
- 指针接收者不补 `&`：`p->m()` → `p->__t_vptr->m(p)`，`p->m(a)` → `p->__t_vptr->m(p, a)`。
- 数组元素 / 指针下标：`ps[i].m()` → `ps[i].__t_vptr->m(&ps[i])`；`T *ps[n]` 的元素**自身是指针**，
  故 `ps[i]->m()` → `ps[i]->__t_vptr->m(ps[i])`；而 `T *p` 上的 `p[i]` 是值，补 `&`。
- 指针字段链按**每跳字段是否为指针**决定 `.` 或 `->`，末跳经指针则不补 `&`：
  `a.next->m()` → `a.next->__t_vptr->m(a.next)`；`a.next.m()`（`next` 是值字段）→ `a.next.__t_vptr->m(&a.next)`。
- 参数内部的嵌套调用会被继续处理：`q.add(1, q.add(2, 3))` → `q.__greeter_vptr->add(&q, 1, q.__greeter_vptr->add(&q, 2, 3))`。
- **右值接收者**（条件 1′）：接收者先被提升为一个临时变量，求值**恰好一次**，再按上面同一规则派发。
  临时变量名为 `__ct_tmp<N>`（`N` 在单个文件内递增，从 0 开始）：
  - 值返回：`f().m(a)` → 前一行 `struct S __ct_tmp0 = f();`，本行 `__ct_tmp0.__t_vptr->m(&__ct_tmp0, a)`；
  - 指针返回：`mk()->m(a)` → 前一行 `struct S *__ct_tmp0 = mk();`，本行 `__ct_tmp0->__t_vptr->m(__ct_tmp0, a)`。
  - 提升**只允许**在两种位置：接收者位于**语句行首**（`f().m();`），或位于**赋值 / 声明初始化式的
    右值行首**（`int r = f().m();`）。这两种位置求值无条件且有序，提升到前一行**不改变语义**。
  - 接收者出现在其它位置（如 `x = 1 + f().m();`、`g(f().m());`）时无法在不改变求值顺序的前提下重写，
    **按 `文件:行:列: error:` 报错退出**，而不是产出明知编不过的 C。
  - 提升出的临时变量声明文本为等宽对齐的源行缩进；它在生成的 `.c` 中占一行。
- 字符串字面量、字符字面量、注释内的内容**永不重写**。
- `impl` 方法体与顶层代码共用同一重写管线：方法体内的 `self->m(...)`、字段链 `self->f->m(...)`、
  参数接收者 `o->m(...)`、局部变量接收者 `q.m(...)` 都按同一规则重写（见 4.3）。
- **仅变量下标接收者的表达式会被求值两次**（`ps[i]` 在产物里出现两遍），因此带副作用的下标
  （如 `ps[i++]`）不保证正确；右值接收者（1′）用临时变量，只求值一次。

#### 4.6 普通函数的签名 → 限定 struct 类型

```c
void show(Person p);
static Person make(char *n);
Person *pick(Person *a, Person *b);
```

```c
void show(struct Person p);
static struct Person make(char *n);
struct Person *pick(struct Person *a, struct Person *b);
```

规则：

| 源码形态 | 处理 |
| --- | --- |
| 返回类型里的已知 struct 名（含 `static` 等前缀词、多词类型、指针返回） | 原地插入 `struct `（其余字符原样保留） |
| 值参数 `Person p` | 插入 `struct `；**有函数体时**把参数登记进变量表（`ptr=0`），使体内 `p.m()` 可被重写 |
| 指针参数 `Person *q` | 插入 `struct `；登记为指针（`ptr=1`），使体内 `q->m()` 可被重写 |
| 函数原型 `void f(Person *q);` | 只限定类型，**不登记**参数（没有函数体） |
| 参数已写成 `struct X …` | 不重复插入 `struct ` |
| `if` / `while` / `else if` / `return …` 等语句 | 不会被误判为函数签名 |
| 参数**列表本身跨多行**的签名 | 不识别，按原样透传 |

#### 4.7 组合、数组与堆对象（构造语义）

vptr 在「构造点」写入：对象**自身**的 vptr 写进初始化式；**嵌套字段 / 数组元素 / 堆对象**改用
**声明之后的赋值语句**（避免追加的 `.field` 指定初始化覆盖用户自己写的 `.field = {…}`）。

| 源码形态 | 处理 |
| --- | --- |
| `struct Shop { Person owner; };` | 字段类型补 `struct `：`struct Person owner;` |
| `Shop s;` | `struct Shop s = { … };` 之后追加 `s.owner.__greeter_vptr = &Person_Greeter_vtable;` |
| `s.owner.greet();` | `s.owner.__greeter_vptr->greet(&s.owner);` |
| `Person ps[3];` | 声明 + 块内循环 `for (…; __ct_i < 3; …) ps[__ct_i].__greeter_vptr = …;` |
| `ps[0].greet();`、`ps[i].greet();` | `ps[0].__greeter_vptr->greet(&ps[0]);`（下标可为任意表达式） |
| `Person *ptrs[2]; ptrs[0]->greet();` | `ptrs[0]->__greeter_vptr->greet(ptrs[0]);`（元素自身是指针） |
| `struct Box { Person *who; } … b.who->greet();` | `b.who->__greeter_vptr->greet(b.who);`（指针字段链） |
| `delete q;` | `if (q) free(q);`（`q` 必须是已登记的指针变量） |

命名与限制：

- 数组展开的循环变量固定为 `__ct_i`，包在块内。
- **文件作用域的对象 / 数组**：文件作用域放不下 vptr 赋值**语句**，其 vptr 改由编译器生成的构造器
  `static void __ct_init(void) __attribute__((constructor))` 在 `main` 之前写入（决策 D5 = A）；
  对象本身照常声明，`main` 里可直接派发。
- 数组只支持 `Type name[<n>];`（无初始化式、常量下标）；需要初始化时的其它形态一律 `die`，不静默产出坏 C。
- **堆对象自动初始化**（Phase 1，D1=A）：`T *p = malloc(sizeof(struct T));`（或 `calloc`）在声明后自动写
  vptr（含嵌套值字段），不再需要手写。
- **ct 不对手写 C 里的类型名做限定**：`sizeof(Person)` 不会被改写，请写成 `sizeof(struct Person)`。

#### 4.8 接口多态（trait 作类型）

每个 trait 额外生成一个**接口值类型**（胖指针，`self` + 该对象的 vtable）：

```c
struct Greeter_iface { void *self; struct Greeter_vtbl *vt; };
```

| 源码形态 | 处理 |
| --- | --- |
| `Greeter g;` | `struct Greeter_iface g = { 0, 0 };` |
| `Greeter g = p;` | `struct Greeter_iface g = (struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable };` |
| `Greeter g = q;`（`q` 是 `Person *`） | 同上，`self` 取 `q` 本身（**不加 `&`**） |
| `g = s;` | 按 `g` 的 trait 装箱后再赋值 |
| `void announce(Greeter who);` | `void announce(struct Greeter_iface who);` |
| `announce(p);` | `announce((struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable });` |
| `Greeter pick(void);` | `struct Greeter_iface pick(void);` |
| 返回接口的函数里 `return p;` | `return (struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable };` |
| `g.greet();` | `g.vt->greet(g.self);` |
| `g.greet_name("Jerry");` | `g.vt->greet_name(g.self, "Jerry");` |

**接口作为 struct 字段**（值字段 `T x;` → `struct T_iface x;`；指针字段 `struct T *x;` → `struct T_iface *x;`）：

| 源码形态 | 处理 |
| --- | --- |
| 字段 `Node lhs;` / `struct Node *lhs;` | 字段类型展开为 `struct Node_iface lhs;` / `struct Node_iface *lhs;` |
| `s.lhs.show();` / `self->lhs.show();` | `s.lhs.vt->show(s.lhs.self);`（值字段经 `.`，字段链可递归） |
| `s.p->lhs->show();` | `s.p->lhs->vt->show(s.p->lhs->self);`（指针字段经 `->`） |
| `s.lhs = v;`（**值**接口字段） | 按字段声明的 trait 装箱：`s.lhs = (struct Node_iface){ (void *)&v, &Lit_Node_vtable };` |

规则与限制：

- 只有**变量**或 `&变量`（以及「返回同款接口」的函数调用）能装箱；类型无法推断 → `die`。
- 装箱的目标 trait 由**声明/赋值的左值**或**当前函数返回类型**决定；实参则由**函数签名表**决定，
  因此遵循「定义先于使用」——调用点看不到签名或看不到具体类型时不会装箱。
- 被装箱的 struct 必须 `use` 了该 trait；跨 trait 装箱 → `die`。
- **不做**隐式空检查：空接口值（`{0,0}`）上派发会崩，与 C 一致。
- **L0 限制（本文所述）**：接口**数组**不支持，声明即 `die`；接口字段**不参与**构造点递归，`Node lhs;`
  声明后为空（`vt == NULL`），需自行赋值；装箱仅覆盖**语句赋值**（`s.lhs = v;`），**指定初始化式**
  （`Pair p = { .lhs = v };`）中的接口字段**不装箱**；**指针**接口字段（`struct T *x`）只支持派发，
  赋值保持原样（需要已有胖指针的地址，如 `s.x = &someIface;`）。
- **CT 侧（L2）已扩展**：`selfhost/l2/**` 放开上一条的全部限制，并给出统一的「接口值 / 指向接口值的指针 / 接口值数组 / 接口指针数组」模型；装箱规则在**赋值、构造点、`return`、实参**四处完全一致：

| 形态 | 含义 | 派发 | 下标元素的种类 |
| --- | --- | --- | --- |
| `T x` | 接口值（胖指针） | `x.m()` → `x.vt->m(x.self)` | — |
| `T *x` | 指向接口值的指针 | `x->m()` → `x->vt->m(x->self)` | `x[i]` 是**值**（`x[i].m()`） |
| `T xs[n]` | 接口值数组 | `xs[i].m()` → `xs[i].vt->m(xs[i].self)` | 值 |
| `T *xs[n]` | 接口指针数组 | `xs[i]->m()` | 指针 |
| 形参 `T xs[]` / `T *xs` | 同上，函数体内可下标 | 同左 | 值 |

  另有：接口**数组字段**（`Node items[4]`、`self->items[i].eval()`）、指针接口字段的下标（`s.f[0].m()`）、**构造点**装箱（`Pair p = { .l = v, .ptr = &v };`，值字段与指针字段各走各的 box 路径）、以及**堆对象装箱**（`Num *p = malloc(sizeof(struct Num)); Expr e = p;`）。**仍不支持**：带聚合初始化式的接口指针（`T *g = { ... };`）。**struct 类型的数组字段**（`struct Duo { Num ab[2]; }`）L0 / L2 不支持，**ct-ast 已支持**（逐元素写 vptr，见 §6）。理由同顶部状态说明：本文对 L0 依旧准确，新能力只属 CT 线（L2 / ct-ast），由 `test/acceptance/run.sh` 钉住。

#### 4.9 AutoDrop（Phase 5 新增，仅 CT 线）

`own` 是一个**上下文关键字**，只出现在声明行的行首：它把变量标记为「持有对象生命周期」，
编译器在作用域出口自动释放。它是 Phase 5 新增项，**L0（`ctc.c`）不认识它**（会原样透传），
由 CT 线实现：L2（`selfhost/l2/**`，冻结 oracle）与 ct-ast（安装入口）。两者在出口注入的**位置要求**上
自 v0.16.0 起不同，见下表与约束。

| 源码形态 | 处理 |
| --- | --- |
| `own Person *p = malloc(sizeof(struct Person));` | 去掉 `own` 后照常声明；登记 autodrop |
| 声明作用域的闭合 `}`（行首） | 在该行之前插入 `if (p) { Person_Drop_drop(p); free(p); p = 0; }` |
| 每个 `return` 之前（L2 要求行首；ct-ast 无位置要求） | 同上，插入全部 autodrop 变量的释放（声明逆序） |
| `delete p;` | 既有的 `free`/`drop` 照旧；同时取消 autodrop（不重复释放） |
| `p = …;`（重新赋值） | 取消 autodrop（所有权已转移，不再兜底） |
| `p` 以**独立值**形式出现在赋值右值（`q = p;`）或 `return` 的返回表达式中 | 取消 autodrop（逃逸）；读取字段 / 元素（`x = p->n;`、`x = p[0];`）**不**算逃逸 |

约束与限制：

- 只支持 `own T *p = malloc|calloc(...);`：必须是**结构体指针**、必须由 `malloc` / `calloc` 初始化、
  且该 struct 必须 `use Drop`；否则编译期报错。
- `own` 只允许出现在**函数体内**（文件作用域报错）；不支持数组形态（`own T *ps[n]`）。
- 同一作用域的多个 `own` 变量按**声明逆序**释放。
- L2 要求闭合 `}` 与 `return` 位于**行首**；行内形式（`b->n = 1; }`、`if (p) return 0;`）编译期报错，
  不静默跳过——逐行注入无法把释放语句安全地放进条件分支。**ct-ast 只对 `}` 有该要求**：`return`
  无位置要求，分支内与行内的 `return` 都会在它之前注入（v0.16.0 起，见 §4.40）。
- `goto` 跳出声明作用域不会触发释放。
- `static` 局部变量不能是 `own`（`a static local cannot be 'own'`）：静态对象的生命期不归作用域管。
- 逃逸判定是**保守**的：变量以独立值形式出现在赋值右值或 `return` 行上即取消 autodrop；漏放（内存泄漏）
  优于错放（重复释放 / 释放借用对象）。

#### 4.10 `map`（Phase 11 新增 + SH-20 扩展，仅 ct-ast）

`map` 把一个 trait 的方法绑定到一处具体的 C 调用，并为该绑定发射包装函数与一张 vtable。宿主有两种
形态；**Phase 11.2 已把两者接入派发**——被当作 trait 接口值使用时（赋给 `T` 类型的变量、传给 `T`
接口参数、从接口返回、或作为函数实参），装箱会使用绑定的 vtable，从而作为该 trait 的实例运行：

- **对象宿主**：`map trait T for instance x { … }`，`x` 是已声明的全局变量，接口值的 `self` 指向它。
- **命名空间宿主**（SH-20）：`map trait T for namespace A::B { … }`，绑定的是命名空间里的一组函数，
  没有对象可挂，接口值的 `self` 为 `NULL`。

`map` 是 Phase 11 新增项，**L0 与 L2 都不认识**，只由 **ct-ast**（`selfhost/ct-ast/main.ct`）支持。

**零成本静态映射（第三十八批，已实现）**：`.m.ct` 编译期映射单元、静态 trait、命名空间静态调用
`host::Trait.method(…)` 与类型宿主 `map trait T for type <ctype>`——绑定在**调用点**直接展开为裸 C
调用，不生成 wrapper / `_iface` / `_vtbl` / vtable，跨单元同样零成本。规格见
[design/batch38-map-unit/spec.md](history/design/batch38-map-unit/spec.md)。本节其余内容描述动态 `map`，
其产物与行为不变。

```c
trait Controller {
    int send(char *buf, int len);
}
struct Uart { int fd; };
struct Uart uart1;                                    /* 对象宿主：必须是已声明的全局变量 */

map trait Controller for instance uart1 {
    send(buf, len) -> mock_uart_send(&uart1, buf, len);
}

namespace hal;
pub trait Writer { int write(char *buf, int len); }
int hal_write(char *buf, int len) { return len + buf[0]; }

map trait Writer for namespace hal {                  /* 命名空间宿主：没有对象 */
    write(buf, len) -> hal_write(buf, len);
}
Writer w = Writer::hal;                               /* 装箱：self 为 NULL，vt 指向 hal_Writer_vtable */
```

符号命名：宿主路径把 `::` 换成 `_` 得到 `h`，trait 的 C 名记为 `tr`；若 `tr` 已经以 `h_` 开头则
`p = tr`，否则 `p = h_tr`。包装函数是 `p_<方法>`，vtable 是 `p_vtable`。对象宿主的 `h` 是实例的
C 名（如 `uart1`），命名空间宿主的 `h` 是宿主路径（如 `hal`）。

| 产物 | 规则 | 示例 |
| --- | --- | --- |
| 包装函数 | `<宿主>_<Trait>_<方法>`，首参 `void *self`（体内 `(void)self;`）；对象宿主的**直绑不生成**，命名空间宿主**必然生成** | `static int uart1_Controller_send(void *self, char *buf, int len)`；`static int hal_Writer_write(void *self, char *buf, int len)` |
| vtable 变量 | `<宿主>_<Trait>_vtable`，指定初始化 `.方法 = 包装函数`（直绑时为被绑定的 C 函数本身） | `static struct Controller_vtbl uart1_Controller_vtable = { .send = uart1_Controller_send };` |

约束与限制：

- `for` 之后只能跟 `instance` 或 `namespace`，其它写法编译期报错。
- 对象宿主的 `x` 必须是**已声明的全局变量**（文件作用域），否则编译期报错。实例名可写成**命名空间
  限定形式** `A::B::h`（2b.3）；全局按命名空间 mangling（见 §4.11），实际绑定的 C 名是 `A_B_h`，
  实例的 vtable 与包装函数也以它为前缀（`A_B_h_T_vtable`）。
- **不合成宿主**：编译器不会替未声明的名字合成对象（拼写错误会变成静默的宿主）。没有对象可挂时用
  **命名空间宿主**（`map trait Writer for namespace hal { … }`），而不是伪造 `void *netlib;` 占位变量
  ——后者仍可用，但已不必要。
- 命名空间宿主的路径逐段写 `A::B`。装箱 `T::A::B` 在找不到对应 map 时报
  `no map binds trait 'T' to namespace '<宿主路径>'`（`<宿主路径>` 按源写法回显，如 `nosuch` / `a::b`）。
- 命名空间宿主**不接受直绑**：没有 `self` 可以交给被绑函数，`-> fn;` 会被拒绝
  （`a namespace host has no self: bind with a wrapper call`）。
- 命名空间宿主的装箱语法是 `Trait::ns`，且**只能作为接口值**使用；放进其它上下文（如 `int x = Writer::hal;`）
  报 `a namespace host value is only usable as an interface value`。`Trait::ns(...)` 仍是限定调用，不产生装箱。
- `T` 必须是已定义的 trait；无 vtbl 的 trait 不可映射。
- 绑定方法名必须是 `T` 的既有方法，`( … )` 里的参数个数须与 trait 声明一致。
- 绑定必须覆盖 `T` 的**每一个**方法，且每个方法**只绑一次**：漏绑会让 vtable 留一个空指针槽（调用即崩溃），
  重复绑定会发射两份同名包装函数（C 重定义）；两种情况都在编译期报错。
- `->` 右侧（CALL）是**两级绑定**：
  - **直绑**：调用名是裸 C 函数名（纯标识符）时零生成，vtable 槽直接指向它；直绑不校验签名，
    被绑函数必须自行满足 trait 的槽类型（首参 `void *`）。命名空间宿主禁用直绑（见上）。
  - **fallback**：调用含表达式或成员路径时生成宿主级包装函数。每个实参按标识符逐个校验：字符串 / 字符
    字面量、数字字面量、`.` / `->` 后的成员名、`A::B` 限定名直接放行；其余标识符必须是左括号内的形参名、
    本 map 的实例、此前已声明的变量或 ALL_CAPS 宏，否则编译期报错。
- 多个 map 可作用于同一实例或同一命名空间；`MAX_MAPS`（64）是 map 构造总数上限，超限报错。
- **跨单元**：vtable 在 `pub` trait 且（对象宿主）实例是有 `pub` 全局时外部链接（同 §4.11 的 impl 规则）；
  命名空间宿主没有实例，只看 `pub` trait。头文件声明 `extern`、声明单元给出定义，其它单元可直接装箱。
  否则包装函数与 vtable 发射在**声明该 map 的单元**的 `.c` 里（`static`），不会重复出现在其它单元。
- **派发（11.2 / SH-20）**：对象宿主装箱用**实例级** vtable——
  `Controller c = uart1;` → `c = (struct Controller_iface){ (void *)&uart1, &uart1_Controller_vtable };`
  （注意不是 struct 级的 `&Uart_Controller_vtable`）。因此**即便 `Uart` 未 `use Controller`**，
  `uart1` 也能作为 `Controller` 实例使用。命名空间宿主装箱写成
  `Writer w = Writer::hal;` → `w = (struct hal_Writer_iface){ (void *)0, &hal_Writer_vtable };`。
  此后 `c.send(...)` / `w.write(...)` 都经 `<接口>.vt->方法(<接口>.self, ...)` 派发到包装函数；
  命名空间宿主的 `self` 恒为 `NULL`，被绑函数不得解引用首参。
- `--emit-map` 的 JSON 新增 `maps` 字段，逐条列出 trait / instance / file / line 与 `bindings`
  （method → 生成符号）；每个 map 另有 `"host": "instance"|"namespace"` 标明宿主形态，
  每个 binding 还有 `"wrapper": true|false` 区分 fallback 与直绑。

**静态映射（第三十八批，仅 ct-ast）**

`.m.ct` 是**映射单元**：只允许 `namespace`、`import`、`#include` / `#define`（prologue）、`pub trait`
（只写抽象方法）、`map` 与 `_Static_assert`；函数 / 全局 / 类型声明、`impl` 与对象宿主都报错。它
**不产生任何产物**（无 `.c` / `.h`、不进末尾 `cc` 行、不写缓存），只能在 `ct build` 里被 import；
`ct compile` 直接拒绝 `.m.ct` 输入。同一 root 下同名 `foo.h.ct` 与 `foo.m.ct` 并存时报 import 歧义；
映射单元只能 import 另一个映射单元。

三种单元的产物与用法：

| 后缀 | 发布 `.h` | 可 import | 可单独 build | 用途 |
| --- | --- | --- | --- | --- |
| `<name>.ct` | 否 | 否 | 是 | 实现 / 入口；接口写在同目录的 `.h.ct` |
| `<name>.h.ct` | 是 | 是 | 是 | 发布类型、`pub` 声明与 vtable 接口 |
| `<name>.m.ct` | 否 | 是（映射单元之间） | 否（`ct compile` 直接拒绝） | 静态映射 recipe |

`import` 的搜索顺序：先 importer 所在目录，再按 `-I` 顺序逐个 root；每个 root 先探 `<name>.h.ct`、
再探 `<name>.m.ct`，两者都没有才回落到 `<name>.ct` 并报
`only a .h.ct unit can be imported: rename 'x.ct' to 'x.h.ct'`。

`.h.ct` 文件名与其中的**主类型**同名（`Parser.h.ct` ↔ `struct Parser`，入口 `main.ct` 例外）是
**仓库约定**、不是编译器规则：`selfhost/check-ast.sh` 的 unit-name lint 只扫描 `selfhost/ct-ast/**`，
用户工程不受检查。

声明在 `.m.ct` 里的 `pub trait` 自动是**静态 trait**：没有 `_iface` / `_vtbl` / vtable，不能 `impl`、
不能进 `use`、不能作类型、不能装箱（`T::host`），也不能带默认体。

两类宿主：

- **命名空间宿主**：`map trait T for namespace A::B { m(p…) -> callee(…); }`，trait 必须声明在
  宿主命名空间内；调用写成 `A::B::T.m(args)`，直接展开为 recipe 里的 C 调用（无接收者、无 `self`）。
- **类型宿主**：`map trait T for type <ctype> { m(recv, p…) -> callee(…); }`，首个绑定参数是接收者，
  trait 方法本身不声明它；绑定参数个数 = 方法参数个数 + 1。调用 `value.m(args)` 时按接收者的静态
  类型（数组先 decay 成元素指针）做规范化文本比较，命中后把 `recv` 换成接收者表达式；普通
  struct / 接口方法优先，查找失败才回退到类型宿主，多个候选报歧义。

recipe 替换（逐出现点）：

| recipe 写法 | 生成的 C |
| --- | --- |
| `p`（值位） | `(<actual>)` |
| `&p`（后接的不是 `[`） | `&(<TP>){<actual>}`（C99 compound literal） |
| `&p[…]` | `&((<actual>)[…])` |
| `sizeof p` | `sizeof(<TP>)`（不求值） |
| `p.field` / `p->field` / `p[i]` | `((<actual>).field)` / `((<actual>)->field)` / `((<actual>)[i])` |
| 参数没有求值出现 | 调用式前缀 `(void)(<actual>), `（按绑定参数顺序） |
| `p++` / `p--` / `p = …` / `p += …` | 编译期报错 |

一个参数最多一次求值出现；出现多次时实参必须是可重复表达式（字面量、变量或它们的稳定成员
链），否则要求先提局部变量。`<TP>` 是该绑定参数的声明类型（类型宿主的接收者是 `host_type`）。
`sizeof` 后只接受不加括号的绑定参数（`sizeof p`）；`sizeof(p)` 会替换成实参值的大小，故作为
编译期错误拒绝（`map recipe takes 'sizeof p', not 'sizeof(p)'`）。

`.m.ct` 的 prologue（`#include` / `#define`）按整行去重后展开进**消费者** `.c` 顶部（banner 之后），
消费者不写这些 `#include` 也能编译；消费者 `.h` 不含 prologue。`ct compile` 不解析 import，
故不参与展开。

**伴随 C shim（第三十九批，仅 ct-ast）**：映射单元可以让同目录同名的 C 文件承担 recipe 写不出的
形状——宏 / 语句宏、全局量（`errno` / `stdin`）、需要类型转换的调用、变参前缀转发、无 userdata 的
回调。约定是 `<base>.shim.h` 与 `<base>.shim.c`（两个都可选，但**有 `.shim.c` 就必须有
`.shim.h`**，否则报 `a shim source needs a matching .shim.h: <头路径>`）。

- 编译器只为 `.m.ct` 探测 shim（`foo.h.ct` / `foo.ct` 旁的 `foo.shim.h` 被忽略）；命中的文件必须是
  可读普通文件，否则报 `a shim header is not a readable file` / `a shim source is not a regular file`。
- 两个映射单元的 shim 同名但目录不同 → 构建失败：
  `ctc: shim base name '<base>' is ambiguous: <dir1> and <dir2>`（不静默取先命中者）。
- 消费者的生成 `.c` 自动出现 `#include "<base>.shim.h>"`（在该单元的 prologue **之前**，按整行
  去重）；shim 头按**文件名**解析，`ct build` 因此在该 `cc` 行打印 `-I <shim 目录>`（同一目录
  只一次）。
- 存在的 `<base>.shim.c` 直接列入同一条 `cc` 行的源文件（不复制、不进产物目录），头文件式 shim
  只增加 `-I`。
- shim 两文件的 `mtime.size` 折叠进映射单元的缓存 key，任一方变化都会重建消费者。
- `.m.ct` 仍然零产物；shim 不是生成物，也不是编译器构建步骤。

`--emit-map` 的静态条目带 `"static": true`、`"host": "namespace"|"type"`、类型宿主另有
`"type": "<ctype>"`，每个 binding 带 `"inline": true`、`"wrapper": false` 与 `"symbol": <callee>`；
带 shim 的静态条目还带 `"shim": {"header": "<path>", "source": "<path>"}`（无 `.shim.c` 时省略
`source`）。动态 `map` 的字段与取值不变。

#### 4.11 跨单元链接：`pub` 全局与 `extern`（ct-ast）

- `pub int g_counter = 5;` 在其定义单元的 `.c` 里发射定义，在该单元的 `.h` 里发射 `extern int g_counter;`；
  其它单元 `import` 后即可按名引用。`pub` 只表示导出：未标 `pub` 的全局仍只属于本单元。
- `extern int lib_flag;` 只声明、不定义：声明进入 `.h`，本单元的 `.c` 不发射定义，符号由外部 C 目标文件
  或库提供。`extern` 不能带初始化式（编译期报错）。`extern` 同样接受函数原型
  （`extern int lib_fn(int);`）：只声明、不定义，`pub extern` 的原型进入 `.h`；`extern` 的名字不参与
  mangling，因为它指向 C 库的符号。
- 导出的类型（`pub struct` / `pub trait` / `pub typedef`）在命名空间内仍可**用裸名**引用：消费者写
  `Writer w;` 或 `struct Uart u;`，编译器解析到 `hal_Writer` / `hal_Uart`。两个被导入的命名空间导出同名
  类型时，裸名报错并要求用别名 import（`import a::b::T as T;`）。类型的**限定写法**（`struct A::B`）仍不支持。
- 命名空间内的全局变量按命名空间 **mangling**：`namespace A::B; int h;` 的 C 名是 `A_B_h`，因此两个命名空间
  可以各有一个 `h` 而不会在链接期冲突。`extern` 是例外——它声明的符号由 C 库提供，保留原名与空命名空间。
- 导入单元可以用**限定名**引用导出的全局：`a::h` 读写 `a_h`；只有一个候选时裸名同样可用。若两个被导入的
  命名空间导出同名全局，裸名会被拒绝并提示改用限定名，避免静默选错对象。
- 跨单元可装箱的边界：`impl` 的 vtable 仅在 **`pub` trait 且 `pub` struct** 同时成立时外部链接——
  头文件声明 `extern struct T_vtbl S_T_vtable;`，实现单元给出定义（不再是 `static`）；否则保持单元私有。
  同一 `struct` 的同一 trait 只能有一个 `impl`，重复定义在编译期报错并指出首个定义所在位置。

#### 4.12 函数指针（ct-ast）

声明位置支持 `ret (*name)(params)`：参数、struct 字段、全局与局部。生成 C 与源码同形，名字留在类型内部。

```c
int (*p)(int);
struct Box { int (*op)(int); };
static int apply(int (*fn)(int), int v) { return (*fn)(v); }
```

- `typedef` 可用：`typedef int (*BinOp)(int, int);` 发射为 `typedef int (*BinOp)(int, int);`，
  别名可作局部、参数与 struct 字段；typedef 一个函数指针数组同理（`typedef int (*Table[2])(int, int);`）。
- 函数指针数组把维度写进声明子内部：`int (*tbl[2])(int, int);`。全局可带初始化器
  （`static int (*tbl[2])(int, int) = { plus, minus };`），局部可逐元素赋值，struct 字段同样支持
  （`int (*cb[2])(int);`）；`tbl[i](x)` 直接调用。
- 文件作用域的初始化器可以命名本单元的函数（`static int (*gp)(int, int) = plus;`）：原型先于全局发射。
- 赋值接受 `p = handler;` 与 `p = &handler;`；函数名作为右值时发射其 C 名。`#include` 引入的库函数
  同样可用（`p = strcmp;`）：CT 符号表里没有的名字原样发射，由 C 编译器按原型校验；普通调用一直如此。
- 调用接受 `p(args)` 与 `(*p)(args)`，两种写法统一发射为 `(*p)(args)`。函数指针字段可以直接调用：
  `c.add(2, 3)`（`.`）与 `p->add(2, 3)`（`->`）分别发射为 `c.add(2, 3)` 与 `p->add(2, 3)`。
- 限制：不返回函数指针；不支持嵌套函数指针（`int (**f)(int)` 报
  `nested function pointers are not supported`）；函数指针数组不能作参数（报
  `function-pointer arrays are not supported as parameters`）；一条声明只写一个名字
  （`int (*a)(void), (*b)(void);` 报错）。

#### 4.13 `switch` 与 `do-while`（ct-ast）

```c
switch (key) {
case 1:
    out = 10;
    break;
case 2:
case KIND_B:                  /* 两个标签共享下一段语句 */
    out = 20;
    break;
default:
    break;
}

do {
    total = total + i;
    i = i + 1;
} while (i < 4);
```

- 一个标签拥有从自身到下一个标签（或 `}`）之间的语句，因此 `case` 与它后面的 `break` 同处一级缩进；
  连续的 `case 1: case 2:` 共享下一段语句，中间可以没有语句。
- `case` 的取值是任意整数常量表达式：数字、字符字面量、枚举成员、`#define` 常量、括号与算术 / 位运算、
  一元 `- ! ~`、`sizeof`、`offsetof`，一律原样发射并由 C 折叠，因此 `case (1 << 2):` 与 `case 1 + 2:` 都合法。
  表达式里出现普通变量（`case key + 1:`）报 `a case label must be an integer constant`；
  整棵树就是单个名字（宏名或已声明全局）时始终放行。
- `switch` 体可以直接写声明，但**不能**紧跟在标签之后（C 的标签不构成作用域）：
  `case 1: int x;` 报 `a declaration cannot follow a case label; wrap it in a block`；
  标签后直接就是 `}` 报 `a case label needs a statement`。
- `switch` 体内的 `own` 被拒绝（`own is not supported inside a switch`）：一个 case 可能被跳过、也可能贯穿，
  按顺序块假设的释放点不成立，留待所有权分析支持 case 可达性。
- `do-while` 的体可以带花括号，也可以只写一条语句；`while (...)` 之后必须写 `;`，否则报
  `a do statement must be followed by while (...)`。
- `case` / `default` 出现在 `switch` 体之外（包括 `switch` 体内的嵌套块）报
  `a case label is only allowed inside a switch`。
- 重复的 case 值原样发射，由 C 编译器报错；`case 1 ... 5:` 范围标签见 §4.25。

#### 4.14 `enum`、常量表达式与 `offsetof`（ct-ast）

```c
enum Color { RED, GREEN = 5, BLUE, };

typedef enum Mode { Fast, Slow } Mode;

struct Point { int x; int y; };
typedef struct Pair { int a; int b; } Pair;

int off = (int)offsetof(struct Point, y);
```

```c
enum Color {
    RED,
    GREEN = 5,
    BLUE
};

typedef enum Mode {
    Fast,
    Slow
} Mode;

/* struct Point / Pair 的定义不变；offsetof 原样发射 */
int off = (int)(offsetof(struct Point, y));
```

- 顶层 `enum Tag { … }` 的标签必填（缺标签报 `expected an enum name`），花括号紧跟其名，没有前置声明形式；
  允许尾逗号。同一命名空间内重复的标签报 `duplicate enum 'Color'`。
- `typedef enum [Tag] { … } Alias;` 两种写法都接受：有标签时 `enum Tag` 与 `Alias` 都是类型名。
- 类型名与 struct 同规则：`enum Color c;` 与裸名 `Color c;` 等价，前者发射 `enum <C 名>`，裸名由编译器补回 `enum` 前缀。
- 每个成员都是文件作用域的 `int` 常量，命名空间 mangling 与全局变量相同（`namespace a::b;` 里的 `RED` 发射为 `a_b_RED`）。
- 成员初值必须是整数常量表达式，否则报 `an enum value must be an integer constant`。初值不做折叠，
  `GREEN = RED + 1` 原样发射；无初值的成员不发射 `= …`，自增语义交给 C。
- `pub enum` 的声明进入依赖单元的生成头文件，成员作为常量导入消费单元：裸名 `Mid` 与限定名 `app::High` 都能用。
- `offsetof(<struct 类型>, <字段>)` 是**内建**（CT 没有预处理器，无法把它当宏）：第一个参数接受 `struct S`
  与 typedef 别名；编译器校验结构体存在且字段存在，否则报 `offsetof needs a struct type` /
  `struct 'S' has no field 'f'`（前向声明的结构体字段未知，放行交给 C）。
- 生成物按原样发射 `offsetof(struct S, f)`，因此**源文件必须自己写 `#include <stddef.h>`**——
  生成物只透传源文件里的 `#include`，不会替它补。

#### 4.15 `union`（ct-ast）

```c
union Value { int i; char c; long long ll; };

typedef union Tagged { int i; char c; } Tagged;

typedef union { int a[2]; long long ll; } Wide;

struct Holder { int tag; union Value v; };
```

- `union` 与 `struct` 是同一套记录文法：标签必填的前置声明形式相同（`union Value;` 也接受），
  `typedef union [Tag] { … } Alias;` 两种写法都接受，允许尾逗号，`};` 与 `}` 都可收尾。
- 标签与 struct 标签共享一张表但**类型类别不同**：`union Value v;` 与裸名 `Value v;` 等价，
  前者发射 `union <C 名>`，裸名由编译器补回 `union` 前缀。命名空间 mangling 同 struct。
- `pub union` 的声明进入依赖单元的生成头文件，消费单元按裸名引用。
- **没有 `use` 子句**：union 的成员共享同一块存储，追加 vptr 字段会与用户成员冲突，因此
  `union Value { … } use Greeter;` 报 `a union cannot use a trait`。同一标签的第二个函数体报
  `duplicate union 'Value'`。
- `offsetof` 同样接受 union 类型（`offsetof(union Value, c)`），字段校验与 struct 共用一套代码；
  字段缺失报 `union 'Value' has no field 'd'`。
- 既无标签也无别名的**顶层**记录定义（`union { int a; float b; };`）没有可引用的类型名，
  不在本文描述的范围内；作为**成员**出现的匿名 struct / union 见 §4.18。

#### 4.16 `goto` 与标签（ct-ast）

```c
static int find(int n) {
    int i;
    int found;

    found = -1;
    for (i = 0; i < n; i++) {
        if (i * i == 9) {
            found = i;
            goto done;
        }
    }
done:
    return found;
}
```

- 语句层接受两条 C 的跳转形式：`goto <label>;` 与 `<label>:`。生成物同形：标签独占一行，
  `goto` 原样发射。
- 标签是**函数作用域**：同一函数内重复的标签报 `duplicate label '<name>'`（即使分处不同的块）；
  `goto` 的目标必须出现在同一个函数里，否则在函数体解析结束时报
  `label '<name>' is not defined`（位置指向那条 `goto`）。不同函数可以复用同名标签。
- 标签拥有语句链，规则与 `case` 相同：从标签到下一个标签（`goto` 标签 / `case` / `default`）或 `}`
  之间的语句都属于它，发射时整条链缩进一级。连续的标签（`again: done:`）允许，第一条标签拥有第二条：
  发射为嵌套标签，语义不变。因此 `goto` 既可以向后跳（手写循环），也可以向前跳出
  多层循环或 `switch`。
- 标签后不能直接跟声明（C 的标签不构成作用域）：`again: int x;` 报
  `a declaration cannot follow a label; wrap it in a block`，把声明包进块即可。
- 标签不能直接碰 `}`（C99 要求标签后面必须有一条语句）：`again: }` 报 `a label needs a statement`。
  最省的写法是空语句 `again: ;`（见 §4.21）。
- `goto` 可以跳入 / 跳出块与循环（C 允许）。`goto` 跳出 `own` 的声明作用域**不会**触发自动释放（§4.9）。
- 一个函数最多 64 个标签与 64 条 `goto`，超出报 `too many labels in one function` /
  `too many gotos in one function`。
- 已知边界：`out:` 直接接 `case 2:` 不在子集内——标签链在 `case` / `default` 处终止，链空即按上面
  的「标签需要一条语句」报错。

#### 4.17 位域（ct-ast）

```c
struct Flags {
    unsigned a : 3;
    unsigned b : 5;
    unsigned : 4;            /* 填充位：无名 */
    unsigned c : 8;
};

typedef struct {
    unsigned kind : 2;
    unsigned size : 6;
} Header;
```

- 字段可以带位宽：`<type> [name] : <宽度>;`。`struct`、`union`、`typedef struct { … }` 的匿名体
  以及 `pub` 版本都支持。
- 宽度是整数常量表达式，规则与 `case` 取值相同：数字、字符字面量、枚举成员、宏名、括号与算术 /
  位运算、一元 `- ! ~`、`sizeof`、`offsetof`。宽度**不做折叠**，原样发射，因此
  `unsigned nib : NIBBLE;`（宏为 `(1 << 2)`）与 `unsigned m : (2 + 2);` 都成立。表达式里出现
  变量（`a : (w + 1)`）报 `a bit-field width must be an integer constant`；整棵树就是单个名字时
  始终放行（可能来自 `#define`）。缺宽度报 `expected a bit-field width`。
- 名字可以省略：`unsigned : 4;` 是填充位。空名不进成员查找，不影响同 struct 的其它字段。
- 位域必须是整数类型：指针（含函数指针）与显式 `struct` / `union` 类型报
  `a bit-field must have an integer type`；typedef 别名放行，由 C 编译器判断。
- 不能是数组：`int a[2] : 3;` 报 `a bit-field cannot be an array`。
- 一条声明可写多个声明符：`unsigned a : 3, b : 5;`，与普通字段的 `int lo, hi;` 同一文法。
- 位域不写入 `structs[]` 的维度槽，因此成员访问的类型推断、普通字段的 `offsetof` 与 vptr 追加
  都不受影响；带 `use` 的 struct，vptr 字段排在该 struct 的所有位域之后。
- `offsetof` 取位域在 C 里是未定义行为，不做特殊处理。

#### 4.18 匿名成员（ct-ast）

```c
struct Outer {
    int tag;
    union {
        int i;
        struct {
            short lo;
            short hi;
        };
    };
    unsigned bits : 4;
};
```

- 记录体内直接写 `struct { … };` 或 `union { … };`（**无名字**）就是匿名成员（C11）。它的成员名
  **提升**进外层记录：`o.i`、`o.lo`、`o.hi` 都按提升后的名字访问，`sizeof(struct Outer)` 由 C 计算。
- 可以嵌套：匿名 `union` 里再放匿名 `struct`，名字逐层提升。匿名成员里可以有位域，`use` 的
  vptr 字段仍排在外层记录的最后。
- 提升后的名字在解析期写进外层记录的字段表，因此成员访问的类型推断、`offsetof(struct Outer, i)`
  的字段校验、以及 trait 字段的 vptr 初始化（`.obj.__x_vptr`）都不需要第二套代码。
- 提升后重名（与已有具名字段同名，或两个匿名成员之间同名）报 `duplicate member '<name>'`。
- 两条拒绝的形态：`union { int i; } u;`（无名记录类型的**具名**字段）报
  `an anonymous record member cannot have a name; tag the record instead`；
  空的 `union { };` 报 `an anonymous record needs a member`。
- 匿名成员是 C11 语法：生成物照原样发射嵌套记录，用 C99 编译时需要编译器把它当扩展接受
  （`cc -std=c99` 下 clang / gcc 都不告警）。

#### 4.19 `static` 局部变量（ct-ast）

```c
static int next_id(void) {
    static int n = 0;
    n = n + 1;
    return n;
}

static const char *greeting(void) {
    static const char *msg = "hi";
    return msg;
}
```

- 函数体内可以写 `static <type> name[dims] [= init] (, name …)*;`：对象具有静态存储期，
  跨调用保持取值，未写初始化器时按 C 规则零初始化。生成物原样发射 `static` 前缀。
- 初始化器不做折叠：是否常量由 C 编译期判断（`initializer element is not constant`）。
- 声明本身与普通局部变量相同（`declare_var` 照常登记），因此成员访问、数组下标、方法调用
  的类型推断都不变；带 trait 的 struct 仍由编译器补 vptr 初始化器
  （`static struct Pair p = { .__named_vptr = &Pair_Named_vtable };`，常量地址，合法）。
- 静态对象不归作用域管，因此：`static own …` 报 `a static local cannot be 'own'`；
  static 声明**不**进入泄漏分析，`static T *p = malloc(...)` 这种刻意的单例不会被报泄漏。
- `static` 后面必须是声明：`static;` 报 `expected a declaration after 'static'`。
- 范围外：`static` 直接跟在 `case` / goto 标签之后仍按「声明不能跟在标签后」拒绝；
  `for (static int i = 0; …)` 见 §4.21。

#### 4.20 复合字面量（ct-ast）

```c
struct Point { int x; int y; };

p = (struct Point){ 1, 2 };
total = sum_point((struct Point){ 3, 4 });
tail = (struct Point){ .y = 9, .x = 8 }.y;

static struct Point make(int x, int y) {
    return (struct Point){ x, y };
}
```

- `(type){ … }` 是 C99 的复合字面量：一个**临时对象**。它可以用在赋值右侧、实参、`return`，
  也可以直接接 `.field` / `[i]` 后缀。
- 花括号里的内容按声明的初始化器处理：位置式、指定式（`.y = 9`）、嵌套花括号、字符串字面量都原样发射；
  ct-ast 不折叠初始化器，是否常量由 C 判断。
- 带 trait 的 struct 由编译器补 vptr 项：
  `(struct Pair){ 10, 20 , .__named_vptr = &Pair_Named_vtable}`。
- 类型必须是**对象类型**：`(struct P *){ … }` 报 `a compound literal needs an object type`。
- 范围外：数组类型 `(int[]){ … }`（类型文法不读 `[]`，报 `unexpected token`）；
  对复合字面量直接调 trait 方法（`((struct Pair){ … }).val()`）不支持——方法接收者的允许形态仍是
  变量 / 元素 / 调用 / 字段链，先赋给变量再调用。
- 存储期由 C 决定：函数内是自动存储期，文件作用域是静态存储期，ct-ast 不做区分。

#### 4.21 空语句与 `for` 首句的 `static`（ct-ast）

```c
for (i = 0; i < 3; i++) ;

if (n == 0) ;
else n = 1;

switch (i) {
case 3:
    ;
    break;
default:
    break;
}

for (static int i = 0; i < 2; i++) {
    total = total + 1;
}
```

- `;` 是空语句：`for (...) ;`、`while (c) ;`、`if (c) ; else …` 都可以写，
  也是「标签后必须有语句」的最省写法（`case 3: ;`、`done: ;`）。空语句不发射任何字符，
  外层块的 `{` `}` 照常输出。
- `for` 的首句可以写 `static` 声明：初始化只执行一次，变量跨调用保持取值，
  因此第二次进入同一 `for` 时直接以余值判断条件（C 的规定）。
- 空语句与 `for` 首句的 static 都不新增诊断；`static` 后面不是声明时沿用
  `expected a declaration after 'static'`。

#### 4.22 变参函数（ct-ast）

```c
#include <stdarg.h>

static int sum_all(int n, ...);

static int sum_all(int n, ...) {
    va_list ap;
    int total;
    int i;

    total = 0;
    va_start(ap, n);
    for (i = 0; i < n; i++) {
        total = total + va_arg(ap, int);
    }
    va_end(ap);
    return total;
}
```

- 参数表末尾可以写 `...`，它前面必须至少有一个具名参数（`int f(...)` 报
  `'...' needs a named parameter before it`）。声明与定义都支持，原型同样带 `...`。
- `va_list` 是内置类型词，`va_list ap;` 是普通声明，原样发射。
- `va_arg(ap, <类型>)` 是内建（第二个实参是类型，不能按普通调用解析），发射为同形调用；
  它的类型就是括号里写的类型，因此可以直接参与运算或赋给同类型变量。
- `va_start` / `va_end` 是普通调用：ct 不声明它们，与 `printf` 一样按未知被调函数发射，
  由源文件的 `#include <stdarg.h>` 提供声明。
- trait 方法不能变参：`impl` 里出现 `...` 报 `a trait method cannot be variadic`
  （vtable 槽位是固定的函数指针类型）；trait 声明本身也不接受 `...`，会在参数位置报
  `expected a type`。

#### 4.23 内置类型词与 `inline`（ct-ast）

```c
#include <stddef.h>
#include <stdint.h>
#include <stdbool.h>

static volatile int ticks;

static inline int twice(int v) { return v + v; }

inline static int thrice(int v) { return v + v + v; }

static int first(int *restrict p, int n) { return p[0] + n; }

static bool positive(int32_t v) { return v > 0; }
```

- 类型关键字与 L0 / L1 / L2 对齐：`void` / `char` / `short` / `int` / `long` / `float` /
  `double` / `signed` / `unsigned` / `_Bool` / `bool` / `const` / `volatile` / `restrict` /
  `struct` / `union` / `enum` / `size_t` / `ssize_t` / `ptrdiff_t` / `wchar_t` /
  `int8_t`–`uint64_t` / `FILE` / `DIR` / `va_list`。声明**原样发射**，语义由 C 与对应头文件负责。
- `volatile` / `restrict` 是类型的一部分，因此 `volatile int x;`、`int *restrict p`、
  `volatile unsigned char *reg;` 在全局、局部、字段、参数、返回值上都成立。
- `inline` 是函数说明符：顶层接受 `static inline` 与 `inline static` 两种顺序，发射为
  `static inline ` / `inline `。生成的**原型**不带 `inline`（C 允许原型与定义不同）。
- `inline` 后面不是函数（`inline int value = 1;`）报 `'inline' can only declare a function`。
- 范围外：无（`_Static_assert` 见 §4.26；`_Alignas` / `_Alignof` / `_Generic` 见 §4.35；
  `__attribute__((…))` 见 §4.36；浮点字面量见 §4.24）。

#### 4.24 浮点字面量（ct-ast）

```c
double d = 1.5;
float f = 2.25f;
long double ld = 3.5L;
double tiny = .5;
double big = 1.5e3;

n = (int)9.99;              /* 截断为 9 */
```

- 支持 `<digits>.<digits>`、以点开头的 `.5`、带指数的 `1e9` / `1.5E-3`，以及后缀
  `f` / `F` / `l` / `L`。字面量按**原文**发射，因此后缀与指数写法都不会丢。
- 整数不受影响：`0x1F` / `0755` 仍按十六进制 / 八进制读成数值，并按十进制发射；
  `1...5` 里的三连点仍是范围 / 变参记号，不会被当成小数点。
- 浮点字面量**不是**整数常量表达式：`case 1.5:` 报 `a case label must be an integer constant`
  （位域宽度、枚举值同理）。
- 范围外：十六进制浮点（`0x1p3`）；`printf` 的格式串与实参类型匹配由用户负责，与 C 一致。

#### 4.25 `case` 范围标签（ct-ast）

```c
switch (score) {
case 0 ... 59:
    return 1;
case 60 ... 89:
    return 2;
case 90 ... 100:
    return 3;
default:
    return 0;
}

switch (c) {
case 'a' ... 'z':
    return 1;
case 'A' ... 'Z':
    return 2;
default:
    return 0;
}
```

- `case <low> ... <high>:` 按原样发射。两端都是整数常量表达式，规则与单值标签相同
  （`const_ok`，或整棵树是单个名字时放行）；任一端出现变量报
  `a case label must be an integer constant`。
- 范围标签与单值标签可以混排在同一个 `switch` 里；区间重叠、上下界颠倒不检查，交给 C 编译器。
- 缺下端（`case ... 5:`）在表达式位置报 `expected an expression`。
- 范围是 GNU 扩展（C23 正式化）：`cc -Wall -Wextra -std=c99` 下 clang 与 gcc 都接受且不告警，
  这是本特性的编译期依赖。

#### 4.26 `_Static_assert`（ct-ast）

```c
struct Pair { int a; int b; };

_Static_assert(sizeof(int) == 4, "int is four bytes");
_Static_assert(sizeof(struct Pair) >= 8, "a pair holds two ints");

static int check(int v) {
    _Static_assert(sizeof(char) == 1, "char is one byte");
    return v;
}
```

- 文件作用域与函数体内都可以写 `_Static_assert(<条件>, "<消息>");`，生成物同形。
- 条件必须是整数常量表达式（规则同 `case` 标签），否则报
  `a static assertion needs a constant condition`；消息必须是字符串字面量，否则报
  `a static assertion message must be a string literal`。消息可以省略（C23 放宽）。
- 文件作用域的多条断言统一在「类型之后、原型之前」发射，因此断言里引用本单元上面
  定义过的 struct / enum 仍然成立；引用**后面**才定义的类型则不行。
- 判定的最终结果仍由 C 编译器给出（断言失败时是它的错误消息）。
- 范围外：无（`_Alignas` / `_Generic` 见 §4.35；`__attribute__((…))` 见 §4.36）。

#### 4.27 一条声明多个字段（ct-ast）

```c
struct Buf {
    char name[8];
    unsigned len, cap;
    int *data, count;
    unsigned a : 3, b : 5;
    struct Range first, second;
};
```

- 记录体内的一条声明可以写多个声明符，共享同一类型：`int lo, hi;`、`unsigned len, cap;`。
  第一个声明符的拼写作为共享类型，后续声明符各自补上自己的星号、维度与位宽。
- `*` 只属于带它的那个声明符：`int *data, count;` 里 `data` 是 `int *`，`count` 是 `int`，
  与局部声明的规则一致。
- 位域可以成列：`unsigned a : 3, b : 5;`，每个声明符各自检查宽度与类型。
- 函数指针仍是一声明一个名字：`int (*a)(int), (*b)(int);` 报
  `a function pointer declares one name`。
- 字段表按名字逐个登记，因此成员访问、`offsetof`、匿名成员提升、vptr 追加都不受影响。

#### 4.28 数组长度表达式（ct-ast）

```c
#define WIDTH 4
#define SLOTS (WIDTH * 2)

static int g_tbl[WIDTH * 2];

struct Box {
    int cells[SLOTS];
    char name[(1 << 3)];
    short pairs[WIDTH + 1];
};

int main(void) {
    int local[WIDTH + 1];
    return local[0];
}
```

- 方括号里除了数字、单个名字与空之外，还可以写**表达式**：宏乘倍数、位移、括号求和等，
  一律按源码原文发射，因此 `[MAX_NAME * 2]` 与 `[(1 << 3)]` 都成立，长度由 C 折叠。
- 单个名字若解析为枚举成员，仍按其 C 拼写（命名空间 mangling 后的名字）发射；多 token 的
  表达式不做这种归一化，原样保留。
- 维度只用于发射与「是不是数组」的判定，因此数组长度是表达式还是字面量，对成员访问、
  `sizeof`、`offsetof` 与 vptr 初始化没有区别。
- 运行期长度（VLA）同样原样发射，由 C 判断；维度里的字符串字面量不做特殊处理。

#### 4.29 前缀 `++` / `--`（ct-ast）

```c
while (n && s[n - 1] == 0) s[--n] = 9;
i = *(--p);
j = ++i;                       /* j 取更新后的值 */
k = i++;                       /* k 取更新前的值 */
```

- 前缀自增 / 自减与其它一元运算符同级：操作数是再一个一元表达式，因此
  `s[--n]`、`*--p` 与独立的 `--n;` 都按 C 的读法成立。
- 值是**更新后**的值，与后缀形式相反；ct-ast 只按原顺序发射运算符与操作数。
- 没有额外限制，也不需要类型推断（与后缀形式处境相同）。

#### 4.30 初始化器的长度（ct-ast）

```c
static const char *kw[] = {
    "void", "char", "short", "int", "long", "float", "double", /* ... 一整张表 */
};

static const char *notes[] = {
    "单个列表项也可以是长字符串，整项保留",
    "short"
};
```

- 花括号初始化器不再受节点的 160 字节 `text` 字段限制：捕获与重写各用独立的
  大缓冲区（单个初始化器 4 KiB，重写后 16 KiB，单个列表项 4 KiB），最终文本存进
  arena 的字符串池。
- 因此关键字表、消息表这类长列表，以及由长字符串组成的列表项，都能完整保留。
- 超出上述上限仍报 `error: initializer is too long`，绝不静默截断。

#### 4.31 变参函数指针（ct-ast）

```c
typedef int (*logger_fn)(const char *fmt, ...);

struct Sink {
    const char *name;
    logger_fn log;
};

static logger_fn g_log = say;
static logger_fn tbl[2] = { say, say };

p = counts;                 /* 局部变量同样可以指向变参函数 */
r = p(2, 3, 4);
s.log("sink %s %d\n", s.name, r);
```

- `...` 属于函数指针**签名拼写**的一部分：它连同其余参数一起写进 `(*)(…)`，因此
  typedef、结构体字段、指针数组与局部声明都自动带上它（§4.22 已说明 `...` 的含义）。
- 与 §4.22 的规则一致：`...` 前面必须至少有一个具名参数。`(...)` 与 `(void, ...)`
  都报 `a variadic function pointer needs a named parameter before '...'`。
- 通过指针调用就是普通调用，多余实参原样透传；ct 不检查实参类型（与 `printf` 一致）。

#### 4.32 逗号表达式（ct-ast）

```c
i = 1, j = 2;
for (i = 0, j = 10; i < 3; i++, j--) sum = sum + j;

bump(&i), bump(&j);
x = (i++, j * 2);              /* 取值位置要加括号 */
```

- 一个完整表达式可以是若干「赋值表达式」用 `,` 连成的列表：从左到右求值，值是最后一项。
- 接受的位置：
  - 表达式语句、以及 `for` 的初始化子句与步进子句（三者共用同一个解析入口）。每个操作数
    按赋值表达式解析，所以 `i = 1, j = 2` 就是 `(i = 1), (j = 2)`，与 C 的读法一致；
  - **括号内的取值位置**：`x = (a, b);`、`f((a, b))`、`while ((a, b))`。此时列表就是一个
    普通表达式，值取最后一项；括号里的操作数也可以是赋值（见 §4.34）。
- 生成物把列表写成 `(a, (b, c))`：右结合只是解析产物，求值顺序仍是左到右。
- 仍然不做：`for` 条件子句里**不带括号**的逗号（`for (; a, b; )`）。实参之间的 `,` 永远是
  分隔符，要写取值逗号必须加括号。

#### 4.33 头文件里的类型名（ct-ast）

```c
#include <time.h>

static time_t g_base;

struct Stamp {
    time_t when;
};

static void show(time_t t) { printf("%ld\n", (long)t); }

int main(void)
{
    time_t now;                /* 未知类型 + 名字 */
    time_t *ref;               /* 未知类型 + `*` + 名字 */
    now = 7;
    ref = &now;
    show(*ref);
    return 0;
}
```

- ct 不展开 `#include`，头文件里的 typedef 对解析器就是未知名字。在声明位置上，
  「未知标识符 + 声明符名」的序列按类型处理，拼写原样发射，是否真是类型交给 C 编译器判断。
- 判据：该名字既不能是已登记的类型（struct / union / enum / trait / typedef），也不能是
  已声明的变量或函数，还不能是语句关键字。所以 `return found;`、`goto done;`、
  `own Box *b` 仍按语句解析，`a * b;`（`a` 是变量）仍是表达式。
- 转换与 `sizeof` 里同样可用：`(time_t)raw`、`(time_t *)&t`、`sizeof(time_t)`。
  判据比声明位置更严——括号里的名字必须紧跟 `)`（可隔着若干 `*`），并且既不是
  已声明的变量 / 函数，也不是全大写宏常量。因此 `(f(x))` 仍是被括号包住的调用，
  `(MAX) + 1` 仍是表达式。

#### 4.34 表达式里的赋值（ct-ast）

```c
while ((c = getchar()) != EOF) { … }
if ((n = parse(line)) > 0) { … }

x = (a = b = 0);          /* 右结合 */
y = (arr[0] = 4) + 1;     /* 下标目标 */
z = (p->n = 7);           /* 成员目标 */
w = (a += 2);             /* 复合赋值 */
```

- 括号里，以及 `if` / `while` / `do … while` / `switch` / `for` 的条件里，赋值可以当作
  取值使用：`(c = getchar())` 的值就是赋进去的值；`a = b = 0` 右结合；`+=` 等复合赋值同样可用。
- 语句层的赋值完全不变：`x = 1;` 仍由语句解析，生成物不加括号。
- 目标必须是变量、成员、下标或解引用，否则报 `assignment target is not assignable`。
- 目标是 `own` 变量时拒绝：`an 'own' variable can only be assigned in a statement`。
  所有权（AutoDrop / 泄漏分析）只在语句层记账，值位置的赋值会绕过它，所以宁可报错。

#### 4.35 C11 对齐与泛型选择（ct-ast）

```c
_Alignas(16) int g_a;            /* 文件作用域 */
static _Alignas(16) int g_b;

struct Frame {
    _Alignas(8) int kind;
    int size;
};

int main(void)
{
    _Alignas(16) int local;      /* 块作用域 */

    printf("%d\n", (int)_Alignof(double));   /* 只接受类型名，不接受操作数 */

    int n = 0;
    double d = 0.0;
    int kind_n = _Generic(n, int: 1, double: 2, default: 3);   /* 1 */
    int kind_d = _Generic(d, int: 1, double: 2, default: 3);   /* 2 */
    return 0;
}
```

- `_Alignas(…)` 是类型拼写的一部分：解析器把它**原样**放到声明类型之前，全局、局部、字段、
  参数、`typedef` 五个入口因此自动生效，不需要额外语法。生成物写成
  `_Alignas ( 16 ) int x`，是否合法由 C 编译器判断。其他说明符仍写在前面
  （`static _Alignas(16) int g;`）；`_Alignas(16) static int g;` 这种顺序不在子集内。
- `_Alignof(type)` 与 `sizeof(type)` 共用一个节点，只接受**类型**形式：写 `_Alignof x`
  报 `_Alignof needs a type in parentheses`（C11 本来也只允许类型）。
- `_Generic(…)` 整段透传：控制表达式与每个分支都交给 C 编译器（各 token 之间补一个空格），
  类型匹配与分支选择都由它完成。ct 不读分支，所以分支里的 trait 调用、装箱等重写
  **不会发生**——分支要写成 C 编译器自己能接受的代码。
- 三者都由 ct-ast 解析并重新发射；L0 / L2 的透传行为不变。生成的 `.c` 保留 C11 拼写，
  因此构建它的 C 编译器需要接受该写法（clang 与 GCC 都可以）。

#### 4.36 GNU `__attribute__((…))`（ct-ast）

```c
static void trace(const char *fmt, ...) __attribute__((format(printf, 1, 2)));

int g_tick __attribute__((aligned(16)));

struct Frame {
    int kind __attribute__((aligned(8)));
    int size;
} __attribute__((packed));

typedef int word __attribute__((aligned(8)));

static int twice(int n __attribute__((unused))) { return 2 * n; }
```

- `__attribute__((…))` 是 GNU 扩展，ct 只负责把它**原样带进生成物**：属性列表（含
  `format(printf, 1, 2)`、`aligned(8)` 这类嵌套实参）按 token 原文捕获，连续的多个
  `__attribute__` 组一起捕获，在声明的**同一尾部位置**重新发射；语义完全交给 C 编译器。
- 接受的位置：函数声明与定义（参数表之后、`;` 或 `{` 之前）、形参（名字/维度之后）、
  结构体字段（名字/维度之后；位域的宽度之后）、全局变量（声明符之后、`=` 之前）、
  `typedef` 别名之后，以及 `struct` / `union` / `enum` 定义体的 `}` 之后。
- typedef 的记录类型统一发射在**别名之前**：`} __attribute__((packed)) Alias;`。
  这是 clang 与 GCC 对 `packed` / `aligned` 都生效的位置；源里写在别名之后也会被挪到这里。
- 边界：写在声明符**之前**的属性（`__attribute__((unused)) static int x;`）、局部变量、
  `impl` 方法与 trait 方法上的属性不在子集内。未闭合的属性列表报
  `unterminated __attribute__`；同一声明同时写在两个捕获位置报
  `duplicate __attribute__ on one declaration`。
- 生成的 `.c` 保留属性原文，因此构建它的 C 编译器需要认识它（clang 与 GCC 都接受）。

#### 4.37 整数字面量后缀与其余 C 拼写（ct-ast）

```c
_Noreturn void stop(void);
static_assert(1 + 1 == 2, "arithmetic works");

unsigned long a = 0xFFu;      /* 大小写不限 */
long b = 0777L;
unsigned long long c = 1ULL;  /* 写法顺序不限：uLL / LLu / lL 都成 */

static int mix(const int *__restrict a, int *__restrict__ b) { return *a + *b; }
```

- 整数字面量接受 `U` / `L` / `UL` / `LL` / `ULL` 及其任意大小写与顺序（十进制、十六进制、
  八进制同路径）。后缀只影响**拼写**，不改变数值；发射时规范化为「先 `U` 后 `L`」
  （`0xFFu` → `0xFFU`，`16l` → `16L`）。
- 非法组合（`U` 多于一个、`L` 多于两个）报 `an integer suffix may be U, L or LL`。
- 值仍存放在 `long` 里：超过 `LONG_MAX` 的 `ULL` 字面量会按 `long` 回绕，这是既有的容量
  边界（与浮点字面量按拼写保留的做法不同）。
- `static_assert` 是 `_Static_assert` 在 C23 / `<assert.h>` 下的同义拼写，两者都接受，
  生成物统一写 `_Static_assert`。
- 函数声明的 `_Noreturn` 以**第一处声明**为准：`_Noreturn void f(void);` 之后的
  `void f(void) {}` 不会把它抹掉。
- `__restrict` / `__restrict__` 与 `restrict` 同义，原样保留在类型拼写里。

#### 4.38 头文件里的写法顺序（ct-ast）

```c
_Atomic(int) counter;                          /* 也可写 _Atomic int */
_Alignas(16) static int aligned;
__attribute__((aligned(32))) static int tagged;

__attribute__((unused)) static int helper(int n);   /* 原型在前，定义不带属性 */

int main(void)
{
    _Alignas(8) static int local;
    __attribute__((unused)) int spare = 7;
    int trailing __attribute__((unused));

    printf("%d\n", (int)sizeof(_Atomic(int)));
    return 0;
}
```

- `_Atomic(type)` 与裸 `_Atomic` 都作为类型拼写原样保留，声明、块作用域、cast 与 `sizeof`
  都能识别；原子语义完全由 C 编译器负责。
- `_Alignas(…)` 可以写在存储类**之前**（文件与块作用域都接受）。发射统一为规范顺序
  `static _Alignas ( 16 ) int aligned;`；同一声明写两次报
  `duplicate _Alignas on one declaration`。
- GNU `__attribute__((…))` 可以写在**声明符之前**：全局变量、函数原型 / 定义、局部变量；
  局部变量也接受尾部写法。无论源里写在哪一侧，发射都放在声明尾部（局部变量的 `=`
  之前）。同一声明两侧都写报 `duplicate __attribute__ on one declaration`；属性后面
  不是声明时报 `an attribute must prefix a declaration`。
- `_Atomic(type)` 的括号未闭合报 `unterminated _Atomic`。
- 边界：`typedef` / `trait` / `impl` / 记录定义上的属性仍不在子集内；`_Alignas` 的语义
  （能否用于某个对象）由 C 编译器判断。

#### 4.39 trait 默认方法（第三十六批，仅 ct-ast）

```ct
trait Logger {
    int write(char *buf, int len);                 /* abstract */

    int write_all(char *buf, int len) {            /* default */
        int sent = 0;
        while (sent < len) sent = sent + self->write(buf + sent, len - sent);
        return sent;
    }
}

struct Conn { int fd; } use Logger;                /* 全 default：impl 整块可省 */

impl Logger for Conn {
    int write(char *buf, int len) { return send(self->fd, buf, len); }
}
```

- 展开语义：默认体在**每个采纳点**各展开一份，函数名仍是 `<Struct>_<Trait>_<method>`，
  vtable 槽与普通 impl 方法一致；`self->other()` 沿用既有派发规则生成
  `_self->__<trait>_vptr->other(_self, …)`。不共享一份，也不新增派发路径。
- `self` 在默认体里是 `struct <S> *`：可读字段、可派发兄弟方法、可调自由函数。采纳的 struct
  由 `use` 决定，所以同一 trait 被两个 struct 采纳时生成两份实现。
- 覆盖优先级：impl 显式方法 > 默认方法。抽象方法仍必须实现，缺失仍报
  `trait method 'x' is not implemented for struct 'S'`；全 default 的 trait 只写 `use` 即可
  （外来类型写空 `impl T for S { }`，见 D-3）。
- 诊断：默认体互相派发成环、没有抽象叶子时报
  `trait 'T' has no non-default method to break the cycle`（位置在 trait 声明行）；默认体在某个
  struct 上不成立（例如用了 `self->fd` 而该 struct 没有 `fd`）时报
  `trait T::m (declared at <path>:<line>) cannot be expanded for struct S: <reason>`，
  指回 trait 声明而不是采纳点。
- 边界：不做字段注入、不做 supertrait、不做 trait 层共享默认体；`Drop` 不受影响。

#### 4.40 `borrow` 与 `Handback`（Phase 5 续，仅 ct-ast）

`borrow` 与 `own` 一样是**上下文关键字**：只在参数列表或语句行首被识别，其它位置仍是普通标识符
（函数名 `borrow` 不受影响）。它表达「这个指针是借来的：出口归还，绝不释放」。`Handback` 是
**内建 trait**（照 `Drop` 处理：无 vptr、无 vtable，只发 `<S>_Handback_handback`），用户不自己声明。

```c
struct Conn { int fd; int in_use; } use Handback;

impl Handback for Conn {
    void handback() { self->in_use = 0; }      /* 归还：对象仍活着 */
}

void render(borrow struct Conn *c)             /* 阶段一：参数注解，代码生成零变化 */
{
    printf("%d\n", c->fd);
}

int main(void)
{
    borrow struct Conn *c = acquire(0);        /* 阶段二：声明 + 出口自动归还 */
    render(c);
    return 0;                                  /* → if (c) { Conn_Handback_handback(c); c = 0; } */
}
```

| 源码形态 | 处理 |
| --- | --- |
| 参数 `void f(borrow Request *r)` | 去掉 `borrow`；参数登记为借用（代码生成不变） |
| `borrow Conn *c = expr;` | 去掉 `borrow` 后照常声明；登记为借用 |
| 声明作用域的闭合 `}` / **每个** `return` 之前（分支内、行内均可，无位置要求） | 插入 `if (c) { Conn_Handback_handback(c); c = 0; }`（与 `own` 共用一张表，按声明逆序） |
| `delete c;`（`c` 是借用） | 编译错误：借用对象不归本作用域 |
| `g = c;` / 外层局部 `x = c;` | 编译错误：借用的生命期比目标短 |
| `c = other;`（借用句柄重新赋值） | 编译错误：会静默丢失归还动作 |

约束与限制：

- 参数与声明都必须是**结构体指针**；数组、`static` 局部、`switch` 体内一律报错；文件作用域直接用
  `borrow` 报 `'borrow' is only allowed inside a function body`。
- 借用句柄**不可重新赋值**，也**不可存入** `static` 局部或文件作用域变量（一律编译错误）——
  这三条都会让归还动作静默丢失。
- 声明必须带初始化式，且类型须 `use Handback` 并已有 `impl Handback for S`；缺失即报错
  （不提供默认空体，否则「归还」会静默变成空操作）。
- 出口注入与 `own` 同构：**不释放内存**，只调 `handback` 并置空——归还后对象仍在池里，可能被他人借走。
- `return c;`（局部借用逃逸）报 `warning: a borrowed pointer escapes through 'return'` 并**取消注入**；
  `return r;`（借用参数逃逸）只警告。
- `Handback` 实现在**被借出的对象**上（出口时编译器只有 `T *c`），与 `Drop` 一致。
  但结构体表按**翻译单元**重建：`impl Handback for S` 必须与 `borrow` 同单元，跨单元借用会报
  `struct '<S>' uses trait 'Handback' but this unit has no impl`（与 `Drop` 的跨单元限制同源）。
- 已知限制（诚实标注）：`store(c)`（实参未标 `borrow`）与字段级 `s->p = c` 不检查；`goto` 跨过声明
  静默失效；不区分池对象与栈对象。**不要宣称「有了 borrow 就不会悬垂」**。

诊断文本（英文、小写、无句号、标识符单引号）：

```text
'borrow' is only allowed inside a function body
'borrow' requires a struct pointer parameter
'borrow' requires an initialiser of struct pointer type
struct '<S>' does not use trait 'Handback'
struct '<S>' uses trait 'Handback' but this unit has no impl
a borrowed pointer cannot be deleted
a borrowed pointer cannot be reassigned
a borrowed pointer cannot be stored in '<name>' (its scope outlives the borrow)
'borrow' is not supported inside a switch
'borrow' does not support arrays
a static local cannot be 'borrow'
warning: a borrowed pointer escapes through 'return'
```

设计与实现说明见 [design/borrow.md](history/design/borrow.md)。

#### 4.41 raw 透传（`#ct-raw`，Phase 17.3，仅 ct-ast）

ct-ast 逐节点重新生成 C，因此它无法重写的 C 片段（宏、手写函数、`#pragma`）需要一个显式的
原样通道：`#ct-raw` 与 `#ct-endraw` 之间的一切**逐字节**进入生成的 `.c`，从不经过词法/语法分析。

```c
#include <stdio.h>

#ct-raw
#define TRIPLE(x) ((x) * 3)
static int raw_helper(int n)
{
    return n + 1;
}
#ct-endraw

int main(void)
{
    printf("%d\n", TRIPLE(raw_helper(2)));
    return 0;
}
```

| 形态 | 处理 |
| --- | --- |
| `#ct-raw` 单独一行且**位于第 1 列** | 打开块；块内容按源顺序插入顶层声明的流中 |
| 块内任何文本 | 原样复制到字面量池，发射时逐个字节写出（不 token 化、不补空格） |
| `#ct-endraw` 单独一行且位于第 1 列 | 关闭块；生成的 `.c` 在块后写 `#line <块后第一行>`（默认开启的行模式） |
| `--no-line` | 块文本照旧原样发射，只是不写 `#line` 重锚 |
| `.h.ct` 单元 | 块只进 `.c`，不进 `.h` |

约束与诊断：

- 一个块最多 **32768 字节**（超限报 `raw block exceeds 32768 bytes`）。
- 标记必须在**第 1 列**（`  #ct-raw` 报 `#ct-raw must start at column 1`），其后只允许空白。
- 未闭合在**起始行**报 `unclosed #ct-raw (expected #ct-endraw)`；孤立的 `#ct-endraw` 报
  `#ct-endraw without #ct-raw`；关闭行后跟非空白文本报 `unexpected text after #ct-endraw`。
- 只在普通 `.ct` / `.h.ct` 单元可用：`.m.ct` 的 prologue 白名单仍只放行 `#include` / `#define`。
- L0 / L1 按行透传，本来就会原样输出块内容；本规定只约束 ct-ast。编译器**自身源码**
  （`selfhost/ct-ast/**`）不得使用块，由 `selfhost/check-ast.sh` 的护栏检查。

### 6. 语义约束与已知问题

#### 6.1 会被诊断的约束

| 约束 | 违反时 |
| --- | --- |
| `use` 引用的 trait 必须已定义（且出现在该 struct 之前） | `error: struct 'S' uses undefined trait 'T'` + `exit 1` |
| `impl` 的 trait 与 struct 必须已定义 | `error: impl for undefined trait/struct 'X'` + `exit 1` |
| struct 必须 `use` 了对应 trait 才可 `impl` | `error: struct 'S' does not use trait 'T'` |
| impl 不得出现 trait 未声明的方法 | `error: method 'm' is not declared in trait 'T'` |
| impl 必须实现 trait 的**每一个**方法（ct-ast：带默认体的方法可不写） | `error: trait method 'm' is not implemented for struct 'S'` |
| ct-ast：默认体互相派发成环、没有抽象叶子 | `error: trait 'T' has no non-default method to break the cycle` |
| ct-ast：默认体在某个采纳 struct 上不成立 | `error: trait T::m (declared at <path>:<line>) cannot be expanded for struct S: <reason>` |
| 大括号/圆括号必须配对 | `error: unterminated '{'` |
| `trait` / `impl` 头部必须完整（名字、`{`、`for`） | `error: expected trait name` / `expected '{' after trait 'X'` / `expected trait name after 'impl'` / `expected 'for' in impl of 'T'` |

**不做**的检查：方法签名是否与 trait 一致（参数类型、个数、返回类型都不比对，原样搬运）。
trait / struct **重名**不是静默接受：ct-ast 报 `duplicate trait '<name>'` / `duplicate struct '<name>'`；
L0 / L2 仍取最先出现者，后者不可达、不报错。

#### 6.2 已知限制

- 变量表无类型信息；变量按**花括号块作用域**回滚（`{` 压栈、`}` 恢复），同一作用域内出现同名时取**最先**登记者（`find_var` 首命中）。
- **登记顺序 = 源码顺序**：在变量声明之前出现的方法调用不会被重写。
- **（仅 L2，行重写管线）**跨行的方法调用语句不重写（按行处理）；函数签名的**参数列表**跨多行时同样不识别。ct-ast 是 AST 管线，两者都不受限。
- **（仅 L2，行重写管线）**跨行的块注释 `/* … */` 只保护第一行：续行会被当作普通代码行处理，其中的 `self`、方法调用等照常改写（单行 `/* … */`、`//` 与字符串 / 字符字面量不受影响）。这是按行处理管线的固有限制，Phase 2–5 用 CT 重做特性时随实现一并保留（见 [roadmap](roadmap.md) 的「自举之后的恢复与新增」）。**ct-ast 不保留源码注释**：整段注释连同其中的代码一起丢弃，生成物只带溯源 banner（若要保留需单独立项）。
- **文件作用域的对象 / 数组**：vptr 由编译器生成的构造器 `__ct_init`（`__attribute__((constructor))`）在 `main` 前写入（D5=A）。
- 数组只支持 `Type name[<n>];`（无初始化式、常量下标）。
- **堆对象自动初始化**（Phase 1，D1=A）：`T *p = malloc(sizeof(struct T));` / `calloc` 在声明后自动写 vptr（含嵌套字段）。
- 接口多态：接口**数组**不支持；接口作为 struct **字段**不参与构造点递归（值字段声明后为空，需自行赋值）；
  装箱只接受**变量**、`&变量` 或「返回同款接口」的函数调用，其它表达式一律 `die`。接口字段的**派发**已支持
  （`s.lhs.m()` → `s.lhs.vt->m(s.lhs.self)`，指针字段经 `->`），**值**接口字段的**语句赋值**会自动装箱；
  但**指定初始化式**里的接口字段不装箱，**指针**接口字段的赋值也不处理（见 §4.8）。
- **ct-ast 已放宽上述接口限制**（v0.12.0 之后的修复，L0 / L2 不变）：构造式里由具体 struct 变量或
  `&变量` 填充的接口**值**字段与接口**指针**字段都会自动装箱（后者取复合字面量的地址）；接口指针形式的
  变量 / 参数（`Expr *xs`）按元素派发（`xs[i].m()`，元素是值而非指针）；结构体类型的**数组字段**逐元素
  写 vptr（`Num ab[2]` 的元素可直接派发）；函数原型的数组参数保留维度（`int f(Expr a[])`）。其它更复杂的
  初始化表达式（如算术式、函数调用结果直接灌进接口字段）仍按原样透传。
- **（仅 L2）**单行函数体（`int f() { … }` 与函数头写在同一行）不处理，与 Phase 0 的按行改写一致。同理，与构造**同处一行**的语句也不会被重写：一行接口装箱、一行右值接收者均按原样透传。（`impl` 构造是例外：它的方法体由块匹配整体抽取，即使与方法头同处一行也会走重写管线。）ct-ast 没有这些限制，跨行语句与单行函数体都照常回写。
- 不完整的 `struct` 头部（缺 `{`）不作为构造，按原样透传。`trait` / `impl` 是 ct 独有关键字：行首出现且其后紧跟标识符或 `{` 即视为构造声明，头部畸形一律报错（其后是其它 token 的行，如 `impl[n] = 0;`，仍透传）。
- 顶层构造不支持嵌套。
- **生成物里「声明了但没用到」的 `static` 实体**：一个 `impl` 总会发射 `<S>_<T>_vtable`，一个
  `use Drop` 的 struct 总会发射 `<S>_Drop_drop`，即使本单元从不调用该 trait 的方法、也不 `delete`
  （ct-ast 不做跨过程可达性分析）。这些符号一律带 `__attribute__((unused))`，因此 `cc -Wall -Wextra`
  不会因为它们告警；属性与既有的 `__ct_init` 的 `__attribute__((constructor))` 同源，需要
  GCC / clang。它们**不影响**语义与运行。

### 7. 容量上限

> 下表是 **L0**（冻结种子）的上限。**ct-ast**（安装入口）把用户可见的上限整体抬高：`MAX_NODES` 131072、
> `MAX_TRAITS` 64、`MAX_STRUCTS` 128、`MAX_METHODS` 64、`MAX_FIELDS` 64、`MAX_FUNCS` 256、

### 8. 明确不支持

可见性修饰符的完整集合（`pub readonly` / `setter`）、泛型、继承、类型检查、嵌套定义。
（错误恢复是 L0 的边界；CT 线会先收集多个错误再报告，见 §10。）

### 9. 诊断与退出码

- **错误**：格式 `<file>:<line>:<col>: error: <message>`，输出到 `stderr`；L0 **遇错即 `exit(1)`**，
  CT 线则先收集多个错误（§10）。
- **L0 不产生任何警告**；CT 线会输出泄漏警告与签名不一致告警，`--diagnostics` 可切 JSON（§10）。
- 退出码：`0` 成功；`1` 语法 / 语义 / I/O 错误。

### 10. L2 独有：模块系统与诊断（本文不描述其语法）

多文件模式（`ct build`）、`namespace`、`import`、`pub`、`Drop`、`#line`（含 `--line` / `--no-line`）、
泄漏警告与 `--diagnostics`，以及语义诊断（重复定义 / 签名不一致）**均由 CT 线（L2 / ct-ast）支持**，L0 不接受。
这些语法的定义与实现记录见 [roadmap](roadmap.md) 的 Phase 2–5 与 [design/restore.md](history/design/restore.md)；
归档的测试 fixture 见 `test/archive/`，特性完整的旧实现见 git tag `overreach-oracle`。

## English

> **Status**: this document specifies the **core ct grammar** — the subset that L0 (`ctc.c`), the
> CT line (L2, `selfhost/l2/**`, the frozen regression oracle) and the installed entry ct-ast
> (`selfhost/ct-ast/main.ct`) **accept and emit**. The CT line is a superset: it also supports
> `namespace` / `import` / `pub` / multi-file `ct build` / `Drop` / `#line` / leak warnings and
> `--diagnostics`. Those are **not covered by the grammar chapters below**; their semantics and
> landing record live in [roadmap](roadmap.md) (Phases 2–5), [design/restore.md](history/design/restore.md)
> and [design/phase5.md](history/design/phase5.md). AutoDrop (`own`) is also CT-line-only but is described in §4.9.
> The `map` construct added in Phase 11.1 (binding a trait method to a declared global instance, or —
> since SH-20 — to a namespace) is supported by **ct-ast only** — neither L0 nor L2 accepts it;
> see §4.10.
>
> The three are not byte-equivalent: ct-ast is the installed entry and L2 is only the regression
> oracle. Known divergences fall into two groups.
>
> **Deliberately rejected** (a design decision, not a gap):
>
> | Construct | L2 | ct-ast | Why |
> | --- | --- | --- | --- |
> | block form `namespace A::B { … }` | accepted | rejected (`a namespace is file-scoped`) | the per-unit prefix and the directory check both assume one namespace per file |
> | cross-namespace bare call | accepted, falls back to the root table | rejected (needs the qualified `A::f()`) | never silently pick the wrong object between two same-named exports |
> | `import` a plain `.ct` unit | accepted (additive: every unit also writes a `.h`) | rejected (`only a .h.ct unit can be imported: rename 'x.ct' to 'x.h.ct'`) | only `.h.ct` publishes an interface; under ct-ast a plain `.ct` writes no `.h` (build and compile mode alike) |
>
> **C-form coverage**: `goto` / labels, `switch` ranges, bit-fields, anonymous members, variadics,
> `inline`, `_Static_assert` (including the `static_assert` alias), integer literal suffixes
> (§4.37), floating literals (§4.24), `_Alignas` / `_Alignof` / `_Generic`
> (§4.35) and GNU `__attribute__((…))` (§4.36) are accepted by both layers — no known form is
> missing; see the sections under 4.
>
> This is a **capability gap between the two layers**, not a progress difference on one pipeline:
> L0 still reports `'namespace' is not supported by this compiler` for those constructs (same for
> `pub` / `import` / `ct build`; `--line` / `--no-line` / `--diagnostics` report `unknown option`).
> Archived fixtures live in `test/archive/`, and the old, feature-complete implementation is at git
> tag `overreach-oracle`.

This document specifies the input rules, expansion rules, naming rules and diagnostics of the core
grammar. Anything not described here is undefined behaviour and must not be relied upon.

### 1. Source model

A `.ct` file mixes top-level constructs with verbatim C. The compiler scans it **once, in source
order**: top-level constructs are expanded, everything else is copied line by line. Order therefore
matters — all definitions must precede their use.

```
program  ::= { item }
item     ::= trait-def | struct-def | impl-def | raw-text
```

Top-level constructs must sit at file scope (no nesting) and their keyword must start the line
(leading spaces and tabs are allowed). The first line of every generated `.c` is a provenance comment
`Generated by ct v<version> from <input path> -- do not edit; ...` (the `.h` carries an equivalent
comment in its header); it is not part of the source content.

### 2. Lexical notes

- Keywords (`trait`, `struct`, `impl`, `use`, `for`) must appear as whole words (`word_at()` performs
  word-boundary matching), so `traitx` or `my_struct` are not misread.
- `namespace`, `pub` and `import` are no longer keywords: the compiler now rejects them (see the status
  note at the top).
- A line-initial `trait` / `impl` / `struct` starts a construct only when the full header follows
  (`trait IDENT {`, `impl IDENT for`, `struct IDENT {`); otherwise the line is passed through. So
  legal C that uses `trait` / `impl` as ordinary identifiers (e.g. `impl[0] = 1;`, `trait = 2;`) is
  not misread.
- Rewriting is **line-based**: when a construct and an ordinary statement share one line, the statement
  is not rewritten (`p.greet()` inside `int main(void){ Person p = {…}; p.greet(); }` stays as written).
- Every fixed capacity limit (identifier length, parameter count and text, field / method / trait /
  struct counts, variable count, scope depth, …) is a hard `die` — never a
  silent truncation.
- Whitespace, newlines, `//` comments and `/* */` comments may appear freely in construct headers.
- Method declarations inside a trait are separated by `;` and may span lines; comments are stripped
  before splitting.
- Struct bodies are preserved verbatim and not parsed.
- Identifiers are `[A-Za-z_][A-Za-z0-9_]*`; ct-ast reports `identifier is too long` above 159
  characters instead of silently truncating (the L0 seed's limit is 127).

### 3. Grammar

```ebnf
trait-def   ::= "trait" IDENT "{" { method-decl } "}" ;
method-decl ::= type-spec IDENT "(" [ param-list ] ")" ( ";" | block ) ;

struct-def  ::= "struct" IDENT "{" raw-text "}" [ use-clause ] [ ";" ] ;
use-clause  ::= "use" IDENT { "," IDENT } ";" ;

impl-def    ::= "impl" IDENT "for" IDENT "{" { method-def } "}" ;
method-def  ::= type-spec IDENT "(" [ param-list ] ")" block ;

param-list  ::= param { "," param } ;
param       ::= type-spec [ IDENT ] ;   (* type-spec may contain '*' and 'const' *)

type-spec   ::= <C type spelling: everything up to the method/parameter name>
```

Conventions: the `use` clause may follow `}` on the same line or start a new line; a sole `void`
parameter means "no parameters"; the semicolon after a struct definition is optional. A trait method
ending in `;` is abstract; one ending in `{ … }` carries a default implementation (ct-ast; §4.39). Parameter types
and names are split heuristically — the last identifier is taken as the parameter name unless it is a
type keyword (`void` / `char` / `int` / `unsigned` / `size_t` …) or the text ends with `*`.

#### 3.1 Expressions (ct-ast)

ct-ast parses expressions with C's precedence. The supported operator subset, tightest first:

| Level | Operators |
| --- | --- |
| unary | `!` `~` `-` `&` (address-of) `*` (dereference), casts, `sizeof` |
| multiplicative | `*` `/` `%` |
| additive | `+` `-` |
| shift | `<<` `>>` |
| relational / equality | `<` `>` `<=` `>=` `==` `!=` |
| bitwise AND | `&` |
| bitwise XOR | `^` |
| bitwise OR | `\|` |
| logical | `&&` `\|\|` |
| conditional | `?:` |
| assignment | `=` and the compound forms `+=` `-=` `*=` `/=` `%=` `&=` `\|=` `^=` `<<=` `>>=` |

Every binary / unary operation is parenthesised in the output, so the source semantics never rely on
C's own precedence. L0 / L1 / L2 do not parse expressions (they rewrite line by line); this table
describes ct-ast only.

### 4. Expansion rules

#### 4.1 trait → vtable type

```c
trait Greeter { void greet(); int add(int a, int b); }
```

```c
struct Greeter_vtbl {
    void (*greet)(void *);
    int (*add)(void *, int, int);
};
```

Each method gains a leading `void *` parameter; the vtable keeps **types only and drops parameter
names**.

#### 4.2 struct + use → appended vptr field

```c
struct Person {
    char *name;
    int age;
} use Greeter;
```

```c
struct Person {
    char *name;
    int age;
    struct Greeter_vtbl *__greeter_vptr;
};
```

The field body is preserved verbatim; vptr fields are appended at the end, in the order the traits are
written in `use`.

#### 4.3 impl → static methods + vtable variable

```c
impl Greeter for Person {
    void greet() {
        printf("Hello, %s\n", self->name);
    }
}
```

```c
static void Person_Greeter_greet(void *self) {
    struct Person *_self = (struct Person *)self;
    printf("Hello, %s\n", _self->name);
}

static struct Greeter_vtbl Person_Greeter_vtable = {
    .greet = Person_Greeter_greet
};
```

- The generated function takes "`void *self` plus the parameters written in the impl", and the first
  line of its body is always the `_self` cast.
- The method body's indentation is normalised: the minimal shared indentation is stripped and the body
  is re-emitted with 4-space indentation.
- A method body goes through the **very same rewriting pipeline as top-level code**: `self` (a pointer
  to the current struct) and the impl's method parameters are registered in the variable table first,
  then every body line is fed to `transform_line`, and finally the identifier `self` is renamed to
  `_self`. Every receiver form therefore dispatches inside a body, exactly as at top level:
  - sibling call: `self->other()` → `_self->__<trait>_vptr->other(_self)`;
  - field chain: `self->field->m()` → `_self->field->__<trait>_vptr->m(_self->field)` (recursive, §4.5);
  - method parameter: `o->m()` → `o->__<trait>_vptr->m(o)`, `v.m()` → `v.__<trait>_vptr->m(&v)`;
  - a local variable declared in the body: `P q; q.m();` → `q.__<trait>_vptr->m(&q)`.
  - **Same name in several traits**: when more than one trait in the host's `use` list declares `f`,
    a bare `s.f()` takes the **first match in `use` order** (`s.__<first trait>_vptr->f(&s)`). The order
    is part of the semantics and is a **known limitation**; to reach the other implementation, box `s`
    into that trait's interface value (`struct B_iface x = B_of(&s); x->f();`) or rename the method.
- Whenever a body produces a dispatch, a forward declaration
  `static struct <Trait>_vtbl <Struct>_<Trait>_vtable;` is emitted before the method functions, to
  resolve the forward reference to the vtable variable (a C tentative definition, later given its
  initialiser — both are valid together).
- vtable initialisers follow the **declaration order of the methods in the trait**, not the order they
  are written in the impl.
- Across units (ct-ast `build` mode): when **both the trait and the struct are `pub`**, the vtable gets
  external linkage — the declaring unit's header emits `extern struct <Trait>_vtbl <Struct>_<Trait>_vtable;`
  and the implementing unit defines it, so a consumer unit can box directly. Otherwise it stays `static`,
  and every `impl` of one struct/trait pair must live in a single compilation unit.

#### 4.4 Variable declarations → `struct` qualifier + appended vptr designator

```c
Person p = { .name = "Tom", .age = 36 };
```

```c
struct Person p = { .name = "Tom", .age = 36, .__greeter_vptr = &Person_Greeter_vtable };
```

Rules:

| Source form | Handling |
| --- | --- |
| `Person p = { … };` (designated initialisers) | prefix `struct ` and append vptr designators before `}` |
| `Person p = { "Tom", 36 };` (positional initialiser) | same: the vptr designators follow the positional elements (C99 allows the mix `{ 1, .v = 0 }`) |
| `Person p = {};` / `Person p;` | prefix `struct `; an empty list gets the vptr appended, and a declaration without an initialiser gets `= { <vptr> }` added |
| `struct Person p = { … };` | same as above (the qualifier is not added twice when already present) |
| `static Person p;` / `static Person ps[2];` | the `static` prefix is kept verbatim; everything else is as for a non-`static` declaration (objects get the initialiser, arrays go through `__ct_init`) |
| `Person *p = …;` | prefix `struct `, everything else emitted verbatim; pointer variables are **registered as pointers**, so `p->m()` is rewritten to `p->__t_vptr->m(p, …)` |
| other types | left completely untouched |

Names recognised as variables of a struct type are registered in the variable table for later
method-call rewriting.

#### 4.5 Method-call rewriting

```c
p.greet();
p.greet_name("Jerry");
```

```c
p.__greeter_vptr->greet(&p);
p.__greeter_vptr->greet_name(&p, "Jerry");
```

Trigger conditions (rewriting happens only when 1 or 1′ holds **and** 2–4 all hold):

1. the left-hand side is an identifier that has been registered **earlier in this file** as a variable
   of some struct type (`T x`, `T *x`, `T x[n]` and `T *x[n]` all qualify); **or**
1′. the left-hand side is a call `f(...)` whose return type is a **previously registered struct**
   (returned by value or by pointer: `f().m()`, `mk()->m()`, `f().a.b.m()`);
2. when that variable is an array or a pointer, one subscript `[<expr>]` may follow, with an arbitrary
   balanced expression (`ps[i]`, `ps[i + 1]`, `ps[f()]`);
3. then comes `.`, `->`, or a run of field hops (each `.field` / `->field`), and the **final** member
   name is a **method name** of some trait of the struct reached by those hops;
4. the member name is immediately followed by `(`.

Which trait a method belongs to is decided by scanning the traits of the struct's `use` clause in
order and taking the **first** one that declares that name.

Rewriting details:

- a no-argument call `x.m()` → `x.__t_vptr->m(&x)` (no stray comma);
- a call with arguments `x.m(a)` → `x.__t_vptr->m(&x, a)`;
- a pointer receiver does not get `&` added: `p->m()` → `p->__t_vptr->m(p)` and
  `p->m(a)` → `p->__t_vptr->m(p, a)`;
- array elements and pointer subscripts: `ps[i].m()` → `ps[i].__t_vptr->m(&ps[i])`; an element of
  `T *ps[n]` is **itself a pointer**, so `ps[i]->m()` → `ps[i]->__t_vptr->m(ps[i])`, whereas `p[i]` on
  a plain `T *p` is a value and gets `&`;
- a pointer field chain picks `.` or `->` from **each hop's** field kind, and the final hop being via a
  pointer means no `&`: `a.next->m()` → `a.next->__t_vptr->m(a.next)`, while `a.next.m()` (a value
  field) → `a.next.__t_vptr->m(&a.next)`;
- nested calls inside arguments are processed recursively:
  `q.add(1, q.add(2, 3))` → `q.__greeter_vptr->add(&q, 1, q.__greeter_vptr->add(&q, 2, 3))`;
- **rvalue receivers** (condition 1′): the receiver is first hoisted into a temporary variable so it is
  evaluated **exactly once**, then dispatched by the same rules above. The temporary is named
  `__ct_tmp<N>` (`N` increments within a single file, starting at 0):
  - returned by value: `f().m(a)` → the previous line `struct S __ct_tmp0 = f();`, this line
    `__ct_tmp0.__t_vptr->m(&__ct_tmp0, a)`;
  - returned by pointer: `mk()->m(a)` → the previous line `struct S *__ct_tmp0 = mk();`, this line
    `__ct_tmp0->__t_vptr->m(__ct_tmp0, a)`.
  - the hoist is allowed **only** in two positions: the receiver starts the **statement**
    (`f().m();`), or it starts the right-hand side of an **assignment / declaration initialiser**
    (`int r = f().m();`). In both, evaluation is unconditional and ordered, so hoisting to the previous
    line does **not** change the semantics.
  - in any other position (e.g. `x = 1 + f().m();`, `g(f().m());`) it cannot be rewritten without
    changing evaluation order, so the compiler **reports `file:line:col: error:` and exits** instead of
    emitting C that is known not to compile.
  - the hoisted declaration keeps the source line's indentation; it occupies one line in the generated
    `.c`.
- content inside string literals, character literals and comments is **never rewritten**;
- an `impl` body shares the top-level pipeline: `self->m(...)`, a field chain `self->f->m(...)`, a
  parameter receiver `o->m(...)` and a local-variable receiver `q.m(...)` are all rewritten by the
  same rule (see 4.3);
- **only a variable-subscript receiver's expression is evaluated twice** (`ps[i]` appears twice in the
  output), so a subscript with a side effect (`ps[i++]`) is not guaranteed correct; an rvalue receiver
  (1′) uses a temporary and is evaluated once.

#### 4.6 Ordinary function signatures → struct types qualified

```c
void show(Person p);
static Person make(char *n);
Person *pick(Person *a, Person *b);
```

```c
void show(struct Person p);
static struct Person make(char *n);
struct Person *pick(struct Person *a, struct Person *b);
```

Rules:

| Source form | Handling |
| --- | --- |
| a known struct name in the return type (including `static`-style prefixes, multi-word types and pointer returns) | insert `struct ` in place (all other characters preserved) |
| a value parameter `Person p` | insert `struct `; **when the function has a body**, register the parameter (`ptr=0`) so that `p.m()` inside the body is rewritten |
| a pointer parameter `Person *q` | insert `struct `; register it as a pointer (`ptr=1`) so that `q->m()` inside the body is rewritten |
| a prototype `void f(Person *q);` | qualify the types only; the parameters are **not** registered (there is no body) |
| a parameter already written `struct X …` | no second `struct ` is inserted |
| statements such as `if` / `while` / `else if` / `return …` | never mistaken for a function signature |
| a signature whose **parameter list itself** spans several lines | not recognised; copied through verbatim |

#### 4.7 Composition, arrays and heap objects (construction semantics)

A vptr is written at a **construction point**: an object's **own** vptr goes into the initialiser, while
**nested fields / array elements / heap objects** use **post-declaration assignments** (so an appended
`.field` designator can never override a `.field = {…}` the user wrote).

| Source form | Handling |
| --- | --- |
| `struct Shop { Person owner; };` | the field type gains `struct `: `struct Person owner;` |
| `Shop s;` | after `struct Shop s = { … };`, append `s.owner.__greeter_vptr = &Person_Greeter_vtable;` |
| `s.owner.greet();` | `s.owner.__greeter_vptr->greet(&s.owner);` |
| `Person ps[3];` | the declaration plus a scoped loop `for (…; __ct_i < 3; …) ps[__ct_i].__greeter_vptr = …;` |
| `ps[0].greet();`, `ps[i].greet();` | `ps[0].__greeter_vptr->greet(&ps[0]);` (any subscript expression) |
| `Person *ptrs[2]; ptrs[0]->greet();` | `ptrs[0]->__greeter_vptr->greet(ptrs[0]);` (the element itself is a pointer) |
| `struct Box { Person *who; } … b.who->greet();` | `b.who->__greeter_vptr->greet(b.who);` (pointer field chain) |
| `delete q;` | `if (q) free(q);` (`q` must be a registered pointer variable) |

Naming and limits:

- The loop variable emitted for arrays is always `__ct_i`, wrapped in its own block.
- **File-scope objects / arrays**: file scope cannot hold the vptr assignment **statements**, so the
  vptr is written before `main` by a generated constructor
  `static void __ct_init(void) __attribute__((constructor))` (decision D5 = A); the object is declared
  normally and dispatched from `main` as usual.
- Arrays only support `Type name[<n>];` (no initialiser, constant subscripts); any other form that needs
  initialisation `die`s instead of emitting bad C.
- **Heap objects are initialised automatically** (Phase 1, D1=A): `T *p = malloc(sizeof(struct T));`
  (or `calloc`) writes the vptrs (including nested value fields) right after the declaration.
- **ct never qualifies type names in hand-written C**: `sizeof(Person)` is not rewritten — write
  `sizeof(struct Person)` instead.

#### 4.8 Interface polymorphism (a trait used as a type)

Each trait additionally generates an **interface value type** (a fat pointer: the object plus its
vtable):

```c
struct Greeter_iface { void *self; struct Greeter_vtbl *vt; };
```

| Source form | Handling |
| --- | --- |
| `Greeter g;` | `struct Greeter_iface g = { 0, 0 };` |
| `Greeter g = p;` | `struct Greeter_iface g = (struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable };` |
| `Greeter g = q;` (`q` is `Person *`) | as above, with `self` taken from `q` itself (**no `&`**) |
| `g = s;` | box according to `g`'s trait, then assign |
| `void announce(Greeter who);` | `void announce(struct Greeter_iface who);` |
| `announce(p);` | `announce((struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable });` |
| `Greeter pick(void);` | `struct Greeter_iface pick(void);` |
| `return p;` inside an interface-returning function | `return (struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable };` |
| `g.greet();` | `g.vt->greet(g.self);` |
| `g.greet_name("Jerry");` | `g.vt->greet_name(g.self, "Jerry");` |

**An interface used as a struct field** (a value field `T x;` → `struct T_iface x;`; a pointer field
`struct T *x;` → `struct T_iface *x;`):

| Source form | Handling |
| --- | --- |
| field `Node lhs;` / `struct Node *lhs;` | the field type is expanded to `struct Node_iface lhs;` / `struct Node_iface *lhs;` |
| `s.lhs.show();` / `self->lhs.show();` | `s.lhs.vt->show(s.lhs.self);` (a value field hops with `.`, and the chain can recurse) |
| `s.p->lhs->show();` | `s.p->lhs->vt->show(s.p->lhs->self);` (a pointer field hops with `->`) |
| `s.lhs = v;` (**value** interface field) | boxed into the field's declared trait: `s.lhs = (struct Node_iface){ (void *)&v, &Lit_Node_vtable };` |

Rules and limits:

- Only a **variable** or `&variable` (or a call that already returns the same interface) can be boxed;
  when the type cannot be inferred the compiler `die`s.
- The boxing target trait comes from the **left-hand side** of a declaration/assignment, or from the
  **current function's return type**; for arguments it comes from the **signature table**, hence the
  definition-before-use rule applies — where the call site cannot see a signature (or the concrete
  type) nothing is boxed.
- The boxed struct must `use` that trait; boxing across different traits `die`s.
- **No** implicit null check: dispatching on a null interface value (`{0,0}`) crashes, as in C.
- **L0 limits (what this document describes)**: interface **arrays** are not supported (`die` at the
  declaration); interface fields do **not** participate in construction-point recursion (`Node lhs;`
  starts empty, `vt == NULL`, and must be assigned); boxing only covers **statement assignments**
  (`s.lhs = v;`), so an interface field inside a **designated initialiser**
  (`Pair p = { .lhs = v };`) is **not** boxed; and a **pointer** interface field (`struct T *x`)
  supports dispatch only, its assignment staying verbatim (it needs the address of an existing fat
  pointer, e.g. `s.x = &someIface;`).
- **Extended on the CT side (L2)**: `selfhost/l2/**` lifts every limit above and gives one uniform
  model for "interface value / pointer to an interface value / array of interface values / array of
  interface pointers"; boxing behaves identically in all four places (assignment, construction point,
  `return`, argument):

| Shape | Meaning | Dispatch | Kind of a subscripted element |
| --- | --- | --- | --- |
| `T x` | an interface value (fat pointer) | `x.m()` → `x.vt->m(x.self)` | — |
| `T *x` | a pointer to an interface value | `x->m()` → `x->vt->m(x->self)` | `x[i]` is a **value** (`x[i].m()`) |
| `T xs[n]` | an array of interface values | `xs[i].m()` → `xs[i].vt->m(xs[i].self)` | value |
| `T *xs[n]` | an array of interface pointers | `xs[i]->m()` | pointer |
| parameter `T xs[]` / `T *xs` | as above, indexable in the body | as above | value |

  Also: interface **array fields** (`Node items[4]`, `self->items[i].eval()`), subscripting a pointer
  interface field (`s.f[0].m()`), **construction-point** boxing (`Pair p = { .l = v, .ptr = &v };` —
  value and pointer fields take their own path) and **heap-object** boxing
  (`Num *p = malloc(sizeof(struct Num)); Expr e = p;`). **Still unsupported**: an interface pointer
  with an aggregate initialiser (`T *g = { ... };`). **Struct-typed array fields**
  (`struct Duo { Num ab[2]; }`) are unsupported by L0 / L2 but **supported by ct-ast** (element-wise
  vptr writes, see §6). Rationale as in the status note at the top: this document stays accurate for
  L0, and the new capability belongs to the CT line (L2 / ct-ast) alone, pinned by
  `test/acceptance/run.sh`.

#### 4.9 AutoDrop (new in Phase 5, CT line only)

`own` is a **contextual keyword** recognised only at the start of a declaration line. It marks the
variable as owning its object's lifetime, so the compiler releases it at scope exit. This is a Phase 5
addition: **L0 (`ctc.c`) does not know it** (it passes the line through), and the CT line implements
it: L2 (`selfhost/l2/**`, the frozen oracle) and ct-ast (the installed entry). The two differ in the
**position requirement** for exit injection from v0.16.0 on, see the table and the constraints.

| Shape | Expansion |
| --- | --- |
| `own Person *p = malloc(sizeof(struct Person));` | emit the declaration without `own`; register it as auto-dropped |
| the declaring scope's closing `}` (line-initial) | insert `if (p) { Person_Drop_drop(p); free(p); p = 0; }` before it |
| before every `return` (line-initial for L2; no position requirement for ct-ast) | the same, for every auto-dropped variable in reverse declaration order |
| `delete p;` | the usual `free`/`drop`; auto-drop is cancelled (no double release) |
| `p = …;` (reassignment) | auto-drop is cancelled (ownership moved) |
| `p` as a standalone value on the right-hand side of an assignment (`q = p;`) or in the returned expression | auto-drop is cancelled (escape); reading a field or an element (`x = p->n;`, `x = p[0];`) is **not** an escape |

Constraints and limits:

- Only `own T *p = malloc|calloc(...);` is accepted: a **struct pointer**, initialised by
  `malloc` / `calloc`, whose struct `use Drop`; anything else is a compile-time error.
- `own` is allowed **inside a function body only** (file scope is an error), and arrays are rejected.
- Multiple auto-dropped variables in one scope are released in **reverse declaration order**.
- L2 requires the closing `}` and the `return` to start their line; inline forms (`b->n = 1; }`,
  `if (p) return 0;`) are a compile-time error rather than a silent skip — a line-oriented injector
  cannot place the release inside a conditional. **ct-ast only requires that of the `}`**: a `return`
  has no position requirement, and branch-internal or inline `return`s get the injection before them
  (from v0.16.0 on, see §4.40).
- `goto` out of the declaring scope does not release.
- A `static` local cannot be `own` (`a static local cannot be 'own'`): a static object's lifetime is
  not the scope's to end.
- Escape detection is **conservative**: a standalone mention on the right-hand side of an assignment
  or on a `return` line cancels auto-drop, because a missed release (a leak) beats a wrong one
  (double free / freeing a borrow).

#### 4.10 `map` (new in Phase 11, extended by SH-20, ct-ast only)

`map` binds a trait's method to a concrete C call, emitting a wrapper plus a vtable. The host takes two
forms; **Phase 11.2 has wired both into dispatch** — when the binding is used as a trait interface
value (assigned to a `T`-typed variable, passed to a `T` interface parameter, returned from an
interface, or used as a call argument), boxing uses the bound vtable, so it runs as an instance of the
trait:

- **Object host**: `map trait T for instance x { … }`, where `x` is a declared global variable; the
  interface value's `self` points at it.
- **Namespace host** (SH-20): `map trait T for namespace A::B { … }`, binding a set of functions in
  that namespace. There is no object, so the interface value's `self` is `NULL`.

**Zero-cost static mapping (batch 38, implemented)**: compile-time `.m.ct` mapping units, static
traits, namespace static calls `host::Trait.method(…)` and the type host
`map trait T for type <ctype>` expand every binding **at the call site** into a plain C call —
no wrapper, no `_iface` / `_vtbl`, no vtable, and the same across units. See
[design/batch38-map-unit/spec.md](history/design/batch38-map-unit/spec.md). The rest of this section
describes the dynamic `map`, whose output and behaviour are unchanged.

`map` is a Phase 11 addition: **neither L0 nor L2 knows it** — only **ct-ast**
(`selfhost/ct-ast/main.ct`) supports it.

```c
trait Controller {
    int send(char *buf, int len);
}
struct Uart { int fd; };
struct Uart uart1;                                    /* object host: a declared global */

map trait Controller for instance uart1 {
    send(buf, len) -> mock_uart_send(&uart1, buf, len);
}

namespace hal;
pub trait Writer { int write(char *buf, int len); }
int hal_write(char *buf, int len) { return len + buf[0]; }

map trait Writer for namespace hal {                  /* namespace host: no object */
    write(buf, len) -> hal_write(buf, len);
}
Writer w = Writer::hal;                               /* boxes with a NULL self and hal_Writer_vtable */
```

Symbol naming: the host path with `::` turned into `_` gives `h`, and the trait's C name is `tr`; if
`tr` already starts with `h_` then `p = tr`, else `p = h_tr`. A wrapper is `p_<method>` and the vtable
is `p_vtable`. For an object host `h` is the instance's C name (e.g. `uart1`); for a namespace host
`h` is the host path (e.g. `hal`).

| Artifact | Rule | Example |
| --- | --- | --- |
| wrapper | `<host>_<Trait>_<method>` with a leading `void *self` (body `(void)self;`); **an object host's direct binding generates none**, a namespace host **always gets one** | `static int uart1_Controller_send(void *self, char *buf, int len)`; `static int hal_Writer_write(void *self, char *buf, int len)` |
| vtable | `<host>_<Trait>_vtable`, designated-init `.method = wrapper` (the bound C function itself when direct) | `static struct Controller_vtbl uart1_Controller_vtable = { .send = uart1_Controller_send };` |

Constraints and limits:

- `for` is followed by either `instance` or `namespace`; anything else is a compile-time error.
- An object host's `x` must be a **declared global variable** (file scope), else a compile-time error.
  The instance may be spelled namespace-qualified, `A::B::h` (2b.3); globals are mangled by their
  namespace (§4.11), so the C name bound is `A_B_h` and the instance's vtable / wrappers carry it as
  their prefix (`A_B_h_T_vtable`).
- **No synthesised host**: an undeclared name is never turned into an object silently — a typo would
  otherwise become a hidden host. When there is no object to hang the binding on, use a **namespace
  host** (`map trait Writer for namespace hal { … }`) instead of faking a `void *netlib;` placeholder
  — the placeholder still works but is no longer needed.
- A namespace host is written path segment by path segment, `A::B`. Boxing `T::A::B` with no matching
  map reports `no map binds trait 'T' to namespace '<host path>'` (the path is echoed as written,
  e.g. `nosuch` / `a::b`).
- A namespace host **rejects a direct binding**: there is no `self` to hand the bound function, so
  `-> fn;` is rejected (`a namespace host has no self: bind with a wrapper call`).
- A namespace host is boxed with `Trait::ns`, and that value is **usable only as an interface value**;
  in any other context (e.g. `int x = Writer::hal;`) it reports
  `a namespace host value is only usable as an interface value`. `Trait::ns(...)` stays a qualified
  call and boxes nothing.
- `T` must be a defined trait; a trait without a vtbl cannot be mapped.
- The bound method must be an existing method of `T`, and its `( … )` parameter count must match the
  trait declaration.
- The right-hand side of `->` (the CALL) is a **two-level binding**:
  - **direct**: when the callee is a bare C function name (a single identifier) nothing is generated
    and the vtable slot points at that function. Signatures are not checked: the bound function must
    itself match the slot type (a leading `void *`). A namespace host forbids this (see above).
  - **fallback**: a call containing an expression or member path gets a host-level wrapper. Every
    argument is validated identifier by identifier: string / character literals, numeric literals,
    member names after `.` / `->`, and `A::B` qualified names pass; any other identifier must be a
    parameter name from the `( … )`, this map's instance, an already-declared variable, or an ALL_CAPS
    macro — otherwise it is a compile-time error.
- Several maps may target the same instance or the same namespace; `MAX_MAPS` (64) caps the total
  number of map blocks.
- **Across units**: the vtable gets external linkage when the trait is `pub` and (for an object host)
  the instance is a `pub` global (the same rule as the impl vtable in §4.11); a namespace host has no
  instance, so only the `pub` trait matters. The header declares it `extern` and the declaring unit
  defines it, so another unit can box the binding. Otherwise wrappers and the vtable are emitted
  `static` in the unit that declares the map and never repeat elsewhere.
- **Dispatch (11.2 / SH-20)**: boxing an object host uses the **instance-level** vtable —
  `Controller c = uart1;` becomes
  `c = (struct Controller_iface){ (void *)&uart1, &uart1_Controller_vtable };` (not the struct-level
  `&Uart_Controller_vtable`). So **even when `Uart` never `use`d `Controller`**, `uart1` works as a
  `Controller` instance. A namespace host is boxed as
  `Writer w = Writer::hal;` → `w = (struct hal_Writer_iface){ (void *)0, &hal_Writer_vtable };`.
  Afterwards both `c.send(...)` and `w.write(...)` dispatch via `<iface>.vt->method(<iface>.self, ...)`
  to the wrapper; a namespace host's `self` is always `NULL`, so the bound function must not
  dereference it.
- The `--emit-map` JSON gains a `maps` field listing trait / instance / file / line and `bindings`
  (method → generated symbol) per map; each map also carries `"host": "instance"|"namespace"` for the
  host form, and each binding carries `"wrapper": true|false` to tell fallback from a direct binding.

**Static mapping (batch 38, ct-ast only)**

A `.m.ct` file is a **mapping unit**: it admits only `namespace`, `import`, `#include` / `#define`
(the prologue), `pub trait` (abstract methods only), `map` and `_Static_assert`. Functions, globals,
type declarations, `impl` and object hosts are all errors. It **produces no artefact** (no `.c` /
`.h`, absent from the trailing `cc` line, never stored in the cache) and can only be imported in a
`ct build`; `ct compile` refuses a `.m.ct` input outright. A `foo.h.ct` and a `foo.m.ct` in the same
root make an import ambiguous, and a mapping unit may only import another mapping unit.

The three unit kinds, by artefact and usage:

| Suffix | Publishes `.h` | Importable | Buildable on its own | Purpose |
| --- | --- | --- | --- | --- |
| `<name>.ct` | no | no | yes | implementation / entry; its interface lives in a sibling `.h.ct` |
| `<name>.h.ct` | yes | yes | yes | publishes types, `pub` declarations and vtable interfaces |
| `<name>.m.ct` | no | yes (between mapping units) | no (`ct compile` refuses it) | static mapping recipes |

`import` searches the importer's own directory first, then every `-I` root in order; within each root
`<name>.h.ct` is probed before `<name>.m.ct`, and only when neither exists does `<name>.ct` fall through
to `only a .h.ct unit can be imported: rename 'x.ct' to 'x.h.ct'`.

A `.h.ct` file name matching the **main type** it declares (`Parser.h.ct` ↔ `struct Parser`, with
`main.ct` as the exception) is a **repository convention**, not a compiler rule: the unit-name lint in
`selfhost/check-ast.sh` scans only `selfhost/ct-ast/**`, and user projects are not checked.

A `pub trait` declared in a `.m.ct` is automatically a **static trait**: it emits no `_iface` /
`_vtbl` / vtable, cannot be `impl`ed, cannot appear in a `use` list, cannot be used as a type, cannot
be boxed (`T::host`), and cannot carry a default body.

Two host forms:

- **Namespace host**: `map trait T for namespace A::B { m(p…) -> callee(…); }`, where the trait must
  be declared in that namespace. The call `A::B::T.m(args)` expands directly into the recipe's C call
  (no receiver, no `self`).
- **Type host**: `map trait T for type <ctype> { m(recv, p…) -> callee(…); }`, where the first binding
  parameter is the receiver and the trait method itself does not declare it; the binding has one
  parameter more than the method. In `value.m(args)` the receiver's static type is compared as
  normalized text (arrays decay to an element pointer first), and a hit substitutes `recv` with the
  receiver expression. Ordinary struct / interface methods win; the type host is only a fallback
  when that lookup fails, and several candidates are ambiguous.

Recipe substitution (per occurrence):

| In the recipe | Generated C |
| --- | --- |
| `p` (value position) | `(<actual>)` |
| `&p` (not followed by `[`) | `&(<TP>){<actual>}` (C99 compound literal) |
| `&p[…]` | `&((<actual>)[…])` |
| `sizeof p` | `sizeof(<TP>)` (not evaluated) |
| `p.field` / `p->field` / `p[i]` | `((<actual>).field)` / `((<actual>)->field)` / `((<actual>)[i])` |
| a parameter with no evaluated occurrence | call prefix `(void)(<actual>), ` (in binding order) |
| `p++` / `p--` / `p = …` / `p += …` | a compile-time error |

A parameter may be evaluated at most once; when it occurs more than once the argument must be a
repeatable expression (a literal, a variable, or a stable member chain of them), otherwise the
argument has to be bound to a local first. `<TP>` is that binding parameter's declared type (the
type host's receiver uses `host_type`). After `sizeof`, a binding parameter must be spelled without
parentheses (`sizeof p`); `sizeof(p)` would substitute the argument value's size, so it is rejected
with a compile-time error (`map recipe takes 'sizeof p', not 'sizeof(p)'`).

The `.m.ct` prologue (`#include` / `#define`) expands, de-duplicated per whole line, at the top of
every **consumer** `.c` (after the banner); the consumer compiles without writing those `#include`
lines itself, and a consumer `.h` never carries the prologue. `ct compile` resolves no imports, so
it never expands one.

**Sibling C shim (batch 39, ct-ast only)**: a mapping unit may delegate the shapes a recipe cannot
spell -- macros and statement macros, globals (`errno` / `stdin`), calls that need a cast, prefixed
varargs forwarding, callbacks without userdata -- to same-directory, same-base C files:
`<base>.shim.h` and `<base>.shim.c` (both optional, but **a `.shim.c` requires its `.shim.h`**,
otherwise `a shim source needs a matching .shim.h: <header path>` is reported).

- Only a `.m.ct` is probed for a shim (`foo.shim.h` beside `foo.h.ct` / `foo.ct` is ignored); a
  hit must be a readable regular file, otherwise `a shim header is not a readable file` /
  `a shim source is not a regular file` is reported.
- Two mapping units whose shims share a base name in different directories fail the build:
  `ctc: shim base name '<base>' is ambiguous: <dir1> and <dir2>` (no silent first-win).
- The consumer's generated `.c` automatically carries `#include "<base>.shim.h"` (before that
  unit's prologue, de-duplicated per whole line); the shim header is resolved **by file name**,
  so `ct build` prints `-I <shim directory>` on that `cc` line (once per directory).
- An existing `<base>.shim.c` joins the same `cc` line as a source (never copied, never written to
  the output directory); a header-only shim adds just the `-I`.
- Both shim files' `mtime.size` are folded into the mapping unit's cache key, so touching either
  rebuilds the consumer.
- The `.m.ct` still produces nothing; a shim is not an artefact and never a compiler build step.

A static `--emit-map` entry carries `"static": true`, `"host": "namespace"|"type"` and, for a type
host, `"type": "<ctype>"`; each binding carries `"inline": true`, `"wrapper": false` and
`"symbol": <callee>`. A static entry with a shim also carries
`"shim": {"header": "<path>", "source": "<path>"}` (`source` is omitted without a `.shim.c`).
Dynamic `map` fields and values are unchanged.

#### 4.11 Cross-unit linkage: `pub` globals and `extern` (ct-ast)

- `pub int g_counter = 5;` emits its definition into the defining unit's `.c` and
  `extern int g_counter;` into that unit's `.h`; any importing unit may then refer to it by name.
  `pub` means export only: a global without `pub` still belongs to its own unit.
- `extern int lib_flag;` declares without defining: the declaration goes into the `.h`, and the
  unit's `.c` emits no definition — the symbol comes from an external C object file or library.
  `extern` cannot carry an initializer (a compile-time error). It also accepts a function prototype
  (`extern int lib_fn(int);`): declaration only, and a `pub extern` prototype reaches the `.h`.
  An `extern` name is never mangled, because it names a C library symbol.
- Exported types (`pub struct` / `pub trait` / `pub typedef`) inside a namespace are still reachable by
  their **bare name**: a consumer writes `Writer w;` or `struct Uart u;`, and the compiler resolves
  `hal_Writer` / `hal_Uart`. When two imported namespaces export the same bare name, the bare reference
  is refused and an alias import is required (`import a::b::T as T;`). A **qualified** type spelling
  (`struct A::B`) is still not supported.
- Globals inside a namespace are **mangled**, like type and exported function names: `namespace A::B; int h;`
  has the C name `A_B_h`, so two namespaces may each declare `h` without a link-time collision. `extern` is
  the exception — the symbol belongs to a C library, so it keeps its own name and no namespace.
- An importing unit may reference an exported global with the **qualified** form: `a::h` reads and writes
  `a_h`; a bare name works while only one candidate exists. If two imported namespaces export the same name,
  the bare reference is refused with an instruction to qualify, instead of silently picking one.
- The boundary of cross-unit boxing: an `impl` vtable gets external linkage only when the trait is
  **`pub`** and the struct is **`pub`** — the header declares `extern struct T_vtbl S_T_vtable;`
  and the implementing unit defines it (no longer `static`); otherwise it stays unit-private.
  One struct may have only one `impl` per trait; a duplicate is a compile-time error naming the
  first definition's location.

#### 4.12 Function pointers (ct-ast)

The declarator form `ret (*name)(params)` is accepted as a parameter, a struct field, a global
and a local. The generated C matches the source, with the name kept inside the type.

```c
int (*p)(int);
struct Box { int (*op)(int); };
static int apply(int (*fn)(int), int v) { return (*fn)(v); }
```

- `typedef` works: `typedef int (*BinOp)(int, int);` is emitted as
  `typedef int (*BinOp)(int, int);`, and the alias is usable as a local, a parameter and a struct
  field. A typedef of an array of pointers works the same way
  (`typedef int (*Table[2])(int, int);`).
- A function-pointer array keeps its dimensions inside the declarator (`int (*tbl[2])(int, int);`).
  A global may carry an initialiser (`static int (*tbl[2])(int, int) = { plus, minus };`), a local
  is filled element by element, and a struct field is supported too (`int (*cb[2])(int);`);
  `tbl[i](x)` calls an element directly.
- A file-scope initialiser may name a function of this unit
  (`static int (*gp)(int, int) = plus;`): the prototypes are emitted before the globals.
- Assignment accepts `p = handler;` and `p = &handler;`; a function name used as an rvalue emits
  its C name. A library function brought in by `#include` works the same way (`p = strcmp;`): a name
  CT never declared is emitted verbatim and the C compiler checks it against the prototype, just as an
  ordinary call already does.
- A call accepts `p(args)` and `(*p)(args)`; both are emitted as `(*p)(args)`. A function-pointer
  field may be called directly: `c.add(2, 3)` (`.`) and `p->add(2, 3)` (`->`) are emitted as
  `c.add(2, 3)` and `p->add(2, 3)`.
- Limits: no returning a function pointer; no nested function pointers (`int (**f)(int)` reports
  `nested function pointers are not supported`); a function-pointer array cannot be a parameter
  (`function-pointer arrays are not supported as parameters`); one declaration names exactly one
  pointer (`int (*a)(void), (*b)(void);` is an error).

#### 4.13 `switch` and `do-while` (ct-ast)

```c
switch (key) {
case 1:
    out = 10;
    break;
case 2:
case KIND_B:                  /* both labels guard the same statements */
    out = 20;
    break;
default:
    break;
}

do {
    total = total + i;
    i = i + 1;
} while (i < 4);
```

- A label owns the statements from itself to the next label (or `}`), so a `case` and the `break` after it share
  one indentation level; `case 1: case 2:` share the next statements, and a label run may have no statements
  between its members.
- A case value is any integer constant expression: a number, a character literal, an enum member, a `#define`
  constant, parentheses with arithmetic / bit operators, a unary `- ! ~`, `sizeof`, `offsetof`. It is emitted
  as written and C folds it, so `case (1 << 2):` and `case 1 + 2:` are both accepted. A plain variable inside
  the expression (`case key + 1:`) reports `a case label must be an integer constant`; a tree that is a single
  name (a macro or a declared global) is always let through.
- A `switch` body may hold declarations, but not directly after a label (C labels open no scope):
  `case 1: int x;` reports `a declaration cannot follow a case label; wrap it in a block`, and a label that
  runs straight into `}` reports `a case label needs a statement`.
- `own` inside a `switch` is refused (`own is not supported inside a switch`): a case may be skipped or fall
  through, so the ordered-block release point does not hold; this waits for case reachability in the ownership
  pass.
- A `do-while` body may be braced or a single statement; `while (...)` must be followed by `;`, otherwise
  `a do statement must be followed by while (...)`.
- A `case` / `default` outside a `switch` body (including in a block nested inside one) reports
  `a case label is only allowed inside a switch`.
- A duplicated case value is emitted as written and left to the C compiler; `case 1 ... 5:` ranges
  are described in §4.25.

#### 4.14 `enum`, constant expressions and `offsetof` (ct-ast)

```c
enum Color { RED, GREEN = 5, BLUE, };

typedef enum Mode { Fast, Slow } Mode;

struct Point { int x; int y; };
typedef struct Pair { int a; int b; } Pair;

int off = (int)offsetof(struct Point, y);
```

```c
enum Color {
    RED,
    GREEN = 5,
    BLUE
};

typedef enum Mode {
    Fast,
    Slow
} Mode;

/* the struct Point / Pair definitions are unchanged; offsetof is re-emitted */
int off = (int)(offsetof(struct Point, y));
```

- A top-level `enum Tag { … }` needs its tag (a missing one reports `expected an enum name`); the braces follow
  the name directly, there is no forward form, and a trailing comma is allowed. A repeated tag in one namespace
  reports `duplicate enum 'Color'`.
- Both forms of `typedef enum [Tag] { … } Alias;` are accepted: with a tag, `enum Tag` and `Alias` are both type names.
- Type names follow the struct rule: `enum Color c;` and the bare `Color c;` are equivalent — the first emits
  `enum <C name>`, the bare one gets the `enum` prefix back.
- Every member is a file-scope `int` constant, mangled by its namespace like any global (`RED` inside
  `namespace a::b;` is emitted as `a_b_RED`).
- A member value must be an integer constant expression, otherwise `an enum value must be an integer constant`.
  Values are not folded: `GREEN = RED + 1` is emitted as written, and a member without a value emits no `= …`
  so C supplies the increment.
- A `pub enum` reaches the dependency unit's generated header, and its members import into a consumer as
  constants: both the bare `Mid` and the qualified `app::High` work.
- `offsetof(<struct type>, <field>)` is a **builtin** (CT has no preprocessor, so it cannot be a macro). The first
  argument accepts `struct S` and a typedef alias; the compiler checks that the struct and the field exist and
  otherwise reports `offsetof needs a struct type` / `struct 'S' has no field 'f'` (a forward-declared struct has
  no field list yet, so it is let through to C).
- The output re-emits `offsetof(struct S, f)` verbatim, so **the source must supply `#include <stddef.h>` itself** —
  the generated file only passes through the `#include`s the source wrote.

#### 4.15 `union` (ct-ast)

```c
union Value { int i; char c; long long ll; };

typedef union Tagged { int i; char c; } Tagged;

typedef union { int a[2]; long long ll; } Wide;

struct Holder { int tag; union Value v; };
```

- A `union` is the same record grammar as a `struct`: the same forward form (`union Value;` is accepted), both
  spellings of `typedef union [Tag] { … } Alias;`, a trailing comma, and either `};` or `}` closing the body.
- The tag shares the table with struct tags but has its **own type kind**: `union Value v;` and the bare
  `Value v;` are equivalent — the first emits `union <C name>`, the bare one gets the `union` prefix back.
  Namespace mangling matches struct.
- A `pub union` reaches the dependency unit's generated header and a consumer names it bare.
- **There is no `use` clause**: the members of a union share one storage, so an appended vptr field would collide
  with a user member; `union Value { … } use Greeter;` therefore reports `a union cannot use a trait`. A second
  body for one tag reports `duplicate union 'Value'`.
- `offsetof` accepts a union type too (`offsetof(union Value, c)`); the field check is shared with struct and a
  missing field reports `union 'Value' has no field 'd'`.
- A **top-level** record definition with neither a tag nor an alias (`union { int a; float b; };`) has no
  type name to be referred to and is outside this document; an anonymous struct / union used as a
  **member** is described in §4.18.

#### 4.16 `goto` and labels (ct-ast)

```c
static int find(int n) {
    int i;
    int found;

    found = -1;
    for (i = 0; i < n; i++) {
        if (i * i == 9) {
            found = i;
            goto done;
        }
    }
done:
    return found;
}
```

- The statement layer accepts both C jump forms: `goto <label>;` and `<label>:`. The output keeps the
  shape — the label sits on its own line and `goto` is emitted as written.
- Labels are **function-scoped**: a second label with the same name in one function reports
  `duplicate label '<name>'` (even when the two sit in different blocks); a `goto` whose target never
  appears in the same function reports `label '<name>' is not defined` when the body ends, pointing at
  the `goto`. Different functions may reuse one label name.
- A label owns the statements up to the next label of any kind (`goto` label / `case` / `default`) or
  the closing `}`, the chain rule `case` follows; the whole chain is emitted one level deeper. A run of
  labels (`again: done:`) is allowed — the first label owns the second and the output nests them, with
  the meaning unchanged. So a `goto` may jump backwards (a hand-written loop) or forwards out of nested
  loops or a `switch`.
- A declaration cannot sit directly behind a label (C opens no scope at one): `again: int x;` reports
  `a declaration cannot follow a label; wrap it in a block` — wrap the declaration in a block.
- A label cannot run straight into `}` (C99 requires a statement after it): `again: }` reports
  `a label needs a statement`. The cheapest fix is the empty statement, `again: ;` (§4.21).
- A `goto` may jump into or out of blocks and loops (C allows it). Jumping out of an `own`
  declaration's scope does **not** release it (§4.9).
- One function holds at most 64 labels and 64 `goto`s; beyond that it reports
  `too many labels in one function` / `too many gotos in one function`.
- Known edge: `out:` followed directly by `case 2:` is not part of the subset — the label chain stops
  at `case` / `default`, and an empty chain reports the "label needs a statement" complaint above.

#### 4.17 Bit-fields (ct-ast)

```c
struct Flags {
    unsigned a : 3;
    unsigned b : 5;
    unsigned : 4;            /* padding: nameless */
    unsigned c : 8;
};

typedef struct {
    unsigned kind : 2;
    unsigned size : 6;
} Header;
```

- A field may carry a width: `<type> [name] : <width>;`. This works in a `struct`, a `union`, the
  anonymous body of a `typedef struct { … }` and in the `pub` form.
- The width is an integer constant expression under the same rule as a `case` value: numbers, character
  literals, enum members, macro names, parentheses and arithmetic / bitwise operators, unary
  `- ! ~`, `sizeof`, `offsetof`. The width is **not folded** — it is emitted as written, so
  `unsigned nib : NIBBLE;` (with `#define NIBBLE (1 << 2)`) and `unsigned m : (2 + 2);` both work. A
  variable inside the expression (`a : (w + 1)`) reports
  `a bit-field width must be an integer constant`; a tree that is a single name is always let through
  (it may come from a `#define`). A missing width reports `expected a bit-field width`.
- The name may be omitted: `unsigned : 4;` is padding. An empty name never reaches member lookup, so
  the other fields of the struct are unaffected.
- A bit-field must have an integer type: a pointer (function pointers included) and an explicit
  `struct` / `union` type report `a bit-field must have an integer type`; a typedef alias is left to
  the C compiler.
- It cannot be an array: `int a[2] : 3;` reports `a bit-field cannot be an array`.
- One declaration may carry several declarators: `unsigned a : 3, b : 5;` follows the same grammar as
  an ordinary `int lo, hi;`.
- A width never lands in the `structs[]` dimension slot, so member type inference, `offsetof` on a
  plain field and the vptr append are unchanged; in a struct with `use`, the vptr field follows every
  bit-field.
- `offsetof` of a bit-field is undefined behaviour in C and is not special-cased.

#### 4.18 Anonymous members (ct-ast)

```c
struct Outer {
    int tag;
    union {
        int i;
        struct {
            short lo;
            short hi;
        };
    };
    unsigned bits : 4;
};
```

- A `struct { … };` or `union { … };` written directly inside a record body (**without a name**) is an
  anonymous member (C11). Its member names are **promoted** into the enclosing record: `o.i`, `o.lo`
  and `o.hi` all use the promoted spelling, and `sizeof(struct Outer)` is what C computes.
- Nesting works: an anonymous `union` may hold another anonymous `struct`, and the names promote
  level by level. An anonymous member may carry bit-fields, and a `use` vptr field still comes last
  in the enclosing record.
- The promoted names are written into the enclosing record's field table at parse time, so member
  type inference, the field check of `offsetof(struct Outer, i)` and the vptr initialisation of a
  trait-carrying field (`.obj.__x_vptr`) all need no second code path.
- A collision after promotion (with an existing named field, or between two anonymous members)
  reports `duplicate member '<name>'`.
- Two shapes are refused: a **named** field of an untagged record type (`union { int i; } u;`) reports
  `an anonymous record member cannot have a name; tag the record instead`, and an empty
  `union { };` reports `an anonymous record needs a member`.
- Anonymous members are C11 syntax: the output emits the nested record as written, so compiling it
  under `-std=c99` relies on the C compiler accepting the form as an extension (both clang and gcc
  do so without a warning).

#### 4.19 `static` locals (ct-ast)

```c
static int next_id(void) {
    static int n = 0;
    n = n + 1;
    return n;
}

static const char *greeting(void) {
    static const char *msg = "hi";
    return msg;
}
```

- A function body may write `static <type> name[dims] [= init] (, name …)*;`: the object has static
  storage duration, keeps its value across calls and starts zeroed when no initialiser is given. The
  output carries the `static` prefix as written.
- Initialisers are not folded: whether one is constant is judged by the C compiler
  (`initializer element is not constant`).
- The declaration is otherwise an ordinary local (`declare_var` still registers it), so member
  access, array indexing and method-call type inference are unchanged; a trait-carrying struct still
  gets its vptr through the compiler's initialiser
  (`static struct Pair p = { .__named_vptr = &Pair_Named_vtable };` — a constant address, legal).
- A static object is not the scope's to release: `static own …` reports
  `a static local cannot be 'own'`, and a static declaration stays out of the leak analysis, so a
  deliberate singleton such as `static T *p = malloc(...)` is never reported as a leak.
- `static` has to introduce a declaration: `static;` reports `expected a declaration after 'static'`.
- Out of scope: `static` directly after a `case` / goto label is still refused as "a declaration
  cannot follow a label"; `for (static int i = 0; …)` is described in §4.21.

#### 4.20 Compound literals (ct-ast)

```c
struct Point { int x; int y; };

p = (struct Point){ 1, 2 };
total = sum_point((struct Point){ 3, 4 });
tail = (struct Point){ .y = 9, .x = 8 }.y;

static struct Point make(int x, int y) {
    return (struct Point){ x, y };
}
```

- `(type){ … }` is a C99 compound literal: a **temporary object**. It may sit on the right-hand side of
  an assignment, as an argument, in a `return`, and it takes a `.field` / `[i]` suffix directly.
- The braces are handled exactly like a declaration initialiser: positional, designated (`.y = 9`),
  nested braces and string literals all pass through; ct-ast never folds an initialiser, so whether it
  is constant is the C compiler's call.
- A struct that carries a trait gets its vptr item from the compiler:
  `(struct Pair){ 10, 20 , .__named_vptr = &Pair_Named_vtable}`.
- The type must be an **object type**: `(struct P *){ … }` reports
  `a compound literal needs an object type`.
- Out of scope: an array type (`(int[]){ … }` — the type grammar does not read `[]`, so it reports
  `unexpected token`), and calling a trait method straight on a compound literal
  (`((struct Pair){ … }).val()`) — the allowed receiver shapes stay variable / element / call / field
  chain, so assign it to a variable first.
- Storage duration is C's: automatic inside a function, static at file scope; ct-ast does not
  distinguish them.

#### 4.21 The empty statement and `for`-init statics (ct-ast)

```c
for (i = 0; i < 3; i++) ;

if (n == 0) ;
else n = 1;

switch (i) {
case 3:
    ;
    break;
default:
    break;
}

for (static int i = 0; i < 2; i++) {
    total = total + 1;
}
```

- `;` is the empty statement: `for (...) ;`, `while (c) ;` and `if (c) ; else …` all work, and it is
  the cheapest way to satisfy "a label needs a statement" (`case 3: ;`, `done: ;`). It emits no
  characters — the surrounding block still prints its braces.
- The first clause of a `for` may declare a `static`: the initialiser runs once and the variable keeps
  its value across calls, so entering the same `for` again tests the leftover value (as C specifies).
- Neither form adds a diagnostic; `static` that does not introduce a declaration keeps reporting
  `expected a declaration after 'static'`.

#### 4.22 Variadic functions (ct-ast)

```c
#include <stdarg.h>

static int sum_all(int n, ...);

static int sum_all(int n, ...) {
    va_list ap;
    int total;
    int i;

    total = 0;
    va_start(ap, n);
    for (i = 0; i < n; i++) {
        total = total + va_arg(ap, int);
    }
    va_end(ap);
    return total;
}
```

- A parameter list may end with `...`, which needs at least one named parameter in front of it
  (`int f(...)` reports `'...' needs a named parameter before it`). Declarations and definitions both
  accept it, and the generated prototype carries the `...` too.
- `va_list` is a built-in type word, so `va_list ap;` is an ordinary declaration and is emitted
  as written.
- `va_arg(ap, <type>)` is a builtin (its second argument is a type, so it cannot be parsed as a
  normal call) and is emitted as the same call; its type is the one written in the parentheses, so it
  can feed arithmetic or a variable of that type directly.
- `va_start` / `va_end` are ordinary calls: ct does not declare them, so they are emitted like
  `printf` — as an unknown callee — and the source's `#include <stdarg.h>` supplies the declarations.
- A trait method cannot be variadic: `...` inside an `impl` reports
  `a trait method cannot be variadic` (a vtable slot is a fixed function-pointer type), and a trait
  declaration does not accept `...` either — it reports `expected a type` at the parameter position.

#### 4.23 Built-in type words and `inline` (ct-ast)

```c
#include <stddef.h>
#include <stdint.h>
#include <stdbool.h>

static volatile int ticks;

static inline int twice(int v) { return v + v; }

inline static int thrice(int v) { return v + v + v; }

static int first(int *restrict p, int n) { return p[0] + n; }

static bool positive(int32_t v) { return v > 0; }
```

- The type keywords match L0 / L1 / L2: `void` / `char` / `short` / `int` / `long` / `float` /
  `double` / `signed` / `unsigned` / `_Bool` / `bool` / `const` / `volatile` / `restrict` /
  `struct` / `union` / `enum` / `size_t` / `ssize_t` / `ptrdiff_t` / `wchar_t` /
  `int8_t`–`uint64_t` / `FILE` / `DIR` / `va_list`. A declaration is **emitted as written**; the C
  compiler and the matching header own the meaning.
- `volatile` and `restrict` are part of the type, so `volatile int x;`, `int *restrict p` and
  `volatile unsigned char *reg;` all work — globally, locally, as a field, a parameter or a return
  type.
- `inline` is a function specifier: the top level accepts `static inline` and `inline static` alike
  and emits `static inline ` / `inline `. The generated **prototype** does not repeat `inline`
  (C lets a prototype differ from the definition).
- `inline` in front of something that is not a function (`inline int value = 1;`) reports
  `'inline' can only declare a function`.
- Out of scope: none (`_Static_assert` is covered in §4.26; `_Alignas` / `_Alignof` / `_Generic`
  in §4.35; `__attribute__((…))` in §4.36; floating-point literals in §4.24).

#### 4.24 Floating-point literals (ct-ast)

```c
double d = 1.5;
float f = 2.25f;
long double ld = 3.5L;
double tiny = .5;
double big = 1.5e3;

n = (int)9.99;              /* truncates to 9 */
```

- Supported forms: `<digits>.<digits>`, the leading-dot `.5`, exponents (`1e9`, `1.5E-3`) and the
  suffixes `f` / `F` / `l` / `L`. A literal is emitted **exactly as written**, so neither the suffix
  nor the exponent spelling is lost.
- Integers are unchanged: `0x1F` / `0755` are still read as hex / octal and emitted in decimal, and
  the three dots in `1...5` remain a range / variadic marker rather than a decimal point.
- A floating literal is **not** an integer constant expression: `case 1.5:` reports
  `a case label must be an integer constant` (the same holds for a bit-field width or an enum value).
- Out of scope: hexadecimal floating literals (`0x1p3`); a `printf` format string matching its
  arguments stays the programmer's job, exactly as in C.

#### 4.25 `case` ranges (ct-ast)

```c
switch (score) {
case 0 ... 59:
    return 1;
case 60 ... 89:
    return 2;
case 90 ... 100:
    return 3;
default:
    return 0;
}

switch (c) {
case 'a' ... 'z':
    return 1;
case 'A' ... 'Z':
    return 2;
default:
    return 0;
}
```

- `case <low> ... <high>:` is emitted as written. Both ends are integer constant expressions under the
  same rule as a single value (`const_ok`, or a whole name that may be a macro); a variable in either
  end reports `a case label must be an integer constant`.
- Ranges and single-value labels may be mixed in one `switch`; overlapping or inverted ranges are not
  checked and are left to the C compiler.
- A missing low end (`case ... 5:`) reports `expected an expression` at the expression position.
- The range is a GNU extension (standardised in C23): `cc -Wall -Wextra -std=c99` accepts it in both
  clang and gcc without a warning, and that is this feature's compile-time dependency.

#### 4.26 `_Static_assert` (ct-ast)

```c
struct Pair { int a; int b; };

_Static_assert(sizeof(int) == 4, "int is four bytes");
_Static_assert(sizeof(struct Pair) >= 8, "a pair holds two ints");

static int check(int v) {
    _Static_assert(sizeof(char) == 1, "char is one byte");
    return v;
}
```

- `_Static_assert(<condition>, "<message>");` may appear at file scope and inside a function body,
  and is emitted as written.
- The condition must be an integer constant expression (the rule `case` labels follow), otherwise it
  reports `a static assertion needs a constant condition`; the message must be a string literal,
  otherwise `a static assertion message must be a string literal`. The message may be omitted (C23
  relaxed it).
- File-scope assertions are emitted together between the types and the prototypes, so an assertion
  may name a struct / enum defined above it in the unit; naming a type defined **after** it does not
  work.
- The verdict itself still comes from the C compiler (a failing assertion is its error message).
- Out of scope: none (`_Alignas` / `_Generic` are covered in §4.35; `__attribute__((…))` in §4.36).

#### 4.27 Several declarators in one field declaration (ct-ast)

```c
struct Buf {
    char name[8];
    unsigned len, cap;
    int *data, count;
    unsigned a : 3, b : 5;
    struct Range first, second;
};
```

- One declaration inside a record body may carry several declarators sharing a type:
  `int lo, hi;`, `unsigned len, cap;`. The first declarator's spelling is the shared type, and each
  later one adds its own stars, dimensions and width.
- A `*` belongs to the declarator that carries it: in `int *data, count;` `data` is `int *` and
  `count` is `int`, the same rule local declarations follow.
- Bit-fields may share a list: `unsigned a : 3, b : 5;`, with each declarator checked for its width
  and type.
- A function pointer still declares one name: `int (*a)(int), (*b)(int);` reports
  `a function pointer declares one name`.
- Names are registered one by one, so member access, `offsetof`, anonymous-member promotion and the
  vptr append are unaffected.

#### 4.28 Array-length expressions (ct-ast)

```c
#define WIDTH 4
#define SLOTS (WIDTH * 2)

static int g_tbl[WIDTH * 2];

struct Box {
    int cells[SLOTS];
    char name[(1 << 3)];
    short pairs[WIDTH + 1];
};

int main(void) {
    int local[WIDTH + 1];
    return local[0];
}
```

- Besides a number, a single name and the empty form, the brackets accept an **expression**: a macro
  product, a shift, a parenthesised sum. It is emitted exactly as written, so `[MAX_NAME * 2]` and
  `[(1 << 3)]` both work and C folds the length.
- A single name that resolves to an enum member is still emitted under its C spelling (the mangled
  name); a multi-token expression is kept verbatim instead.
- The dimension is only used for emission and for the "is this an array?" test, so whether the length
  is a literal or an expression makes no difference to member access, `sizeof`, `offsetof` or the
  vptr initialisation.
- A run-time length (a VLA) is emitted as written too and left to C; string literals inside a
  dimension are not special-cased.

#### 4.29 Prefix `++` / `--` (ct-ast)

```c
while (n && s[n - 1] == 0) s[--n] = 9;
i = *(--p);
j = ++i;                       /* j takes the updated value */
k = i++;                       /* k takes the value before the update */
```

- Prefix increment / decrement binds like the other unary operators: the operand is another unary
  expression, so `s[--n]`, `*--p` and a standalone `--n;` all read the way C reads them.
- The value is the **updated** one, unlike the postfix form; ct-ast only emits the operator and the
  operand in their original order.
- There is no extra restriction and no type inference (the same position the postfix form is in).

#### 4.30 Initialiser length (ct-ast)

```c
static const char *kw[] = {
    "void", "char", "short", "int", "long", "float", "double", /* ... a whole table */
};

static const char *notes[] = {
    "a single item may be a long string too; it is kept whole",
    "short"
};
```

- A braced initialiser is no longer bound by the node's 160-byte `text` field: the capture and the
  rewrite each get their own large buffer (4 KiB for one initialiser, 16 KiB after rewriting, 4 KiB
  for one item), and the final text lives in the arena's string pool.
- Keyword tables, message tables and items made of long string literals therefore survive in full.
- Exceeding those caps still reports `error: initializer is too long`; nothing is truncated silently.

#### 4.31 Variadic function pointers (ct-ast)

```c
typedef int (*logger_fn)(const char *fmt, ...);

struct Sink {
    const char *name;
    logger_fn log;
};

static logger_fn g_log = say;
static logger_fn tbl[2] = { say, say };

p = counts;                 /* a local may point at a variadic function too */
r = p(2, 3, 4);
s.log("sink %s %d\n", s.name, r);
```

- The `...` is part of the function pointer's **signature spelling**: it is written into `(*)(…)`
  together with the other parameters, so a typedef, a struct field, an array of pointers and a local
  declaration all carry it (§4.22 explains what `...` means).
- The rule matches §4.22: there must be at least one named parameter in front of `...`. Both `(...)`
  and `(void, ...)` report `a variadic function pointer needs a named parameter before '...'`.
- A call through the pointer is an ordinary call; extra arguments are passed through unchanged, and
  ct does not check their types (exactly as with `printf`).

#### 4.32 The comma operator (ct-ast)

```c
i = 1, j = 2;
for (i = 0, j = 10; i < 3; i++, j--) sum = sum + j;

bump(&i), bump(&j);
x = (i++, j * 2);              /* a value position needs the parentheses */
```

- A full expression may be a list of assignment-expressions joined by `,`: they run left to
  right and the value is the last one.
- Accepted positions:
  - an expression statement and a `for` init / step clause (all three share one parse entry
    point). Each operand is parsed as an assignment-expression, so `i = 1, j = 2` is
    `(i = 1), (j = 2)`, exactly as C reads it;
  - **a parenthesised list in a value position**: `x = (a, b);`, `f((a, b))`, `while ((a, b))`.
    There the list is an ordinary expression whose value is the last operand; its operands may also
    be assignments (§4.34).
- The generated C writes the list as `(a, (b, c))`: the right-nesting is a parse artefact and the
  evaluation order is still left to right.
- Still not accepted: a **bare** comma in a `for` condition (`for (; a, b; )`). A comma between
  arguments is always a separator, so a value comma needs the parentheses.

#### 4.33 Type names that only a header declares (ct-ast)

```c
#include <time.h>

static time_t g_base;

struct Stamp {
    time_t when;
};

static void show(time_t t) { printf("%ld\n", (long)t); }

int main(void)
{
    time_t now;                /* unknown type + name */
    time_t *ref;               /* unknown type + `*` + name */
    now = 7;
    ref = &now;
    show(*ref);
    return 0;
}
```

- ct does not expand `#include`, so a header's typedefs are unknown names to the parser. In a
  declaration position, an unknown identifier followed by its declarator is taken as the type and
  its spelling is kept; whether it really is a type is the C compiler's call.
- The test: the name must not be a registered type (struct / union / enum / trait / typedef), must
  not already be a declared variable or function, and must not be a statement keyword. So
  `return found;`, `goto done;` and `own Box *b` still parse as statements, and `a * b;` (with `a`
  a variable) is still an expression.
- A cast or `sizeof` takes one too: `(time_t)raw`, `(time_t *)&t`, `sizeof(time_t)`. The test is
  stricter than in a declaration — the name must be followed by `)` (optionally behind stars), and
  it must be neither a declared variable / function nor an ALL_CAPS macro constant. So `(f(x))`
  is still a call in parentheses and `(MAX) + 1` is still an expression.

#### 4.34 An assignment used as a value (ct-ast)

```c
while ((c = getchar()) != EOF) { … }
if ((n = parse(line)) > 0) { … }

x = (a = b = 0);          /* right-associative */
y = (arr[0] = 4) + 1;     /* subscript target */
z = (p->n = 7);           /* member target */
w = (a += 2);             /* compound assignment */
```

- Inside parentheses, and in an `if` / `while` / `do … while` / `switch` / `for` condition, an
  assignment may be used as a value: `(c = getchar())` yields the assigned value, `a = b = 0` nests
  to the right, and `+=` and friends work the same way.
- A statement's own assignment is unchanged: `x = 1;` still goes through the statement layer and is
  emitted without parentheses.
- The target must be a variable, member, subscript or dereference; otherwise
  `assignment target is not assignable` is reported.
- An `own` target is refused: `an 'own' variable can only be assigned in a statement`. Ownership
  (AutoDrop / the leak analysis) is accounted for at statement level only, and a value-position
  assignment would slip past it.

#### 4.35 C11 alignment and generic selection (ct-ast)

```c
_Alignas(16) int g_a;            /* file scope */
static _Alignas(16) int g_b;

struct Frame {
    _Alignas(8) int kind;
    int size;
};

int main(void)
{
    _Alignas(16) int local;      /* block scope */

    printf("%d\n", (int)_Alignof(double));   /* a type name, not an operand */

    int n = 0;
    double d = 0.0;
    int kind_n = _Generic(n, int: 1, double: 2, default: 3);   /* 1 */
    int kind_d = _Generic(d, int: 1, double: 2, default: 3);   /* 2 */
    return 0;
}
```

- `_Alignas(…)` is part of the type spelling: the parser copies it verbatim in front of the
  declared type, so all five declaration entries — global, local, field, parameter, `typedef` —
  pick it up with no extra syntax. The output is `_Alignas ( 16 ) int x`, and whether that is
  valid is the C compiler's call. Other specifiers still come first
  (`static _Alignas(16) int g;`); the order `_Alignas(16) static int g;` is not part of the subset.
- `_Alignof(type)` shares `sizeof(type)`'s node and accepts the **type** form only: `_Alignof x`
  reports `_Alignof needs a type in parentheses` (C11 allows nothing else either).
- `_Generic(…)` is passed through whole: the controlling expression and every arm are handed to
  the C compiler (the tokens are joined with a space), which does the type match and the arm
  choice. ct never reads an arm, so a trait call or a boxing inside one is **not** rewritten —
  write arms the C compiler can take on its own.
- All three are parsed and re-emitted by ct-ast; the pass-through behaviour of L0 / L2 is
  unchanged, and the generated `.c` keeps the C11 spelling, so the C compiler that builds it must
  accept the form (clang and GCC do).

#### 4.36 GNU `__attribute__((…))` (ct-ast)

```c
static void trace(const char *fmt, ...) __attribute__((format(printf, 1, 2)));

int g_tick __attribute__((aligned(16)));

struct Frame {
    int kind __attribute__((aligned(8)));
    int size;
} __attribute__((packed));

typedef int word __attribute__((aligned(8)));

static int twice(int n __attribute__((unused))) { return 2 * n; }
```

- `__attribute__((…))` is a GNU extension; ct only carries it into the output **verbatim**. The
  attribute list (including nested arguments such as `format(printf, 1, 2)` or `aligned(8)`) is
  captured token by token, consecutive `__attribute__` groups are captured together, and the text
  is re-emitted at the declaration's **same trailing position**; the C compiler owns the meaning.
- Accepted positions: function declarations and definitions (after the parameter list, before `;`
  or `{`), parameters (after the name / dims), struct fields (after the name / dims, and after a
  bit-field's width), globals (after the declarator, before `=`), after a `typedef` alias, and after
  the `}` of a `struct` / `union` / `enum` definition.
- A typedef'd record emits its attribute **before the alias** — `} __attribute__((packed)) Alias;`
  — the one position where clang and GCC both honour `packed` / `aligned` on the type; an attribute
  written after the alias is moved there.
- Boundaries: an attribute **before** the declarator (`__attribute__((unused)) static int x;`),
  local variables, and `impl` / trait methods are outside the subset. An unclosed list reports
  `unterminated __attribute__`; writing one declaration's attribute in both captured positions
  reports `duplicate __attribute__ on one declaration`.
- The generated `.c` keeps the attribute spelling, so the C compiler that builds it must accept it
  (clang and GCC do).

#### 4.37 Integer literal suffixes and the remaining C spellings (ct-ast)

```c
_Noreturn void stop(void);
static_assert(1 + 1 == 2, "arithmetic works");

unsigned long a = 0xFFu;      /* any case */
long b = 0777L;
unsigned long long c = 1ULL;  /* any order: uLL / LLu / lL all become ULL */

static int mix(const int *__restrict a, int *__restrict__ b) { return *a + *b; }
```

- An integer literal accepts `U` / `L` / `UL` / `LL` / `ULL` in any case and order (decimal,
  hexadecimal and octal alike). The suffix is **spelling only**: the value does not change, and the
  emitter normalizes it to `U` before `L` (`0xFFu` → `0xFFU`, `16l` → `16L`).
- A malformed suffix (more than one `U`, more than two `L`s) reports
  `an integer suffix may be U, L or LL`.
- The value is still held in a `long`: a `ULL` literal above `LONG_MAX` wraps as a `long`. That is
  the existing capacity boundary (unlike a floating literal, which is kept as spelling).
- `static_assert` is the C23 / `<assert.h>` spelling of `_Static_assert`; both are accepted and the
  emitter always writes `_Static_assert`.
- A function's `_Noreturn` belongs to the **first declaration**: `void f(void) {}` after
  `_Noreturn void f(void);` does not erase it.
- `__restrict` / `__restrict__` are synonyms of `restrict` and stay in the type spelling verbatim.

#### 4.38 Header-style declaration order (ct-ast)

```c
_Atomic(int) counter;                          /* `_Atomic int` works too */
_Alignas(16) static int aligned;
__attribute__((aligned(32))) static int tagged;

__attribute__((unused)) static int helper(int n);   /* prototype first, plain definition */

int main(void)
{
    _Alignas(8) static int local;
    __attribute__((unused)) int spare = 7;
    int trailing __attribute__((unused));

    printf("%d\n", (int)sizeof(_Atomic(int)));
    return 0;
}
```

- `_Atomic(type)` and bare `_Atomic` are both kept in the type spelling, and declarations,
  block scope, casts and `sizeof` all recognise them; the atomic semantics belong to the C
  compiler.
- `_Alignas(…)` may be written **before** the storage class (file and block scope alike). The
  emitter normalises the order to `static _Alignas ( 16 ) int aligned;`; writing it twice in one
  declaration reports `duplicate _Alignas on one declaration`.
- A GNU `__attribute__((…))` may appear **before the declarator** on globals, function prototypes /
  definitions and local variables; a local also accepts the trailing form. Wherever it is written,
  it is emitted at the declaration's trailing position (before `=` on a local). Writing it on both
  sides reports `duplicate __attribute__ on one declaration`; an attribute that is not followed by
  a declaration reports `an attribute must prefix a declaration`.
- An unclosed `_Atomic(type)` reports `unterminated _Atomic`.
- Boundaries: attributes on `typedef` / `trait` / `impl` / record definitions remain outside the
  subset; whether `_Alignas` applies to a given object is the C compiler's verdict.

#### 4.39 Trait default methods (batch 36, ct-ast only)

```ct
trait Logger {
    int write(char *buf, int len);                 /* abstract */

    int write_all(char *buf, int len) {            /* default */
        int sent = 0;
        while (sent < len) sent = sent + self->write(buf + sent, len - sent);
        return sent;
    }
}

struct Conn { int fd; } use Logger;                /* all default: no impl at all */

impl Logger for Conn {
    int write(char *buf, int len) { return send(self->fd, buf, len); }
}
```

- Expansion: a default body is expanded **once per adopting struct**. The function name is still
  `<Struct>_<Trait>_<method>` and its vtable slot is like any impl method; `self->other()` keeps the
  existing dispatch rule (`_self->__<trait>_vptr->other(_self, …)`). There is no shared copy and no
  new dispatch path.
- Inside a default body `self` is `struct <S> *`: fields are readable, sibling methods dispatch, and
  free functions are callable. The adopting struct comes from `use`, so one trait adopted by two
  structs produces two expansions.
- Override priority: an impl method wins over the default body. Abstract methods are still required,
  and a missing one still reports `trait method 'x' is not implemented for struct 'S'`; a trait whose
  methods are all default needs only `use` (a foreign type writes an empty `impl T for S { }`, D-3).
- Diagnostics: a cycle among default bodies with no abstract leaf reports
  `trait 'T' has no non-default method to break the cycle` (at the trait declaration line); a body
  that does not hold for one struct (for example `self->fd` on a struct without `fd`) reports
  `trait T::m (declared at <path>:<line>) cannot be expanded for struct S: <reason>`, pointing back
  at the trait rather than at the adoption site.
- Boundaries: no field injection, no supertraits, no shared trait-level default body; `Drop` is
  unaffected.

#### 4.40 `borrow` and `Handback` (Phase 5 follow-on, ct-ast only)

Like `own`, `borrow` is a **contextual keyword**: it is recognised only in a parameter list or as
the first token of a statement, and stays an ordinary identifier everywhere else (the function name
`borrow` is unaffected). It states that the pointer is borrowed: hand it back at exit, never free it.
`Handback` is a **built-in trait** handled like `Drop` (no vptr, no vtable; only
`<S>_Handback_handback` is emitted), and users do not declare it.

```c
struct Conn { int fd; int in_use; } use Handback;

impl Handback for Conn {
    void handback() { self->in_use = 0; }      /* return: the object stays alive */
}

void render(borrow struct Conn *c)             /* stage one: annotation, no codegen change */
{
    printf("%d\n", c->fd);
}

int main(void)
{
    borrow struct Conn *c = acquire(0);        /* stage two: declaration + handback at exit */
    render(c);
    return 0;                                  /* → if (c) { Conn_Handback_handback(c); c = 0; } */
}
```

| Shape | Expansion |
| --- | --- |
| parameter `void f(borrow Request *r)` | drop `borrow`; the parameter is recorded as borrowed (output unchanged) |
| `borrow Conn *c = expr;` | drop `borrow` and declare as usual; recorded as borrowed |
| the declaring scope's closing `}` / before **every** `return` (branches and inline included, no position requirement) | insert `if (c) { Conn_Handback_handback(c); c = 0; }` (one list shared with `own`, reverse declaration order) |
| `delete c;` on a borrow | compile error: the object is not this scope's to free |
| `g = c;` / outer local `x = c;` | compile error: the borrow outlives its target |
| `c = other;` (reassigning a borrow handle) | compile error: the handback would be silently lost |

Constraints and limits:

- Both the parameter and the declaration must be a **struct pointer**; arrays, `static` locals and a
  `switch` body are errors; a file-scope `borrow` reports `'borrow' is only allowed inside a function body`.
- A borrow handle **cannot be reassigned** and **cannot be stored** in a `static` local or a
  file-scope variable (all compile errors) — each would silently lose the handback.
- A declaration needs an initialiser, the type must `use Handback`, and `impl Handback for S` must
  exist; otherwise it is an error (no default body — "hand back" would silently do nothing).
- Exit injection mirrors `own` but **never frees**: it calls `handback` and nulls the pointer, because
  a handed-back object still lives in the pool and may be re-borrowed.
- `return c;` (a local borrow escapes) reports `warning: a borrowed pointer escapes through 'return'`
  and **cancels the injection**; `return r;` (a borrowed parameter) only warns.
- The `Handback` implementation lives on the **borrowed object** (at exit the compiler only holds
  `T *c`), exactly as `Drop` does. The struct table is rebuilt per **translation unit** though, so
  `impl Handback for S` must share the unit with the `borrow`; borrowing across units reports
  `struct '<S>' uses trait 'Handback' but this unit has no impl` (the same cross-unit limit `Drop` has).
- Known limits (state them honestly): `store(c)` (a callee parameter not marked `borrow`) and the field
  store `s->p = c` are not checked; a `goto` jumping over the declaration fails silently; pooled and
  stack objects are not distinguished. **Never claim that `borrow` removes dangling altogether.**

Diagnostics (English, lowercase, no trailing period, identifiers in single quotes):

```text
'borrow' is only allowed inside a function body
'borrow' requires a struct pointer parameter
'borrow' requires an initialiser of struct pointer type
struct '<S>' does not use trait 'Handback'
struct '<S>' uses trait 'Handback' but this unit has no impl
a borrowed pointer cannot be deleted
a borrowed pointer cannot be reassigned
a borrowed pointer cannot be stored in '<name>' (its scope outlives the borrow)
'borrow' is not supported inside a switch
'borrow' does not support arrays
a static local cannot be 'borrow'
warning: a borrowed pointer escapes through 'return'
```

Design and implementation notes: [design/borrow.md](history/design/borrow.md).

#### 4.41 Raw passthrough (`#ct-raw`, Phase 17.3, ct-ast only)

ct-ast regenerates C node by node, so a C fragment it cannot rewrite (a macro, a hand-written
function, a `#pragma`) needs an explicit pass-through: everything between `#ct-raw` and
`#ct-endraw` lands in the generated `.c` **byte for byte**, never touching the lexer or the parser.

```c
#include <stdio.h>

#ct-raw
#define TRIPLE(x) ((x) * 3)
static int raw_helper(int n)
{
    return n + 1;
}
#ct-endraw

int main(void)
{
    printf("%d\n", TRIPLE(raw_helper(2)));
    return 0;
}
```

| Shape | Expansion |
| --- | --- |
| `#ct-raw` on its own line **at column 1** | opens the block; its text joins the top-level declaration stream in source order |
| any text inside the block | copied into the literal pool and written out byte by byte (no tokenising, no padding) |
| `#ct-endraw` on its own line at column 1 | closes the block; the generated `.c` then writes `#line <first line after the block>` (line mode is on) |
| `--no-line` | the block is still emitted verbatim, only the `#line` re-anchor is dropped |
| a `.h.ct` unit | the block goes into the `.c` only, never into the `.h` |

Constraints and diagnostics:

- One block is capped at **32768 bytes** (`raw block exceeds 32768 bytes`).
- The markers must sit **at column 1** (`  #ct-raw` reports `#ct-raw must start at column 1`), and
  only whitespace may follow them.
- An unclosed block is reported at its **opening line** (`unclosed #ct-raw (expected #ct-endraw)`);
  a stray `#ct-endraw` is `#ct-endraw without #ct-raw`; trailing text on the closing line is
  `unexpected text after #ct-endraw`.
- The block is available in an ordinary `.ct` / `.h.ct` unit only: the `.m.ct` prologue whitelist
  still admits `#include` / `#define` alone.
- L0 / L1 pass lines through as they stand, so the block already reaches their output; the rule binds
  ct-ast only. The compiler's **own sources** (`selfhost/ct-ast/**`) must not use a block, which
  `selfhost/check-ast.sh` enforces.

### 5. Naming contract

The namespace prefix is a **feature removed from L0**; Phase 2 restored it under `selfhost/l2/**`
(this document does not cover it).

| Artifact | Rule | Example (trait `Greeter`, struct `Person`, method `greet`) |
| --- | --- | --- |
| vtable type | `<Trait>_vtbl` | `struct Greeter_vtbl` |
| interface value type | `<Trait>_iface` | `struct Greeter_iface` (a fat pointer `{ self, vt }`) |
| vptr field | `__<lowercase trait>_vptr` | `__greeter_vptr` |

### 6. Diagnosed constraints and known issues

#### 6.1 Diagnosed constraints

| Constraint | On violation |
| --- | --- |
| traits referenced by `use` must be defined (and appear before the struct) | `error: struct 'S' uses undefined trait 'T'` + `exit 1` |
| the trait and struct of an `impl` must both be defined | `error: impl for undefined trait/struct 'X'` + `exit 1` |
| a struct must `use` a trait before it can `impl` it | `error: struct 'S' does not use trait 'T'` |
| an impl must not contain methods the trait does not declare | `error: method 'm' is not declared in trait 'T'` |
| an impl must implement **every** method of the trait (ct-ast: a default body exempts it) | `error: trait method 'm' is not implemented for struct 'S'` |
| ct-ast: default bodies dispatch each other in a cycle with no abstract leaf | `error: trait 'T' has no non-default method to break the cycle` |
| ct-ast: a default body does not hold for one adopting struct | `error: trait T::m (declared at <path>:<line>) cannot be expanded for struct S: <reason>` |
| braces and parentheses must balance | `error: unterminated '{'` |
| a `trait` / `impl` header must be complete (name, `{`, `for`) | `error: expected trait name` / `expected '{' after trait 'X'` / `expected trait name after 'impl'` / `expected 'for' in impl of 'T'` |

**Not** checked: whether method signatures agree with the trait (parameter types, arity and return type
are never compared — everything is copied verbatim). A redefined trait/struct name is not silently
accepted: ct-ast reports `duplicate trait '<name>'` / `duplicate struct '<name>'`, while L0 and L2 still
pick the first occurrence and leave the later definition unreachable.

#### 6.2 Known limitations

- The variable table is type-less; variables roll back at **brace block scope** (pushed at `{`,
  restored at `}`), and within one scope a repeated name resolves to the **earliest** registration
  (`find_var` returns the first match).
- **Registration order = source order**: calls appearing before the variable's declaration are not
  rewritten.
- **(L2 only, the line-rewriting pipeline)** Call statements spanning multiple lines are not rewritten
  (processing is line by line); a function signature whose **parameter list** spans several lines is not
  recognised either. ct-ast is an AST pipeline and is bound by neither.
- **(L2 only, the line-rewriting pipeline)** A block comment `/* … */` is only protected on its first
  line: continuation lines are treated as ordinary source lines, so `self`, method calls and the rest
  inside them ARE rewritten (single-line `/* … */`, `//` and string / character literals are unaffected).
  This is an inherent limit of line-based processing and Phases 2–5 keep it as they redo the features in
  CT (see "Restoring and adding features after self-hosting" in the [roadmap](roadmap.md)). **ct-ast
  keeps no source comments**: a whole comment, including any code inside it, is dropped, and generated
  output carries only the provenance banner (retaining them would be a separate project).
- **File-scope objects / arrays**: the vptr is written before `main` by the generated constructor
  `__ct_init` (`__attribute__((constructor))`, D5 = A).
- Arrays only support `Type name[<n>];` (no initialiser, constant subscripts).
- **Heap objects are initialised automatically** (Phase 1, D1=A): `T *p = malloc(sizeof(struct T));` /
  `calloc` writes the vptrs (nested fields included) right after the declaration.
- Interface polymorphism: interface **arrays** are unsupported; an interface **field** does not
  participate in construction-point recursion (a value field starts empty and must be assigned);
  boxing accepts only a **variable**, `&variable` or a call returning the same interface — any other
  expression `die`s. **Dispatch** through an interface field is supported
  (`s.lhs.m()` → `s.lhs.vt->m(s.lhs.self)`, a pointer field hops with `->`), and a **statement
  assignment** into a **value** interface field is boxed; an interface field inside a **designated
  initialiser** is not boxed, and a **pointer** interface field's assignment is left verbatim (see §4.8).
- **ct-ast relaxes the interface limits above** (fixed after v0.12.0; L0 / L2 are unchanged): an
  interface **value** field and an interface **pointer** field both box a concrete struct given as a
  bare variable or `&variable` in a construction (the pointer form takes the address of the compound
  literal); an interface-pointer variable / parameter (`Expr *xs`) dispatches per element
  (`xs[i].m()`, the element being a value, not a pointer); a **struct-typed array field** gets its
  vptrs written per element (`Num ab[2]` dispatches directly); and a function prototype keeps the
  array dimension of a parameter (`int f(Expr a[])`). Richer initialiser expressions (an arithmetic
  expression or a call result poured straight into an interface field) still pass through verbatim.
- **(L2 only)** A single-line function body (`int f() { … }` on one line) is not processed, matching
  Phase 0's line-by-line rewriting. By the same rule, a statement **sharing its line** with a construct
  is not rewritten either: a one-line interface boxing and a one-line rvalue receiver both pass
  through. (An `impl` construct is the exception: its method body is extracted as a whole by block
  matching, so it goes through the rewriting pipeline even when it shares the header's line.) ct-ast
  has none of these limits: multi-line statements and single-line bodies are rewritten normally.
- An incomplete `struct` header (no `{`) is not treated as a construct and passes through. `trait` /
  `impl` are ct-only keywords: a line that starts with one and is followed by an identifier or `{` is
  an attempted construct, so a malformed header is an error (other follows, like `impl[n] = 0;`, still
  pass through).
- Top-level constructs cannot be nested.
- **`static` entities in the output that are declared but never used**: an `impl` always emits
  `<S>_<T>_vtable` and a struct that `use Drop` always emits `<S>_Drop_drop`, even when the unit never
  calls that trait's methods and never `delete`s (ct-ast does no cross-procedure reachability). They all
  carry `__attribute__((unused))`, so `cc -Wall -Wextra` stays quiet; the attribute comes from the same
  GCC / clang family as `__ct_init`'s `__attribute__((constructor))`. Semantics and behaviour are
  unaffected.

### 8. Out of scope

The full set of visibility modifiers (`pub readonly` / `setter`), generics, inheritance, type checking,
nested definitions. (Error recovery is an L0 boundary; the CT line collects several errors before
reporting, see §10.)

### 9. Diagnostics

- **Errors**: `<file>:<line>:<col>: error: <message>` on stderr; L0 **exits immediately** with code
  `1`, while the CT line collects several errors first (§10).
- **L0 produces no warnings at all**; the CT line reports leak and signature-mismatch warnings, and
  `--diagnostics` switches them to JSON (§10).
- Exit code: `0` on success; `1` on syntax / semantic / I/O errors.
