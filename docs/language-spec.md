# .ct 语言规范

> 中文 · [English](#english)

> **状态**：本文描述 **ct 语言的核心语法**——L0（`ctc.c`）、CT 线（L2，`selfhost/l2/**`；冻结的回归
> oracle）与安装入口 ct-ast（`selfhost/ct-ast/main.ct`）**共同**接受与产出的部分。CT 线是 L0 的超集，额外支持 `namespace` / `import` / `pub` / 多文件 `ct build` /
> `Drop` / `#line` / 泄漏警告与 `--diagnostics`；这些**不在本文的语法章节内**，语义与落地记录见
> [roadmap](roadmap.md) 的 Phase 2–5、[design/restore.md](design/restore.md) 与
> [design/phase5.md](design/phase5.md)。AutoDrop（`own`）虽然也是 CT 线独有，但在 §4.9 一并描述。
> Phase 11.1 新增的 `map`（把 trait 方法绑定到已声明的全局实例；SH-20 起也可绑定到命名空间）**仅 ct-ast** 支持，L0 与 L2 都不接受，见 §4.10。
>
> 三者并非逐字节等价：ct-ast 是安装入口，L2 只是回归 oracle。已知分叉如下：
>
> | 构造 | L2 | ct-ast |
> | --- | --- | --- |
> | 块式 `namespace A::B { … }` | 接受 | 拒绝（`a namespace is file-scoped`） |
> | 跨命名空间裸调用 | 接受并回退到根表 | 拒绝（要求限定写法 `A::f()`） |
> | 其它 C 透传（`goto` / 标签、`enum`、`union`、`offsetof` 等） | 原样透传 | 只接受已实现的语法子集，报 `unexpected token` |
>
> 这是两层的**能力差**，不是「尚未实现」：L0 命中上述构造仍报
> `'namespace' is not supported by this compiler`（`pub` / `import` / `ct build` 同类；
> `--line` / `--no-line` / `--diagnostics` 报 `unknown option`）。归档 fixture 见 `test/archive/`，
> 特性完整的旧实现见 git tag `overreach-oracle`。

本文描述核心语法的输入规则、展开规则、命名规则与诊断行为。凡本文未写明的行为，均属未定义，不应依赖。

## 中文

### 1. 源文件模型

一个 `.ct` 文件是「若干顶层构造」与「原样透传的 C 代码」的混合体。
编译器**单趟顺序扫描**，按源码顺序处理：顶层构造被展开成 C，其余内容逐行透传。
因此**顺序敏感**：所有定义必须出现在使用之前。

```
program  ::= { item }
item     ::= trait-def | struct-def | impl-def | raw-text
```

顶层构造只能出现在文件的最外层（不支持嵌套），且其关键字必须位于行首（允许前置空格/制表符）。

生成物的第一行固定是溯源注释 `Generated by ct v<版本> from <输入路径> -- do not edit; ...`（`.h` 头部也有一段等效注释），它不属于源文件内容。

### 2. 词法与书写要求

- 关键字（`trait` / `struct` / `impl` / `use` / `for`）必须成**独立单词**出现，由 `word_at()` 做词边界判断；`traitx`、`my_struct` 不会被误判。
- `namespace` / `pub` / `import` 已不再是关键字：这三个词现在会被编译器拒绝（见开头的状态说明）。
- 行首的 `trait` / `impl` / `struct` 只有在**完整构造头部**紧跟其后时才算构造（`trait IDENT {`、`impl IDENT for`、`struct IDENT {`），否则按原样透传。因此把 `trait` / `impl` 当作普通标识符的合法 C（如 `impl[0] = 1;`、`trait = 2;`）不会被误判。
- 重写**按行**进行：构造与普通语句写在同一行时，语句不会被重写（`int main(void){ Person p = {…}; p.greet(); }` 中的 `p.greet()` 保持原样）。
- 所有固定容量上限（标识符长度、参数个数与文本、字段 / 方法 / trait / struct 数、变量数、作用域深度等）越界一律 `die` 报错，**不静默截断**。
- 空白、换行、`//` 行注释、`/* */` 块注释在构造头部可自由插入。
- trait 体内的方法声明以 `;` 分隔，允许一条声明跨多行；注释在切分前被剥离。
- struct 体内的字段原样保留、不做解析。
- 标识符为 `[A-Za-z_][A-Za-z0-9_]*`；超出 127 字符会**报错**（`identifier too long`），不再静默截断。

### 3. 语法

```ebnf
trait-def   ::= "trait" IDENT "{" { method-decl } "}" ;
method-decl ::= type-spec IDENT "(" [ param-list ] ")" ";" ;

struct-def  ::= "struct" IDENT "{" raw-text "}" [ use-clause ] [ ";" ] ;
use-clause  ::= "use" IDENT { "," IDENT } ";" ;

impl-def    ::= "impl" IDENT "for" IDENT "{" { method-def } "}";
method-def  ::= type-spec IDENT "(" [ param-list ] ")" block ;

param-list  ::= param { "," param } ;
param       ::= type-spec [ IDENT ] ;   (* type-spec 可含 *、const 等 *)

type-spec   ::= <C 类型写法，取到方法名/参数名之前的全部字符>
```

约定：

- `use` 子句可紧跟 `}` 写在同一行，也可另起一行。
- 单个参数写成 `void` 视为**无参数**。
- struct 定义后的分号可选（`};` 与 `}` 都接受）。
- `param` 的类型与名字靠**启发式**切分：取参数文本的最后一个标识符作为参数名，除非它是类型关键字（`void`/`char`/`int`/`unsigned`/`size_t` …）或参数文本以 `*` 结尾。

#### 3.1 表达式（ct-ast）

ct-ast 按 C 的优先级解析表达式，支持的运算符子集由紧到松为：

| 层级 | 运算符 |
| --- | --- |
| 一元 | `!` `~` `-` `&`（取地址） `*`（解引用）、强制转换、`sizeof` |
| 乘除 | `*` `/` `%` |
| 加减 | `+` `-` |
| 移位 | `<<` `>>` |
| 比较 | `<` `>` `<=` `>=` `==` `!=` |
| 位与 | `&` |
| 位异或 | `^` |
| 位或 | `\|` |
| 逻辑 | `&&` `\|\|` |
| 条件 | `?:` |
| 赋值 | `=` 以及复合赋值 `+=` `-=` `*=` `/=` `%=` `&=` `\|=` `^=` `<<=` `>>=` |

生成物给每个二元 / 一元运算都加括号，因此源码语义不依赖 C 侧的优先级重排。
L0 / L1 / L2 不解析表达式（按行透传），本表只约束 ct-ast。

### 4. 展开规则

#### 4.1 trait → vtable 类型

```c
trait Greeter { void greet(); int add(int a, int b); }
```

```c
struct Greeter_vtbl {
    void (*greet)(void *);
    int (*add)(void *, int, int);
};
```

每个方法多出一个前置参数 `void *`；参数列表在 vtable 中**只保留类型、去掉参数名**。

#### 4.2 struct + use → 追加 vptr 字段

```c
struct Person {
    char *name;
    int age;
} use Greeter;
```

```c
struct Person {
    char *name;
    int age;
    struct Greeter_vtbl *__greeter_vptr;
};
```

字段体原样保留，vptr 字段按 `use` 的书写顺序追加在末尾。

#### 4.3 impl → 静态方法 + vtable 变量

```c
impl Greeter for Person {
    void greet() {
        printf("Hello, %s\n", self->name);
    }
}
```

```c
static void Person_Greeter_greet(void *self) {
    struct Person *_self = (struct Person *)self;
    printf("Hello, %s\n", _self->name);
}

static struct Greeter_vtbl Person_Greeter_vtable = {
    .greet = Person_Greeter_greet
};
```

- 生成函数的参数是「`void *self` + impl 中书写的方法参数」，函数体第一行固定为 `_self` 强转。
- 方法体的缩进按最小公共缩进去除后重新以 4 空格排版。
- **方法体走与顶层代码完全相同的重写管线**：先把 `self`（指向当前 struct 的指针）与 impl 中书写的
  方法参数登记进变量表，再逐行 `transform_line`，最后把标识符 `self` 重命名为 `_self`。因此方法体内
  的各类接收者都会被派发，与顶层代码无差别：
  - 兄弟方法：`self->other()` → `_self->__<trait>_vptr->other(_self)`；
  - 字段链：`self->field->m()` → `_self->field->__<trait>_vptr->m(_self->field)`（可递归，见 §4.5）；
  - 方法参数：`o->m()` → `o->__<trait>_vptr->m(o)`、`v.m()` → `v.__<trait>_vptr->m(&v)`；
  - 方法体内局部变量：`P q; q.m();` → `q.__<trait>_vptr->m(&q)`。
- 只要某个方法体会产生派发，就会在方法函数之前先输出一行前向声明
  `static struct <Trait>_vtbl <Struct>_<Trait>_vtable;`，以解决 vtable 变量的前向引用
  （C 的 tentative definition，随后再带初始化式定义，合法）。
- vtable 初始化项按 **trait 中方法的声明顺序**排列，而不是 impl 中的书写顺序。
- 跨单元（ct-ast `build` 模式）：当 trait 与 struct **都标 `pub`** 时，vtable 改为外部链接——声明单元的
  头文件发射 `extern struct <Trait>_vtbl <Struct>_<Trait>_vtable;`，实现单元给出定义，消费单元可直接装箱。
  其它情况仍为 `static`，且同一对 `struct`/trait 的 `impl` 必须位于同一编译单元。

#### 4.4 变量声明 → 限定 `struct` + 追加 vptr 指定初始化

```c
Person p = { .name = "Tom", .age = 36 };
```

```c
struct Person p = { .name = "Tom", .age = 36, .__greeter_vptr = &Person_Greeter_vtable };
```

规则：

| 源码形态 | 处理 |
| --- | --- |
| `Person p = { … };`（指定初始化） | 前缀 `struct `，并在 `}` 前追加 vptr 指定初始化项 |
| `Person p = { "Tom", 36 };`（位置式初始化） | 同上：追加的 vptr 项接在位置式元素之后（C99 允许 `{ 1, .v = 0 }` 混用） |
| `Person p = {};` / `Person p;` | 前缀 `struct `；空列表追加 vptr，无初始化式则补上 `= { <vptr> }` |
| `struct Person p = { … };` | 同上（已有限定符时不重复添加） |
| `static Person p;` / `static Person ps[2];` | 前缀 `static` 原样保留，其余与非 `static` 声明相同（对象补初始化式、数组走 `__ct_init`） |
| `Person *p = …;` | 前缀 `struct `，其余原样输出；指针变量**登记为指针**，故 `p->m()` 会重写为 `p->__t_vptr->m(p, …)` |
| 其它类型 | 完全不动 |

被识别为「结构体类型变量」的名字会登记进变量表，供后续方法调用重写使用。

#### 4.5 方法调用重写

```c
p.greet();
p.greet_name("Jerry");
```

```c
p.__greeter_vptr->greet(&p);
p.__greeter_vptr->greet_name(&p, "Jerry");
```

触发条件（满足 1 或 1′，且 2–4 全满足才重写）：

1. 左边是一个标识符，且它在**本文件此前**已被登记为某 struct 类型的变量（`T x`、`T *x`、
   `T x[n]`、`T *x[n]` 均可）；**或**
1′. 左边是一次调用 `f(...)`，且 `f` 的返回类型是**此前已登记的 struct**（值返回或指针返回均可，
   如 `f().m()`、`mk()->m()`、`f().a.b.m()`）；
2. 若该变量是数组或指针，其后可先跟一个下标 `[<表达式>]`（表达式可为任意平衡内容，例如
   `ps[i]`、`ps[i + 1]`、`ps[f()]`）；
3. 之后是 `.`、`->`，或一串字段跳（每跳 `.field` / `->field`），且**最终**成员名是（跳转后那个
   struct 的）某个 trait 的**方法名**；
4. 成员名后紧跟 `(`。

方法归属的判定顺序：按该 struct `use` 子句中的 trait 顺序查找，**取第一个**声明了该名字的 trait。

重写细节：

- 形如 `x.m()` 的无参调用 → `x.__t_vptr->m(&x)`（不产生多余逗号）。
- 形如 `x.m(a)` → `x.__t_vptr->m(&x, a)`。
- 指针接收者不补 `&`：`p->m()` → `p->__t_vptr->m(p)`，`p->m(a)` → `p->__t_vptr->m(p, a)`。
- 数组元素 / 指针下标：`ps[i].m()` → `ps[i].__t_vptr->m(&ps[i])`；`T *ps[n]` 的元素**自身是指针**，
  故 `ps[i]->m()` → `ps[i]->__t_vptr->m(ps[i])`；而 `T *p` 上的 `p[i]` 是值，补 `&`。
- 指针字段链按**每跳字段是否为指针**决定 `.` 或 `->`，末跳经指针则不补 `&`：
  `a.next->m()` → `a.next->__t_vptr->m(a.next)`；`a.next.m()`（`next` 是值字段）→ `a.next.__t_vptr->m(&a.next)`。
- 参数内部的嵌套调用会被继续处理：`q.add(1, q.add(2, 3))` → `q.__greeter_vptr->add(&q, 1, q.__greeter_vptr->add(&q, 2, 3))`。
- **右值接收者**（条件 1′）：接收者先被提升为一个临时变量，求值**恰好一次**，再按上面同一规则派发。
  临时变量名为 `__ct_tmp<N>`（`N` 在单个文件内递增，从 0 开始）：
  - 值返回：`f().m(a)` → 前一行 `struct S __ct_tmp0 = f();`，本行 `__ct_tmp0.__t_vptr->m(&__ct_tmp0, a)`；
  - 指针返回：`mk()->m(a)` → 前一行 `struct S *__ct_tmp0 = mk();`，本行 `__ct_tmp0->__t_vptr->m(__ct_tmp0, a)`。
  - 提升**只允许**在两种位置：接收者位于**语句行首**（`f().m();`），或位于**赋值 / 声明初始化式的
    右值行首**（`int r = f().m();`）。这两种位置求值无条件且有序，提升到前一行**不改变语义**。
  - 接收者出现在其它位置（如 `x = 1 + f().m();`、`g(f().m());`）时无法在不改变求值顺序的前提下重写，
    **按 `文件:行:列: error:` 报错退出**，而不是产出明知编不过的 C。
  - 提升出的临时变量声明文本为等宽对齐的源行缩进；它在生成的 `.c` 中占一行。
- 字符串字面量、字符字面量、注释内的内容**永不重写**。
- `impl` 方法体与顶层代码共用同一重写管线：方法体内的 `self->m(...)`、字段链 `self->f->m(...)`、
  参数接收者 `o->m(...)`、局部变量接收者 `q.m(...)` 都按同一规则重写（见 4.3）。
- **仅变量下标接收者的表达式会被求值两次**（`ps[i]` 在产物里出现两遍），因此带副作用的下标
  （如 `ps[i++]`）不保证正确；右值接收者（1′）用临时变量，只求值一次。

#### 4.6 普通函数的签名 → 限定 struct 类型

```c
void show(Person p);
static Person make(char *n);
Person *pick(Person *a, Person *b);
```

```c
void show(struct Person p);
static struct Person make(char *n);
struct Person *pick(struct Person *a, struct Person *b);
```

规则：

| 源码形态 | 处理 |
| --- | --- |
| 返回类型里的已知 struct 名（含 `static` 等前缀词、多词类型、指针返回） | 原地插入 `struct `（其余字符原样保留） |
| 值参数 `Person p` | 插入 `struct `；**有函数体时**把参数登记进变量表（`ptr=0`），使体内 `p.m()` 可被重写 |
| 指针参数 `Person *q` | 插入 `struct `；登记为指针（`ptr=1`），使体内 `q->m()` 可被重写 |
| 函数原型 `void f(Person *q);` | 只限定类型，**不登记**参数（没有函数体） |
| 参数已写成 `struct X …` | 不重复插入 `struct ` |
| `if` / `while` / `else if` / `return …` 等语句 | 不会被误判为函数签名 |
| 参数**列表本身跨多行**的签名 | 不识别，按原样透传 |

#### 4.7 组合、数组与堆对象（构造语义）

vptr 在「构造点」写入：对象**自身**的 vptr 写进初始化式；**嵌套字段 / 数组元素 / 堆对象**改用
**声明之后的赋值语句**（避免追加的 `.field` 指定初始化覆盖用户自己写的 `.field = {…}`）。

| 源码形态 | 处理 |
| --- | --- |
| `struct Shop { Person owner; };` | 字段类型补 `struct `：`struct Person owner;` |
| `Shop s;` | `struct Shop s = { … };` 之后追加 `s.owner.__greeter_vptr = &Person_Greeter_vtable;` |
| `s.owner.greet();` | `s.owner.__greeter_vptr->greet(&s.owner);` |
| `Person ps[3];` | 声明 + 块内循环 `for (…; __ct_i < 3; …) ps[__ct_i].__greeter_vptr = …;` |
| `ps[0].greet();`、`ps[i].greet();` | `ps[0].__greeter_vptr->greet(&ps[0]);`（下标可为任意表达式） |
| `Person *ptrs[2]; ptrs[0]->greet();` | `ptrs[0]->__greeter_vptr->greet(ptrs[0]);`（元素自身是指针） |
| `struct Box { Person *who; } … b.who->greet();` | `b.who->__greeter_vptr->greet(b.who);`（指针字段链） |
| `delete q;` | `if (q) free(q);`（`q` 必须是已登记的指针变量） |

命名与限制：

- 数组展开的循环变量固定为 `__ct_i`，包在块内。
- **文件作用域的对象 / 数组**：文件作用域放不下 vptr 赋值**语句**，其 vptr 改由编译器生成的构造器
  `static void __ct_init(void) __attribute__((constructor))` 在 `main` 之前写入（决策 D5 = A）；
  对象本身照常声明，`main` 里可直接派发。
- 数组只支持 `Type name[<n>];`（无初始化式、常量下标）；需要初始化时的其它形态一律 `die`，不静默产出坏 C。
- **堆对象自动初始化**（Phase 1，D1=A）：`T *p = malloc(sizeof(struct T));`（或 `calloc`）在声明后自动写
  vptr（含嵌套值字段），不再需要手写。
- **ct 不对手写 C 里的类型名做限定**：`sizeof(Person)` 不会被改写，请写成 `sizeof(struct Person)`。

#### 4.8 接口多态（trait 作类型）

每个 trait 额外生成一个**接口值类型**（胖指针，`self` + 该对象的 vtable）：

```c
struct Greeter_iface { void *self; struct Greeter_vtbl *vt; };
```

| 源码形态 | 处理 |
| --- | --- |
| `Greeter g;` | `struct Greeter_iface g = { 0, 0 };` |
| `Greeter g = p;` | `struct Greeter_iface g = (struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable };` |
| `Greeter g = q;`（`q` 是 `Person *`） | 同上，`self` 取 `q` 本身（**不加 `&`**） |
| `g = s;` | 按 `g` 的 trait 装箱后再赋值 |
| `void announce(Greeter who);` | `void announce(struct Greeter_iface who);` |
| `announce(p);` | `announce((struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable });` |
| `Greeter pick(void);` | `struct Greeter_iface pick(void);` |
| 返回接口的函数里 `return p;` | `return (struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable };` |
| `g.greet();` | `g.vt->greet(g.self);` |
| `g.greet_name("Jerry");` | `g.vt->greet_name(g.self, "Jerry");` |

**接口作为 struct 字段**（值字段 `T x;` → `struct T_iface x;`；指针字段 `struct T *x;` → `struct T_iface *x;`）：

| 源码形态 | 处理 |
| --- | --- |
| 字段 `Node lhs;` / `struct Node *lhs;` | 字段类型展开为 `struct Node_iface lhs;` / `struct Node_iface *lhs;` |
| `s.lhs.show();` / `self->lhs.show();` | `s.lhs.vt->show(s.lhs.self);`（值字段经 `.`，字段链可递归） |
| `s.p->lhs->show();` | `s.p->lhs->vt->show(s.p->lhs->self);`（指针字段经 `->`） |
| `s.lhs = v;`（**值**接口字段） | 按字段声明的 trait 装箱：`s.lhs = (struct Node_iface){ (void *)&v, &Lit_Node_vtable };` |

规则与限制：

- 只有**变量**或 `&变量`（以及「返回同款接口」的函数调用）能装箱；类型无法推断 → `die`。
- 装箱的目标 trait 由**声明/赋值的左值**或**当前函数返回类型**决定；实参则由**函数签名表**决定，
  因此遵循「定义先于使用」——调用点看不到签名或看不到具体类型时不会装箱。
- 被装箱的 struct 必须 `use` 了该 trait；跨 trait 装箱 → `die`。
- **不做**隐式空检查：空接口值（`{0,0}`）上派发会崩，与 C 一致。
- **L0 限制（本文所述）**：接口**数组**不支持，声明即 `die`；接口字段**不参与**构造点递归，`Node lhs;`
  声明后为空（`vt == NULL`），需自行赋值；装箱仅覆盖**语句赋值**（`s.lhs = v;`），**指定初始化式**
  （`Pair p = { .lhs = v };`）中的接口字段**不装箱**；**指针**接口字段（`struct T *x`）只支持派发，
  赋值保持原样（需要已有胖指针的地址，如 `s.x = &someIface;`）。
- **CT 侧（L2）已扩展**：`selfhost/l2/**` 放开上一条的全部限制，并给出统一的「接口值 / 指向接口值的指针 / 接口值数组 / 接口指针数组」模型；装箱规则在**赋值、构造点、`return`、实参**四处完全一致：

| 形态 | 含义 | 派发 | 下标元素的种类 |
| --- | --- | --- | --- |
| `T x` | 接口值（胖指针） | `x.m()` → `x.vt->m(x.self)` | — |
| `T *x` | 指向接口值的指针 | `x->m()` → `x->vt->m(x->self)` | `x[i]` 是**值**（`x[i].m()`） |
| `T xs[n]` | 接口值数组 | `xs[i].m()` → `xs[i].vt->m(xs[i].self)` | 值 |
| `T *xs[n]` | 接口指针数组 | `xs[i]->m()` | 指针 |
| 形参 `T xs[]` / `T *xs` | 同上，函数体内可下标 | 同左 | 值 |

  另有：接口**数组字段**（`Node items[4]`、`self->items[i].eval()`）、指针接口字段的下标（`s.f[0].m()`）、**构造点**装箱（`Pair p = { .l = v, .ptr = &v };`，值字段与指针字段各走各的 box 路径）、以及**堆对象装箱**（`Num *p = malloc(sizeof(struct Num)); Expr e = p;`）。**仍不支持**：带聚合初始化式的接口指针（`T *g = { ... };`）。**struct 类型的数组字段**（`struct Duo { Num ab[2]; }`）L0 / L2 不支持，**ct-ast 已支持**（逐元素写 vptr，见 §6）。理由同顶部状态说明：本文对 L0 依旧准确，新能力只属 CT 线（L2 / ct-ast），由 `test/acceptance/run.sh` 钉住。

#### 4.9 AutoDrop（Phase 5 新增，仅 CT 线）

`own` 是一个**上下文关键字**，只出现在声明行的行首：它把变量标记为「持有对象生命周期」，
编译器在作用域出口自动释放。它是 Phase 5 新增项，**L0（`ctc.c`）不认识它**（会原样透传），
由 CT 线（L2，`selfhost/l2/**`；ct-ast 行为等价）实现。

| 源码形态 | 处理 |
| --- | --- |
| `own Person *p = malloc(sizeof(struct Person));` | 去掉 `own` 后照常声明；登记 autodrop |
| 声明作用域的闭合 `}`（行首） | 在该行之前插入 `if (p) { Person_Drop_drop(p); free(p); p = 0; }` |
| 函数帧顶层的 `return`（行首） | 同上，插入全部 autodrop 变量的释放（声明逆序） |
| `delete p;` | 既有的 `free`/`drop` 照旧；同时取消 autodrop（不重复释放） |
| `p = …;`（重新赋值） | 取消 autodrop（所有权已转移，不再兜底） |
| `p` 以**独立值**形式出现在赋值右值（`q = p;`）或 `return` 的返回表达式中 | 取消 autodrop（逃逸）；读取字段 / 元素（`x = p->n;`、`x = p[0];`）**不**算逃逸 |

约束与限制：

- 只支持 `own T *p = malloc|calloc(...);`：必须是**结构体指针**、必须由 `malloc` / `calloc` 初始化、
  且该 struct 必须 `use Drop`；否则编译期报错。
- `own` 只允许出现在**函数体内**（文件作用域报错）；不支持数组形态（`own T *ps[n]`）。
- 同一作用域的多个 `own` 变量按**声明逆序**释放。
- 闭合 `}` 与 `return` 必须位于**行首**；行内形式（`b->n = 1; }`、`if (p) return 0;`）编译期报错，
  不静默跳过——逐行注入无法把释放语句安全地放进条件分支。
- `goto` 跳出声明作用域不会触发释放。
- 逃逸判定是**保守**的：变量以独立值形式出现在赋值右值或 `return` 行上即取消 autodrop；漏放（内存泄漏）
  优于错放（重复释放 / 释放借用对象）。

#### 4.10 `map`（Phase 11 新增 + SH-20 扩展，仅 ct-ast）

`map` 把一个 trait 的方法绑定到一处具体的 C 调用，并为该绑定发射包装函数与一张 vtable。宿主有两种
形态；**Phase 11.2 已把两者接入派发**——被当作 trait 接口值使用时（赋给 `T` 类型的变量、传给 `T`
接口参数、从接口返回、或作为函数实参），装箱会使用绑定的 vtable，从而作为该 trait 的实例运行：

- **对象宿主**：`map trait T for instance x { … }`，`x` 是已声明的全局变量，接口值的 `self` 指向它。
- **命名空间宿主**（SH-20）：`map trait T for namespace A::B { … }`，绑定的是命名空间里的一组函数，
  没有对象可挂，接口值的 `self` 为 `NULL`。

`map` 是 Phase 11 新增项，**L0 与 L2 都不认识**，只由 **ct-ast**（`selfhost/ct-ast/main.ct`）支持。

```c
trait Controller {
    int send(char *buf, int len);
}
struct Uart { int fd; };
struct Uart uart1;                                    /* 对象宿主：必须是已声明的全局变量 */

map trait Controller for instance uart1 {
    send(buf, len) -> mock_uart_send(&uart1, buf, len);
}

namespace hal;
pub trait Writer { int write(char *buf, int len); }
int hal_write(char *buf, int len) { return len + buf[0]; }

map trait Writer for namespace hal {                  /* 命名空间宿主：没有对象 */
    write(buf, len) -> hal_write(buf, len);
}
Writer w = Writer::hal;                               /* 装箱：self 为 NULL，vt 指向 hal_Writer_vtable */
```

符号命名：宿主路径把 `::` 换成 `_` 得到 `h`，trait 的 C 名记为 `tr`；若 `tr` 已经以 `h_` 开头则
`p = tr`，否则 `p = h_tr`。包装函数是 `p_<方法>`，vtable 是 `p_vtable`。对象宿主的 `h` 是实例的
C 名（如 `uart1`），命名空间宿主的 `h` 是宿主路径（如 `hal`）。

| 产物 | 规则 | 示例 |
| --- | --- | --- |
| 包装函数 | `<宿主>_<Trait>_<方法>`，首参 `void *self`（体内 `(void)self;`）；对象宿主的**直绑不生成**，命名空间宿主**必然生成** | `static int uart1_Controller_send(void *self, char *buf, int len)`；`static int hal_Writer_write(void *self, char *buf, int len)` |
| vtable 变量 | `<宿主>_<Trait>_vtable`，指定初始化 `.方法 = 包装函数`（直绑时为被绑定的 C 函数本身） | `static struct Controller_vtbl uart1_Controller_vtable = { .send = uart1_Controller_send };` |

约束与限制：

- `for` 之后只能跟 `instance` 或 `namespace`，其它写法编译期报错。
- 对象宿主的 `x` 必须是**已声明的全局变量**（文件作用域），否则编译期报错。实例名可写成**命名空间
  限定形式** `A::B::h`（2b.3）；全局按命名空间 mangling（见 §4.11），实际绑定的 C 名是 `A_B_h`，
  实例的 vtable 与包装函数也以它为前缀（`A_B_h_T_vtable`）。
- **不合成宿主**：编译器不会替未声明的名字合成对象（拼写错误会变成静默的宿主）。没有对象可挂时用
  **命名空间宿主**（`map trait Writer for namespace hal { … }`），而不是伪造 `void *netlib;` 占位变量
  ——后者仍可用，但已不必要。
- 命名空间宿主的路径逐段写 `A::B`。装箱 `T::A::B` 在找不到对应 map 时报
  `no map binds trait 'T' to namespace '<宿主路径>'`（`<宿主路径>` 按源写法回显，如 `nosuch` / `a::b`）。
- 命名空间宿主**不接受直绑**：没有 `self` 可以交给被绑函数，`-> fn;` 会被拒绝
  （`a namespace host has no self: bind with a wrapper call`）。
- 命名空间宿主的装箱语法是 `Trait::ns`，且**只能作为接口值**使用；放进其它上下文（如 `int x = Writer::hal;`）
  报 `a namespace host value is only usable as an interface value`。`Trait::ns(...)` 仍是限定调用，不产生装箱。
- `T` 必须是已定义的 trait；无 vtbl 的 trait 不可映射。
- 绑定方法名必须是 `T` 的既有方法，`( … )` 里的参数个数须与 trait 声明一致。
- 绑定必须覆盖 `T` 的**每一个**方法，且每个方法**只绑一次**：漏绑会让 vtable 留一个空指针槽（调用即崩溃），
  重复绑定会发射两份同名包装函数（C 重定义）；两种情况都在编译期报错。
- `->` 右侧（CALL）是**两级绑定**：
  - **直绑**：调用名是裸 C 函数名（纯标识符）时零生成，vtable 槽直接指向它；直绑不校验签名，
    被绑函数必须自行满足 trait 的槽类型（首参 `void *`）。命名空间宿主禁用直绑（见上）。
  - **fallback**：调用含表达式或成员路径时生成宿主级包装函数。每个实参按标识符逐个校验：字符串 / 字符
    字面量、数字字面量、`.` / `->` 后的成员名、`A::B` 限定名直接放行；其余标识符必须是左括号内的形参名、
    本 map 的实例、此前已声明的变量或 ALL_CAPS 宏，否则编译期报错。
- 多个 map 可作用于同一实例或同一命名空间；`MAX_MAPS`（64）是 map 构造总数上限，超限报错。
- **跨单元**：vtable 在 `pub` trait 且（对象宿主）实例是有 `pub` 全局时外部链接（同 §4.11 的 impl 规则）；
  命名空间宿主没有实例，只看 `pub` trait。头文件声明 `extern`、声明单元给出定义，其它单元可直接装箱。
  否则包装函数与 vtable 发射在**声明该 map 的单元**的 `.c` 里（`static`），不会重复出现在其它单元。
- **派发（11.2 / SH-20）**：对象宿主装箱用**实例级** vtable——
  `Controller c = uart1;` → `c = (struct Controller_iface){ (void *)&uart1, &uart1_Controller_vtable };`
  （注意不是 struct 级的 `&Uart_Controller_vtable`）。因此**即便 `Uart` 未 `use Controller`**，
  `uart1` 也能作为 `Controller` 实例使用。命名空间宿主装箱写成
  `Writer w = Writer::hal;` → `w = (struct hal_Writer_iface){ (void *)0, &hal_Writer_vtable };`。
  此后 `c.send(...)` / `w.write(...)` 都经 `<接口>.vt->方法(<接口>.self, ...)` 派发到包装函数；
  命名空间宿主的 `self` 恒为 `NULL`，被绑函数不得解引用首参。
- `--emit-map` 的 JSON 新增 `maps` 字段，逐条列出 trait / instance / file / line 与 `bindings`
  （method → 生成符号）；每个 map 另有 `"host": "instance"|"namespace"` 标明宿主形态，
  每个 binding 还有 `"wrapper": true|false` 区分 fallback 与直绑。

#### 4.11 跨单元链接：`pub` 全局与 `extern`（ct-ast）

- `pub int g_counter = 5;` 在其定义单元的 `.c` 里发射定义，在该单元的 `.h` 里发射 `extern int g_counter;`；
  其它单元 `import` 后即可按名引用。`pub` 只表示导出：未标 `pub` 的全局仍只属于本单元。
- `extern int lib_flag;` 只声明、不定义：声明进入 `.h`，本单元的 `.c` 不发射定义，符号由外部 C 目标文件
  或库提供。`extern` 不能带初始化式（编译期报错）。`extern` 同样接受函数原型
  （`extern int lib_fn(int);`）：只声明、不定义，`pub extern` 的原型进入 `.h`；`extern` 的名字不参与
  mangling，因为它指向 C 库的符号。
- 导出的类型（`pub struct` / `pub trait` / `pub typedef`）在命名空间内仍可**用裸名**引用：消费者写
  `Writer w;` 或 `struct Uart u;`，编译器解析到 `hal_Writer` / `hal_Uart`。两个被导入的命名空间导出同名
  类型时，裸名报错并要求用别名 import（`import a::b::T as T;`）。类型的**限定写法**（`struct A::B`）仍不支持。
- 命名空间内的全局变量按命名空间 **mangling**：`namespace A::B; int h;` 的 C 名是 `A_B_h`，因此两个命名空间
  可以各有一个 `h` 而不会在链接期冲突。`extern` 是例外——它声明的符号由 C 库提供，保留原名与空命名空间。
- 导入单元可以用**限定名**引用导出的全局：`a::h` 读写 `a_h`；只有一个候选时裸名同样可用。若两个被导入的
  命名空间导出同名全局，裸名会被拒绝并提示改用限定名，避免静默选错对象。
- 跨单元可装箱的边界：`impl` 的 vtable 仅在 **`pub` trait 且 `pub` struct** 同时成立时外部链接——
  头文件声明 `extern struct T_vtbl S_T_vtable;`，实现单元给出定义（不再是 `static`）；否则保持单元私有。
  同一 `struct` 的同一 trait 只能有一个 `impl`，重复定义在编译期报错并指出首个定义所在位置。

#### 4.12 函数指针（ct-ast）

声明位置支持 `ret (*name)(params)`：参数、struct 字段、全局与局部。生成 C 与源码同形，名字留在类型内部。

```c
int (*p)(int);
struct Box { int (*op)(int); };
static int apply(int (*fn)(int), int v) { return (*fn)(v); }
```

- `typedef` 可用：`typedef int (*BinOp)(int, int);` 发射为 `typedef int (*BinOp)(int, int);`，
  别名可作局部、参数与 struct 字段；typedef 一个函数指针数组同理（`typedef int (*Table[2])(int, int);`）。
- 函数指针数组把维度写进声明子内部：`int (*tbl[2])(int, int);`。全局可带初始化器
  （`static int (*tbl[2])(int, int) = { plus, minus };`），局部可逐元素赋值，struct 字段同样支持
  （`int (*cb[2])(int);`）；`tbl[i](x)` 直接调用。
- 文件作用域的初始化器可以命名本单元的函数（`static int (*gp)(int, int) = plus;`）：原型先于全局发射。
- 赋值接受 `p = handler;` 与 `p = &handler;`；函数名作为右值时发射其 C 名。`#include` 引入的库函数
  同样可用（`p = strcmp;`）：CT 符号表里没有的名字原样发射，由 C 编译器按原型校验；普通调用一直如此。
- 调用接受 `p(args)` 与 `(*p)(args)`，两种写法统一发射为 `(*p)(args)`。函数指针字段可以直接调用：
  `c.add(2, 3)`（`.`）与 `p->add(2, 3)`（`->`）分别发射为 `c.add(2, 3)` 与 `p->add(2, 3)`。
- 限制：不返回函数指针；不支持嵌套函数指针（`int (**f)(int)` 报
  `nested function pointers are not supported`）；函数指针数组不能作参数（报
  `function-pointer arrays are not supported as parameters`）；一条声明只写一个名字
  （`int (*a)(void), (*b)(void);` 报错）。

#### 4.13 `switch` 与 `do-while`（ct-ast）

```c
switch (key) {
case 1:
    out = 10;
    break;
case 2:
case KIND_B:                  /* 两个标签共享下一段语句 */
    out = 20;
    break;
default:
    break;
}

do {
    total = total + i;
    i = i + 1;
} while (i < 4);
```

- 一个标签拥有从自身到下一个标签（或 `}`）之间的语句，因此 `case` 与它后面的 `break` 同处一级缩进；
  连续的 `case 1: case 2:` 共享下一段语句，中间可以没有语句。
- `case` 的取值只接受数字（可带一个前置 `-`）、字符 / 字符串字面量、单个标识符（`#define` 常量原样发射，
  已知全局按其 C 拼写发射）。ct-ast 不做常量折叠，所以 `case (1 + 2):` 报
  `a case label must be an integer constant`。
- `switch` 体可以直接写声明，但**不能**紧跟在标签之后（C 的标签不构成作用域）：
  `case 1: int x;` 报 `a declaration cannot follow a case label; wrap it in a block`；
  标签后直接就是 `}` 报 `a case label needs a statement`。
- `switch` 体内的 `own` 被拒绝（`own is not supported inside a switch`）：一个 case 可能被跳过、也可能贯穿，
  按顺序块假设的释放点不成立，留待所有权分析支持 case 可达性。
- `do-while` 的体可以带花括号，也可以只写一条语句；`while (...)` 之后必须写 `;`，否则报
  `a do statement must be followed by while (...)`。
- `case` / `default` 出现在 `switch` 体之外（包括 `switch` 体内的嵌套块）报
  `a case label is only allowed inside a switch`。
- 不做 `case 1 ... 5:` 范围语法；重复的 case 值原样发射，由 C 编译器报错。

### 5. 命名规则（稳定契约）

命名空间前缀属**已移出 L0 的特性**，已由 Phase 2 在 `selfhost/l2/**` 恢复（本文不描述它）。

| 产物 | 规则 | 示例（trait `Greeter`，struct `Person`，方法 `greet`） |
| --- | --- | --- |
| vtable 类型 | `<Trait>_vtbl` | `struct Greeter_vtbl` |
| 接口值类型 | `<Trait>_iface` | `struct Greeter_iface`（胖指针 `{ self, vt }`） |
| vptr 字段 | `__<trait 全小写>_vptr` | `__greeter_vptr` |
| 方法实现 | `<Struct>_<Trait>_<method>` | `Person_Greeter_greet` |
| vtable 变量 | `<Struct>_<Trait>_vtable` | `Person_Greeter_vtable` |
| 隐式参数 | 固定为 `self`，函数体内强转目标固定为 `_self` | — |
| 数组循环变量 | 固定为 `__ct_i`，包在自己的块内 | — |

### 6. 语义约束与已知问题

#### 6.1 会被诊断的约束

| 约束 | 违反时 |
| --- | --- |
| `use` 引用的 trait 必须已定义（且出现在该 struct 之前） | `error: struct 'S' uses undefined trait 'T'` + `exit 1` |
| `impl` 的 trait 与 struct 必须已定义 | `error: impl for undefined trait/struct 'X'` + `exit 1` |
| struct 必须 `use` 了对应 trait 才可 `impl` | `error: struct 'S' does not use trait 'T'` |
| impl 不得出现 trait 未声明的方法 | `error: method 'm' is not declared in trait 'T'` |
| impl 必须实现 trait 的**每一个**方法 | `error: trait method 'm' is not implemented for struct 'S'` |
| 大括号/圆括号必须配对 | `error: unterminated '{'` |
| `trait` / `impl` 头部必须完整（名字、`{`、`for`） | `error: expected trait name` / `expected '{' after trait 'X'` / `expected trait name after 'impl'` / `expected 'for' in impl of 'T'` |

**不做**的检查：方法签名是否与 trait 一致（参数类型、个数、返回类型都不比对，原样搬运）；
trait / struct 是否重名（`find_*` 取最先出现者，后者不可达，不报错）。

#### 6.2 已知限制

- 变量表无类型信息；变量按**花括号块作用域**回滚（`{` 压栈、`}` 恢复），同一作用域内出现同名时取**最先**登记者（`find_var` 首命中）。
- **登记顺序 = 源码顺序**：在变量声明之前出现的方法调用不会被重写。
- 跨行的方法调用语句不重写（按行处理）；函数签名的**参数列表**跨多行时同样不识别。
- **跨行的块注释 `/* … */` 只保护第一行**：续行会被当作普通代码行处理，其中的 `self`、方法调用等照常改写（单行 `/* … */`、`//` 与字符串 / 字符字面量不受影响）。这是按行处理管线的固有限制，Phase 2–5 用 CT 重做特性时随实现一并保留（见 [roadmap](roadmap.md) 的「自举之后的恢复与新增」）。
- **文件作用域的对象 / 数组**：vptr 由编译器生成的构造器 `__ct_init`（`__attribute__((constructor))`）在 `main` 前写入（D5=A）。
- 数组只支持 `Type name[<n>];`（无初始化式、常量下标）。
- **堆对象自动初始化**（Phase 1，D1=A）：`T *p = malloc(sizeof(struct T));` / `calloc` 在声明后自动写 vptr（含嵌套字段）。
- 接口多态：接口**数组**不支持；接口作为 struct **字段**不参与构造点递归（值字段声明后为空，需自行赋值）；
  装箱只接受**变量**、`&变量` 或「返回同款接口」的函数调用，其它表达式一律 `die`。接口字段的**派发**已支持
  （`s.lhs.m()` → `s.lhs.vt->m(s.lhs.self)`，指针字段经 `->`），**值**接口字段的**语句赋值**会自动装箱；
  但**指定初始化式**里的接口字段不装箱，**指针**接口字段的赋值也不处理（见 §4.8）。
- **ct-ast 已放宽上述接口限制**（v0.12.0 之后的修复，L0 / L2 不变）：构造式里由具体 struct 变量或
  `&变量` 填充的接口**值**字段与接口**指针**字段都会自动装箱（后者取复合字面量的地址）；接口指针形式的
  变量 / 参数（`Expr *xs`）按元素派发（`xs[i].m()`，元素是值而非指针）；结构体类型的**数组字段**逐元素
  写 vptr（`Num ab[2]` 的元素可直接派发）；函数原型的数组参数保留维度（`int f(Expr a[])`）。其它更复杂的
  初始化表达式（如算术式、函数调用结果直接灌进接口字段）仍按原样透传。
- 单行函数体（`int f() { … }` 与函数头写在同一行）不处理，与 Phase 0 的按行改写一致。同理，与构造**同处一行**的语句也不会被重写：一行接口装箱、一行右值接收者均按原样透传。（`impl` 构造是例外：它的方法体由块匹配整体抽取，即使与方法头同处一行也会走重写管线。）
- 不完整的 `struct` 头部（缺 `{`）不作为构造，按原样透传。`trait` / `impl` 是 ct 独有关键字：行首出现且其后紧跟标识符或 `{` 即视为构造声明，头部畸形一律报错（其后是其它 token 的行，如 `impl[n] = 0;`，仍透传）。
- 顶层构造不支持嵌套。
- **生成物里「声明了但没用到」的 `static` 实体**：一个 `impl` 总会发射 `<S>_<T>_vtable`，一个
  `use Drop` 的 struct 总会发射 `<S>_Drop_drop`，即使本单元从不调用该 trait 的方法、也不 `delete`
  （ct-ast 不做跨过程可达性分析）。这些符号一律带 `__attribute__((unused))`，因此 `cc -Wall -Wextra`
  不会因为它们告警；属性与既有的 `__ct_init` 的 `__attribute__((constructor))` 同源，需要
  GCC / clang。它们**不影响**语义与运行。

### 7. 容量上限

## English

> **Status**: this document specifies the **core ct grammar** — the subset that L0 (`ctc.c`), the
> CT line (L2, `selfhost/l2/**`, the frozen regression oracle) and the installed entry ct-ast
> (`selfhost/ct-ast/main.ct`) **accept and emit**. The CT line is a superset: it also supports
> `namespace` / `import` / `pub` / multi-file `ct build` / `Drop` / `#line` / leak warnings and
> `--diagnostics`. Those are **not covered by the grammar chapters below**; their semantics and
> landing record live in [roadmap](roadmap.md) (Phases 2–5), [design/restore.md](design/restore.md)
> and [design/phase5.md](design/phase5.md). AutoDrop (`own`) is also CT-line-only but is described in §4.9.
> The `map` construct added in Phase 11.1 (binding a trait method to a declared global instance, or —
> since SH-20 — to a namespace) is supported by **ct-ast only** — neither L0 nor L2 accepts it;
> see §4.10.
>
> The three are not byte-equivalent: ct-ast is the installed entry and L2 is only the regression
> oracle. Known divergences:
>
> | Construct | L2 | ct-ast |
> | --- | --- | --- |
> | block form `namespace A::B { … }` | accepted | rejected (`a namespace is file-scoped`) |
> | cross-namespace bare call | accepted, falls back to the root table | rejected (needs the qualified `A::f()`) |
> | other C passthrough (`goto` / labels, `enum`, `union`, `offsetof`, …) | passed through as-is | only the implemented subset; reports `unexpected token` |
>
> This is a **capability gap between the two layers**, not work in progress: L0 still reports
> `'namespace' is not supported by this compiler` for those constructs (same for `pub` / `import` /
> `ct build`; `--line` / `--no-line` / `--diagnostics` report `unknown option`). Archived fixtures
> live in `test/archive/`, and the old, feature-complete implementation is at git tag
> `overreach-oracle`.

This document specifies the input rules, expansion rules, naming rules and diagnostics of the core
grammar. Anything not described here is undefined behaviour and must not be relied upon.

### 1. Source model

A `.ct` file mixes top-level constructs with verbatim C. The compiler scans it **once, in source
order**: top-level constructs are expanded, everything else is copied line by line. Order therefore
matters — all definitions must precede their use.

```
program  ::= { item }
item     ::= trait-def | struct-def | impl-def | raw-text
```

Top-level constructs must sit at file scope (no nesting) and their keyword must start the line
(leading spaces and tabs are allowed). The first line of every generated `.c` is a provenance comment
`Generated by ct v<version> from <input path> -- do not edit; ...` (the `.h` carries an equivalent
comment in its header); it is not part of the source content.

### 2. Lexical notes

- Keywords (`trait`, `struct`, `impl`, `use`, `for`) must appear as whole words (`word_at()` performs
  word-boundary matching), so `traitx` or `my_struct` are not misread.
- `namespace`, `pub` and `import` are no longer keywords: the compiler now rejects them (see the status
  note at the top).
- A line-initial `trait` / `impl` / `struct` starts a construct only when the full header follows
  (`trait IDENT {`, `impl IDENT for`, `struct IDENT {`); otherwise the line is passed through. So
  legal C that uses `trait` / `impl` as ordinary identifiers (e.g. `impl[0] = 1;`, `trait = 2;`) is
  not misread.
- Rewriting is **line-based**: when a construct and an ordinary statement share one line, the statement
  is not rewritten (`p.greet()` inside `int main(void){ Person p = {…}; p.greet(); }` stays as written).
- Every fixed capacity limit (identifier length, parameter count and text, field / method / trait /
  struct counts, variable count, scope depth, …) is a hard `die` — never a
  silent truncation.
- Whitespace, newlines, `//` comments and `/* */` comments may appear freely in construct headers.
- Method declarations inside a trait are separated by `;` and may span lines; comments are stripped
  before splitting.
- Struct bodies are preserved verbatim and not parsed.
- Identifiers are `[A-Za-z_][A-Za-z0-9_]*`; longer than 127 characters is an **error**
  (`identifier too long`) — no longer a silent truncation.

### 3. Grammar

```ebnf
trait-def   ::= "trait" IDENT "{" { method-decl } "}" ;
method-decl ::= type-spec IDENT "(" [ param-list ] ")" ";" ;

struct-def  ::= "struct" IDENT "{" raw-text "}" [ use-clause ] [ ";" ] ;
use-clause  ::= "use" IDENT { "," IDENT } ";" ;

impl-def    ::= "impl" IDENT "for" IDENT "{" { method-def } "}" ;
method-def  ::= type-spec IDENT "(" [ param-list ] ")" block ;

param-list  ::= param { "," param } ;
param       ::= type-spec [ IDENT ] ;   (* type-spec may contain '*' and 'const' *)

type-spec   ::= <C type spelling: everything up to the method/parameter name>
```

Conventions: the `use` clause may follow `}` on the same line or start a new line; a sole `void`
parameter means "no parameters"; the semicolon after a struct definition is optional. Parameter types
and names are split heuristically — the last identifier is taken as the parameter name unless it is a
type keyword (`void` / `char` / `int` / `unsigned` / `size_t` …) or the text ends with `*`.

#### 3.1 Expressions (ct-ast)

ct-ast parses expressions with C's precedence. The supported operator subset, tightest first:

| Level | Operators |
| --- | --- |
| unary | `!` `~` `-` `&` (address-of) `*` (dereference), casts, `sizeof` |
| multiplicative | `*` `/` `%` |
| additive | `+` `-` |
| shift | `<<` `>>` |
| relational / equality | `<` `>` `<=` `>=` `==` `!=` |
| bitwise AND | `&` |
| bitwise XOR | `^` |
| bitwise OR | `\|` |
| logical | `&&` `\|\|` |
| conditional | `?:` |
| assignment | `=` and the compound forms `+=` `-=` `*=` `/=` `%=` `&=` `\|=` `^=` `<<=` `>>=` |

Every binary / unary operation is parenthesised in the output, so the source semantics never rely on
C's own precedence. L0 / L1 / L2 do not parse expressions (they rewrite line by line); this table
describes ct-ast only.

### 4. Expansion rules

#### 4.1 trait → vtable type

```c
trait Greeter { void greet(); int add(int a, int b); }
```

```c
struct Greeter_vtbl {
    void (*greet)(void *);
    int (*add)(void *, int, int);
};
```

Each method gains a leading `void *` parameter; the vtable keeps **types only and drops parameter
names**.

#### 4.2 struct + use → appended vptr field

```c
struct Person {
    char *name;
    int age;
} use Greeter;
```

```c
struct Person {
    char *name;
    int age;
    struct Greeter_vtbl *__greeter_vptr;
};
```

The field body is preserved verbatim; vptr fields are appended at the end, in the order the traits are
written in `use`.

#### 4.3 impl → static methods + vtable variable

```c
impl Greeter for Person {
    void greet() {
        printf("Hello, %s\n", self->name);
    }
}
```

```c
static void Person_Greeter_greet(void *self) {
    struct Person *_self = (struct Person *)self;
    printf("Hello, %s\n", _self->name);
}

static struct Greeter_vtbl Person_Greeter_vtable = {
    .greet = Person_Greeter_greet
};
```

- The generated function takes "`void *self` plus the parameters written in the impl", and the first
  line of its body is always the `_self` cast.
- The method body's indentation is normalised: the minimal shared indentation is stripped and the body
  is re-emitted with 4-space indentation.
- A method body goes through the **very same rewriting pipeline as top-level code**: `self` (a pointer
  to the current struct) and the impl's method parameters are registered in the variable table first,
  then every body line is fed to `transform_line`, and finally the identifier `self` is renamed to
  `_self`. Every receiver form therefore dispatches inside a body, exactly as at top level:
  - sibling call: `self->other()` → `_self->__<trait>_vptr->other(_self)`;
  - field chain: `self->field->m()` → `_self->field->__<trait>_vptr->m(_self->field)` (recursive, §4.5);
  - method parameter: `o->m()` → `o->__<trait>_vptr->m(o)`, `v.m()` → `v.__<trait>_vptr->m(&v)`;
  - a local variable declared in the body: `P q; q.m();` → `q.__<trait>_vptr->m(&q)`.
- Whenever a body produces a dispatch, a forward declaration
  `static struct <Trait>_vtbl <Struct>_<Trait>_vtable;` is emitted before the method functions, to
  resolve the forward reference to the vtable variable (a C tentative definition, later given its
  initialiser — both are valid together).
- vtable initialisers follow the **declaration order of the methods in the trait**, not the order they
  are written in the impl.
- Across units (ct-ast `build` mode): when **both the trait and the struct are `pub`**, the vtable gets
  external linkage — the declaring unit's header emits `extern struct <Trait>_vtbl <Struct>_<Trait>_vtable;`
  and the implementing unit defines it, so a consumer unit can box directly. Otherwise it stays `static`,
  and every `impl` of one struct/trait pair must live in a single compilation unit.

#### 4.4 Variable declarations → `struct` qualifier + appended vptr designator

```c
Person p = { .name = "Tom", .age = 36 };
```

```c
struct Person p = { .name = "Tom", .age = 36, .__greeter_vptr = &Person_Greeter_vtable };
```

Rules:

| Source form | Handling |
| --- | --- |
| `Person p = { … };` (designated initialisers) | prefix `struct ` and append vptr designators before `}` |
| `Person p = { "Tom", 36 };` (positional initialiser) | same: the vptr designators follow the positional elements (C99 allows the mix `{ 1, .v = 0 }`) |
| `Person p = {};` / `Person p;` | prefix `struct `; an empty list gets the vptr appended, and a declaration without an initialiser gets `= { <vptr> }` added |
| `struct Person p = { … };` | same as above (the qualifier is not added twice when already present) |
| `static Person p;` / `static Person ps[2];` | the `static` prefix is kept verbatim; everything else is as for a non-`static` declaration (objects get the initialiser, arrays go through `__ct_init`) |
| `Person *p = …;` | prefix `struct `, everything else emitted verbatim; pointer variables are **registered as pointers**, so `p->m()` is rewritten to `p->__t_vptr->m(p, …)` |
| other types | left completely untouched |

Names recognised as variables of a struct type are registered in the variable table for later
method-call rewriting.

#### 4.5 Method-call rewriting

```c
p.greet();
p.greet_name("Jerry");
```

```c
p.__greeter_vptr->greet(&p);
p.__greeter_vptr->greet_name(&p, "Jerry");
```

Trigger conditions (rewriting happens only when 1 or 1′ holds **and** 2–4 all hold):

1. the left-hand side is an identifier that has been registered **earlier in this file** as a variable
   of some struct type (`T x`, `T *x`, `T x[n]` and `T *x[n]` all qualify); **or**
1′. the left-hand side is a call `f(...)` whose return type is a **previously registered struct**
   (returned by value or by pointer: `f().m()`, `mk()->m()`, `f().a.b.m()`);
2. when that variable is an array or a pointer, one subscript `[<expr>]` may follow, with an arbitrary
   balanced expression (`ps[i]`, `ps[i + 1]`, `ps[f()]`);
3. then comes `.`, `->`, or a run of field hops (each `.field` / `->field`), and the **final** member
   name is a **method name** of some trait of the struct reached by those hops;
4. the member name is immediately followed by `(`.

Which trait a method belongs to is decided by scanning the traits of the struct's `use` clause in
order and taking the **first** one that declares that name.

Rewriting details:

- a no-argument call `x.m()` → `x.__t_vptr->m(&x)` (no stray comma);
- a call with arguments `x.m(a)` → `x.__t_vptr->m(&x, a)`;
- a pointer receiver does not get `&` added: `p->m()` → `p->__t_vptr->m(p)` and
  `p->m(a)` → `p->__t_vptr->m(p, a)`;
- array elements and pointer subscripts: `ps[i].m()` → `ps[i].__t_vptr->m(&ps[i])`; an element of
  `T *ps[n]` is **itself a pointer**, so `ps[i]->m()` → `ps[i]->__t_vptr->m(ps[i])`, whereas `p[i]` on
  a plain `T *p` is a value and gets `&`;
- a pointer field chain picks `.` or `->` from **each hop's** field kind, and the final hop being via a
  pointer means no `&`: `a.next->m()` → `a.next->__t_vptr->m(a.next)`, while `a.next.m()` (a value
  field) → `a.next.__t_vptr->m(&a.next)`;
- nested calls inside arguments are processed recursively:
  `q.add(1, q.add(2, 3))` → `q.__greeter_vptr->add(&q, 1, q.__greeter_vptr->add(&q, 2, 3))`;
- **rvalue receivers** (condition 1′): the receiver is first hoisted into a temporary variable so it is
  evaluated **exactly once**, then dispatched by the same rules above. The temporary is named
  `__ct_tmp<N>` (`N` increments within a single file, starting at 0):
  - returned by value: `f().m(a)` → the previous line `struct S __ct_tmp0 = f();`, this line
    `__ct_tmp0.__t_vptr->m(&__ct_tmp0, a)`;
  - returned by pointer: `mk()->m(a)` → the previous line `struct S *__ct_tmp0 = mk();`, this line
    `__ct_tmp0->__t_vptr->m(__ct_tmp0, a)`.
  - the hoist is allowed **only** in two positions: the receiver starts the **statement**
    (`f().m();`), or it starts the right-hand side of an **assignment / declaration initialiser**
    (`int r = f().m();`). In both, evaluation is unconditional and ordered, so hoisting to the previous
    line does **not** change the semantics.
  - in any other position (e.g. `x = 1 + f().m();`, `g(f().m());`) it cannot be rewritten without
    changing evaluation order, so the compiler **reports `file:line:col: error:` and exits** instead of
    emitting C that is known not to compile.
  - the hoisted declaration keeps the source line's indentation; it occupies one line in the generated
    `.c`.
- content inside string literals, character literals and comments is **never rewritten**;
- an `impl` body shares the top-level pipeline: `self->m(...)`, a field chain `self->f->m(...)`, a
  parameter receiver `o->m(...)` and a local-variable receiver `q.m(...)` are all rewritten by the
  same rule (see 4.3);
- **only a variable-subscript receiver's expression is evaluated twice** (`ps[i]` appears twice in the
  output), so a subscript with a side effect (`ps[i++]`) is not guaranteed correct; an rvalue receiver
  (1′) uses a temporary and is evaluated once.

#### 4.6 Ordinary function signatures → struct types qualified

```c
void show(Person p);
static Person make(char *n);
Person *pick(Person *a, Person *b);
```

```c
void show(struct Person p);
static struct Person make(char *n);
struct Person *pick(struct Person *a, struct Person *b);
```

Rules:

| Source form | Handling |
| --- | --- |
| a known struct name in the return type (including `static`-style prefixes, multi-word types and pointer returns) | insert `struct ` in place (all other characters preserved) |
| a value parameter `Person p` | insert `struct `; **when the function has a body**, register the parameter (`ptr=0`) so that `p.m()` inside the body is rewritten |
| a pointer parameter `Person *q` | insert `struct `; register it as a pointer (`ptr=1`) so that `q->m()` inside the body is rewritten |
| a prototype `void f(Person *q);` | qualify the types only; the parameters are **not** registered (there is no body) |
| a parameter already written `struct X …` | no second `struct ` is inserted |
| statements such as `if` / `while` / `else if` / `return …` | never mistaken for a function signature |
| a signature whose **parameter list itself** spans several lines | not recognised; copied through verbatim |

#### 4.7 Composition, arrays and heap objects (construction semantics)

A vptr is written at a **construction point**: an object's **own** vptr goes into the initialiser, while
**nested fields / array elements / heap objects** use **post-declaration assignments** (so an appended
`.field` designator can never override a `.field = {…}` the user wrote).

| Source form | Handling |
| --- | --- |
| `struct Shop { Person owner; };` | the field type gains `struct `: `struct Person owner;` |
| `Shop s;` | after `struct Shop s = { … };`, append `s.owner.__greeter_vptr = &Person_Greeter_vtable;` |
| `s.owner.greet();` | `s.owner.__greeter_vptr->greet(&s.owner);` |
| `Person ps[3];` | the declaration plus a scoped loop `for (…; __ct_i < 3; …) ps[__ct_i].__greeter_vptr = …;` |
| `ps[0].greet();`, `ps[i].greet();` | `ps[0].__greeter_vptr->greet(&ps[0]);` (any subscript expression) |
| `Person *ptrs[2]; ptrs[0]->greet();` | `ptrs[0]->__greeter_vptr->greet(ptrs[0]);` (the element itself is a pointer) |
| `struct Box { Person *who; } … b.who->greet();` | `b.who->__greeter_vptr->greet(b.who);` (pointer field chain) |
| `delete q;` | `if (q) free(q);` (`q` must be a registered pointer variable) |

Naming and limits:

- The loop variable emitted for arrays is always `__ct_i`, wrapped in its own block.
- **File-scope objects / arrays**: file scope cannot hold the vptr assignment **statements**, so the
  vptr is written before `main` by a generated constructor
  `static void __ct_init(void) __attribute__((constructor))` (decision D5 = A); the object is declared
  normally and dispatched from `main` as usual.
- Arrays only support `Type name[<n>];` (no initialiser, constant subscripts); any other form that needs
  initialisation `die`s instead of emitting bad C.
- **Heap objects are initialised automatically** (Phase 1, D1=A): `T *p = malloc(sizeof(struct T));`
  (or `calloc`) writes the vptrs (including nested value fields) right after the declaration.
- **ct never qualifies type names in hand-written C**: `sizeof(Person)` is not rewritten — write
  `sizeof(struct Person)` instead.

#### 4.8 Interface polymorphism (a trait used as a type)

Each trait additionally generates an **interface value type** (a fat pointer: the object plus its
vtable):

```c
struct Greeter_iface { void *self; struct Greeter_vtbl *vt; };
```

| Source form | Handling |
| --- | --- |
| `Greeter g;` | `struct Greeter_iface g = { 0, 0 };` |
| `Greeter g = p;` | `struct Greeter_iface g = (struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable };` |
| `Greeter g = q;` (`q` is `Person *`) | as above, with `self` taken from `q` itself (**no `&`**) |
| `g = s;` | box according to `g`'s trait, then assign |
| `void announce(Greeter who);` | `void announce(struct Greeter_iface who);` |
| `announce(p);` | `announce((struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable });` |
| `Greeter pick(void);` | `struct Greeter_iface pick(void);` |
| `return p;` inside an interface-returning function | `return (struct Greeter_iface){ (void *)&p, &Person_Greeter_vtable };` |
| `g.greet();` | `g.vt->greet(g.self);` |
| `g.greet_name("Jerry");` | `g.vt->greet_name(g.self, "Jerry");` |

**An interface used as a struct field** (a value field `T x;` → `struct T_iface x;`; a pointer field
`struct T *x;` → `struct T_iface *x;`):

| Source form | Handling |
| --- | --- |
| field `Node lhs;` / `struct Node *lhs;` | the field type is expanded to `struct Node_iface lhs;` / `struct Node_iface *lhs;` |
| `s.lhs.show();` / `self->lhs.show();` | `s.lhs.vt->show(s.lhs.self);` (a value field hops with `.`, and the chain can recurse) |
| `s.p->lhs->show();` | `s.p->lhs->vt->show(s.p->lhs->self);` (a pointer field hops with `->`) |
| `s.lhs = v;` (**value** interface field) | boxed into the field's declared trait: `s.lhs = (struct Node_iface){ (void *)&v, &Lit_Node_vtable };` |

Rules and limits:

- Only a **variable** or `&variable` (or a call that already returns the same interface) can be boxed;
  when the type cannot be inferred the compiler `die`s.
- The boxing target trait comes from the **left-hand side** of a declaration/assignment, or from the
  **current function's return type**; for arguments it comes from the **signature table**, hence the
  definition-before-use rule applies — where the call site cannot see a signature (or the concrete
  type) nothing is boxed.
- The boxed struct must `use` that trait; boxing across different traits `die`s.
- **No** implicit null check: dispatching on a null interface value (`{0,0}`) crashes, as in C.
- **L0 limits (what this document describes)**: interface **arrays** are not supported (`die` at the
  declaration); interface fields do **not** participate in construction-point recursion (`Node lhs;`
  starts empty, `vt == NULL`, and must be assigned); boxing only covers **statement assignments**
  (`s.lhs = v;`), so an interface field inside a **designated initialiser**
  (`Pair p = { .lhs = v };`) is **not** boxed; and a **pointer** interface field (`struct T *x`)
  supports dispatch only, its assignment staying verbatim (it needs the address of an existing fat
  pointer, e.g. `s.x = &someIface;`).
- **Extended on the CT side (L2)**: `selfhost/l2/**` lifts every limit above and gives one uniform
  model for "interface value / pointer to an interface value / array of interface values / array of
  interface pointers"; boxing behaves identically in all four places (assignment, construction point,
  `return`, argument):

| Shape | Meaning | Dispatch | Kind of a subscripted element |
| --- | --- | --- | --- |
| `T x` | an interface value (fat pointer) | `x.m()` → `x.vt->m(x.self)` | — |
| `T *x` | a pointer to an interface value | `x->m()` → `x->vt->m(x->self)` | `x[i]` is a **value** (`x[i].m()`) |
| `T xs[n]` | an array of interface values | `xs[i].m()` → `xs[i].vt->m(xs[i].self)` | value |
| `T *xs[n]` | an array of interface pointers | `xs[i]->m()` | pointer |
| parameter `T xs[]` / `T *xs` | as above, indexable in the body | as above | value |

  Also: interface **array fields** (`Node items[4]`, `self->items[i].eval()`), subscripting a pointer
  interface field (`s.f[0].m()`), **construction-point** boxing (`Pair p = { .l = v, .ptr = &v };` —
  value and pointer fields take their own path) and **heap-object** boxing
  (`Num *p = malloc(sizeof(struct Num)); Expr e = p;`). **Still unsupported**: an interface pointer
  with an aggregate initialiser (`T *g = { ... };`). **Struct-typed array fields**
  (`struct Duo { Num ab[2]; }`) are unsupported by L0 / L2 but **supported by ct-ast** (element-wise
  vptr writes, see §6). Rationale as in the status note at the top: this document stays accurate for
  L0, and the new capability belongs to the CT line (L2 / ct-ast) alone, pinned by
  `test/acceptance/run.sh`.

#### 4.9 AutoDrop (new in Phase 5, CT line only)

`own` is a **contextual keyword** recognised only at the start of a declaration line. It marks the
variable as owning its object's lifetime, so the compiler releases it at scope exit. This is a Phase 5
addition: **L0 (`ctc.c`) does not know it** (it passes the line through), and the CT line
(L2, `selfhost/l2/**`; ct-ast is behaviourally equivalent) implements it.

| Shape | Expansion |
| --- | --- |
| `own Person *p = malloc(sizeof(struct Person));` | emit the declaration without `own`; register it as auto-dropped |
| the declaring scope's closing `}` (line-initial) | insert `if (p) { Person_Drop_drop(p); free(p); p = 0; }` before it |
| a `return` at the function frame's own level (line-initial) | the same, for every auto-dropped variable in reverse declaration order |
| `delete p;` | the usual `free`/`drop`; auto-drop is cancelled (no double release) |
| `p = …;` (reassignment) | auto-drop is cancelled (ownership moved) |
| `p` as a standalone value on the right-hand side of an assignment (`q = p;`) or in the returned expression | auto-drop is cancelled (escape); reading a field or an element (`x = p->n;`, `x = p[0];`) is **not** an escape |

Constraints and limits:

- Only `own T *p = malloc|calloc(...);` is accepted: a **struct pointer**, initialised by
  `malloc` / `calloc`, whose struct `use Drop`; anything else is a compile-time error.
- `own` is allowed **inside a function body only** (file scope is an error), and arrays are rejected.
- Multiple auto-dropped variables in one scope are released in **reverse declaration order**.
- The closing `}` and the `return` must start their line; inline forms (`b->n = 1; }`,
  `if (p) return 0;`) are a compile-time error rather than a silent skip — a line-oriented injector
  cannot place the release inside a conditional.
- `goto` out of the declaring scope does not release.
- Escape detection is **conservative**: a standalone mention on the right-hand side of an assignment
  or on a `return` line cancels auto-drop, because a missed release (a leak) beats a wrong one
  (double free / freeing a borrow).

#### 4.10 `map` (new in Phase 11, extended by SH-20, ct-ast only)

`map` binds a trait's method to a concrete C call, emitting a wrapper plus a vtable. The host takes two
forms; **Phase 11.2 has wired both into dispatch** — when the binding is used as a trait interface
value (assigned to a `T`-typed variable, passed to a `T` interface parameter, returned from an
interface, or used as a call argument), boxing uses the bound vtable, so it runs as an instance of the
trait:

- **Object host**: `map trait T for instance x { … }`, where `x` is a declared global variable; the
  interface value's `self` points at it.
- **Namespace host** (SH-20): `map trait T for namespace A::B { … }`, binding a set of functions in
  that namespace. There is no object, so the interface value's `self` is `NULL`.

`map` is a Phase 11 addition: **neither L0 nor L2 knows it** — only **ct-ast**
(`selfhost/ct-ast/main.ct`) supports it.

```c
trait Controller {
    int send(char *buf, int len);
}
struct Uart { int fd; };
struct Uart uart1;                                    /* object host: a declared global */

map trait Controller for instance uart1 {
    send(buf, len) -> mock_uart_send(&uart1, buf, len);
}

namespace hal;
pub trait Writer { int write(char *buf, int len); }
int hal_write(char *buf, int len) { return len + buf[0]; }

map trait Writer for namespace hal {                  /* namespace host: no object */
    write(buf, len) -> hal_write(buf, len);
}
Writer w = Writer::hal;                               /* boxes with a NULL self and hal_Writer_vtable */
```

Symbol naming: the host path with `::` turned into `_` gives `h`, and the trait's C name is `tr`; if
`tr` already starts with `h_` then `p = tr`, else `p = h_tr`. A wrapper is `p_<method>` and the vtable
is `p_vtable`. For an object host `h` is the instance's C name (e.g. `uart1`); for a namespace host
`h` is the host path (e.g. `hal`).

| Artifact | Rule | Example |
| --- | --- | --- |
| wrapper | `<host>_<Trait>_<method>` with a leading `void *self` (body `(void)self;`); **an object host's direct binding generates none**, a namespace host **always gets one** | `static int uart1_Controller_send(void *self, char *buf, int len)`; `static int hal_Writer_write(void *self, char *buf, int len)` |
| vtable | `<host>_<Trait>_vtable`, designated-init `.method = wrapper` (the bound C function itself when direct) | `static struct Controller_vtbl uart1_Controller_vtable = { .send = uart1_Controller_send };` |

Constraints and limits:

- `for` is followed by either `instance` or `namespace`; anything else is a compile-time error.
- An object host's `x` must be a **declared global variable** (file scope), else a compile-time error.
  The instance may be spelled namespace-qualified, `A::B::h` (2b.3); globals are mangled by their
  namespace (§4.11), so the C name bound is `A_B_h` and the instance's vtable / wrappers carry it as
  their prefix (`A_B_h_T_vtable`).
- **No synthesised host**: an undeclared name is never turned into an object silently — a typo would
  otherwise become a hidden host. When there is no object to hang the binding on, use a **namespace
  host** (`map trait Writer for namespace hal { … }`) instead of faking a `void *netlib;` placeholder
  — the placeholder still works but is no longer needed.
- A namespace host is written path segment by path segment, `A::B`. Boxing `T::A::B` with no matching
  map reports `no map binds trait 'T' to namespace '<host path>'` (the path is echoed as written,
  e.g. `nosuch` / `a::b`).
- A namespace host **rejects a direct binding**: there is no `self` to hand the bound function, so
  `-> fn;` is rejected (`a namespace host has no self: bind with a wrapper call`).
- A namespace host is boxed with `Trait::ns`, and that value is **usable only as an interface value**;
  in any other context (e.g. `int x = Writer::hal;`) it reports
  `a namespace host value is only usable as an interface value`. `Trait::ns(...)` stays a qualified
  call and boxes nothing.
- `T` must be a defined trait; a trait without a vtbl cannot be mapped.
- The bound method must be an existing method of `T`, and its `( … )` parameter count must match the
  trait declaration.
- The right-hand side of `->` (the CALL) is a **two-level binding**:
  - **direct**: when the callee is a bare C function name (a single identifier) nothing is generated
    and the vtable slot points at that function. Signatures are not checked: the bound function must
    itself match the slot type (a leading `void *`). A namespace host forbids this (see above).
  - **fallback**: a call containing an expression or member path gets a host-level wrapper. Every
    argument is validated identifier by identifier: string / character literals, numeric literals,
    member names after `.` / `->`, and `A::B` qualified names pass; any other identifier must be a
    parameter name from the `( … )`, this map's instance, an already-declared variable, or an ALL_CAPS
    macro — otherwise it is a compile-time error.
- Several maps may target the same instance or the same namespace; `MAX_MAPS` (64) caps the total
  number of map blocks.
- **Across units**: the vtable gets external linkage when the trait is `pub` and (for an object host)
  the instance is a `pub` global (the same rule as the impl vtable in §4.11); a namespace host has no
  instance, so only the `pub` trait matters. The header declares it `extern` and the declaring unit
  defines it, so another unit can box the binding. Otherwise wrappers and the vtable are emitted
  `static` in the unit that declares the map and never repeat elsewhere.
- **Dispatch (11.2 / SH-20)**: boxing an object host uses the **instance-level** vtable —
  `Controller c = uart1;` becomes
  `c = (struct Controller_iface){ (void *)&uart1, &uart1_Controller_vtable };` (not the struct-level
  `&Uart_Controller_vtable`). So **even when `Uart` never `use`d `Controller`**, `uart1` works as a
  `Controller` instance. A namespace host is boxed as
  `Writer w = Writer::hal;` → `w = (struct hal_Writer_iface){ (void *)0, &hal_Writer_vtable };`.
  Afterwards both `c.send(...)` and `w.write(...)` dispatch via `<iface>.vt->method(<iface>.self, ...)`
  to the wrapper; a namespace host's `self` is always `NULL`, so the bound function must not
  dereference it.
- The `--emit-map` JSON gains a `maps` field listing trait / instance / file / line and `bindings`
  (method → generated symbol) per map; each map also carries `"host": "instance"|"namespace"` for the
  host form, and each binding carries `"wrapper": true|false` to tell fallback from a direct binding.

#### 4.11 Cross-unit linkage: `pub` globals and `extern` (ct-ast)

- `pub int g_counter = 5;` emits its definition into the defining unit's `.c` and
  `extern int g_counter;` into that unit's `.h`; any importing unit may then refer to it by name.
  `pub` means export only: a global without `pub` still belongs to its own unit.
- `extern int lib_flag;` declares without defining: the declaration goes into the `.h`, and the
  unit's `.c` emits no definition — the symbol comes from an external C object file or library.
  `extern` cannot carry an initializer (a compile-time error). It also accepts a function prototype
  (`extern int lib_fn(int);`): declaration only, and a `pub extern` prototype reaches the `.h`.
  An `extern` name is never mangled, because it names a C library symbol.
- Exported types (`pub struct` / `pub trait` / `pub typedef`) inside a namespace are still reachable by
  their **bare name**: a consumer writes `Writer w;` or `struct Uart u;`, and the compiler resolves
  `hal_Writer` / `hal_Uart`. When two imported namespaces export the same bare name, the bare reference
  is refused and an alias import is required (`import a::b::T as T;`). A **qualified** type spelling
  (`struct A::B`) is still not supported.
- Globals inside a namespace are **mangled**, like type and exported function names: `namespace A::B; int h;`
  has the C name `A_B_h`, so two namespaces may each declare `h` without a link-time collision. `extern` is
  the exception — the symbol belongs to a C library, so it keeps its own name and no namespace.
- An importing unit may reference an exported global with the **qualified** form: `a::h` reads and writes
  `a_h`; a bare name works while only one candidate exists. If two imported namespaces export the same name,
  the bare reference is refused with an instruction to qualify, instead of silently picking one.
- The boundary of cross-unit boxing: an `impl` vtable gets external linkage only when the trait is
  **`pub`** and the struct is **`pub`** — the header declares `extern struct T_vtbl S_T_vtable;`
  and the implementing unit defines it (no longer `static`); otherwise it stays unit-private.
  One struct may have only one `impl` per trait; a duplicate is a compile-time error naming the
  first definition's location.

#### 4.12 Function pointers (ct-ast)

The declarator form `ret (*name)(params)` is accepted as a parameter, a struct field, a global
and a local. The generated C matches the source, with the name kept inside the type.

```c
int (*p)(int);
struct Box { int (*op)(int); };
static int apply(int (*fn)(int), int v) { return (*fn)(v); }
```

- `typedef` works: `typedef int (*BinOp)(int, int);` is emitted as
  `typedef int (*BinOp)(int, int);`, and the alias is usable as a local, a parameter and a struct
  field. A typedef of an array of pointers works the same way
  (`typedef int (*Table[2])(int, int);`).
- A function-pointer array keeps its dimensions inside the declarator (`int (*tbl[2])(int, int);`).
  A global may carry an initialiser (`static int (*tbl[2])(int, int) = { plus, minus };`), a local
  is filled element by element, and a struct field is supported too (`int (*cb[2])(int);`);
  `tbl[i](x)` calls an element directly.
- A file-scope initialiser may name a function of this unit
  (`static int (*gp)(int, int) = plus;`): the prototypes are emitted before the globals.
- Assignment accepts `p = handler;` and `p = &handler;`; a function name used as an rvalue emits
  its C name. A library function brought in by `#include` works the same way (`p = strcmp;`): a name
  CT never declared is emitted verbatim and the C compiler checks it against the prototype, just as an
  ordinary call already does.
- A call accepts `p(args)` and `(*p)(args)`; both are emitted as `(*p)(args)`. A function-pointer
  field may be called directly: `c.add(2, 3)` (`.`) and `p->add(2, 3)` (`->`) are emitted as
  `c.add(2, 3)` and `p->add(2, 3)`.
- Limits: no returning a function pointer; no nested function pointers (`int (**f)(int)` reports
  `nested function pointers are not supported`); a function-pointer array cannot be a parameter
  (`function-pointer arrays are not supported as parameters`); one declaration names exactly one
  pointer (`int (*a)(void), (*b)(void);` is an error).

#### 4.13 `switch` and `do-while` (ct-ast)

```c
switch (key) {
case 1:
    out = 10;
    break;
case 2:
case KIND_B:                  /* both labels guard the same statements */
    out = 20;
    break;
default:
    break;
}

do {
    total = total + i;
    i = i + 1;
} while (i < 4);
```

- A label owns the statements from itself to the next label (or `}`), so a `case` and the `break` after it share
  one indentation level; `case 1: case 2:` share the next statements, and a label run may have no statements
  between its members.
- A case value is a number with at most one leading `-`, a quoted character / string literal, or a single
  identifier (`#define` constants keep their spelling; a known global is emitted under its C name). ct-ast folds
  no constants, so `case (1 + 2):` reports `a case label must be an integer constant`.
- A `switch` body may hold declarations, but not directly after a label (C labels open no scope):
  `case 1: int x;` reports `a declaration cannot follow a case label; wrap it in a block`, and a label that
  runs straight into `}` reports `a case label needs a statement`.
- `own` inside a `switch` is refused (`own is not supported inside a switch`): a case may be skipped or fall
  through, so the ordered-block release point does not hold; this waits for case reachability in the ownership
  pass.
- A `do-while` body may be braced or a single statement; `while (...)` must be followed by `;`, otherwise
  `a do statement must be followed by while (...)`.
- A `case` / `default` outside a `switch` body (including in a block nested inside one) reports
  `a case label is only allowed inside a switch`.
- No `case 1 ... 5:` ranges; a duplicated case value is emitted as written and left to the C compiler.

### 5. Naming contract

The namespace prefix is a **feature removed from L0**; Phase 2 restored it under `selfhost/l2/**`
(this document does not cover it).

| Artifact | Rule | Example (trait `Greeter`, struct `Person`, method `greet`) |
| --- | --- | --- |
| vtable type | `<Trait>_vtbl` | `struct Greeter_vtbl` |
| interface value type | `<Trait>_iface` | `struct Greeter_iface` (a fat pointer `{ self, vt }`) |
| vptr field | `__<lowercase trait>_vptr` | `__greeter_vptr` |
| method implementation | `<Struct>_<Trait>_<method>` | `Person_Greeter_greet` |
| vtable variable | `<Struct>_<Trait>_vtable` | `Person_Greeter_vtable` |
| implicit parameter | always `self`; the cast target inside the body is always `_self` | — |
| array loop variable | always `__ct_i`, wrapped in its own block | — |

### 6. Diagnosed constraints and known issues

#### 6.1 Diagnosed constraints

| Constraint | On violation |
| --- | --- |
| traits referenced by `use` must be defined (and appear before the struct) | `error: struct 'S' uses undefined trait 'T'` + `exit 1` |
| the trait and struct of an `impl` must both be defined | `error: impl for undefined trait/struct 'X'` + `exit 1` |
| a struct must `use` a trait before it can `impl` it | `error: struct 'S' does not use trait 'T'` |
| an impl must not contain methods the trait does not declare | `error: method 'm' is not declared in trait 'T'` |
| an impl must implement **every** method of the trait | `error: trait method 'm' is not implemented for struct 'S'` |
| braces and parentheses must balance | `error: unterminated '{'` |
| a `trait` / `impl` header must be complete (name, `{`, `for`) | `error: expected trait name` / `expected '{' after trait 'X'` / `expected trait name after 'impl'` / `expected 'for' in impl of 'T'` |

**Not** checked: whether method signatures agree with the trait (parameter types, arity and return type
are never compared — everything is copied verbatim); whether a trait/struct name is redefined
(`find_*` picks the first occurrence; the later definition is unreachable and no error is reported).

#### 6.2 Known limitations

- The variable table is type-less; variables roll back at **brace block scope** (pushed at `{`,
  restored at `}`), and within one scope a repeated name resolves to the **earliest** registration
  (`find_var` returns the first match).
- **Registration order = source order**: calls appearing before the variable's declaration are not
  rewritten.
- Call statements spanning multiple lines are not rewritten (processing is line by line); a function
  signature whose **parameter list** spans several lines is not recognised either.
- **A block comment `/* … */` is only protected on its first line**: continuation lines are treated as
  ordinary source lines, so `self`, method calls and the rest inside them ARE rewritten (single-line
  `/* … */`, `//` and string / character literals are unaffected). This is an inherent limit of
  line-based processing and Phases 2–5 keep it as they redo the features in CT (see "Restoring and
  adding features after self-hosting" in the [roadmap](roadmap.md)).
- **File-scope objects / arrays**: the vptr is written before `main` by the generated constructor
  `__ct_init` (`__attribute__((constructor))`, D5 = A).
- Arrays only support `Type name[<n>];` (no initialiser, constant subscripts).
- **Heap objects are initialised automatically** (Phase 1, D1=A): `T *p = malloc(sizeof(struct T));` /
  `calloc` writes the vptrs (nested fields included) right after the declaration.
- Interface polymorphism: interface **arrays** are unsupported; an interface **field** does not
  participate in construction-point recursion (a value field starts empty and must be assigned);
  boxing accepts only a **variable**, `&variable` or a call returning the same interface — any other
  expression `die`s. **Dispatch** through an interface field is supported
  (`s.lhs.m()` → `s.lhs.vt->m(s.lhs.self)`, a pointer field hops with `->`), and a **statement
  assignment** into a **value** interface field is boxed; an interface field inside a **designated
  initialiser** is not boxed, and a **pointer** interface field's assignment is left verbatim (see §4.8).
- **ct-ast relaxes the interface limits above** (fixed after v0.12.0; L0 / L2 are unchanged): an
  interface **value** field and an interface **pointer** field both box a concrete struct given as a
  bare variable or `&variable` in a construction (the pointer form takes the address of the compound
  literal); an interface-pointer variable / parameter (`Expr *xs`) dispatches per element
  (`xs[i].m()`, the element being a value, not a pointer); a **struct-typed array field** gets its
  vptrs written per element (`Num ab[2]` dispatches directly); and a function prototype keeps the
  array dimension of a parameter (`int f(Expr a[])`). Richer initialiser expressions (an arithmetic
  expression or a call result poured straight into an interface field) still pass through verbatim.
- A single-line function body (`int f() { … }` on one line) is not processed, matching Phase 0's
  line-by-line rewriting. By the same rule, a statement **sharing its line** with a construct is not
  rewritten either: a one-line interface boxing and a one-line rvalue receiver both pass through.
  (An `impl` construct is the exception: its method body is extracted as a whole by block matching, so
  it goes through the rewriting pipeline even when it shares the header's line.)
- An incomplete `struct` header (no `{`) is not treated as a construct and passes through. `trait` /
  `impl` are ct-only keywords: a line that starts with one and is followed by an identifier or `{` is
  an attempted construct, so a malformed header is an error (other follows, like `impl[n] = 0;`, still
  pass through).
- Top-level constructs cannot be nested.
- **`static` entities in the output that are declared but never used**: an `impl` always emits
  `<S>_<T>_vtable` and a struct that `use Drop` always emits `<S>_Drop_drop`, even when the unit never
  calls that trait's methods and never `delete`s (ct-ast does no cross-procedure reachability). They all
  carry `__attribute__((unused))`, so `cc -Wall -Wextra` stays quiet; the attribute comes from the same
  GCC / clang family as `__ct_init`'s `__attribute__((constructor))`. Semantics and behaviour are
  unaffected.

### 7. Capacity limits

> The table below lists the **L0** (frozen seed) caps. **ct-ast** (the installed entry) raises the
> user-facing ones: `MAX_NODES` 65536, `MAX_TRAITS` 64, `MAX_STRUCTS` 128, `MAX_METHODS` 64,
> `MAX_FIELDS` 64, `MAX_FUNCS` 256, `MAX_PARAMS` 16, `MAX_VARS` 4096, `MAX_TYPES` 256,
> `MAX_CALLS` 1024; the rest (`MAX_TEXT` / `MAX_PATH` / `MAX_SCOPE` / `MAX_UNITS` / `MAX_IMPORTS` /
> `MAX_MAPS`) are unchanged. The policy is still "fixed cap + hard error", not dynamic allocation.

| Constant | Value | Meaning | On overflow |
| --- | --- | --- | --- |
| `MAX_TRAITS` | 16 | traits / traits per `use` | error, exit |
| `MAX_FIELDS` | 32 | fields per struct whose type is a known ct type (value / pointer struct fields and value / pointer interface fields are counted in separate tables) | error, exit |
| `MAX_DEPTH` | 8 | recursion cap for nested construction / field chains | error, exit |
| `MAX_SCOPE` | 256 | nested brace-scope depth | error, exit |
| `MAX_STRUCT` | 32 | structs | error, exit |
| `MAX_METHOD` | 32 | methods per trait or impl | error, exit |
| `MAX_PARAMS` | 16 | parameters per method | error, exit |
| `MAX_VARS` | 512 | registered variables | error, exit |
| `MAX_FUNCS` | 64 | function-signature table entries | error, exit |
| `MAX_NAME` | 128 | identifier / type name length | error, exit |
| `MAX_PARAM` | 256 | parameter string length | error, exit |

### 8. Out of scope

The full set of visibility modifiers (`pub readonly` / `setter`), generics, inheritance, type checking,
error recovery, nested definitions.

### 9. Diagnostics

- **Errors**: `<file>:<line>:<col>: error: <message>` on stderr; an error **exits immediately** with
  code `1` (no error recovery).
- **No warnings are produced at all**; errors are the only diagnostics.
- Exit code: `0` on success; `1` on syntax / semantic / I/O errors.

### 10. L2 only: module system and diagnostics (syntax not described here)

Multi-file mode (`ct build`), `namespace`, `import`, `pub`, `Drop`, `#line` (with the `--line` /
`--no-line` overrides), leak warnings and `--diagnostics`, plus semantic checks (duplicate
definitions / signature mismatches) are **all supported by the CT line (L2 / ct-ast)** and rejected by L0. Their grammar
and implementation record live in [roadmap](roadmap.md) (Phases 2–5) and
[design/restore.md](design/restore.md); archived test fixtures are in `test/archive/`, and the
feature-complete old compiler is at git tag `overreach-oracle`.
