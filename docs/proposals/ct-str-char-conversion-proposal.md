## 1. 事实：当前的两条转换路径

### 1.1 `Str` 的布局与生命周期

- `Str` 布局为 `{ char *data; int len; }`，字段私有；`len` 是契约，允许内嵌 `\0`
  （[language-spec.md §Str](../language-spec.md#L2559)、[Str.h.ct:18-21](../../lib/std/Str.h.ct#L18-L21)）。
- `str_from_len` 在分配时多留一个字节并写入结尾 NUL（[Str.h.ct:39-46](../../lib/std/Str.h.ct#L39-L46)），
  因此内部缓冲区对 C 读者可用，但 C 读者会在内嵌 `\0` 处截断。
- `Str` 拥有缓冲区，`Drop` 负责释放（[Str.h.ct:23-29](../../lib/std/Str.h.ct#L23-L29)）。

### 1.2 现有的显式转换

| 方向 | 现有写法 | 实际行为 |
| --- | --- | --- |
| `char *` → `Str` | `str_from(p)` | 扫描 NUL 长度后**深拷贝**（[Str.h.ct:51-60](../../lib/std/Str.h.ct#L51-L60)）；分配失败返回 `len = -1` 的释放态，不终止 |
| `Str` → `char *` | `str_c_str(s)` | **分配**一份 NUL 结尾副本，调用方负责 `free`（[Str.h.ct:115-127](../../lib/std/Str.h.ct#L115-L127)） |
| `char *` → `Str` 形参 | 直接传参 | **默认路径硬错**：`type mismatch ... expected 'Str', got 'char *'`（[language-spec.md §6.1](../language-spec.md#L2000-L2005)，v0.53.2 起） |

事实层面的结果是：两个方向的纯搬运都要绕一圈——一个要显式 `str_from`，另一个要显式
`str_c_str` 再手动 `free`；直接传参还会撞上既有的硬错。

## 2. 建议：两条自动转换

### 2.0 前提：转换函数保留

两条自动转换**不新增替换路径，也不消灭现有函数**。`str_from` 仍是公开、可显式调用的
`char *` → `Str` 转换函数；`str_c_str` 仍保留，供需要独立副本的场景使用。编译器只是在
适用位置自动插入对转换函数的调用——源码字面不出现，底层仍由该函数完成转换
（与 C++ 的转换函数同理）。

`Str` → `char *` 需要一个公开的**借用**函数（暂记 `str_view`，最终名字由项目组定），
返回内部缓冲区的起始地址，不分配、不复制；编译器在适用位置插入对它的调用。
`str_c_str` 的「分配副本」语义不变，二者是不同能力，不互相替代。

显式场景（把借用视图存进变量、从函数返回、存进字段、需要一份明确副本）仍然直接调用
上述公开函数；自动转换只负责「调用者本来就要手写的那一步」。

### 2.1 `Str` → `char *`：借用视图，不分配

允许**立即实参**，也允许赋给 `const char *` 变量：

- 调用 C 接口时，实参位置期望 `const char *` / `char *`；
- 调用 CT 函数时，实参位置期望 `const char *` / `char *`；
- 实参必须是**非临时左值** `Str`（`f(s)` 可以，`f(make_str())` 不接受）；
- 优先只借 `const char *`；是否允许可写 `char *` 由项目组另行裁定。

不得出现在下列位置：赋给可写 `char *` 变量、作为返回值、存入字段、存入容器、参与三目。
比较按 §2.4.2 的比较协议处理，不经过本节的隐式转换。

自动转换的语义：

- 不分配、不复制；
- 不改变所有权，`Str` 仍是唯一所有者；
- 属借用视图，指针只在 `Str` 存活且未被 `release()` 的期间有效；存变量时同样受此约束（§7）；
- 调用方不得 `free` 该指针。

这条只替代「取地址」的搬运，不替代需要独立副本或需要转移所有权的场景。

### 2.2 `char *` → `Str`：隐式深拷贝，范围限死三处

只允许下面三处，且由**期望类型**触发，不按语句形状识别：

1. **声明**：`Str s = p;`
2. **赋值**：`s = p;`
3. **传参**：`f(p)`，且 `f` 的形参类型是 `Str`。

三处都生成一份**独立拥有**的深拷贝（编译期插入 `str_from(p)` 调用），与原串无别名关系；
原 `char *` 的生命周期结束后，`Str` 仍有效。

精确匹配优先：同一调用点同时存在 `f(char *)` 与 `f(Str)` 时，实参本身是 `char *` 就走
`char *` 版本，本身是 `Str` 就走 `Str` 版本；需要转换且仍有多个候选时**报二义**，不静默选一个。

三处之外不得静默拷贝：返回位置、字段初始化、容器字面量、三目、显式类型转换等上下文
仍需写 `str_from` / `str_from_len`。这样把隐藏开销限制在可预期的位置。

### 2.3 深拷贝的失败语义

**已被后续裁定覆盖（2026-11-16，负责人）：** 分配失败**不终止程序**、不返回半成品，改为通过
可判定的返回值报告失败（`bool` 加出参，或等价结果形态）并设置错误码；也不采用「返回空值」。
理由是库不替宿主决定终止，失败必须可被调用方观察到。完整条目见
[ct-str-builtin-type-proposal.md](ct-str-builtin-type-proposal.md) §3.7。

以下为原建议，保留为历史记录，不再作为执行口径：~~分配失败时终止程序，不返回空值或释放态~~
——原理由是普通声明与赋值不应迫使调用方处处判空。现状 `str_from_len` 返回 `len = -1` 的释放态
（[Str.h.ct:39-43](../../lib/std/Str.h.ct#L39-L43)），同样不符合新裁定。

仍未定：隐式转换位置没有返回值通道，与「失败必须可观察」存在张力；该位置是否继续实施自动
深拷贝，需与提案 §3.7 末段一起裁定。

### 2.4 通用机制：目标类型决定产出与内存归属

下面三条是**通用机制**，不是只为 `Str` / `char *` 开的口子：任何「产出型操作 + 两种表示」
都按同一口径处理。

#### 2.4.1 结果类型由目标类型决定（target typing）

产出型操作（字符串拼接、构造、转换等）不固定返回类型；结果类型由**接收它的声明、赋值目标或形参类型**决定：

- 目标是 `char *` → 产出裸内存；
- 目标是 `Str` → 产出拥有型值；
- 目标是其它类型 → 由该类型的转换函数决定。

例如同一句 `a.concat(b)`：

```c
Str joined = a.concat(b);       /* 结果是 Str，由 Drop 回收 */
char *joined = a.concat(b);     /* 结果是 char *，由调用方 free */
```

编译器负责把产出转换成目标类型；转换仍由公开转换函数完成（§2.0）。

没有目标类型的上下文（独立表达式语句、`if (a.concat(b))` 之类）不适用本规则：
退回该操作的默认返回类型，或由项目组规定固定诊断。嵌套调用按最内层接收者的目标类型逐层传播。

#### 2.4.2 不产出新值的位置退回最易表示

比较类操作不产出新值，也不适用 target typing 的分配语义：

- `a == b` 直接比较内容，不分配、不拷贝；
- 一方是 `Str`、一方是 `char *` 时，用能同时看到字节与长度的表示比较；
- 对 `Str` 必须按 `data` + `len` 比较，不能只用 NUL 结尾视图，否则内嵌 `\0` 会被截断（§1.1）。

#### 2.4.3 内存归属随目标类型变化

同一条产出调用，目标类型不同，归属规则不同：

- 目标 `char *`：被调方分配，调用方负责 `free`（C 的 `malloc` / `free` 规矩）；
- 目标 `Str`：拥有型，由 `Drop` 回收；
- 目标其它拥有型：按该类型的 `Drop` / 释放规则。

这条必须在调用点的文档与诊断里写清，不能让使用者猜。临时值参与嵌套表达式时，归属随其最终目标类型
确定；没有目标类型的临时值沿用默认返回类型的归属。

## 3. 影响面

### 3.1 会变简单的写法

- C 接口调用：`c_fn(s)` 取代 `char *t = str_c_str(s); c_fn(t); free(t);`
- 接受 `char *` 的 CT 函数：同上，不再需要临时变量与 `free`。
- 声明与赋值：`Str s = p;` 取代 `Str s = str_from(p);`
- 传参：`f(p)` 取代 `f(str_from(p))`，同时消除 v0.53.2 起该位置的硬错。
- 调用点统一：不再出现「有人手写 `str_from`、有人手写包装方法」的分叉；底层仍由公开转换函数
  完成，函数本身保留，供显式场景直接调用。

### 3.2 仍需显式转换的地方

- `char *` 变量接 `Str` 的地址：`char *p = s;` 涉及生命周期，建议继续要求显式取用。
- 需要独立副本给 C 侧释放：仍用 `str_c_str`。
- 需要从「带长度、可能含 `\0`」的缓冲区构造：仍用 `str_from_len`。
- `Str` 作为返回值、字段初值、容器元素等三处之外的位置：仍用 `str_from`。
- 把借用视图存进变量、从函数返回、存进字段、需要一份明确副本：直接调用公开转换函数。
- 可空 `char *`：`NULL` 是否等于空 `Str`，需要单独裁定（见 §5）。

## 4. 实现上需要项目组决定的部分

以下都是设计决策，不是本提案替项目组下的结论：

1. **借用视图的生命周期模型**：本提案允许立即实参或赋给 `const char *` 变量（§7）；
   是否进一步引入借用标注或逃逸分析，由项目组决定。
2. **临时值**：按裁判口径拒绝 `f(make_str())`；若项目组要延长临时值生命周期，需另立规则。
3. **`const` 正确性**：`Str` 的 `data` 只读，借出的是 `const char *`；需要可写内容时走显式副本
   （`to_c_str` / 可变缓冲区），不通过 `data` 写。
4. **`NULL` → `Str`**：空指针转成空 `Str`、直接拒绝，还是终止；需要与现有 `str_from(0)`
   的行为（返回空串）对齐还是区分。
5. **失败语义**：自动深拷贝分配失败终止程序，是否同时改变 `str_from` / `str_from_len` 的现状。
6. **与既有 trait / 方法解析的交互**：语言侧已有显式取址或转换包装；引入自动转换后，
   方法解析、重载选择、trait 派发是否会产生新的歧义，需要给出优先级规则。
7. **重载与歧义**：同一调用点同时存在 `f(char *)` 与 `f(Str)` 时，自动转换会不会让原本明确的
   调用变成二义；需要规定「精确匹配优先、转换次之」还是直接报歧义。
8. **诊断**：`ct check --types` 目前把 `char *` 传给 `Str` 形参判为硬错
   （[language-spec.md:2000-2005](../language-spec.md#L2000-L2005)）；改为自动转换后，
   这条错误文案、`ct check` 与 `ct build` 的分工都要重新定义。
9. **target typing 的传播**：嵌套调用、条件分支两臂类型不同、无目标类型上下文各按什么规则；
   是否要求产出型操作提供默认返回类型。
10. **比较协议**：`Str` 与 `char *` 的 `==` 是否走统一的内容比较协议；内嵌 `\0` 时如何按
    `data` + `len` 判定；是否允许其它类型沿用同一「最易表示」规则。
11. **归属与 ABI**：`char *` 产出的 `free` 责任如何在签名/文档/诊断中体现；临时值的释放点；
    同一操作为不同目标类型生成不同签名时，ABI 与符号名如何安排。

## 5. 供评估的验收建议（不构成排期）

- `Str s = p;` 后修改 `p` 的内容，`s` 不受影响；`s` 的内容修改也不影响 `p`。
- `s = p;` 同样产生独立副本，旧缓冲区按 `Drop` 规则释放。
- 接受 `Str` 的函数的传参位置可直接传 `char *`，生成物可编译运行。
- 接受 `char *` 的 C 接口可直接传 `Str`，运行期读到相同字节；不产生额外分配（可用分配计数或
  `strace` 类手段验证）。
- 借用指针在 `Str` 释放后不再被使用；误用应能在编译期或运行期被明确拦截。
- 内嵌 `\0` 的 `Str` 传给 C 接口时，按 `len` 契约截断，行为与 `str_c_str` 一致。
- target typing：`Str s = a.concat(b);` 与 `char *p = a.concat(b);` 各自得到对应类型；
  `p` 由调用方 `free`，`s` 由 `Drop` 回收；ASAN 无泄漏、无 double-free。
- `a == b`（`Str` 与 `char *` 混合）按内容比较，分配计数为 0；含内嵌 `\0` 的 `Str`
  按 `data` + `len` 判定，不被 NUL 截断。
- 无目标类型上下文（独立表达式语句）按最终裁定的默认类型或诊断执行，不得静默改变归属。
- 三处之外的上下文（返回值、字段初值、容器字面量）仍要求显式 `str_from`，不得静默拷贝。
- `NULL` 的处理按 §4 第 4 条的最终裁定给出固定行为与夹具。
- 全量门禁零失败，既有 `str_c_str` / `str_from` 调用零回归。

## 6. 未决问题清单

1. `char *` → `Str` 是否覆盖「声明 + 赋值 + 传参」三处之外的位置？本提案建议不覆盖。
2. `Str` → `char *` 是否允许出现在初始化与返回值，还是只允许实参？
3. 自动转换与 `own` / 借用语义如何交叉：借用视图是否需要语言层的生命周期标注。
4. 失败终止是否与项目的错误处理约定（AGENTS §4）一致，还是需要单独的 OOM 政策。

以上四条均需项目组裁定；本提案不预设结论。

## 7 后续裁定（2026-11-16）：借用可存变量、`Str` 只读

负责人后续裁定覆盖 §2.1 / §3.2 / §4 中「借用只限立即实参、不得赋给指针变量」的旧口径：

- 从 `Str` 借出的指针类型为 `const char *`，**允许赋给变量**，不再限立即实参；
- 借用不延长 `Str` 寿命：`s = other;` 会释放旧 buffer，此前借出的指针立即失效，再读未定义；
  `s2 = s;` 是深拷贝，`s` 的 buffer 不变，从 `s` 借出的指针仍有效；
- 语言侧没有借用检查器，编译器不拦；靠规范、文档与使用方自查约束；
- `data` 为 `const char *`，`Str` 内容只读；要改内容走可变缓冲区再转 `Str`。

本条只放宽「存变量」，不把 `Str` 隐式转换成 `char *`；借用仍通过显式视图 / `find` / 方法获得。
失效矩阵与只读职责的完整表述见
[ct-str-builtin-type-proposal.md](ct-str-builtin-type-proposal.md) §2.6 / §2.7。
