## 1. 事实：当前的两条转换路径

### 1.1 `Str` 的布局与生命周期

- `Str` 布局为 `{ char *data; int len; }`，字段私有；`len` 是契约，允许内嵌 `\0`
  （[language-spec.md §Str](../language-spec.md#L2559)、[Str.h.ct:18-21](../../lib/std/Str.h.ct#L18-L21)）。
- `str_from_len` 在分配时多留一个字节并写入结尾 NUL（[Str.h.ct:39-46](../../lib/std/Str.h.ct#L39-L46)），
  因此内部缓冲区对 C 读者可用，但 C 读者会在内嵌 `\0` 处截断。
- `Str` 拥有缓冲区，`Drop` 负责释放（[Str.h.ct:23-29](../../lib/std/Str.h.ct#L23-L29)）。

### 1.2 现有的显式转换

| 方向 | 现有写法 | 实际行为 |
| --- | --- | --- |
| `char *` → `Str` | `str_from(p)` | 扫描 NUL 长度后**深拷贝**（[Str.h.ct:51-60](../../lib/std/Str.h.ct#L51-L60)）；分配失败返回 `len = -1` 的释放态，不终止 |
| `Str` → `char *` | `str_c_str(s)` | **分配**一份 NUL 结尾副本，调用方负责 `free`（[Str.h.ct:115-127](../../lib/std/Str.h.ct#L115-L127)） |
| `char *` → `Str` 形参 | 直接传参 | **默认路径硬错**：`type mismatch ... expected 'Str', got 'char *'`（[language-spec.md §6.1](../language-spec.md#L2000-L2005)，v0.53.2 起） |

事实层面的结果是：两个方向的纯搬运都要绕一圈——一个要显式 `str_from`，另一个要显式
`str_c_str` 再手动 `free`；直接传参还会撞上既有的硬错。

## 2. 建议：两条自动转换

### 2.1 `Str` → `char *`：借用视图，不分配

建议在**需要裸指针的实参位置**（调用 C 接口、传给接受 `char *` / `const char *` 的 CT 函数）
自动取 `Str` 内部缓冲区的起始地址：

- 不分配、不复制；
- 不改变所有权，`Str` 仍是唯一所有者；
- 属借用视图，指针只在 `Str` 存活且未被 `release()` 的期间有效；
- 调用方不得 `free` 该指针。

这条只替代「取地址」的搬运，不替代需要独立副本或需要转移所有权的场景。

### 2.2 `char *` → `Str`：隐式深拷贝，范围限死三处

建议只在下面三处允许 `char *` 自动转成 `Str`：

1. **声明**：`Str s = p;`
2. **赋值**：`s = p;`
3. **传参**：`f(p)`，且 `f` 的形参类型是 `Str`。

三处都生成一份**独立拥有**的深拷贝，与原串无别名关系；原 `char *` 的生命周期结束后，`Str` 仍有效。

三处之外不得静默拷贝：返回位置、字段初始化、容器字面量、三目、比较、显式类型转换等上下文
仍需写 `str_from` / `str_from_len`。这样把隐藏开销限制在可预期的位置。

### 2.3 深拷贝的失败语义

建议分配失败时**终止程序**，不返回空值或释放态。理由：普通声明与赋值不应迫使调用方处处判空；
`Str` 是拥有型值，释放态继续流动会把失败推迟到更难定位的位置。

这与现状不同：`str_from_len` 目前返回 `len = -1` 的释放态
（[Str.h.ct:40-43](../../lib/std/Str.h.ct#L40-L43)）。若采纳，需要项目组同时决定
既有 `str_from` 的失败语义是否跟着改，还是只让自动转换走终止路径。

## 3. 影响面

### 3.1 会变简单的写法

- C 接口调用：`c_fn(s)` 取代 `char *t = str_c_str(s); c_fn(t); free(t);`
- 接受 `char *` 的 CT 函数：同上，不再需要临时变量与 `free`。
- 声明与赋值：`Str s = p;` 取代 `Str s = str_from(p);`
- 传参：`f(p)` 取代 `f(str_from(p))`，同时消除 v0.53.2 起该位置的硬错。
- 同一能力只剩一种写法：不再出现「有人用 `str_from`，有人用包装方法」的并存。

### 3.2 仍需显式转换的地方

- `char *` 变量接 `Str` 的地址：`char *p = s;` 涉及生命周期，建议继续要求显式取用。
- 需要独立副本给 C 侧释放：仍用 `str_c_str`。
- 需要从「带长度、可能含 `\0`」的缓冲区构造：仍用 `str_from_len`。
- `Str` 作为返回值、字段初值、容器元素等三处之外的位置：仍用 `str_from`。
- 可空 `char *`：`NULL` 是否等于空 `Str`，需要单独裁定（见 §5）。

## 4. 实现上需要项目组决定的部分

以下都是设计决策，不是本提案替项目组下的结论：

1. **转换点的精确判定**：只允许实参位置，还是也允许 `char *p = s;` 这样的初始化？
   若允许，借用指针的生命周期如何约束。
2. **临时值**：`f(g())` 中 `g()` 返回的 `Str` 是临时值，借用指针在调用期间是否始终有效；
   需要明确是拒绝临时值，还是延长其生命周期。
3. **`const` 正确性**：内部缓冲区可写，借出 `char *` 会让被调方有机会改长度契约；
   是否只借出 `const char *`，或对 `char *` 形参另设限制。
4. **`NULL` → `Str`**：空指针转成空 `Str`、直接拒绝，还是终止；需要与现有 `str_from(0)`
   的行为（返回空串）对齐还是区分。
5. **失败语义**：自动深拷贝分配失败终止程序，是否同时改变 `str_from` / `str_from_len` 的现状。
6. **与既有 trait / 方法解析的交互**：工程里已有 `.data()` / `to_str()` 这类包装方法；
   引入自动转换后，方法解析、重载选择、trait 派发是否会产生新的歧义，需要给出优先级规则。
7. **重载与歧义**：同一调用点同时存在 `f(char *)` 与 `f(Str)` 时，自动转换会不会让原本明确的
   调用变成二义；需要规定「精确匹配优先、转换次之」还是直接报歧义。
8. **诊断**：`ct check --types` 目前把 `char *` 传给 `Str` 形参判为硬错
   （[language-spec.md:2000-2005](../language-spec.md#L2000-L2005)）；改为自动转换后，
   这条错误文案、`ct check` 与 `ct build` 的分工都要重新定义。

## 5. 供评估的验收建议（不构成排期）

- `Str s = p;` 后修改 `p` 的内容，`s` 不受影响；`s` 的内容修改也不影响 `p`。
- `s = p;` 同样产生独立副本，旧缓冲区按 `Drop` 规则释放。
- 接受 `Str` 的函数的传参位置可直接传 `char *`，生成物可编译运行。
- 接受 `char *` 的 C 接口可直接传 `Str`，运行期读到相同字节；不产生额外分配（可用分配计数或
  `strace` 类手段验证）。
- 借用指针在 `Str` 释放后不再被使用；误用应能在编译期或运行期被明确拦截。
- 内嵌 `\0` 的 `Str` 传给 C 接口时，按 `len` 契约截断，行为与 `str_c_str` 一致。
- 三处之外的上下文（返回值、字段初值、容器字面量）仍要求显式 `str_from`，不得静默拷贝。
- `NULL` 的处理按 §4 第 4 条的最终裁定给出固定行为与夹具。
- 全量门禁零失败，既有 `str_c_str` / `str_from` 调用零回归。

## 6. 未决问题清单

1. `char *` → `Str` 是否覆盖「声明 + 赋值 + 传参」三处之外的位置？本提案建议不覆盖。
2. `Str` → `char *` 是否允许出现在初始化与返回值，还是只允许实参？
3. 自动转换与 `own` / 借用语义如何交叉：借用视图是否需要语言层的生命周期标注。
4. 失败终止是否与项目的错误处理约定（AGENTS §4）一致，还是需要单独的 OOM 政策。

以上四条均需项目组裁定；本提案不预设结论。
