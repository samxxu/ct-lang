## 0. 一句话

**不新增语法，先用一块真实 MCU 证明：CT 生成的 C 能在“上层业务 + 驱动封装”中替代手写 C，而启动、ISR、DMA、寄存器和 linker 仍由 C/汇编负责。**

外部硬件视角的评估大约给到“可试点、不可全面替换”（约 6.2/10）。本提案不争分数，直接把差距转成可执行的验收项。

## 1. 背景与问题

CT 的真实价值不在“新语法”，而在：

- 保留厂商 HAL、CMSIS、BSP 的 C 实现，用 `trait` / `impl` 组织驱动接口；
- 生成普通 C，无独立运行时，最终仍走 ARM GCC / Clang / 厂商编译器；
- 用 `map`、`#include` 直通和 C shim 把上层协议、状态机、设备管理做得比裸 C 清晰。

但硬件团队不能只凭“生成 C”就信任它。当前缺的是**目标板证据**，不是更多语言特性：

| 缺口 | 现状 | 为什么不能靠现有 host 测试替代 |
| --- | --- | --- |
| 交叉编译 | 主要是 host `cc` 与 golden | 目标 ABI、`volatile`、对齐、编译器扩展不同 |
| 寄存器访问 | CT 把 `volatile` 交给 C | 需要反汇编确认宽度、顺序、未被优化 |
| ISR / 回调 | 可用 C 函数指针，但没有板级验证 | 中断上下文、栈、可重入性必须上板 |
| DMA / Cache | 语言没有 DMA 生命周期模型 | buffer 生命周期、屏障、缓存维护是板级问题 |
| 内存 | `own` / `Drop` 是注解，不是完整借用检查器 | 中断/任务跨上下文时，自动清理可能不适用 |
| 工具链 | `ct build` 默认调用本地 C 编译器 | 量产要走厂商构建系统，不能替换工具链 |
| 安全认证 | 无工具资格/生成物追溯证据 | 安全关键项目需要 tool qualification |

此外，CT 的类型检查是**部分、opt-in** 的，`ct check --types` 也只覆盖有限场景；硬件代码仍必须依赖目标 C 编译器告警、静态分析和人工审查。不能把 CT 当作“更严格的 C”。

## 2. 定位与分层

| 层 | 是否用 CT | 内容 |
| --- | --- | --- |
| 上层 | **优先试点** | 协议解析、设备状态机、业务逻辑、传感器数据处理、配置管理 |
| 中间层 | **CT + C 混合** | GPIO/UART/SPI/I²C 驱动封装、RTOS 任务接口、定时器、内存池、设备抽象 |
| 底层 | **保留 C / 汇编** | 启动文件、向量表、ISR 入口、DMA 底层、寄存器直接操作、Cache/MPU、特殊指令、linker script |

最终产物仍是：

`CT 源码 → ct build --emit-c → 生成的 C → 厂商工具链 → ELF/HEX`

CT 是**构建期代码生成器**，不是运行时，也不是要替代 C 编译器。生成 C 才是要评审、要进版本库、要上板的交付物。

## 3. 试点范围

### 3.1 H0 冻结项

- 一块真实板：候选 STM32G4（或同档 Cortex-M4/M33），必须能跑厂商 HAL 与至少一个 RTOS；
- 一条工具链：ARM GCC 与 Clang 二选一为主，另一个作交叉验证；
- 一个 CT 版本：以 H0 记录的 `ct -v` 与生成 C 的 sha 为准，试点期间不升级；
- 一套阈值：代码体积、栈余量、关键路径周期、ISR 延迟，由硬件组在 H0 写死，后续不得放宽。

### 3.2 分两段，不一次上全

**P0（最小闭环，先做）**

- UART + GPIO + 一个协议状态机；
- 底层 UART/GPIO 用 C shim 调厂商 HAL；CT 只写接口与状态机；
- 用 `ct build --emit-c` 生成 C，直接纳入厂商 Makefile/CMake；
- 不碰 DMA、不碰 RTOS 任务切换、不碰 Cache/MPU。

**P1（只有 P0 全过才做）**

- 一个 ISR 回调 + 一个 RTOS 任务交接；
- 一个 DMA 收发通道，含 buffer 生命周期、对齐、屏障/缓存测试；
- 注入超时、半包、DMA 完成与关闭竞争等失败场景。

### 3.3 明确不做

- 不用 CT 重写启动代码、向量表、linker script、汇编；
- 不要求 CT 支持所有厂商头文件/宏/编译器扩展；复杂 SDK 用 C shim 隔离；
- 不把 `own` / `Drop` 当作 DMA buffer 或 ISR 长生命周期资源的唯一保障；
- 不做安全认证；若目标是功能安全，先另立 tool qualification 评估；
- 不把试点结果外推为“所有 MCU 可用”。

## 4. 验收矩阵

| # | 项目 | 判据 | 证据 |
| --- | --- | --- | --- |
| A1 | 交叉编译 | ARM GCC / Clang 在目标 flags 下 0 error；告警按项目门槛处理 | 原始编译日志 + 生成 C |
| A2 | 寄存器/`volatile` | 读写宽度、顺序、位操作与手写 C 一致；反汇编确认未被意外优化 | `.s` / `objdump` 对照 |
| A3 | ISR | 通过 C shim 接入向量；中断上下文无不可重入清理；栈不越界 | 上板中断测试 + 栈高水位 |
| A4 | DMA | buffer 生命周期、对齐、缓存维护、关闭竞争无 UAF/越界 | 失败注入 + ASAN/板上断言 |
| A5 | 内存 | 生产路径无堆分配；静态池/栈用量可解释 | map 文件 + 高水位 |
| A6 | ABI | 与 C HAL、RTOS、SDK 混合链接；符号/调用约定稳定 | `nm` + 链接产物 |
| A7 | 实时性 | 关键路径周期、ISR 延迟、代码体积与手写 C 对比；阈值 H0 冻结 | 基准 + 反汇编 |
| A8 | 调试 | 断点、变量观察、源码映射可接受；生成 C 可追溯 | 调试记录 |
| A9 | 回归 | host mock 与目标板测试都通过；生成 C 与手写 C 的差异可解释 | 测试报告 |
| A10 | 生成 C 审计 | 首模块 100% 行级审查；无隐藏分配、无意外清理、无未定义行为 | 审查记录 |

**建议的默认阈值（H0 可调，不可事后放宽）**：同一模块 `-Os` 代码体积不超过手写 C 的 +10%；关键路径周期不超过 +5%；ISR 入口不增加额外函数调用；栈保留至少 20% 余量。达不到就记录为 no-go，不调阈值凑绿。

## 5. 工作切分

| 切片 | 交付物 | 验收 | 工量 |
| --- | --- | --- | --- |
| H0 | 板卡/工具链/CT 版本/阈值冻结；基线生成 C | 记录 sha、`ct -v`、编译命令 | S |
| H1 | C shim + 厂商构建集成 + UART/GPIO 最小工程 | 目标板点灯/回环；生成 C 进构建 | M |
| H2 | CT 协议状态机 + 生成 C 审查 + 调试映射 | A1/A2/A7/A8/A10 的 P0 部分 | M |
| H3 | ISR + RTOS 任务交接 | A3/A6/A9 的 P1 部分 | M |
| H4 | DMA 通道 + 失败注入 | A4/A5 的 P1 部分 | M |
| H5 | 试点报告与 go/no-go | 全部证据、问题清单、结论 | S |

依赖：H0 → H1 → H2 →（H3 与 H4 可并行，但同一文件族串行）→ H5。每片可单独回滚；生成 C 按片保存快照。

## 6. 交付物

- 参考工程：板卡配置、C shim、厂商构建文件、CT 源码与生成的 C；
- 验收脚本：交叉编译、反汇编对照、栈/周期测量、失败注入；
- 报告：逐条 A1–A10 的原始输出、go/no-go、未解决问题；
- 问题清单：试点中发现的 CT 缺陷按 issue 走 patch；需要新能力的另提提案，不夹带。

## 7. 风险与边界

| 风险 | 处置 |
| --- | --- |
| 厂商头文件/宏/属性无法被 CT 完整解析 | 只暴露 C shim 的干净声明；不把整棵 SDK 头文件喂给 CT |
| `volatile`/屏障被优化或重排 | A2 反汇编逐条核对；底层屏障用 C/intrinsic |
| DMA buffer 生命周期 | P1 单独做失败注入；不依赖 `own`/`Drop` 单独保障 |
| ISR 中插入清理代码 | 审查生成 C；ISR 入口只用 C shim，不调用可能分配/清理的 CT 函数 |
| 生成 C 漂移 | 固定 CT 版本；生成 C 进版本库；升级必须 diff |
| 安全认证 | 不在本提案范围；需要时另立 tool qualification 评估 |
| 结论外推 | 只覆盖 H0 板卡/工具链；其他平台重新验证 |

## 8. 对 CT 组的请求

1. **接受/拒绝本试点**；接受则指定负责人、板卡、工具链与 H0 时间盒；
2. **不先分配 phase 号**：这是验证项目，不是语言特性；只有发现的缺陷才走 issue/patch；
3. **冻结阈值与版本**：H0 写死，后续不得为了过验收放宽；
4. **产出报告**：P0 不过就停在 P0，不进入 P1；P1 不过就明确 no-go，不用“再调一版”掩盖。

如果试点失败，CT 仍可保留为“上层代码组织工具”，底层继续 C；如果试点通过，再讨论是否扩大板卡/RTOS/驱动范围。这比继续增加语法更能回答“CT 是否适合日常硬件开发”。
