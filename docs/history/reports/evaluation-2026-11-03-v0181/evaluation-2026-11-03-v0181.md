# ct（C with Traits）v0.18.1 评估意见

> 评估对象：`github.com/samxxu/ct-lang`，`main` 分支（HEAD `528d7c5`），`CTC_VERSION = 0.18.1`
> v0.19.1 复核：见附录 C（2026-11-03，结论未变）
> 评估日期：2026-11-03
> 评估方式：源码通读 + 本机完整自举 + 全量硬门禁 + 针对性探针（容量 / macOS 原生库 / 线程 / 诊断）
> 结论一句话：**这是一个工程质量罕见地扎实、定位极其克制、但生态几乎为零的 pre-1.0 语言；作为「可读 C 的生成器」值得押注，作为「商业 GUI 应用的开发平台」现在还不够。**

## 0. 结论摘要

| 维度 | 判断 |
| --- | --- |
| 语言设计 | 克制且自洽：trait + 组合 + 无运行时，不做类型检查与优化，边界写得很清楚 |
| 编译器实现 | 强。四级自举 6.4 秒完成，L0 单文件 2930 行可通读，生成物是可读的普通 C |
| 工程质量 | 很强。11 道硬门禁本机全绿；逐字节 golden、ASAN/UBSAN、确定性 fuzz、三平台 CI |
| 文档 | 良好但有过期点（tutorial 标 v0.16.0）；121 条公开自审台账，透明度罕见 |
| 生态 | 极薄。官方包 3 个、binding 示例 2 个、std 7 模块 1072 行；无 GUI / 音频 / HTTP / JSON / SQL |
| 生产可用性（GUI 商业应用） | 低。pre-1.0、无类型检查、单文件容量硬上限、C 头常量不可见、跨单元装箱有已知 High 缺陷 |

**给创业项目的一句话建议**：把 ct 当作**「可读 C 的代码生成器 + 核心逻辑层」**，不要指望它承担 UI 与平台集成；UI 用 SwiftUI，平台能力用 `.m.ct` / shim 薄封装，核心状态机、内容模型、播放编排写在 ct 里。这样即使 ct 停在 0.x，你的核心资产仍是可编译的普通 C，存在完整逃生通道。

## 3. 优点

### 3.1 定位克制，边界写死

- **source-to-source，不做类型检查、不做优化、零运行时**。生成物是普通 C，可直接用 clang/gcc 的 `-Wall -Wextra`、ASAN、反编译工具链审阅。
- **机械映射**：`HAL::UART::huart1.send(...)` 直接变成 `HAL_UART_Transmit(...)`，没有隐藏的中间层。这一点对嵌入式、对需要审计生成代码的团队非常有价值。
- **明确不做**：泛型、继承、类型检查、优化。`1.0.0` 才定稿语言。边界越清楚，长期维护越便宜。

### 3.2 trait 体系把 C 的「管理问题」变成「编译器问题」

- trait / impl / use、trait 当类型（接口值、数组、字段、装箱）、**trait 默认方法**；
- `Drop` / `own`（AutoDrop）/ `borrow` + `Handback`，配合**路径敏感泄漏告警**，在无 GC 的前提下给出接近 RAII 的体验；
- `map` 与 `.m.ct` **零成本静态映射**，把既有 C 库的调用在编译期展开成普通 C 函数调用，不产生 wrapper；
- 命名规则（`<Struct>_<Trait>_<method>`、`<Trait>_iface`、`__<trait>_vptr`）被写成**稳定契约**，这对生成物审计、反向映射表（`--emit-map`）和工具链扩展都很关键。

> 判断：这是「用编译期手段解决 C 的管理问题」而非「引入 runtime 兜底」的路线，和 Go/Rust/Zig 都不同，属于有独立价值的第三条路。

### 3.3 工程质量罕见地扎实

实测证据：

```
==> building L0 (the C seed)
==> building L1
==> building L2 (the regression oracle)
==> building ct-ast (the installed entry)
==> installed /tmp/ctbin/ct (ct v0.18.1) and /tmp/ctbin/ctc
...
check-all: OK (11 hard gates green)
```

- 11 道硬门禁包含：L0 八层套件、L1 逐字节 golden 与不动点、L2 对归档 oracle 的对差、L0/L1 逐字节一致、编辑器语法断言、包管理、AST 编译器的语料等价、零告警构建、文档链接与版本门禁、std 端到端。
- **逐字节 golden** 锁住展开细节，而不是只比对运行输出 —— 这是很多自研语言缺失的一环。
- ASAN/UBSAN + 确定性 fuzz + Ubuntu/macOS CI 矩阵 + 夜间任务。
- **自审台账**：121 条 issue，含 High/Medium 分级、复现证据、修复 commit、甚至「不采纳」的理由（如 SH-46）。这种「把缺陷公开写进仓库」的纪律，比任何宣传都更能说明项目可信度。

### 3.4 诊断与溯源做得比预期好

实测：

```
$ ct bad.ct -o bad.c
bad.ct:4:1: error: no method 'g' for type 'struct S'
$ echo $?
1
```

- 统一格式 `文件:行:列: error: 描述`；ct-ast 支持多错误收集（`MAX_ERRORS=20`）、`--diagnostics=json|text`；
- `#line` 能把 gcc 对生成 C 的报错**映回 `.ct` 源行**，这是 source-to-source 方案能不能日常使用的分水岭；
- `--emit-map` 输出 trait / struct / 函数 / impl → C 符号的反向映射，为 IDE 跳转和调试符号预留了接口。

### 3.5 对 AI 生成代码确实友好（不是营销话术）

- 无宏、无条件编译；`import` 由编译器解析，不需要推断 include 路径与顺序；
- `.h` 由编译器生成，不存在「改了实现忘了改声明」；
- 单文件 L0 可整体塞进上下文；诊断 JSON 化便于工具消费；
- 生成物可读，AI 改错时人能直接看 C。

这是它与 Zig/Rust 的差异点：**AI 的产出物是可被人直接审阅的 C，而不是另一层需要信任的中间表示。**

### 3.6 商业许可友好

编译器 GPL，但 `LICENSE.EXCEPTION` 明确：**生成的 `.c/.h` 与你的 `.ct` 不受 GPL 约束**。这意味着可以拿它做闭源商业产品，只要不改编译器本身（改了要开源编译器）。对创业项目是加分项。

### 3.7 macOS 实际可用性（实测）

| 能力 | 实测结果 |
| --- | --- |
| 多单元 + `std` 构建 | 通过。`ct build -I std main.ct -o app`，生成 `main.c` + `Str.c` 并链接运行 |
| pthread | 通过。`pthread_create` + 结构体回调正常编译运行 |
| AudioToolbox 类型 | 通过。`AudioFileID file = 0;` + `sizeof(file)` 正常 |
| Framework 链接 | 通过。`--ldflags "-framework AudioToolbox -framework CoreFoundation"` 生效 |
| 生成物可读性 | 好。trait 展开后是直白的 vtable + 静态方法，见附录 A.2 |

结论：**ct 可以承担 macOS 应用的「非 UI 核心」**，包括音频解码调度、状态机、内容模型、缓存、网络请求。

## 4. 缺点与风险

### 4.1 没有类型检查，且 trait 签名不比对（P0）

- README 明确「不做类型检查」；`language-spec §6.1` 明确：**方法签名是否与 trait 一致（参数类型、个数、返回类型）不比对，原样搬运**。
- 后果：`impl` 写错参数个数，不会在 ct 阶段报错，会漏到 C 编译器，错误信息指向生成物；AI 生成代码的「编译期兜底」因此打了折扣。
- Phase 19（v0.19.0，实施中）才开始补「调用点 arity、实参粗粒度类型、trait 方法歧义、跨单元签名」的受限语义检查。**这是 1.0 之前必须完成的项。**

### 4.2 单文件容量硬上限（P0，已实测）

`ct-ast` 的上限是固定常量：`MAX_FUNCS 256`、`MAX_STRUCTS 128`、`MAX_METHODS 64`、`MAX_PARAMS 16`、`MAX_VARS 4096`、`MAX_NAME 128`。实测：

```
$ ct many_funcs.ct -o mf.c
many_funcs.ct:515:1: error: too many functions
$ ct many_structs.ct -o ms.c
many_structs.ct:130:8: error: too many structs
```

- 300 个函数、140 个 struct 就撞墙；且错误消息**不点名上限值与单元**（对比 SH-47 已把字段上限消息改好）。
- 对商业应用意味着：必须**按单元切分**，且切分粒度受限于编译器而非设计。重构成本被工具反向约束。

### 4.3 生态几乎为零（P0/P1）

| 需要的能力 | 现状 |
| --- | --- |
| GUI | 无任何绑定；`bindings/` 只有 `mock-hal`（假 HAL）与 `posix-socket` |
| 音频 | 无；只能自己包 AudioToolbox / CoreAudio / miniaudio |
| HTTP / JSON / SQL / 正则 / 时间 / 日志 | 无。`std` 只有 str / vec / arena / fs / utf8 / test / map |
| 线程 / 异步 | 无语言层抽象；可透传 pthread / C11 atomics，但需自己保证 |
| 包 | 官方 3 个（hal、hal-posix、clib），索引刚建 |

### 4.4 C 头文件不是输入，常量不可见（P1，已实测）

`.ct` 里的 `#include` 只是**逐行透传**，编译器不解析 C 头文件。因此头文件里的 **enum 常量 / 宏对象**在表达式里不可见：

```
$ cat au.ct
#include <AudioToolbox/AudioToolbox.h>
...
printf("...", (int)kAudioFormatMPEG4AAC);
$ ct build au.ct ...
au.ct:6:84: error: use of an undeclared variable
```

- 类型名（`AudioFileID`）可用，函数声明可用，但**常量必须过 shim**（`static inline int ct_kAudioFormatMPEG4AAC(void) { return kAudioFormatMPEG4AAC; }`）或者 `#ct-raw`。
- 这不是 bug，是「单趟结构重写、不跑预处理器」的必然结果；但它把每个平台 SDK 的对接成本都推给了用户。**这是 macOS/iOS 项目最大的摩擦点。**

### 4.5 跨单元接口装箱存在 High 级已知缺陷（P0）

`issues/selfhost/ct-ast-cross-unit-vtable-static.md`（SH-14，状态「待修」）：vtable 定义是 `static`，只有拥有 impl 的单元能装箱，**消费单元拿到接口值后无法自行装箱**。对「UI 层拿核心层对象」的多模块应用是结构性障碍。

> 缓解办法（方案文件里会用到）：把 impl 与所有装箱点收敛到**同一个 factory 单元**，跨单元只传不透明的具体 struct 指针，不传接口值。

### 4.6 三套管线 + 测试口径缺口（P1）

- L0（C 种子）、L1/L2（冻结 oracle）、ct-ast（主线）三套实现同时存在；L2 还有行管线的语义分叉（跨行调用不重写、块注释只保护第一行）。虽然已明确「L2 只做 oracle」，但文档读者仍要理解三套边界。
- `TEST-7`（High）：**ct-ast 的生成 C 没有逐字节 oracle**，`§4.12–4.38` 共 27 节只有行为探针。「改写错了但运行输出仍对」的退化不会被门禁发现。

### 4.7 文档漂移与版本治理成本（P2）

- `docs/tutorial.md` 标「适用版本 v0.16.0」，而 README/AGENTS 已是 v0.18.1；`issues/docs/**` 里有 30+ 条文档漂移记录（多数已修）。
- 版本号写入生成物 banner，**bump 一次要同步 5 处源码 + 重新生成 71 个以上 golden**。对维护者友好（行为稳定），对贡献者不友好（改一行可能全红）。

### 4.8 语言面与工具链的长期缺口（P2）

- 无泛型、无继承、无方法重载、无异常；容器只能靠 `VecInt` / `VecStr` / `MapStrInt` 这类**手写具体类型**（`std` 就是这么做的），组合爆炸靠人扛。
- 多 trait 同名方法**按 `use` 顺序静默取第一个**（SH-46，决定不报错）。这在大型代码库里是隐性陷阱。
- 无 LSP / 调试器集成；`--emit-map` 还没有接到 IDE。大型项目导航基本靠 grep。
- 无基准测试目录，缺「生成物 `-O2` 运行时性能 / 代码体积」的量化数据；编译吞吐很好（自举 6.4s），但运行时性能没有公开数字。
- pre-1.0：语法仍可能破坏性变更；社区极小，招聘和外包几乎不可能。

### 4.9 「零运行时」的另一面

无 GC、无 runtime 是优点，但也意味着：字符串、UTF-8 文本处理、JSON、HTTP、定时器、日志、错误传播约定**全部要自建**。对嵌入式是合理取舍，对应用层是巨大前期成本。

## 6. 改进建议

### P0 — 1.0 之前必须解决的「承诺级」问题

| # | 建议 | 为什么 | 验收标准 |
| --- | --- | --- | --- |
| S1 | 完成 Phase 19 受限语义检查，并把 **trait 签名一致性**纳入（arity、参数/返回类型粗粒度比对） | 现在「编译器兜底」的核心卖点有缺口；AI 生成代码最需要的正是这一层 | 383 文件语料零误报；4 个探针全部诊断；`impl` 参数个数/类型不符必须报错 |
| S2 | 容量从「固定上限」改为「动态扩容」，至少做到**诊断点名上限值与单元** | 实测 300 函数 / 140 struct 即失败；商业项目会被工具反向约束 | 单文件 1000 函数、300 struct 可编译；或错误消息形如 `too many functions in unit 'main.ct' (limit 256)` |
| S3 | 修掉 SH-14：跨单元 vtable 可见性（`hidden` 可见性 + `pub` 导出，或显式 `pub vtable`） | 多模块应用的装箱要在消费单元发生，这是刚需 | 新增跨单元装箱用例：A 单元 impl，B 单元装箱并派发，全链路通过 |
| S4 | 发布 **1.0 语言冻结清单 + ABI 文档**：生成命名、vtable 布局、struct 布局、跨单元链接、错误码约定 | 生态与工具（bindgen、LSP、调试器）都依赖这层契约；不冻结没人敢押注 | `docs/abi.md` 成文，并在门禁中校验生成物命名未漂移 |
| S5 | 同名 trait 方法冲突：至少给 **warning**（而不是静默取第一个） | SH-46 的「按 use 顺序取第一个」在大型项目里会静默调错实现 | 默认告警，`--allow-ambiguous` 可关；现有 `06_name_collision.ct` 语义保留 |

| --- | --- | --- |
| S11 | 版本 token、门禁条数、阶段状态、tutorial 版本号**全部脚本生成并自动修** | 已有 `test/docs/check-docs.py`，从「检查」升级为「修复」；减少 5 处同步与 golden 重生成的人为风险 |
| S12 | 加 `bench/`：编译吞吐、生成物 `-O2` 运行时、代码体积，进 CI 趋势 | 现在没有任何性能数字，无法对外证明「零开销」 |
| S13 | 读者路径收敛：对外只讲 **L0 + ct-ast**，L1/L2 标为「仅测试 oracle，不对外」 | 降低认知负担；`tutorial` 里删掉 L2 行管线限制 |
| S14 | `ct new` 脚手架 + CI 模板 + 三个完整示例（CLI 工具、嵌入式 HAL、macOS 核心库） | 生态从「能跑示例」到「能开工」 |
| S15 | 包索引质量分级（官方 / 认证 / 社区）+ 安全审计流程 | 生态扩大后，供应链安全会成为信任瓶颈 |

### 明确不建议做的事

- **不要**为追热点加继承、泛型、异常、GC。这些会摧毁「零运行时 + 可读 C」的立身之本。
- **不要**把 Objective-C / Swift 语义塞进语言。GUI 交给宿主语言，ct 守住 C 边界。
- **不要**为了「AI 友好」做花哨的 DSL；AI 真正需要的是**确定的诊断、稳定的命名、可读的产物**，这三样已经在做。

## 7. 适用性结论

### 适合现在就用

- 嵌入式 / 裸机 / HAL 抽象（这正是 `vision.md` 的主战场，且有 `hal` / `hal-posix` 可参考）；
- CLI 工具、编译器/解释器、协议栈、需要「生成可审计 C」的中间层；
- 教学与语言研究（L0 2930 行、6 秒自举，是极好的教材）；
- 作为 AI 生成 C 的**护栏层**：让模型写 `.ct`，产物是能被人审的 C。

### 现在不适合

- **macOS GUI 商业应用的全栈开发**：无 GUI/音频/网络绑定、无类型检查、容量硬上限、跨单元装箱缺陷、pre-1.0；
- Web 服务后端（生态为零，且 PHP/Go 更成熟）；
- 需要快速招人的团队（无人才市场、无 IDE 生态）。

### 给本项目的具体用法（详见方案文件）

1. UI 用 SwiftUI（原生、可上架、可访问性齐全）；
2. 音频、状态机、内容模型、播放编排、缓存、进度、订阅校验用 ct 写；
3. 平台 API 走 `.m.ct` + shim，且 **impl 与装箱收敛到同一 factory 单元**（规避 SH-14）；
4. 内容清单在构建期由 Python 生成 `.ct` 静态表（规避「无 JSON」与「无类型检查」）；
5. 保留 `ct build --emit-c` 产物，随时可退回手写 C —— 这是对冲 pre-1.0 风险的保险。

### C.4 新增实测

**1）静态初始化里的跨变量引用仍不重写命名空间前缀**

```c
/* 输入 */
namespace ns;
static Foo k_foo = { 7 };
static Bar k_bar = { 9, &k_foo };
```

```c
/* 生成（v0.19.1） */
static struct ns_Bar ns_k_bar = { 9, &k_foo };   /* &k_foo 未变成 &ns_k_foo */
```

结论：这是生成器缺陷，不是本次新增；本项目 `core/content/Catalog.h.ct` 继续用 `catalog_init()` 在函数内接指针规避。

**2）`ct check` 仍拒绝 `import`，但报错已带列号**

```text
$ ct check main.ct
main.ct:1:1: error: 'import' is not supported in compile mode
```

无 `import` 的单元可独立检查；本项目 `Glyph.h.ct`、`Segment.h.ct`、`Profile.h.ct` 均为 `rc=0`。

**3）`--emit-c --outdir` 要求目录已存在**

目录缺失时报 `ctc: cannot write the output file`；`app/build.sh` 已先 `mkdir -p`，不受影响。

### C.6 结论

- v0.19.1 是**修复版**，不带来语言层新能力；综合评分维持 **6.4 / 10**（语言项目 7.8；应用开发平台 4.2）。
