### 2.1 `Vec`/`Map`：不是"省多少"，是"无处可省"

用户假设"有手写动态数组（扩容、realloc、长度簿记）"。**这个文件里不存在这样的代码。**

- `grep -E 'malloc|calloc|realloc|free'` → **0 命中**。
- `JsonIter`（`json.ct:555-561`）只有 5 个 int：`i / end / obj / done / dmax`，指向调用方文本，**没有任何缓冲区**。
- writer 的嵌套栈是结构体内的两个定长数组：`in_object[64]` / `state[64]`（`json.ct:99-100`），**2 行**。
- 唯一的"容器操作"是重新扫描（`jv_iter_next` 585–640），它不是数据结构，是游标推进。

如果把 `Vec` 塞进来，第一件事是给 `JsonView` 加堆分配，然后要 `retain/release`，再然后 `parse` 失败路径要清理——**净增 40–80 行**，还把"零分配"这个最大优点弄丢。

> 结论：该特性对本文件 **不适用**（0 行，方向为负）。它真正有用的场景是"给 DOM 版存 children"或"给 O(n²) 修法存边界索引"——那两项都在 §3 的变长侧。

### 2.2 `foreach`：只救得回 4 行，而且只在测试里

31 处循环里 **26 处是逐字节扫描**（`while (i < n && ...)`、`while (1)` 状态机），`foreach` 只接受数组 / `Vec` / `Map`，对这些一行都帮不上。可选的两处：

- `json.ct:1857-1861`：`for (i=0;i<count;i++) { item = doc.at(&tags,i); ... }` —— 被遍历的是 `JsonView`，**不是容器**，`foreach` 用不了。
- `json.ct:2206-2236`：`for (i=0;i<count;i++)` 遍历 `struct JsonBadCase cases[25]` —— 这是真数组，可改成 `foreach (cases)`，并把 `cases[i].x` 换成 `item.x`，**省 4 行**。

> 结论：−4 行。占全文 0.17%。

### 2.3 `into`：省的是前缀，不是行

`doc.` 出现 109 次，**全部在 S10 的 demo/测试里，库代码 0 次**（库内都是 `self->` 或 ops 参数）。

`into` 的语义是"绑定接收者，块内用 `.m()` / `$`"，它把 `doc.member(&root,"a")` 变成 `doc into { .member(&root,"a") }`——**同一行，更多字符**。它真正的收益是可读性和"接收者只求值一次"，本文件里接收者是一个栈上变量，没有重复求值问题。

> 结论：0 行（可能 ±0）。把它算成"省行"是常见的误判。

### 2.4 泛型：没有"重复的节点类型"，只有"逐 kind 的空实现"

这是最容易误判的一条。文件里**没有** `JsonIntNode` / `JsonStringNode` / `JsonBoolNode` 这样的重复结构体——只有一个 `JsonView{start,len}`（`json.ct:138-141`）。

重复的是 **7 个 ops 实现之间互斥的空桩**。实测（脚本按"函数体 ≤3 行且含 `read_err`"识别）：**34 个桩函数、136 行**；同段另有 36 个真实函数、353 行，其余 81 行是 `impl` 头与空行。

为什么泛型合并不了：`JsonNumberOps.as_double` 是 100 行真实逻辑，`JsonStringOps.as_double` 是 4 行"不是数字"；`JsonStringOps.as_string` 是 30 行真实逻辑，`JsonNumberOps.as_string` 是 4 行"不是字符串"。**它们的函数体不同，泛型参数化的是类型而不是行为**，P28 的约束泛型、P35 的泛型 trait 都只会把"同一种行为套不同类型"变短，不会把"不同 kind 的不同行为"合并。

能合并它们的是**单一 tag + `switch`**（今天的 CT 就支持 `switch`，`json_message` 1756–1783 就在用）或 **P34 的固有方法静态派发**。这属于设计重写，单独列在 §2.9。

> 结论：0 行（语言特性层面）；设计层面 −280 ~ −350 行（§2.9）。

### 2.5 `Option`：会把调用点变长

现状的错误模型是"返回值 + 出参 + `doc->read_err` 侧信道"：

- 哨兵视图：`jv_missing_view()`（`json.ct:921-926`，6 行）+ 16 处调用。
- 每个访问器先 `json_ops_for_view` 校验、再派发、再置 `read_err`（S8 里 11 个访问器约 95 行委托）。
- 46 + 9 = 55 处 `read_err` 赋值。

换成 `Option<JsonView>` / `Option<long long>` 后：哨兵函数可以删（−6 行），但 55 处 `read_err` 赋值不会消失——**per-kind 的"类型不匹配"仍然要在某处表达**；而 CT 目前没有 `match`、没有 `?`、没有 `if let`，`Option` 只能 `.unwrap()` / `.is_some()` 手动判断，**每个调用点会多 1–2 行**。S10 有 109 处 `doc.` 调用，即使只有 1/3 需要解包，也是 +30 行量级。

> 结论：−6 ~ +15 行。**方向不确定，偏变长。**

### 2.6 `Drop`：没有可归零的东西

全文 0 次 `free`、0 次 `release`、0 次 `retain`。`JsonDoc` 持有的只是调用方文本的指针（`json.ct:127`），`JsonView` 是偏移量，`JsonOut` 持有调用方缓冲。**没有所有权，就没有释放路径**，`Drop` 无从下手。

> 结论：0 行。同样：把 `Vec` 引进来才会让 `Drop` 变得有用——那是负收益。

### 2.7 `ct check --types`：没有类型前置校验可替

现在的校验全是**运行期字节校验**：`jv_view_ok` 查区间（433–441），`jv_iter_begin` 查首字节（563–582），`as_int` 查首字符是不是 `-`/数字（1241、1295）。这些依赖的是**输入内容**，不是静态类型，`--types` 一条都替不掉。

> 结论：0 行。

### 2.8 `enum` 替 `#define`：−10 ~ −15 行（唯一确定的正收益）

30 个 `#define` 集中在 `json.ct:33-69`，分 5 组（kind 8、parse 错误 11、read 错误 5、emit 错误 4、深度 2）。`DECISIONS.md` 明确说这些只能用 `#define`，因为示例要同时被 L0 与 ct-ast 编译（"没有使用 enum、namespace、map"）。

实测 ct-ast **今天支持 enum**（`/tmp` 里 `enum Color { RED, GREEN = 5, BLUE };` 编译通过，生成的 C 保留 enum）。换成 5 个 enum 块后约 22–27 行，**净减 10–15 行**。

> 注意：这是"放弃 L0 双编译"带来的收益，不是某个 Phase 的新语法。

### 2.9 附加变体 A2：P34 静态派发（真正的省行来源）

| 被替换 | 行数 | 替换后 | 说明 |
| --- | --- | --- | --- |
| `trait JsonValue` + 7 个 ops struct 声明 | 34（884–918） | 0 | 不需要接口值与 vtable |
| 7 个 `impl JsonValue` | 570（964–1533） | 390–430 | 合并成 11 个方法，每个方法内 `switch`；136 行空桩消失，真实逻辑 353 行保留，加 switch 开销约 40 |
| ops 实例表 / `json_ops_for` / `json_ops_for_view` | 51（1536–1585） | 0–10 | 直接调 `<View>_<method>` |
| `impl Json` 里的 11 个委托包装 | ≈95（1589–1752 内） | 20–30 | 只剩 `parse`/`root`/错误定位/`read_err` |
| **合计** | **751** | **400–470** | **净 −280 ~ −350** |

即：**−280 ~ −350 行**（约 13–16%）。这个区间与"改成 `switch` 后每个方法要加 case 标签"的开销已一并计入。

> 这需要 Phase 34 的"非泛型固有 `impl Name { … }` + 跨单元调用"。**用户列出的 P28–P32 里没有它**，所以它属于 A2 而不是 A1。

## 3 别只算减法：补齐生产缺口会变长

这六项来自上一份评估的 P0/P1，全部是"必须项"（不做就不能对外）。

| # | 缺口 | 改法 | 净增量 | 依据 |
| --- | --- | --- | --- | --- |
| 1 | 实数解码不是正确舍入 | 自研 Eisel-Lemire + 大整数回退（替换 `as_double` 100 行） | **+150 ~ +350** | 现有 13 个样本 7 个 bit-exact；`as_double` 现长 100 行（1284–1383） |
| 1′ | 同上，但借 `strtod` | 加 C-locale 保护 + 失败回退 | **+5 ~ +20** | 换来 libc 依赖与 locale 风险 |
| 2 | `at()`/`member()` 是 O(n²) / O(n) | 一次扫描建元素边界表（调用方给 `int` 缓冲），保留只读视图 | **+80 ~ +150** | 20k 数组全量遍历 1,240 ms；`JsonIter` 89 行需改造为"建表 + 查表" |
| 3 | `depth_limit` 可调到栈溢出 | 方案 a：硬钳上限；方案 b：改显式栈 | **+5 ~ +10** / **+120 ~ +200** | 110k 层 SIGSEGV(139)；递归点在 351、378 |
| 4 | 输入 UTF-8 不校验 | 增加 UTF-8 校验器 + 错误码 + 开关 | **+60 ~ +120** | 裸 `0xFF 0xFE` 当前被接受 |
| 5 | writer 不接收长度 | `string_len(const char*, int)` + 循环改按长度 | **+10 ~ +25** | `jw_escaped` 711 行 `while (text[i] != '\0')`；`\u0000` 会被截断 |
| 6 | 截断静默 | 新增 `JSON_EMIT_TRUNCATED` + `finish` 判定 | **+5 ~ +10** | `cap=8` 请求 21 字节时只返回长度（852–866） |

组合后的总量：

| 组合 | 增量 |
| --- | --- |
| 最省（strtod + 钳深度） | **+280 ~ +525** |
| 中间（自研舍入 + 钳深度） | **+310 ~ +665** |
| 最重（自研舍入 + 显式栈） | **+425 ~ +855** |

**B1 = A1 + 增量 → 2,547 – 3,142 行**（取整 2,550 – 3,150）。
**B2 = A2 + 增量 → 2,217 – 2,845 行**（取整 2,210 – 2,850）。

一个容易被忽略的耦合：第 2 项"边界表"如果不用调用方缓冲，最自然的写法就是 `Vec<int>`——**这时 `Vec` 才第一次有用，而且它让代码变长**。同理，`Map<char*, JsonView>` 做键索引能把 `member` 变 O(1)，但那是 +60 ~ +100 行。**语言特性在这里的价值是"让新增能力更好写"，不是"让已有代码更短"**。

## 5 按 cJSON 能力集重写：规模估算

### 5.1 锚点（实测，非估计）


## 6 反直觉结论：为什么"省的远少于直觉"

### 6.1 原因一：文件里根本没有"语言在拖后腿"的代码

用户预期的大头是"手写动态数组 + 手写释放 + 重复节点类型"。实测：

- 动态数组：**0 行**（零分配设计，`grep malloc|realloc` 零命中）。
- 释放路径：**0 行**（无所有权）。
- 重复节点类型：**0 个**（只有一个 `JsonView`；重复的是逐 kind 的**空实现**，行为不同，泛型合不了）。
- 类型前置校验：**0 行**。

也就是说，**`Vec`/`Map`/`Drop`/`Option`/`--types` 这五项在本文件上全部落在"没有可替换对象"或"换完更长"的格子**。它们是为"要分配、要所有权、要解包"的代码准备的，而这个文件恰好是反着设计的。

### 6.2 原因二：真正的体量是"固有工作"，任何语言都省不掉

| 固有工作量 | 行数 | 为什么省不掉 |
| --- | --- | --- |
| 字符串转义三件套（扫描校验 72 + 解码 80 + 编码 30 + 键比较 22） | **204** | RFC 8259 的规则；需要逐字节状态机、代理对校验、UTF-8 编码 |
| 数字词法 + `as_int` + `as_double` | **200** | 前导零/指数/溢出/精度；换语言不会让 IEEE-754 变简单 |
| 结构化扫描（对象/数组/字面量） | **117**（317–431） | 递归下降骨架 + 每个错误点的偏移 |
| 迭代器 | **89** | 无 DOM 时，遍历必须现场解析 |
| writer 状态机 + API | **233** | 逗号/冒号/括号的状态与错误 |
| 小计 | **≈843** | 占全文 37%，**语言特性对这块的边际收益是 0** |

### 6.3 原因三：真正的"重复"是设计选择，不是语言缺陷——而且它可以用今天的 CT 修

**最省不下来的一段，就是 S7 的 712 行**。其中 136 行是纯空桩，例如：

```c
/* JsonStringOps 里的四个"不是这个类型"的桩，JsonNumberOps 里再抄一遍，共 6 份 */
int as_int(struct JsonDoc *doc, struct JsonView v, long long *out) {
    doc->read_err = JSON_READ_KIND;
    return 0;
}
int as_double(struct JsonDoc *doc, struct JsonView v, double *out) {
    doc->read_err = JSON_READ_KIND;
    return 0;
}
```

（`json.ct:1164-1175`、`1221-1233`、`1420-1427`、`1464-1471`、`1508-1515` …）

这 136 行**不是任何新语法能省的**（`Vec`/泛型/`Option`/`Drop` 都碰不到它）：它来自"每种 kind 一个 ops 对象 + 11 个方法全实现"的接口值设计。换成 `switch (kind)` 或 P34 固有方法即可消失——**但这是今天就能做的重构，不是 P28–P32 的功劳**。这也是为什么 A2（−280 ~ −350）显著大于 A1（≈0）：**省钱的是设计决策，不是编译器版本。**

### 6.4 原因四：一半的"行数"其实是测试

S10 有 **502 行（22%）**，其中真正的库代码是 0。任何"换语言省行"的直觉，如果用整文件行数做分母，都会被这 502 行稀释；如果用库代码（1,784 行）做分母，A1 的收益也只有 1%。

### 6.5 反过来说：什么时候这套新特性真的值钱

用同一套特性去写**另一个**程序会完全不同：

| 场景 | 新特性的实际收益 |
| --- | --- |
| 一个有 `Vec<JsonNode*>` 的 DOM（§5） | 高：`Vec` 替手写扩容与链表、`foreach` 替遍历、`Drop` 替递归释放（约 −150 ~ −250 行） |
| 一个会失败、要传播错误的业务层 | 中：`Option`/`Result` 替错误码与出参（但要等 `match`/`?` 才能真正省行） |
| 一个零分配、视图式、把错误码当 ABI 的解析器（本文件） | **≈0**：所有特性都打在空处 |

## 7 决策（2026-11-12）

C 路线（按 cJSON 能力集重写可变 DOM）**作废**：建树、改节点、深拷贝直接用 cJSON，不重复造轮子。同时 A1 的收益（不超过 1%）与 A2 的收益（13–16%）都不足以支撑专门投入，`examples/json` 维持"零拷贝只读视图"的样例定位，暂不排期生产化补齐。
