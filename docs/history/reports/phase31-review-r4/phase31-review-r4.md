### 1.1 第 1 项：链式访问材料化 —— 设施存在，但实现落点缺两条（High H1）

| `emit_hoists` | `Emitter.h.ct` 定义在 `1776` 起，签名 `int emit_hoists(int ind)`；临时声明在 `1785` | ✅ |
| `static_ctype` | `Expr.h.ct:146` 声明、`3130` 定义，签名 `int static_ctype(int n, char *out, int cap, int *array_depth, int depth)`，能取任意表达式节点的 C 拼写与数组层数 | ✅ 存在 |
| 取值入口可达性 | 它是 `struct Expr` 的方法，`struct Emitter`（`Emitter.h.ct:185-252`）只有 `arena/sym/ty/lex/out/...`，**没有 `Expr` 句柄**；可达路径是单例 `frontend::parse::expr_get()`（`Expr.h.ct:4956`，现成用法见 `MapBuild.h.ct:886`） | ⚠️ 卡片没写入口 |

**两个漏写的必改落点（这是 H2 未闭合的原因）**

1. **`N_MCALL` 分支没有临时名短路。** `N_CALL` 分支在 `Emitter.h.ct:4025-4027` 有
   `if (nodes[n].text3[0] && n != raw_call) { fputs(nodes[n].text3); return 0; }`，
   而固有方法 `aux == 9/10` 分支（`3913-3936`）从第一行 `snprintf(base, …, nodes[n].text)` 到 `fputs(")", out)` **完全不看 `text3`**。`raw_call` 全文件只出现于 `1786/1788/1791`（emit_hoists）和 `4025`（N_CALL）。因此按卡片字面实现：
   ```
   emit_hoists:  struct Vec_int __ct_tmp0 = Vec_int_get(&g, 0);   ← 第一次（正确）
   len 调用:     Vec_int_len(&Vec_int_get(&g, 0))                  ← 第二次且 & 加在调用上
   ```
   即**同一接收者求值两次**，并且仍然发射非法 C —— 正是卡片第 327 行想根除的形态。E31-24 的产物 grep（第 805 行：禁止 `&Vec_*_(`）会在落地时变红，说明判据能兜住，但 S21a 的计划描述是错的。
   修法（两行）：在 `aux == 9/10` 分支开头加与 `4025` 同形的 `text3`/`raw_call` 短路；S21a 行补一句「`N_MCALL` 分支按 `N_CALL` 的 `text3` 约定只打印临时名」。
2. **`hoist_scan` 的入口门槛会把 `N_MCALL` 挡在门外。** `1755-1757` 的条件是
   `root->kind == N_CALL && !root->text3[0] && sym->find_func(root->text2) >= 0`；
   `N_MCALL` 的 `text2` 是方法名（`get`/`len`），`find_func` 返回 <0；`emit_hoists` 的 `1782-1783` 还会因 `find_func < 0` 直接 `fail_from("cannot infer the type of a hoisted receiver")`。
   卡片只说「`emit_hoists` 的类型来源改用 `static_ctype`（不再 `find_func`）」，没写**入口条件**也要换（改用 `find_struct(...).is_inst` + 方法表判定）。修法：S21a 注明「`hoist_scan` 的 `find_func(...) >= 0` 改为「`N_CALL` 走 `find_func`、`N_MCALL` 走实例结构体的方法查表」，`emit_hoists` 按节点 kind 分支取类型（`N_MCALL` → `expr_get()->static_ctype`）」。

**一次求值的结论**：卡片第 334 行写的是结果承诺（「同一接收者一次表达式只求值一次」），但没有任何实现落点支撑；按现有代码，材料化只会让调用更糟（多一次完整调用）。这一条不闭合。

### 1.6 第 6 项：E31-29 的产物断言（Medium M1）

- `malloc(sizeof(struct ct_buf))` 在哪个产物里可 grep：`/tmp/p31base/probe_alias.c:27` 实为 `v.h = (struct ct_buf *)(malloc(sizeof(struct ct_buf)));` ✅ 子串存在。
- **但「后紧跟 `abort()`」按一行窗口 grep 会假红**：当前产物里紧跟的排版是
  ```
  v.h = (struct ct_buf *)(malloc(sizeof(struct ct_buf)));
  if (v.h == 0) {
      return v;            ← 改成 abort 后是 abort();
  }
  ```
  发射器会把 `if (v.h == 0) abort();` 展开成三行（`probe_alias.c:27-30` 就是这种花括号换行），所以 `grep -A1` 只能看到 `if (v.h == 0) {`。断言应写成「`-A2` 内出现 `abort()`」或「`grep -c "abort()"` 在 `Vec_*_from` 体内恰为 3」。
- `from` 体内不含 `free(` 成立且有意义：基线 `Vec.h.ct:73` 正是 data 失败的 `free(v.h); v.h = 0;`，新方案删除它改 `abort()` —— 进程终止，不存在泄漏，卡片第 429–430 行已说明。✅
- **但 data 分配失败分支没有独立断言**：现有断言只覆盖 `malloc(sizeof(struct ct_buf))` 与「无 free」，data 的 `malloc` 失败是契约文字、不可观测。建议一并断言 `Vec_*_from` 内 `abort()` 恰 3 处（空表 header / 非空 header / data）。

## 4 Battle 裁定

1. **H2 是否应判 High**：应。卡片第 327–336 行的核心主张是「材料化后不再发射 `&调用`」，而按现有 `N_MCALL` 分支实现，产物仍然是 `&Vec_int_get(&g, 0)` 且执行两次。判据（E31-24 的 grep）能兜住，但 S21a 的计划缺两条落点，属于「照着做就做错」，必须在开工前补齐。这不是措辞问题，`text3`/`raw_call` 的短路是唯一能阻止二次发射的机制。
2. **E31-15 的「两个 19」是不是重复计数**：不是。19 个夹具各有两条计数线（显式断言行 + `errors` 目录自动扫描行），迁出时两条各减一次；`+19` 是这 19 个夹具作为正例目录后的新增计数，三者互不重复。真正的缺口是**另外 15 个新正例目录与 module 夹具**从未进公式。

4. **roadmap「无需归档」是否要改成「phase19 已归档」**：不要。phase19 早已归档、窗口 12/12，现行「无需归档」准确；卡片该句是从前几轮残留的指令，应删而不是执行。
