# 第十九批特性：数组长度表达式（2026-10-30）

> 锚点：`7d4b962`（第十八批收口），工作树干净。
> 仍由 ctc.c 探针驱动：第十八批之后报错点推进到 `static char g_guard[MAX_NAME * 2];`。

## 1. 实测现状

- `parse_array_dims` 的方括号里只接受三种形态：数字、单个名字、空。
  因此 `[MAX_NAME * 2]`（宏乘倍数）、`[(1 << 3)]`、`[WIDTH + 1]` 都在 `expect("]")` 处失败。
- 名字形态会把枚举成员换成它的 C 拼写（命名空间 mangling），这条归一化必须保留。

## 2. 决策

- **D-1 简单形态原样保留**：数字 → 十进制、单个名字 → `var_cname` 归一化、
  空 → `[]`。只有「方括号里不止一个 token」才走新路径。
- **D-2 表达式形态按源码原文捕获**：记下 `[` 的位置，读掉第一个 token 后发现后继不是 `]`，
  就从 `[` 之后逐字符拷到配对的 `]`（嵌套方括号计数，字符串不特殊处理——数组长度里没有），
  再把词法器重新定位到 `]` 之后。维度文本因此与源码同形，不做求值也不做规范化。
- **D-3 影响面为零**：`text3`（维度槽）的消费者只把它当字符串拼接，`TypeCheck` / `Init`
  只判断它是否为空，所以表达式维度与数字维度在下游没有区别。
- **D-4 范围外**：VLA（运行期长度）同样按原文发射，C 自己决定是否接受；维度里的字符串
  字面量不做特殊处理。

## 3. 影响面

- 改：`frontend/parse/Expr.h.ct`（`parse_array_dims` 一条 `raw` 路径）。
- **impl 方法预算**：不新增方法（255/256）。
- 不动：`TypeCheck` / `Init` / 发射器、`ctc.c` / `l1` / `l2`、`CTC_VERSION`、golden。
