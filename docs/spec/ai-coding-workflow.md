## 0. 第一性原理：以文档为核心的工程管理

> 本章先于角色与流程。它只回答一件事：**什么算完成**。后面的角色、权限与门禁，都是为了让这一章成立。

### 0.1 主张

工程的验收对象是仓库内的文档，不是会话里的结论。角色可以换、会话会丢失、代理可以重来，唯一能跨会话、跨人、跨时间交接的只有仓库里的文件。因此：**任何成果，先落文档，再谈完成。**

### 0.2 存在的判据

| 载体 | 算不算"成果已存在" | 判据 |
| --- | --- | --- |
| 会话对话 | 不算 | 无仓库路径；会话关闭即不可寻址 |
| 口头/会议结论 | 不算 | 无文件、无锚点 |
| 代码注释 | 不算 | 只解释实现，不构成主张或验收承诺，不进验收清单 |
| 提交信息 | 部分算 | 只证明"发生过变更"，不证明主张、验收与结论 |
| 仓库内文档 | 算 | 有路径、有版本锚点；若声称可执行行为，还必须有可运行判据 |
| 测试、证据包、台账 | 算 | 有命令、原始输出、锚点（第 8.1 节） |

| 规则 | 内容 | 判据 |
| --- | --- | --- |
| D0-1 | 任何"已完成 / 已修复 / 已决定 / 已验收"的主张，必须给出仓库内文件路径与锚点；给不出即视为未完成 | G6（台账证据字段）、G8（提交正文） |
| D0-2 | 只存在于对话的结论，下一次会话不得当作既定事实引用，必须重新落盘后才能引用 | G6 + 评审报告「文档时效」节 |
| D0-3 | "成果"的最小单位是：文件路径 + 版本锚点 +（若适用）可执行判据；三者缺一不成立 | G1、G4、G6 |

### 0.3 文档四层

| 层 | 回答的问题 | 最小充分集（缺一不算完成） | 产出 | 维护 | 守它的门禁 |
| --- | --- | --- | --- | --- | --- |
| 主张层 | 为什么做、不做什么、受什么约束 | 目标一句话 + 非目标 + 约束 + 术语 + 决策记录索引 | `docs/requirements/`、`docs/decisions/` | REQ | G0、G1 |
| 规格层 | 做什么、怎么判对错 | 每个对外行为一个 ID + 输入/输出 + 失败语义 + 验收命令与阈值 | `docs/spec/`、`docs/acceptance.md` | REQ | G1、G2 |
| 实现记录层 | 怎么做的 | 可构建源码 + 依赖锁 + 变更说明（提交正文含动机与验证） | 源码、`docs/design/`、提交 | DEV | G3、G8 |
| 验证证据层 | 做对了的证据 | 每条规格至少一个用例；最近一次执行的命令与原始输出；环境与锚点 | `tests/`、`examples/`、`reviews/`、`issues/` | VERIFY、REVIEW | G4、G5、G6、G7 |

| 规则 | 内容 | 判据 |
| --- | --- | --- |
| D0-4 | 四层缺任一层，该成果只能算"进行中"，不得标记完成或验收 | G1、G2、G6 |
| D0-5 | 每层的最小充分集由本表定义；项目可加严，不得删项 | G0 纳管时逐项核对 |

### 0.4 代码与文档的关系

1. 代码是实现记录层文档的一种形式，且是唯一会被执行的那一份；它不是主张层或规格层的替代。
2. **同版本**：主张、规格、snippet、证据与代码共享同一锚点。文档头写 `applies-to: <tag|sha>`，发布时必须等于发布 tag。
3. **不一致时以可执行检查结果为准**，但这不等于代码自动成为新规格：若检查结果与规格冲突，默认规格已过期，走 CR 修正规格；禁止让实现悄悄改写主张。
4. 裁决顺序固定为：可执行检查结果 > 规格正文 > 代码注释 > 会话说法。

| 规则 | 内容 | 判据 |
| --- | --- | --- |
| D0-6 | 文档中每个行为陈述，要么映射到一条门禁或用例，要么显式标 `unverified` | G4 映射检查 |
| D0-7 | 文档 `applies-to` 落后于当前发布锚点时，该文档不得作为验收依据 | G4 时效检查、G9 |
| D0-8 | 规格变更必须先有 `CR-*`，再由实现跟进；实现先行且无 CR 的，按越权处理 | G8 |

### 0.5 决策落盘

| 规则 | 内容 | 判据 |
| --- | --- | --- |
| D0-9 | 三类内容必须落盘：battle 裁决、否决意见（`rejected` 及理由）、被推翻的结论（`superseded` 并链接新旧） | G6 台账检查 |
| D0-10 | 决策位置固定为 `docs/decisions/D-<n>.md`；battle 的原始证据留在 `battle/<id>/`，决策记录只放结论与索引 | 文件存在性检查 |
| D0-11 | 会话记录不能替代决策文档：不可寻址、不可 diff、不可引用。没有 `D-*` 的决策视为未决定 | G6、G8 |
| D0-12 | 决策记录最少字段：`id`、`date`、`anchor`、`status`、`trigger`、`verdict`、`judge`、`seats`、`scope`、`criteria`、`rationale`、`invalidation`、`affected` | 模板字段校验 |

格式沿用第 7.12 节；`status` 只允许 `accepted` / `rejected` / `superseded`。

### 0.6 反面防线：文档腐化检测与强制回改

文档越多越旧越没人看，是本规范最容易失效的地方。因此这一节不写成倡议，而是写成检测项、责任人与处置动作。

**可检测的症状**

| 症状 | 检测方式 | 归属门禁 |
| --- | --- | --- |
| 引用的文件、符号、锚点不存在 | 锚点扫描（文档中的路径与 `file:line` 逐个存在性校验） | G4 `g4-anchors` |
| 文档代码块不能编译或输出不符 | snippet 渲染后编译/运行，与声明输出比对 | G4 `g4-snippets` |
| 文档声明的版本落后于代码 | `applies-to` 与当前 tag/HEAD 的距离超过阈值 | G4 `g4-fresh` |
| 代码里的版本字段与工程状态对不上 | 版本字段核对：所有落点互比 + 与 phase 卡片、CHANGELOG、tag 四项对账（6.7 V-6） | G4 `g4-version`；不一致未立案由 G6 拦 |
| 项目 `AGENTS.md` 的规范块落后或被手改，或 `docs/spec` 全文副本过期 | `sync-agents.sh --check`：块头 version/sha 比对 + 块体逐字 `diff` + 副本 sha 对比 | G0 `g0-block`（未落库即未纳管） |
| phase 收口缺 tag，或 tag 名不带 `v` / 不是 annotated | `git cat-file -t` 与 `git rev-parse <tag>^{commit}` 对比收口提交 | G8 `g8-version`（6.7 V-7） |
| 文档声称的行为没有对应用例 | 规格 ID 与用例 ID 的双向映射表 | G4、G5 |
| 同一事实在多处出现且不一致 | 评审报告「文档时效」节逐条对照 | 评审 |
| 连续两个发布周期未被任何提交触及却仍被引用 | `git log` 时间窗 + 引用扫描 | G4、评审 |

**谁在什么时候检测**

| 时机 | 执行者 | 动作 | 产物 |
| --- | --- | --- | --- |
| 每次提交 | 机器 | 跑 `g4-snippets`、`g4-anchors` | 门禁输出 |
| 每次发版 | 机器 + REQ | 全量 G4；`applies-to` 对齐发布 tag；跑 `g4-version` 四项对账 | 发版检查表 |
| 每次 phase 收口 | 机器 + 主编 | 跑 `g4-version`：落点互比，与 `PH-<n>`、CHANGELOG、本 phase 的 fix 数对账 | 收口对照表 |
| 每轮评审 | REV | 报告必须有「文档时效」节，列出 `stale_docs`、`unverified_claims`、`docs_without_gate` 三项计数与清单 | 评审报告 |
| 每轮评审 | REV | 发现即立 `DOC-*` 条目，附检测方式与锚点 | `issues/DOC-*.md` |

**发现后如何强制回改**

| 规则 | 内容 | 判据 |
| --- | --- | --- |
| D0-13 | `DOC-*` 与普通 issue 同一状态机（第 5.4 节）；P1 必须在下一个发布前关闭 | G6 |
| D0-14 | 修改责任按层分配：主张层 REQ，实现与使用层 DEV，证据层 VERIFY/REVIEW | 提交路径与角色一致 |
| D0-15 | 关闭必须由 REV 复核并写 `verified`；DEV 不得自行关闭文档条目 | G6 状态词检查 |
| D0-16 | 发版时存在未关闭的 `DOC-*` P1，发版门禁失败 | 发布检查 |
| D0-17 | `deferred` 需 REQ 写理由与触发条件；无签字的 deferred 视为未处置 | G6 |

**什么情况下允许删除文档**

| 规则 | 内容 | 判据 |
| --- | --- | --- |
| D0-18 | 删除必须同时满足：主张已被新文档吸收并给出新路径 + `D-*`；全仓库 0 引用；历史由 git 保留；REQ 批准且 REV 复核；删除单独成一次提交并写明理由 | 五项逐条可查 |

## 1. 加载层级与阅读顺序

规范必须能被代理稳定读到，而 `AGENTS.md` 通常只在本项目根生效，所以采用三层加载：

| 层 | 位置 | 内容 | 谁维护 |
| --- | --- | --- | --- |
| L1 用户级 | 用户级记忆/规则（一句话指针） | 指向主规范仓库路径与当前 `spec-version` | 用户 |
| L2 项目级 | `<project>/AGENTS.md` 首节 | 薄引用（路径 + 版本 + 摘要）+ 本项目实例化 + 加严项 + 偏离项 | 需求管理员 |
| L3 主规范 | 主规范仓库 | 全文（本文件） | 需求管理员（跨项目） |

代理进入任一项目时的读取顺序固定为：`AGENTS.md` → 本文件 → `AGENTS.md` 的「实例化」节 → 当前 handoff 包。冲突时以更严的一条为准。

### 1.1 作为 AGENTS.md 首节的最小可用形态

项目 `AGENTS.md` 开头直接粘贴下面这段（只改尖括号内容），其余章节保留本项目既有内容。块内由 `bin/sync-agents.sh` 生成与刷新，**任何人不得手改块内字符**（11.5）。

**这是模板，不是实参。** 下面块内的 `0.1 / 0.2 / 0.3` 只是骨架示例（带 `<...>` 占位）；落地时必须在 `spec:end` **之后**原样生成同名小节并填入实参。块内那份不参与任何校验：`g0-landing` 只认块外（`spec:end` 之后、`spec:begin` 之前），块内同名小节一律忽略（11.5 L-2）。

**为什么模板不改成 `0.1T` 之类的异号。** 改号不会破坏 `g0-block`（块由主规范生成，改号后块与主规范仍逐字一致），真正的代价是：①编号与实参不再同名，读者要多做一次映射；②`0.1/0.2/0.3` 被 11.5 L-2、G0、12 节以「同名小节」引用，改号要连带改这些引用；③模板的用途是照抄填空，同号能直接对位。因此只在判据侧区分，不改号。

## 2. 三个基本概念

| 概念 | 定义 | 判据 |
| --- | --- | --- |
| 角色（lane） | 一组稳定的权责边界，决定"能写什么、不能写什么" | 由第 5 节权限矩阵唯一确定 |
| 对话（session） | 工作容器，只有四种：需求池、技术池、评审、phase 对话 | 标题必须命中 9.3 四格式；不得存在身份不明的对话 |
| 执行体（worker） | 承载角色的实体，可以是常驻对话、一次性子代理或人 | 同一时刻只以一个角色行事；同一对话可在不同阶段切换角色，但不得同时持有两席 |
| 产物（artifact） | 角色之间唯一的交接介质：文档、代码、报告、台账条目、决策记录、handoff 包 | 每次交接必须有文件路径；口头交接无效 |

推论，也是本规范与"五个角色各开一个会话"的关键区别：

1. **角色数 ≠ 对话数**。职责是稳定的，容器是可伸缩的；对话按 phase 组织，角色在容器内切换（第 9 节）。
2. **交接只走产物**。任何"我已经跟他说过了"都不成立，必须落到文件或台账条目。
3. **同一文件同一时刻只有一个落笔权持有者**。并发改写是历史事故的直接来源。

## 3. 角色与职责

### 3.1 七类职责、三类常驻对话 + 每 phase 一对话

| 职责 | 落在哪个对话 | 是否常驻 | 说明 |
| --- | --- | --- | --- |
| 主编（EDITOR） | 不单独开对话，由协调者承担 | — | 总负责人：排期、拆任务、判定 phase 收口、卡不合规项；**不写实现代码**（3.2） |
| 需求管理员（REQ） | 需求池对话 | 是 | 主张权持有者；需求池、规格类文档与验收判据 |
| 架构（ARCH） | 技术池对话 | 是 | 技术池、架构设计与 ADR；评审时列席出架构意见，状态词仍归 REVIEW |
| 编码工程师（DEV，执笔人） | phase 对话内 | — | 落笔权持有者；**唯一**负责测试夹具、测试断言与实现代码；红测试由其产出，红证由 VERIFY 认定（3.5） |
| 测试工程师（VERIFY，旧称 QA） | phase 对话内 | — | 红证认定与签字、独立复现、示例；battle 证据席 |
| 评审员（REVIEW，旧称 REV） | 评审对话 | 是（跨 phase 复用） | 独立验证、报告、Issue 台账与状态词 |
| 安全（APPSEC，旧称 SEC） | 无独立对话 | 否 | 评审的 `security` profile + 机械门禁 |

**为什么这样切**：编排与主张分离（主编只排顺序、只能引用池中已有条目，不能自造条目）；架构独立成席，但只出意见、不写状态词；角色是权责边界、对话是工作容器，切换角色必须声明当前角色（9.5）；实现与验收分离（红测试归 DEV，红证归 VERIFY）；测试与评审分离（产物被执行 vs 不被执行）；安全结论并入评审，日常项脚本化，发版前跑全量模式（3.8 `SEC-*`）。代价是架构与安全没有独立常驻席位，靠按需开会话与固定 checklist 补偿。

### 3.8 安全（APPSEC，旧称 SEC，评审的 `security` profile）

| 维度 | 审什么 | 时机 | 判据 |
| --- | --- | --- | --- |
| 供应链 | 锁文件、依赖来源、摘要算法、传递依赖 | 每次提交（机械）+ 新增依赖时（人工） | 锁文件变更必须与依赖清单同提交；来源白名单；摘要非弱算法 |
| 凭据 | 工作树与历史中的密钥、CI secret 引用 | 每次提交 | 扫描 0 命中；命中即 P0 阻断 |
| 注入面 | SQL / shell / 路径拼接 / 模板 / 反序列化 | 新增外部输入解析时 | 每个入口在报告里有一条"输入→净化→使用"链路说明 |
| 内存安全 | C/unsafe 代码、越界、UAF、整数溢出 | 新增或改动 unsafe/C 代码时 | sanitizer 门禁全绿；新增 unsafe 块需说明理由 |
| 权限与暴露 | 发布权限、token 作用域、日志中的个人信息 | 发版前 | 发版检查表逐项勾选 |

执行方式：机械项并入 G7；深度项由 REV 以 `security` profile 执行，产物并入同一份评审报告的「安全」章节，条目编号 `SEC-*`，与功能条目共用同一本台账。

### 3.9 例外：test-fix

测试夹具与断言由 DEV 写（3.5），修正"测试本身写错"不属越界；但改动必须满足：提交标题含 `test-fix`；正文说明原用例为何错且不改验收判据；VERIFY 在 1 个评审轮次内复核。VERIFY 未复核前，该用例不计入 G5 的"可失败"统计。

## 4. 三权分离：主张权 / 落笔权 / 验收权

### 4.1 冲突的根源

"编码是执笔人，可以修改所有文档"与"需求只动需求方文档"同时成立时，**边界失效的原因不是权限给了谁，而是没有区分"改字节"和"决定内容"**。前者是工作量，后者是权力。不拆开，任何一方都可以声称自己在"维护文档"。

### 4.2 三种权利的判据

| 权利 | 定义 | 判据（机械可查） | 持有者 |
| --- | --- | --- | --- |
| 主张权 | 决定文档/规格"说什么"：需求范围、协议语义、验收判据、术语定义 | 该内容被修改时，是否必须产生一条 `CR-*` 记录 | REQ |
| 落笔权 | 决定文件字节怎么组织：段落、措辞、格式、链接、代码同步 | `git diff` 的路径归属 | DEV（默认）/ 各角色对自有产物 |
| 验收权 | 判定产物是否满足主张 | 是否可写 `verified`/`reopened`/最终放行 | REV + USER |

**分离约束**：同一产物上，主张权与验收权不得由同一角色持有；DEV 不持有规格类文档的主张权，但持有其落笔权。

### 4.3 claim 块：让主张权可被 diff 检查

规格类与使用类文档用注释块标记主张区：

```markdown
<!-- claim:begin id=C-012 -->
要求：`ct verify` 必须在无网络环境下完成校验。
验收判据：`ACC-07`，命令见 `docs/acceptance.md`。
<!-- claim:end -->
```

规则：

| 角色 | 时机 | 产物 | 判据 |
| --- | --- | --- | --- |
| DEV | 每次提交 | 提交正文 | `git diff` 触及任意 `claim:begin..claim:end` 时，提交正文必须引用 `CR-<n>`，且该 CR 的提出者为 REQ；否则 G8 失败 |
| REQ | 主张变更时 | `docs/requirements/cr/CR-<n>.md` | 含旧主张、新主张、影响面、验收判据变更、生效版本 |
| REV | 评审时 | 报告「主张一致性」节 | 每条 claim 能找到对应门禁或标 `unverified` |

claim 块之外的一切（措辞、排版、示例位置、链接修复）DEV 可直接改，不需要 CR。这就是"编码可以修改所有文档"的准确含义。

## 5. 权限矩阵

### 5.1 符号

### 5.3 逐列判据

| 列 | 判据 |
| --- | --- |
| 需求文档 | 只有 REQ 可改正文；DEV 的 `W*` 仅限错字、链接、格式，且有无 claim 块由 G8 检查 |
| 设计文档 | claim 块 = 协议语义、接口承诺、验收相关；其余 = 实现细节 |
| README/教程 | 结构与目录由 EDITOR 编排、主张由 REQ 定；「依赖与技术选型」「技术性限制」两小节归 ARCH（取代旧表述「默认 DEV 落笔」）；其余正文 DEV 落笔；≤300 行与分拆规则见 8.4 |
| 示例 | VERIFY 拥有，因为它是可执行验收载体；DEV 只做构建集成 |
| 测试用例 | DEV 拥有：夹具与断言先红后绿（6.6 T-7）；VERIFY 复跑认定红证并签字；test-fix 见 3.9 |
| 门禁脚本 | DEV 唯一；VERIFY/REVIEW 只能提 proposal，不能直接改 |
| 源码 | DEV 唯一 |
| Issues 台账 | REV 立案与状态；其他人只能追加区段 |
| 决策记录 | EDITOR 写判决段与生效范围；REQ 写争点与主张段；ARCH 写架构意见段；其余只追加证据段（取代旧表述「REQ 写裁决」） |

### 5.4 Issue 状态词分权

| 状态词 | 谁能写 | 含义 | 必备证据 |
| --- | --- | --- | --- |
| `open` | REV / REQ | 已立案 | 复现命令或 `file:line` |
| `fixed` | DEV（写处置段，不动状态字段） | 主张已修复 | 提交 sha + 验证命令原始输出 |
| `verified` | REV | 复核通过 | 独立复现 + 逐条对照 |
| `reopened` | REV | 复核未过 | 失败复现 |
| `rejected` | REQ / USER | 不采纳 | 理由；涉及规范时附决策记录 id |
| `deferred` | REQ / USER | 延后 | 触发条件或日期 |
| `wontfix` | USER | 永不修 | 理由 |
| `superseded` | REQ | 被新条目取代 | 新条目 id |

判据（G6）：每个条目 front-matter 的 `status` 必须属于上表，且 `status` 与证据字段非空；`fixed` 只能出现在正文处置段，不得写入 `status`。

## 6. 工作流与门禁

### 6.0 端到端主线（索引）

一条新需求从提出到落地只走这一条主链；每环的正文与判据在所指章节，本节只给交接物与入口/出口，不复制条款。

| # | 环节 | 入口产物（上一环必须交出） | 出口产物与判据（怎样算做完） | 负责 |
| --- | --- | --- | --- | --- |
| 1 | 需求提出 | 用户或干系人的诉求（仓库外；新项目先按第 12 节纳管） | 需求池条目字段齐全（6.1 P-3）；每条要求有稳定 ID 与带命令的验收判据（G1） | 主张 REQ |
| 2 | 分析 | 需求池中 `status: open` 的条目 | `docs/planning/analysis/AN-<id>.md` 四段非空：问题陈述、范围、验收判据、依赖与风险（6.1 AN-1）；ARCH 的可行性与成本意见并入同文件 | 主张 REQ（ARCH 列席） |
| 3 | 制定 roadmap | 已有分析结论的条目 `id` | 路线图每个 phase 行能追到 `AN-<id>`，顺序、依赖、边界写明（6.1 R-1、R-2、P-1） | 主编 EDITOR |
| 4 | 阶段切分 | 路线图中的 phase 行 | phase 卡片开卡必填齐全，任务清单逐条过 6.6 **T-1…T-7**（6.2、6.1 P-5）；退出判据写死并冻结（6.2） | 主编 EDITOR |
| 5 | 逐 phase 开发 | 已冻结的 phase 卡片 | 每个任务**先红后绿**（6.6 T-7）、粒度到 T-1/T-2、一次提交一事；八环节走完、退出判据逐条有证据（6.2、6.4） | 执笔 DEV（VERIFY 认定红证） |

**环间判据**：上一环的出口产物缺失或为空，下一环不得开工，补齐后再继续。需求或分析缺失由 G1 拦（主张不完整，不得进入实现）；路线图追不到池条目按 6.1 R-2 的越权处理。

**不适用本链的通道**：单个 issue 的单点修复走 6.3 小循环，线上故障走 6.3 热修，两者不经过 roadmap 与 phase 切分；TDD 的红证要求对两者同步生效（6.3、6.6 T-7）。

### 6.1 Planning：三池一图

规划拆三层，主编只持编排层；需求进路线图之前另过一道分析（产物归 REQ，见下文 AN-1）。

| 规划什么 | 归谁 | 产出 | 位置 |
| --- | --- | --- | --- |

**分析**（需求池与路线图之间的独立一环，不并入立项）：产物归主张 REQ，架构 ARCH 只给可行性与成本意见、不写结论；主编不参与，避免"边分析边排期"。

| # | 规则 | 判据 |
| --- | --- | --- |

### 6.2 phase 交付流程

**开卡必填**（缺一不许立项）：

| 字段 | 判据 |
| --- | --- |
| 编号 | `PH-<n>`，与目录 `docs/phases/PH-<n>/` 一致 |
| 目标 | 一句话，可被第三人复述 |
| 范围 | 明确"做什么 / 不做什么" |
| 交付物清单 | 每项一个路径 |
| 任务清单 | 每项一个交付物、一条验收命令、一次提交、可单独回滚；四者缺一不许立项（6.6 T-1…T-7） |
| 退出判据 | 每条带命令或可核对锚点 |
| 依赖 | 前置 phase / issue / 外部条件 |
| 规范版本 | 开卡时项目生成块头的 `version` 快照；只有 `>= 1.6.0` 的卡片受 6.7 约束（6.7 适用边界） |
| version-minor | 收口时应达到的 MINOR，等于 `PH-<n>`；PATCH 由 fix 数决定，不写进卡片（6.7） |
| 已知风险 | 每条带触发信号 |

**硬规则：退出判据必须在开工前写死。** 中途只能新增下一个 phase，不能修改当前 phase 的退出判据。判据：`card.md` 的 `exit-criteria` 字段在本 phase 首个实现提交后不可变，由 G8 `g8-phase-freeze` 检查 diff；确需变更时关闭当前 phase 并新开一个。反例：Phase 20 立项时写"收口 v0.20.0"，P0 四项却是后来才识别的，结果 phase 变成"做到哪算哪"。

**退出判据的固定一条**：每个 phase 的 `exit-criteria` 必须显式包含「任务清单每项可独立验收（6.6 T-6）」；缺此条按 G1 `g1-phase-card` 失败。该条只对本次变更之后新立的 phase 生效，已在途 phase 的退出判据不追溯（仍受上一段的冻结规则保护）。

**八环节**：

| 环节 | 主责 | 产出 | 卡在哪 | 门禁 |
| --- | --- | --- | --- | --- |
| 立项 | 主编 EDITOR | phase 卡片 | 退出判据写不出来不许立项 | G1 `g1-phase-card` |
| 设计 | 主张 REQ + 架构 ARCH | 规格、ADR | 有争议先 battle（第 7 节） | G2 |
| 实现 | 执笔 DEV | 测试夹具与红证 → 实现（6.6 T-7） | 每个任务先红后绿；编译与单测 | G3、G4、G8 |
| 验证 | 验证 VERIFY | 红证认定与签字、独立复现、样例 | 全通过 | G5 |
| 评审 | 评审 REVIEW（架构列席） | 报告 + issues | P0 清零 | G6、G7 |
| 修 Issues | 执笔 DEV | 修复 + 回归 | P0/P1 有归属 | G6 |
| 收口 | 主编 EDITOR | 交付物对照表 | 退出判据逐条核 | G1、G6 `g6-pool` |
| 发布 | 主编 EDITOR | 远端发布、CHANGELOG、迁移说明 | 发布判据：API 稳定、迁移说明、CHANGELOG 完整；版本号与 tag 只在 6.7 判定（V-1、V-6、V-7 与 `g4-version`） | G7（全量）、G9 |

**phase 完成 ≠ 发布。** 发布有独立判据：API 稳定、迁移说明、CHANGELOG 完整。phase 收口必打 phase tag 并推送该 tag（6.7 V-7），但不推分支、不对外发布；分支推送与远端发布须用户指令（6.5）。

**Issues 三去向**：本 phase 必修 / 登记到某个未来 phase / 明确拒绝并写原因。没有第四种"先放着"。判据：收口对照表中每个 issue id 有且只有一个去向；`deferred` 必须写目标 phase 或日期（G6）。

**回顾环节**：每条教训必须落到三处之一——变成一道门禁、变成规范的一条、或明确写"不采纳 + 理由"。写成感想的回顾视为未完成。判据：`reviews/closeout-<phase>.md` 的 `lessons` 表每行有 `landing`，取值形如 `gate:<门禁>`、`spec:<节>`、`rejected:<理由>`。

**旧阶段模型对照**（原 6.1「P0–P6 阶段」被本节八环节取代，旧编号不再使用；G0–G9 编号与判据不变）：

| 旧阶段 | 新环节 | 说明 |
| --- | --- | --- |
| P0 纳管 | 立项（前置） | 首次纳管仍走 G0/G9，不单设环节 |
| P1 需求 | 设计（主张） | 需求与规格并入设计环节，仍由 G1 卡 |
| P2 设计 | 设计（架构） | 同上，由 G2 卡 |
| P3 实现 | 实现 | 不变 |
| P4 测试 | 验证 | 改名，G5 不变 |
| P5 评审 | 评审 + 修 Issues | 拆成两环节，P0 清零才能收口 |
| P6 发版 | 发布 | 从"阶段"改为"独立判据"：phase 完成不必对外发布，但收口必打本地 tag（6.7 V-7） |

### 6.3 三档流程

判据是"有没有独立的交付边界"。

| 档位 | 适用 | 开卡 | 最少记录 | 门禁 |
| --- | --- | --- | --- | --- |
| phase | 有阶段目标、多交付物、跨角色 | 要 | phase 卡片 + 收口对照表 | G0–G9 |
| 小循环 | 单个 issue、单点修复 | 不要 | issue 条目 + 修复提交 + 验证证据 | G3、G5、G6、G8 |
| 热修 | 线上故障 | 不要 | 故障记录 + 回归用例 | G7（机械项）、G5（回归） |

小循环是五步压缩版：**复现（红）→ 修 → 验证 → 合并**，评审可单人，验证证据不能省。判据：issue 条目含复现命令与原始输出；修复提交引用 issue id；验证证据由 VERIFY 出具。复现必须是修复前的失败输出，按 6.6 T-7 带 `baseline: <sha>`；用修好后的代码复跑不算。

热修可跳过评审，但必须补回归用例。判据：故障记录含时间线、影响面、止血措施；回归用例在同一发布周期内提交，且能在缺陷重现时变红（负例验证，G5）。

小循环与热修的红证要求同 T-7：红证段含 `baseline: <sha>` 与原始输出，`<sha>` 必须是修复前的提交。

**反模式红线**：

| # | 禁止 | 检测方式 |
| --- | --- | --- |
| A-1 | phase 中途插"顺便一起改" | 范围外改动应转小循环或新开 phase；G8 范围检查 + 收口对照表 |
| A-2 | 以"差不多了"收口 | 退出判据任一条无证据即失败（G1、G6） |
| A-3 | 回顾写成心得体会 | `lessons.landing` 为空或无 `gate:`/`spec:`/`rejected:` 前缀，视为未完成 |
| A-4 | 池子条目长期沉睡无人清理 | Q-1/Q-2 超窗未处理（G6 `g6-pool`） |
| A-5 | 用一项任务交付整个模块 / 整个 phase | 该任务同时覆盖 ≥2 条退出判据，或包含 ≥2 个无关交付物（6.6 T-5）；G1 任务清单检查 + 收口对照表 |

### 6.6 任务切分：小步快跑

> 原则：phase 是目标，任务是交付单位。目标可以大，交付单位必须小到能被单独验收、单独回滚。

**任务的定义**（术语见第 13 节）：一个交付物 + 一条验收命令 + 一次提交 + 可单独回滚。四者缺一即不是任务，只是"一块工作"。

| # | 规则 | 判据 |
| --- | --- | --- |
| T-1 | 一项任务只有一个交付目的：一个主要交付物（源码、文档或配置），连同它自己的负例与证据；不得把一个模块、一个 phase 或两个无关目的放进同一项任务 | 任务清单每行只有一条 `deliverable`；出现并列交付物且不属同一变更 → 退回重切 |
| T-2 | 一项任务必须能在一轮内完成：一次会话内收口，或一次提交周期内收口；估不出边界的任务不许开工 | 卡片 `tasks` 每行有 `effort`，取值 `S` / `M`；`L` 必须再拆，`XL` 不允许出现 |
| T-3 | 一项任务有自己的验收命令与原始输出，不得借用「整个 phase 门禁全绿」作为自己的验收 | 卡片 `tasks` 每行有 `verify`；收口对照表逐条贴该命令的输出，而不是复述总门禁 |
| T-4 | 一项任务能单独回滚：`git revert` 该任务的提交后，其他任务的交付物与门禁不受影响 | 该提交的路径集合与该任务声明的路径一致（8.3「一提交一事」）；回滚演练后其余任务的门禁仍绿 |
| T-5 | 任何一项任务的完成都不得同时满足该 phase 的全部退出判据——否则说明 phase 没被切开 | 逐项任务对照 `exit-criteria`：一条任务覆盖 ≥2 条退出判据即退回重切 |
| T-6 | 任务清单在开工前写死，与退出判据同受冻结；任一项四要素不全 → 不许开工，收口时有未验收项 → 不许宣称完成 | G1 `g1-phase-card` 校验 `tasks` 非空且四列齐全；G6 收口对照表逐项对应；G8 `g8-phase-freeze` 校验 `tasks` 未被中途修改 |
| T-7 | 先红后绿：任务的第一步是提交测试夹具与断言并产出红证，实现提交随后转绿；纯文档、纯配置、纯注释任务例外，须在任务行写 `no-test: <理由>` 并由评审签字 | 同一 `task-id` 的两个相邻提交：`test(<scope>): <task-id> 红`（只含测试、夹具与红证）是 `feat`/`fix` 实现的**父提交**（G8）；红证含 `baseline: <sha>` 与原始输出，`<sha>` 必须是实现前的提交且是 `HEAD` 的祖先；用当前代码复跑的不算 |

**T-7 的提交与红证格式**

```console
$ git log --oneline -2
<impl-sha> fix(ct-ast): <task-id> 修复 <一句话>
<test-sha> test(ct-ast): <task-id> 红
```

- 红证写在 issue 条目或 phase 卡的任务行，最小字段：`baseline: <sha>`、命令、原始输出、退出码。
- 复跑基线：`git archive <baseline> | tar -x -C /tmp/<task-id>` 后按项目方式构建，不得使用工作树当前产物。
- `baseline` 必须是 `test` 提交的父提交（即实现落地前）；`git merge-base --is-ancestor <baseline> HEAD` 必须为真。
- 例外只覆盖纯文档、纯配置、纯注释：任何改变行为的提交都不适用；`no-test:` 缺评审签字视为任务未完成。
- 归属：`test(...) 红` 与实现两个提交都由 **DEV** 提（3.5）；EDITOR 只在 phase 卡片上批准任务与判据，不代笔、不合入；红证由 **VERIFY** 认定并签字（3.6），DEV 不自签。

**适用边界**：T-7 只对本次变更之后新立的 phase 与新开的任务生效；已在途 phase 不追溯（与 6.2 退出判据冻结同一口径）。小循环不要求开卡，但复现同样先于修复（6.3）；热修保留原有提交顺序，红证要求同步生效。

**与既有条款的关系**：本条不新增门禁编号，判据挂在 G1 `g1-phase-card`、G5、G6、G8 下；「一提交一事」（8.3）是任务粒度在提交层的同一条规则，不另立——`test` 提交与实现提交各是一事，不合并。

**切分方法（三步，可机械执行）**：

1. 把 phase 的交付物逐条列成 `deliverable`，一个交付物一行；
2. 每条交付物再切出"能让它单独变绿的最小改动"，作为一项任务；切不动说明交付物本身太大，退回 6.1 重排 phase；
3. 给每项任务写 `verify` 与 `effort`；写不出验收命令的任务不是任务（与 6.2 的立项判据同源）。

### 6.7 版本号：MINOR 与 phase 同步，PATCH 与 fix 同步

> 本节管的是**项目产品版本**——源码、清单文件、README 徽章里那个数字。主规范自己的 `spec-version` 与项目 `AGENTS.md` 的 pin 不适用本节，见 11.4；两套版本号不要混成一套。

**形态**：`MAJOR.MINOR.PATCH`，声明处不带 `v` 前缀（tag 可带，如 `v0.30.1`）。三个位各自只由一个事件推动：

| 位 | 什么时候 +1 | 触发者 |
| --- | --- | --- |
| MAJOR | 对外破坏性变更，且项目**已发布**；未发布的项目不因签名变更升 MAJOR（6.5） | 用户裁定 |
| MINOR | **每个 phase 交付时**：`PH-<n>` 收口，MINOR 置为 `n`，PATCH 归零（登记了版本偏离的，按偏离里的偏移换算，见下） | phase 收口 |
| PATCH | **每次 fix**：单点修复、热修、缺陷修复；一次 fix 恰好 +1 | 该修复的提交 |

| # | 规则 | 判据（机械） |
| --- | --- | --- |
| V-1 | MINOR 与 phase 严格一一对应：`PH-<n>` 交付时 `MINOR == n`（有版本偏离的按登记的偏移换算），即相对上一 phase 恰好 +1；不许多跳（不得从 `n-2` 直接到 `n`），不许同一 phase 内第二次 +MINOR；PATCH 随 MINOR 归零 | 收口提交的版本 `MINOR == n` 且前一版为其减一；同一 phase 窗口内出现两次 MINOR +1 即失败（`g8-version`、`g1-version`） |
| V-2 | phase 内的新功能不得占用 PATCH：PATCH 只记 fix，不记功能 | phase 窗口内每次 PATCH +1 都能追到一个被立案的缺陷条目（`g8-version`） |
| V-3 | PATCH 与 fix 严格一一对应：一次 fix 一处缺陷、只 +1 一次；同一缺陷 `reopened` 后的返工不重复 +1（它仍是那一次 fix） | 该提交正文引用恰好一个 `issues/<id>.md`，且本次处置为 `fixed`（5.4、`g8-version`） |
| V-4 | 不算 fix、因此不许单独 +PATCH：纯文档 / 措辞 / 格式 / 链接修订、注释、测试夹具与断言自身的修正（3.9 `test-fix`）、门禁脚本重构、CI 配置调整。唯一例外：该改动本身就是一条被立案的缺陷（例如文档写错、用户照做失败），此时按那条 Issue 的 `fixed` 计一次 fix | 提交路径集合命中上述类别、且正文未引用处置为 `fixed` 的 Issue → 失败（`g8-version`） |
| V-5 | 版本号随它所标记的那次 fix / phase 收口在**同一提交**内移动；版本号不是独立事项，不另开提交。同一提交内声明处的三个数字必须一致（落点见下） | 版本落点与行为改动或收口记录同提交；只改版本号、不改任何行为或收口的提交 → 失败（`g8-version`） |
| V-6 | 代码里的版本字段必须与工程状态对得上，**任何不一致即缺陷**：立 `Issue` 并按一次 fix 处置（PATCH +1，V-3）；不得记为历史遗留、不得 `deferred` 放着、不得只改一处凑绿 | 按本节「版本字段核对的两处时机」执行；发现不一致而未立案 → G6 失败；核对工具与两项判据见 `g4-version` |
| V-7 | **phase 收口时版本移动、建 tag、推 tag 在同一次收口动作内完成**，不需要每次另行请示用户：创建 annotated tag `v<MAJOR>.<MINOR>.<PATCH>`（带 `v`，例 `v0.33.0`），指向收口提交，message 含 `PH-<n>` 与收口提交 sha 前 7 位；四项校验通过后 `git push origin <tag>`。**只有 phase tag，fix 不打 tag**（理由见下）。**分支推送不受本条影响**，仍按 6.5 须用户显式指令 | 推前四项全过才推：①名符合 `v<MAJOR>.<MINOR>.<PATCH>`；②`git cat-file -t` = `tag`；③`git rev-parse <tag>^{commit}` 等于收口提交；④该提交可在远端追溯（`git branch -r --contains <sha>` 非空）。任一项不过 → 不推、打印原因、非零退出；缺 tag、名不带 `v` 或未推成功即 `g8-version` 失败 |

**版本落点必须声明。** 一个项目的版本号出现在哪些位置，由该项目在 `AGENTS.md` 实例化节写一行 `版本落点`（例：`composer.json#version`、`src/Version.php:const VERSION`、`README.md` 两处徽章）。未声明即 G0 失败；声明了却没改全，同一提交内所有落点的三个数字不一致即 `g8-version` 失败。

**版本字段核对的两处时机。** `g4-version` 只在两个时点跑，不逐提交跑（逐提交有 `g8-version`）：发版的发布检查表、phase 收口的收口对照表。核对四项：①落点之间相等；②`MAJOR.MINOR` 与 `PH-<n>` 对应（含偏离换算）；③`PATCH` 与该 phase 内的 fix 条目数相等；④CHANGELOG 最新条目与 tag（有此 phase 的 tag 时）所指版本一致。任一项不等即在报告里贴出两边的原值与出处，并按 V-6 立案。

**与 phase 卡片对齐。** phase 卡片增加必填字段 `version-minor`，写收口时应达到的 MINOR（例：`30`），判据等于 `PH-<n>`；PATCH 不写进卡片——它由该 phase 内的 fix 数决定，写死就会和 V-3 打架。该字段与退出判据、任务清单同受冻结（6.2、6.6 T-6）：中途抬高 MINOR 或提前占用 PATCH 都算修改退出判据，由 `g8-phase-freeze` 拦。

**挂在哪道门禁**（不新增门禁编号）：

| 检查 | 挂靠 | 守哪些条 |
| --- | --- | --- |
| `g1-version` | G1 `g1-phase-card` 的扩展 | V-1：卡片 `version-minor` 必填，且等于 `PH-<n>`（有偏离的按登记换算） |
| `g8-version` | G8 的扩展 | V-1…V-5：提交级逐次检查 |
| `g4-version` | G4 的扩展（沿用 `g4-fresh` 的时效语义） | V-6：发版前与 phase 收口各核对一次 |
| G0 实例化项 | G0 | `版本落点` 一行非空 |

**V-7 的生效边界。** 只对 1.8.0 之后新开的 `PH-<n>` 生效；`PH-27`…`PH-33` 等已收口或在途的 phase 不因本条补打 tag，是否回补由用户单独决定（选项与代价见交付报告）。

**tag 只标 phase，不标 fix。** 每个 fix 都 +PATCH（V-3），若逐个打 tag 会让 tag 数量随缺陷数膨胀；而 `applies-to: <tag|sha>` 已允许用 sha 钉住任意提交（§0.3），fix 不需要独立 tag。fix 只进 CHANGELOG，并在下一次 phase tag 时被一并覆盖。判据：一个 phase 窗口内 tag 数 = 1（phase tag），fix 提交上不建 tag。

**tag 自动推 ≠ 发布到远端。** 收口 tag 连同创建一起 `git push origin <tag>`，属收口的一部分，不再逐次请示；但**分支推送**与对外发布仍须用户显式指令（6.5），发布仍按 6.2 的判据（API 稳定、迁移说明、CHANGELOG 完整）。这条区分是本节与发布判据的边界，不是例外。

**适用边界：只对下一个新开的 phase 生效。** 本节自 1.6.0 起约束：开卡时项目 pin 的 `spec-version >= 1.6.0` 的 `PH-<n>` 受本节全部条款；已在途 phase 不追溯——`version-minor` 字段可缺、号段按原样收口。首个受约束的 phase 就是 1.6.0 之后新开的那个。判据：生成块头记的 `version`（三个位按数值比较，不是字典序），`g1-version` 只检查 `>= 1.6.0` 的项目。

**存量落差：登记偏离，不重新编号（本版选定）。** 一个项目若在 1.6.0 之前已走到 `PH-<n>` 而 `MINOR != n`，保留现有号段，在 `AGENTS.md` 的 `偏离项` 里登记一条针对版本号的 `deviation:`：写明偏移 `d = n - MINOR`、生效日期、理由、收敛方式，并由用户签字。判据：G0 认 `偏离项` 这一行；`g1-version` 用登记里的 `d` 换算，`MINOR == n - d`；没有签字即按 V-1 失败。

| 做法 | 代价 | 适用 |
| --- | --- | --- |
| 登记偏离（本版选定） | 版本号与 phase 长期错位；历史 tag 与 CHANGELOG 不动；每次收口多一步换算；需用户签字 | 已发布或已有历史 tag 的项目 |
| 重新编号 | 一次跳号违反 V-1「不许多跳」，并在 CHANGELOG 留下空段；已发布 tag 不可回改，旧号与新号断裂 | 未发布、且没有 tag 的项目 |

**收敛方式必须写死在偏离里。** 在 V-1 下 MINOR 与 phase 每轮都 +1，偏移恒定：两者同速前进时"逐步对齐"不会自动发生。可写进 `deviation:` 的只有三种，必须选一种——

| 方式 | 写法 | 后果 |
| --- | --- | --- |
| 一次性补号 | 指定某个 phase 收口时把 MINOR 一次补到 `n` | 该次收口违反"不许多跳"，须在同一条 deviation 里显式豁免 |
| 永久偏移 | 写 `偏移: <d>`，不设收敛 | 与"MINOR 与 phase 一一对应"名义不符，但机械可查 |
| 将来重编号 | 写明"到 `PH-<m>` 时按重新编号处理" | 届时仍要一次跳号与 CHANGELOG 空段 |

示例（可移植）：`PH-12`、当前 `0.8.3`、`d = 12 - 8 = 4`，即 `偏移: 4`；`PH-13` 收口得到 `0.9.0`，`g1-version` 按 `13 - 4 = 9` 换算通过。

| # | 冲突 | 处置（改后条款 + 位置） | 状态 |

## 7. battle 流程（四席 + 裁判）

用途：对有判据的技术争议做**可复现、可终止、可落盘**的裁决，替代"谁资历高听谁的"和"反复讨论到没人再说话"。

本章使用现行角色名：主编 EDITOR、主张 REQ、架构 ARCH、执笔 DEV、验证 VERIFY、评审 REVIEW、安全 APPSEC。旧简称 SCRIBE / QA / REV / SEC 与旧四角色（`methodology/roles/legacy/`）只作历史保留，语义已并入现行角色；新写一律用现行名。

### 7.1 一条分界线：什么进 battle

**battle 只处理有判据的争议。没有判据的不是争议，是决策。**

| 进 battle（有判据） | 不进 battle，直接升级用户（无判据） |
| --- | --- |
| 技术方案选型，可用命令/数据/门禁判定优劣 | 产品方向与优先级 |
| 代码、协议、门禁的判定分歧 | 成本与资源投入 |
| 某验收判据能否被某实现满足 | 是否值得做 |
| 安全风险是否成立、是否阻断 | 外部依赖是否可得 |
| 文档/规范与实现是否一致 | 价值取舍类问题 |

理由：没有判据时，battle 必然产出一份看似有道理、实际无人信服的结论，只是把争论换个格式延长。

### 7.2 触发条件（任一成立即触发，其余一律不触发）

| ID | 条件 | 判据 |
| --- | --- | --- |
| B-1 | 同一 Issue 在 2 个评审轮次内被 `reopened` | 台账状态历史 |
| B-2 | DEV 与 REVIEW 对同一 `P0/P1` 判定相反 | 双方报告原文 |
| B-3 | REQ 与 DEV 对同一 claim 变更结论相反 | 双方 CR 意见 |
| B-4 | 两个以上方案均通过 G1–G5，且成本差异小于 2 倍 | 方案对比表 |
| B-5 | 用户显式输入 `battle: <topic>` | 用户消息 |

任何角色都有发起权，不必等到上述条件全部确认；但若被裁判判定为无判据，按 7.1 直接升级用户，不立案。

**不触发**：跑一条命令即可定论的事实分歧；纯风格偏好；已有门禁可判定的事项；7.1 右列全部事项。前三类由对应角色按门禁结论直接执行。

### 7.3 四席 + 裁判

证据必须独立成席，避免双方选择性举证。

| 席位 | 担任者 | 职责 | 产出 |
| --- | --- | --- | --- |
| 主张席 | 提出方案的一方 | 说清方案与它满足什么判据 | 主张书 |
| 反对席 | 立场相反的角色 | 必须找出方案的失效条件 | 反证清单 |
| 证据席 | 验证 VERIFY（必要时 ARCH 合署） | 按双方要求出可复现事实 | 命令 + 输出 + 环境 |
| 裁判席 | 主编 EDITOR | 只判证据成不成立、判据有没有被满足；不表态不投票 | 结论与生效范围 |

席位是**职责**，不是人：同一角色可在不同 battle 中换席，但同一场 battle 中一个执行体只能占一席。

### 7.4 按争议类型定对阵

| 争什么 | 主张席 | 反对席 | 证据席 |
| --- | --- | --- | --- |
| 做什么、为什么 | 主张 REQ | 评审 REVIEW | 架构 ARCH（可行性） |
| 能不能做 | 执笔 DEV | 架构 ARCH | 验证 VERIFY（探针） |
| 做对没有 | 执笔 DEV | 评审 REVIEW | 验证 VERIFY（复现） |
| 怎么搭 | 架构 ARCH | 主张 REQ（是否符合目标） | 执笔 DEV（成本） |
| 安全 | 执笔 DEV | 安全 APPSEC | 验证 VERIFY |

裁判恒为主编 EDITOR，不随争议类型变化。

### 7.5 四条硬规则

| # | 规则 | 判据 |
| --- | --- | --- |
| H-1 | 反对席必须存在；无人自荐时由主编指派，且不得指派给提案人 | `question.md` 中 `opposition:` 非空且 ≠ `proposer:` |
| H-2 | 主张人不得担任裁判 | `question.md` 中 `judge: EDITOR` 且 `proposer:` 不含 EDITOR |
| H-3 | 证据必须可复现——命令、输出、环境三样齐全，缺一项视为未举证 | `verify.json` 每条证据三项非空 |
| H-4 | 一场最多三轮，每轮必须新增证据，否则立即终止 | 轮次计数 ≤ 3；证据集哈希逐轮变化 |

### 7.6 各角色在庭内的落点

| 项 | 规则 |
| --- | --- |
| 召集与裁判 | 主编 EDITOR 是唯一召集人与裁判，不表态、不投票 |
| 发起 | 任何角色都有发起权 |
| 反对席默认人选 | 评审 REVIEW；涉安全换安全 APPSEC，涉可行性换架构 ARCH |
| 证据席默认 | 验证 VERIFY；涉及构建、依赖、兼容时 ARCH 合署 |
| 用户出场条件 | 仅两种：无判据需价值判断；三轮后仍无结论 |
| 禁止 | 不得复用提案人所在对话的同一上下文担任反对席或证据席；庭内三席各自独立上下文，不得由同一会话兼任两席 |

### 7.7 举证规格（E1–E5）

举证责任在主张席与反对席，证据席只负责复现与出证，裁判席只判成立与否。任一条不满足要求的证据不计入证据集，不得用叙述替代。

| ID | 要求 | 判据 |
| --- | --- | --- |
| E1 | 可复制的完整命令 + 原始输出（不得改写、不得摘要代替） | 证据席在只读工作树重跑，输出一致 |
| E2 | 当前 HEAD 的 `file:line` 锚点，至少 1 条支持己方、1 条不利于己方 | 行号存在且内容匹配 |
| E3 | 可证伪预测："若己方成立，运行 X 应得到 Y" | 预测可被一次性验证 |
| E4 | 代价量化：改动文件数/行数、影响门禁、回退步骤 | 三项齐全且可核对 |
| E5 | 对对方最强论点的 steelman 回应（引用对方原文） | 引用存在，回应非空 |

### 7.8 时序（可脚本化）

| 步 | 动作 | 产物 | 负责 | 判据 |
| --- | --- | --- | --- | --- |
| T0 | 立案 | `battle/<id>/question.md` | 发起方 + EDITOR 确认 | 争点、逐条判据、`proposer`/`opposition`/`judge` 字段齐全 |
| T1 | 隔离开局 | 三席任务说明 | 调度脚本 | 主张席与反对席互不可见对方输出；证据席可见双方 |
| T2 | 主张书 + 反证清单 | `claim.md`、`counter.md` | 主张席 / 反对席 | E1–E5 齐备；反证清单逐条列出失效条件 |
| T3 | 交叉质证（含首轮，≤3 轮） | `claim-r<n>.md`、`counter-r<n>.md` | 主张席 / 反对席 | 每轮至少新增 1 条 E1/E2，否则终止 |
| T4 | 出证 | `verify.json` | 证据席 | 每条证据命令重跑一致、锚点有效、环境写明 |
| T5 | 判决 | `verdict.md` | 裁判 EDITOR | 逐条判据给出成立/不成立；写明生效范围 |
| T6 | 落盘 | `docs/decisions/D-<n>.md` + Issue 状态回写 | REQ | 决策记录字段齐全 |
| T7 | 归档 | `battle/<id>/closed.md` | 调度脚本 | 关联 Issue 均已离开 `open` |

`question.md` 必填：争点、当前 HEAD、触发理由、相关 Issue/CR、**逐条判据**、`proposer`、`opposition`、`judge`、禁止触碰路径。缺"逐条判据"即不立案——这是 7.1 分界线的机械实现。

### 7.9 判决规则（取代评分）

裁判不投票、不打总分，只对"每条判据 × 每条证据"做二元判定，再由判定推出整体结论：

| 判据状态 | 结论 | `verdict` |
| --- | --- | --- |
| 主张席方案满足全部判据，且反证清单中的失效条件均被证据排除 | 主张成立 | `upheld` |
| 判据未被满足，或反证清单中至少一条失效条件被证据证实 | 主张不成立 | `rejected` |
| 证据不足以判定任一方向（重跑不一致、环境缺失、判据本身不可测） | 无法判定 | `undecidable` |
| 判据缺失，或三轮后仍无法判定且出不了 C | 升级用户 | `escalate` |

- `rejected` 不等于"反对席的方案成立"：反对席只承担证伪，不承担替代方案；需要替代方案时按 7.10 出 C。
- 判决必须写明**生效范围**（哪些 Issue/判据/门禁/版本受影响），范围外不得引用该结论。
- 任一方两轮内 E1–E5 全缺 → 该方主张直接不成立，不必进入第三轮。

### 7.10 无法判定时的出口

禁止以"平局"关闭。必须二选一：

1. **产出 C 方案**：同时满足双方最强约束，写入 `C-proposal.md`，再走一次单方案评审（主张席=原主张人，反对席=REVIEW，证据席=VERIFY）。
2. **登记 open-question**：`docs/decisions/D-<n>.md` 中记 `verdict: undecidable`，并写 owner、截止条件、默认裁决规则（例如"若 2026-12-01 前无新证据，采用 B"）。

### 7.11 防无限循环

| 规则 | 阈值 | 判据 |
| --- | --- | --- |
| 轮数上限 | 全场 ≤ 3 轮（含首轮主张/反证） | `battle/<id>/` 文件计数 |
| 增量要求 | 每轮至少新增 1 条 E1/E2，否则立即终止 | 证据集哈希与上轮不同 |
| 一题一战 | 同一 Issue/CR id 只允许一次 battle，再次需用户书面授权 | 台账 `battle:` 字段 |
| 预算上限 | 默认每席 30 次工具调用或 20 分钟 | 调度脚本计时/计数 |
| 超限处置 | 自动升级用户，附"双方最强论点 + 一条推荐" | `verdict.md` 中 `verdict: escalate` |

### 7.12 决策记录格式

```markdown
---
id: D-013
date: 2026-11-09
anchor: <HEAD sha>
trigger: B-2
status: accepted        # accepted | rejected | superseded
verdict: upheld         # upheld | rejected | undecidable | escalate
judge: EDITOR
seats:
  claim: DEV
  opposition: REVIEW
  evidence: VERIFY
scope: <受影响的 Issue / 判据 / 门禁 / 版本>
spec-claim: C-012       # 若影响 claim，填对应 id
---

## 争点
## 判据（逐条）
## 主张书（claim.md 索引）
## 反证清单（counter.md 索引）
## 出证（verify.json 索引，含命令 / 输出 / 环境）
## 判决（upheld | rejected | undecidable | escalate）
## 生效范围（范围外不得引用）
## 理由（逐条对应判据）
## 失效条件（什么情况下该决定需要重开）
## 影响面（Issue、验收判据、门禁、版本）
```

### 7.13 battle 庭会话（Tribunal）

按需开启，不常设，只在有争议时开。各方把主张书交进去，庭会话按本章规则裁决并出具 ADR。

| 项 | 规则 |
| --- | --- |
| 开启 | 由主编 EDITOR 在立案（T0）时创建，一个 battle 一个庭，结束后关闭 |
| 输入 | `question.md` + 主张书 + 反证清单 + 证据席出证；不接收聊天记录转述 |
| 输出 | `verdict.md` + `docs/decisions/D-<n>.md`（ADR） |
| 关闭 | T7 归档后关闭；未出判决不得关闭 |
| 禁止 | 庭会话不得修改源码、文档主张、门禁；不得在无判据时开启；不得充当生产会话 |
| 解决的问题 | 裁判不参与生产，避免偏向自己写的东西；同时消除协调者在会话间转述造成的失真 |

### 7.14 自动化实现要求

| 项 | 要求 | 判据 |
| --- | --- | --- |
| 入口 | `tools/battle.sh start <issue-id>` | 生成争点包与三席任务说明；校验 H-1/H-2 |
| 校验 | `tools/check-battle.py <id>` | 校验 E1–E5、命令可重跑、锚点有效、环境非空；输出 `verify.json` |
| 判决 | `tools/battle.sh verdict <id>` | 生成"判据 × 证据"矩阵草稿，交裁判逐条确认 |
| 落盘 | `tools/battle.sh close <id>` | 写 ADR、回写 Issue 状态、归档 |
| 禁止 | 脚本不得自动修改源码、文档主张或判决 | 脚本仅写 `battle/`、`verdict.md` 草稿与 ADR |

## 8. 产物与证据要求

### 8.1 证据记录

任何 finding、修复主张、验收结论都必须能展开成下面六项；缺任一项即无效：

```
[条目标识] RV-012 / SEC-003 / ACC-07
[锚点] HEAD <sha>（工作树是否干净）
[命令] <完整可复制命令>
[输出] <原始 stdout/stderr，不得摘要代替>
[位置] <file>:<line>
[结论] PASS | FAIL | STATIC
[时间/环境] <ISO 时间> / <OS/工具版本>
```

无效证据清单（命中即判无效）：无命令；无原始输出；无锚点；把静态推断写成"已复现"；把未运行的命令写成通过；通过修改基线或期望输出"修复"失败；只给结论不给位置。

### 8.2 评审报告最小结构

| 节 | 内容 | 判据 |
| --- | --- | --- |
| 结论 | 通过 / 有条件通过 / 不通过 | 三选一，不得含糊 |
| 分级 | P0 / P1 / P2 清单 | 每条带 ID 与证据索引 |
| 覆盖范围 | 审查了哪些文件/模块/提交范围 | 与台账条目数可对账 |
| 未覆盖声明 | 跳过的套件、仅静态的条目、环境限制 | 显式列出，不得省略 |
| 主张一致性 | claim 与门禁的映射 | 每条 claim 有门禁或标 `unverified` |
| 文档时效 | `stale_docs`、`unverified_claims`、`docs_without_gate` 三项计数与清单 | 第 0.6 节；每轮必填，缺项视为报告不完整 |
| 安全 | 3.8 节各维度结论 | 机械项与深度项分开写 |

### 8.3 提交要求

| 规则 | 判据 |
| --- | --- |
| 一提交一事 | 提交内文件集合只服务一个目的；无关格式化不得混入 |
| 正文写"为什么" | 说明动机、因果关系、验证命令与结果 |
| 路径在权限内 | 与第 5 节矩阵一致；越界由 G8 拦截 |
| claim 变更带 CR | 提交正文含 `CR-<n>` |
| 门禁变更带负例 | 同一提交内有可失败的负例 fixture |
| 不擅自发布 | 唯一判据见 6.5 的「推送与远端发布」行：分支推送须指令，phase tag 随收口自动创建并推送（6.7 V-7） |
| 版本号随事 | 版本号提交形状、落点一致、禁改情形**只在 6.7 V-4、V-5 定义**；版本号与收口 tag 是该次修复 / 收口的属性，不构成第二个目的；本节只要求遵守，不重述判据 |

### 8.4 文档结构与分拆

**README 硬上限 300 行。** 超过即必须分拆；任何文档（教程、设计、ADR、台账条目）超过 300 行同样必须分拆。唯一豁免是 `AGENTS.md` 的生成块（DOC-S8）。

**按模块复杂度决定教程位置**：

| 模块类型 | 判据 | 教程放哪 |
| --- | --- | --- |
| 简单模块 | 新用户只看 API 表就能正确使用（如 `utf8`、`math`） | 直接写在 README 内，不建单独教程文件 |
| 复杂模块 | 有状态、多步骤流程、需先理解概念模型才能用对（如 `io`、`sql`、`json`） | README 只放入口，教程进 `docs/tutorial/`，按主题分文件（`01-concepts.md`、`02-xxx.md`） |

**规则**：

| # | 规则 | 判据 |
| --- | --- | --- |
| DOC-S1 | README 行数 ≤ 300 | `wc -l README.md`；G4 `g4-size` |
| DOC-S2 | 任何单份文档 ≤ 300 行 | 同上，扫描 `docs/**` 与根级 `*.md` |
| DOC-S3 | 分拆按"变更原因"切，不按长度切：两段内容总是一起改的合并，总分开改的两部分拆开 | `git log` 中两部分是否共现于同一提交；评审确认，禁止按 150 行机械对半切 |
| DOC-S4 | 简单模块不建 `docs/tutorial/`，教程写在 README 内 | 目录不存在且 README 含使用示例；G4 `g4-readme` |
| DOC-S5 | 复杂模块 README 只保留入口内容：定位与边界、依赖与安装、最小可运行示例、API 索引（一行一个）、指向教程、限制、版本 | README 节标题逐项匹配；G4 `g4-readme` |
| DOC-S6 | 教程按主题分文件，命名 `01-concepts.md`、`02-xxx.md` 递增，第一份固定为概念模型 | `docs/tutorial/` 文件名匹配 `^\d{2}-.+\.md$` 且 `01` 存在 |
| DOC-S7 | 教程里的第一个例子必须是被 gate 编译运行过的真实文件 | 沿用 G4 snippet 规则：文件存在于 `examples/` 且门禁通过，不得手写"示意代码" |
| DOC-S8 | `AGENTS.md` 的 `<!-- spec:begin … -->` 到 `<!-- spec:end -->` 生成块**不计入 300 行**；块外部分仍受 DOC-S1/S2 约束 | `g4-size` 统计 `AGENTS.md` 前先剔除生成块（`awk` 跳过标记区间），再比对 300；剔除后仍超限即失败 |

**DOC-S8 的理由与边界**：生成块是主规范全文的**派生副本**（11.5），行数由主规范决定，项目无权分拆——把它计入额度等于逼项目删规范正文，反而绕开"落库"。因此给显式豁免，而不是让 `g4-size` 默默跳过 `AGENTS.md`；豁免只覆盖块内，块外自写内容照常算行。

## 9. 冲突与会话管理

### 9.1 会话组织以 phase 为主维度（P-001）

问题：旧规范只写了"角色会话唯一"，没有 phase 维度，也没有新开对话的准入条件。结果是同一件事可能落在两个对话里，派发时归属不清，对话数量随项目增长失控。

| 对话类型 | 数量 | 承担 |
| --- | --- | --- |
| 需求池 | 每项目 1 个，常驻 | 维护需求池、写规格主张 |
| 技术池 | 每项目 1 个，常驻 | 维护技术池、ADR、架构演进 |
| 评审 | 每项目 1 个，常驻、跨 phase 复用 | 所有评审，独立于执笔 |
| phase 对话 | 每个 phase 1 个 | 立项 → 设计 → 实现 → 验证 → 收口，同一对话内按阶段切换 |

- 执笔、验证不设常驻对话，在 phase 对话内承担。
- 主编不单独开对话，该职能由协调者承担（9.2）。
- 例外：battle 庭（7.13）是按需临时会话，不常设、不计入本表；命名 `[项目] 庭 · <battle id>`，开启与关闭按 7.13，结束后封存。
- **取代**：「每项目默认三个基本角色会话」→「两池一评审常驻 + 每 phase 一对话」。

### 9.2 角色与对话的映射

| 角色 | 落在哪个对话 | 判据 |
| --- | --- | --- |
| 主编 EDITOR | 不单独开对话，由协调者承担 | 立项与收口时，在 phase 对话内以 EDITOR 身份执行；`session-map.md` 中该任务的 `role` 写 `EDITOR` |
| 需求 REQ | 需求池对话 | 规格主张类任务只出现在需求池对话 |
| 架构 ARCH | 技术池对话 | 技术池与 ADR 只出现在技术池对话；评审列席时以 `ARCH` 身份进入评审对话 |
| 执笔 DEV | phase 对话内 | 实现/修复类任务只出现在对应 phase 对话 |
| 验证 VERIFY | phase 对话内 | 用例与证据类任务只出现在对应 phase 对话 |
| 评审 REVIEW | 评审对话 | 所有评审任务只出现在评审对话，跨 phase 复用 |
| 安全 APPSEC | 无独立对话 | 评审的 `security` profile |

协调者不是新角色，而是"当次承担 EDITOR 职责的执行体"：默认由 phase 对话在立项与收口时担任，负责维护路线图与 `session-map.md`。

### 9.3 命名规则

必须能从标题判断归属，不允许无身份对话。

| 类型 | 格式 | 示例 |
| --- | --- | --- |
| phase 对话 | `[项目] P<nn> · <目标一句话>` | `[ct] P03 · 统一校验入口` |
| 需求池 | `[项目] 需求池` | `[ct] 需求池` |
| 技术池 | `[项目] 技术池` | `[ct] 技术池` |
| 评审 | `[项目] 评审` | `[ct] 评审` |

判据：对话标题必须命中上表四种格式之一（battle 庭另按 `[项目] 庭 · <battle id>` 命名）；`<nn>` 两位补零，与 `PH-<n>` 编号一致；标题不符合的对话不得承接任务。

### 9.4 新开对话的三条准入理由

其他一律复用已有对话。

| # | 理由 | 判据 |
| --- | --- | --- |
| N-1 | 新 phase 立项 | 存在对应的 `PH-<n>/card.md`，且该 phase 尚无对话 |
| N-2 | 需要独立评审，且现有评审对话已封存 | 评审对话状态为封闭，且本次评审对象未被其他评审对话承接 |
| N-3 | 原对话上下文已不可用（超长、失败、被取消） | 原对话标记不可用，且已落 handoff 包 |

每次新开必须先说明"为什么不能复用"，未说明不得新开。判据：`session-map.md` 的 `reason` 列命中 N-1/N-2/N-3，并附一句不可复用理由。

### 9.5 派发三要素与任务-对话映射表

派发任务时必须报三要素：**这条任务进哪个对话、以什么角色、属于哪个 phase**。三样齐了才能派出。

映射表 `docs/session-map.md` 由协调者维护，四列：

| 任务 | 对话 | 角色 | phase |
| --- | --- | --- | --- |
| 写 PH-03 验收判据 | `[ct] 需求池` | REQ | P03 |
| 实现校验入口 | `[ct] P03 · 统一校验入口` | DEV | P03 |
| PH-03 评审 | `[ct] 评审` | REVIEW | P03 |

判据：每行四列非空；`对话` 列必须是已存在对话且标题符合 9.3；缺任一列不得派发。每行还必须是一个可独立验收的任务（6.6 T-1…T-4），不得把整个模块或整个 phase 写成一行。硬约束：每一个 session 必须有清晰定位，不得存在职责不明的对话。

### 9.6 已知代价与补偿

同一对话内角色切换靠 prompt，可能串味 → 每次切换写 handoff 包（S4）并在派发时报三要素（9.5）；phase 对话会变长 → 按 N-3 新开（9.4）；验证独立性弱于独立对话 → 证据可复现（E1/E3）且 `verified` 只归 REVIEW（5.4）；跨 phase 经验只靠文档 → 收口回顾必须落到门禁/规范/不采纳（6.2）。

### 9.7 会话与冲突硬规则

| ID | 规则 | 角色 | 时机 | 产物 | 判据 |
| --- | --- | --- | --- | --- | --- |

## 11. 落点方案

### 11.1 主规范放哪

`AGENTS.md` 只在本项目根生效，因此主规范必须放在**项目之外、且可被稳定引用**的位置，项目内只放薄引用。

推荐结构（独立 git 仓库，单一事实源）：

```
<workspace>/.ai-engineering/            # 独立 git 仓库，单一事实源
├── methodology/
│   ├── ai-coding-workflow.md           # 本文件（主规范）
│   ├── roles/editor.md, req.md, arch.md, dev.md, verify.md, review.md, appsec.md  # 每个角色一页交底
│   ├── roles/legacy/{coordinator,courier,module-owner,reviewer}.md  # 仅历史，不要据此执行
│   └── battle.md                       # 第 7 节的独立副本（便于脚本引用）
├── templates/project/
│   ├── AGENTS.md                       # 1.1 节的完整模板
│   ├── tools/check.sh                  # g0..g9 骨架
│   └── docs/{requirements,snippets,decisions}/.gitkeep
├── bin/init-project.sh                 # 一条命令完成纳管
└── README.md
```

已经落在这里，无需再迁移；迁移时用 `git mv` 保留历史，各项目只更新生成块。

### 11.2 各项目如何引用

1. `AGENTS.md` 首节粘贴 1.1 节骨架：绝对路径写在块外，`spec-version` 与 `spec-sha256` 由生成块头承载，不手写。
2. 用户级规则/记忆放一行指针：`方法论主规范：<路径> @ <version>`，保证代理在未读项目文件时也能被引导。
3. 项目内保留**全文副本**在 `docs/spec/ai-coding-workflow.md`（1.9.0 起由 `sync-agents.sh --write` 生成，不带块标记），块头 sha 与它绑定；`AGENTS.md` 块里只有判据摘录与章节索引，不重复全文。
4. 每次主规范 bump，按 11.5 用 `bin/sync-agents.sh --write` 同时刷新块与全文副本；没刷新即未落库，按 `g0` 失败处理。

### 11.3 新项目如何自动获得

`bin/init-project.sh <project-dir>` 执行：

| 步 | 动作 | 判据 |
| --- | --- | --- |
| 1 | 复制 `templates/project/AGENTS.md`，填入项目名与路径，再跑 `bin/sync-agents.sh --write` | 块存在且块外三段齐全（11.5 L-2） |
| 2 | 复制 `tools/check.sh` 骨架（g0..g9 均为"未实现即失败"） | `tools/check.sh g0` 可运行 |
| 3 | 建 `docs/{requirements,planning,phases,snippets,decisions}` 与 `issues/` | 目录存在 |
| 4 | 打印对话创建清单（不自动建对话） | 输出三类常驻对话名 + phase 对话命名规则 |
| 5 | 跑 G0，失败则打印缺项 | 退出码 0 |

### 11.4 防漂移与升级

| 规则 | 判据 |
| --- | --- |
| 主规范每次变更 bump `spec-version` | 主规范头部版本与 git tag 一致 |
| `spec-version` 的三个位只管主规范自己：新增或修改条款 → MINOR +1；纯措辞、笔误、链接修订 → PATCH +1；删条或重排导致旧 pin 无法解读 → MAJOR +1 | 变更提交的 diff 与所 bump 的位对应；判据是「这次 diff 里有没有新增/改变一条规范」，有则 MINOR，没有则 PATCH |
| `spec-version` **不**适用 6.7：主规范没有 phase，也没有 fix 计数；6.7 只管项目产品版本 | 主规范文件内不出现「MINOR 与 phase 同步」的自我指涉；项目的 `版本落点` 不含 `methodology/ai-coding-workflow.md` |
| bump 与落库同步 | 唯一判据见 11.5 L-1、L-6，本节不重述 |
| 项目 pin 落后由 G9 报出；块内容被改由 G0 报出 | `spec-sha256` 不匹配即 G9 失败；块与 `--print` 输出不一致即 G0 失败 |
| 升级块单独成提交 | 该提交只改 `AGENTS.md`（生成块，必要时补块外缺段），不夹带其他文件 |
| 项目内出现主规范副本 | G9 失败，除非标记为 `vendor-snapshot` 且带日期 |

### 11.5 落库：每版规范都必须进入每个纳管项目的 `AGENTS.md`

**落库不是放一个链接。** 纳管项目里必须有**规范正文**，打开文件就能读到规则；只写 pin 和路径不算落库。1.9.0 起拆成两处：`AGENTS.md` 块放**每轮必做判据 + 章节索引**（打开就能照做），`docs/spec/ai-coding-workflow.md` 放**全文副本**（要查细节时读）。

**L-1 一版一同步。** 主规范每定一个版本，所有纳管项目必须在同一轮把新块与全文副本刷新到位，不允许"主规范 1.9.0、项目块头还是 1.8.0"。单源不变：主规范是唯一真相，块与副本都是派生物。

**L-2 落库的构成（缺一即未落库）：**

| # | 段 | 内容 | 判据 |
| --- | --- | --- | --- |
| ① | 生成块 | `<!-- spec:begin version=<v> sha256=<s> -->` 到 `<!-- spec:end -->`：块头说明 + 章节索引 + 必做判据摘录（§5.4、§6.4、§6.6、§6.7、§8.3、§11.5 L-1…L-7）。**不再放全文** | 见 G0 的 `g0-block`，本节不重述 |
| ② | 全文副本 | `docs/spec/ai-coding-workflow.md`，与主规范逐字相同，不带块标记 | sha256 等于块头 `sha256`（`g0-block` 第③项） |
| ③ | 实例化节 | 1.1 骨架的 0.1 表，8 行非空（含 `版本落点`） | 见 G0 的 `g0-landing` |
| ④ | 话术路由 | 1.1 骨架的 0.2 表，每行三段：触发话术 / 动作 / 产物 | 见 G0 的 `g0-landing` |
| ⑤ | 偏离登记位 | 0.3 节存在；无偏离写"无"；有偏离逐条带 `deviation:` 与用户签字 | 见 G0 的 `g0-landing` |

**块内同名小节一律不算。** `g0-landing` 只扫描 `spec:begin` 之前与 `spec:end` 之后的内容；块内出现的 `0.1 / 0.2 / 0.3` 是 1.1 模板副本，带 `<...>` 占位，忽略。判失败只有两种：块外找不到实参节，或块外出现第二套同名节（`spec:end` 之后再有 `### 0.1`）。不重排小节号：模板与实参保持同名，靠判据侧区分，理由见 1.1 的注。

**L-2 的边界（代价）。** 块内不再有全文，块里没写的细节必须去读 `docs/spec/ai-coding-workflow.md` 或主规范。**"块里没有"不等于"没规定"**：块只保证"每轮必做"在眼前，不保证覆盖全书；块与正文冲突时以主规范正文为准。索引表每版至少核对一次，漏掉的章节等于不可发现（`g0-block` 只校块体逐字，不校索引完整性）。

**L-3 未落库的后果。** 该项目视为**未纳管**：G0 失败，不得开新 phase（G1 对新开卡拦）；已开的 phase 允许收口，但收口后不得再开新的。判据：`g0` 退出码非 0 或 G1 看到无有效块。

**L-4 谁、何时、怎么查。**

| 角色 | 时点 | 产物 | 判据 |
| --- | --- | --- | --- |
| 主规范侧 REQ | 每次 bump 后、主规范提交前 | 本节纳管清单全绿 | 每行 `sync-agents.sh --check` 退出码 0（块、副本、块外三段都过） |
| 项目侧 REQ | 纳入时、每次会话启动（S3） | `AGENTS.md` + `docs/spec/` | `g0-block`（三项）+ `g0-landing` 通过 |
| 项目侧 DEV | 收到新版本时 | 只含 `AGENTS.md` 与 `docs/spec/ai-coding-workflow.md` 的提交 | 提交路径集合 = `{AGENTS.md, docs/spec/ai-coding-workflow.md}`；`g0` 绿 |

**L-5 生成与校验工具。** `bin/sync-agents.sh`，三种模式，幂等，只改标记之间的部分：

```
bin/sync-agents.sh --check  <AGENTS.md>...   # 校验块头、块体与 docs/spec 全文副本；不一致退出码 1
bin/sync-agents.sh --write  <AGENTS.md>...   # 刷新块 + 写全文副本；块外一字不动；缺块则报错
bin/sync-agents.sh --print                   # 只打印应有的块（索引 + 判据摘录），便于人工 diff
AI_ENGINEERING_SPEC=<主规范路径> ...          # 覆盖默认主规范位置（默认取脚本上级目录的 methodology/）
```

若脚本还没有可执行位，用 `bash bin/sync-agents.sh ...` 等价调用（首次落库时 `chmod +x`）。脚本只读主规范；`--write` 只改目标文件的标记区间，并写 `<AGENTS.md 所在目录>/docs/spec/ai-coding-workflow.md`；`--check` 不做任何写入。

手改块内即漂移：`--check` 用逐字 `diff` 抓，不依赖行号或摘要近似；副本用 sha256 抓，不比对行号。

**L-6 发布流程多出的一步。**

| 步 | 动作 | 判据 |
| --- | --- | --- |
| 1 | 改主规范，bump `spec-version` | 头部版本已改 |
| 2 | `shasum -a 256` 取实算摘要 | 摘要为 64 位小写十六进制 |
| 3 | 对清单内每个项目跑 `sync-agents.sh --write` | 每个目标块头等于新版本与新摘要；`docs/spec` 副本已生成 |
| 4 | 逐个项目跑 `sync-agents.sh --check` | 全部退出码 0（块逐字 + 副本 sha 都对） |
| 5 | 各项目单独提交 `AGENTS.md` 与 `docs/spec/ai-coding-workflow.md`；主规范提交 | 提交路径集合符合 L-4 |

第 4 步任一项目不过，这次 bump 就不算发布完成；不得在清单里留 `pending` 过夜。

**L-7 纳管项目清单（可枚举，唯一一份）。** 新项目纳入时加行；退役标 `retired` 并保留行，不删。`.ai-engineering` 自身是规范仓库，**不是**项目，不进表。

| 项目 | 路径 | `AGENTS.md` | 块头 version | 最近同步 | 状态 |
| --- | --- | --- | --- | --- | --- |
| ct-lang | `/Users/samxx/trae-ws/ct-lang` | `<待项目侧会话回填>` | `<待回填，非已确认>` | `<待回填，非已确认>` | `pending（未落库）` |

后四列一律是占位，由项目侧会话实测后回填；带 `<...>` 的单元格不算已确认，也不得据此宣称已落库。`.ai-engineering` 自身是规范仓库，不是项目，不进表；清单之外的项目即使有 `AGENTS.md`，也不算纳管。

## 13. 术语

| 术语 | 含义 |
| --- | --- |
| 车道（lane） | 角色权责边界，由权限矩阵定义 |
| 执行体（worker） | 承载角色的对话、子代理或人 |
| 主张（claim） | 文档中决定"说什么"的内容：需求、协议语义、验收判据、术语 |
| claim 块 | 文档中标记主张区的注释块，修改需 CR |
| CR | 主张变更请求，由 REQ 提出，DEV 落笔时引用 |
| 负例 | 用于证明门禁/测试确实能失败的 fixture |
| 证据包 | 第 8.1 节六项齐全的记录集合 |
| handoff 包 | 角色切换时的交接文件 |
| `verified` | 评审独立复现后给出的状态，只能由 REV 写 |
| `fixed` | 编码的修复主张，只能写在处置段 |
| battle | 有判据争议的对抗裁决流程：四席（主张/反对/证据/裁判），第 7 节 |
| 需求池 | REQ 维护的"做什么、为什么、优先级"条目集合（6.1） |
| 技术池 | ARCH 维护的演进项与技术债条目集合（6.1） |
| 路线图 | EDITOR 从两池取条目排出的 phase 顺序与边界，不得自造条目（6.1） |
| phase 卡片 | 立项产物：编号、目标、范围、交付物、退出判据、依赖、风险（6.2） |
| 任务（task） | 最小可验收单位：一个交付物 + 一条验收命令 + 一次提交 + 可单独回滚；一个 phase 由若干任务组成（6.6） |
| 红证（red proof） | 由任务基线提交的产物产生的失败输出，含 `baseline: <sha>`、命令、原始输出与退出码；必须在实现前采集，用当前代码复跑的不算（6.6 T-7） |
| 小循环 / 热修 | 无独立交付边界的两种轻量通道（6.3） |
| 产品版本 | 项目对外的 `MAJOR.MINOR.PATCH`：MINOR 与 phase 一一对应、PATCH 与 fix 一一对应，与主规范自己的 `spec-version` 是两套数（6.7、11.4） |
| fix | 版本意义上的修复单位：一处被立案的缺陷的一次处置，PATCH +1 一次；纯文档、注释、测试自身的修正不算（6.7 V-3、V-4） |
| 版本偏离（version deviation） | 存量号段与 phase 对不上时登记的 `deviation:`，写明偏移、日期、理由与收敛方式，由用户签字；不是"历史遗留"的免除理由（6.7） |
| 版本字段核对 | 发版前与 phase 收口各一次的四项对账：落点互比、与 `PH-<n>`、与 CHANGELOG、与本 phase 的 fix 数（6.7 V-6、`g4-version`） |
| 落库（landing） | 把主规范经 `sync-agents.sh` 落到纳管项目两处：`AGENTS.md` 的 `spec:begin…spec:end` 块（章节索引 + 必做判据摘录）与 `docs/spec/ai-coding-workflow.md` 全文副本；块头 version/sha 等于主规范头部与实算值，块体与 `--print` 逐字可复现，副本 sha 等于块头；块外三段齐全。未落库即未纳管（11.5、`g0-block`） |
| 全文副本 | 主规范全文在项目内的只读副本 `docs/spec/ai-coding-workflow.md`，不带块标记；块内只有判据摘录，细节查它（11.5 L-2 ②） |
| phase tag | phase 收口时创建并推送的 annotated tag，名 `v<MAJOR>.<MINOR>.<PATCH>`，指向收口提交；随收口自动，不需另请示（含推到 origin）；分支推送与远端发布仍须用户指令。fix 不打 tag（6.7 V-7） |
| `dormant` | 池条目超窗无动作后的降级状态，是删除前的缓冲期（6.1 Q-2） |
| phase 对话 | 每个 phase 一个工作容器，承担立项到收口，按阶段切换角色（9.1） |
| 协调者 | 当次承担 EDITOR 职责的执行体，不单独开对话，维护路线图与 `session-map.md`（9.2） |
| `session-map.md` | 任务-对话映射表，四列：任务 / 对话 / 角色 / phase，由协调者维护（9.5） |

## 附录 A：本规范对判断点的结论摘要

| 判断点 | 结论 |
| --- | --- |
| 1 角色数量 | 七职责；两池一评审常驻 + 每 phase 一对话；主编由协调者承担，架构按需、安全为评审 profile；角色 ≠ 对话 |
| 2 执笔人与所有权 | 三权分离；claim 块 + CR 使边界可机械检查 |
| 3 需求文档与 gate | snippet 文件 + G4；文档未过门禁不得算完成 |
| 4 测试边界 | 示例归 VERIFY；测试夹具、断言与门禁归 DEV（保留），门禁变更须带负例；红证由 VERIFY 认定 |
| 5 评审与台账 | 允许写报告与台账；判据是"写入是否改变被审对象"；状态词分权 |
| 6 安全 | 审供应链/凭据/注入/内存/权限；机械项每次、深度项按事件、发版前全量；产物并入评审报告 + `SEC-*` |
| 7 battle | 只处理有判据的争议；四席 + 裁判（EDITOR 不表态不投票）；5 个触发条件；E1–E5 证据由证据席复现；逐条判据判 upheld/rejected/undecidable/escalate；最多 3 轮；undecidable 必须出 C 或 open-question；决策记录落盘 |
| 8 Planning 归属 | 三层：需求池归 REQ、技术池归 ARCH、路线图归 EDITOR；主编不决定"做什么"与"架构怎么演进"，只决定先做哪个；池条目超 90 天无动作降 `dormant`，再 90 天删除 |
| 9 phase 交付 | 八环节；退出判据开工前写死、中途不可改，只能新开 phase；phase 完成 ≠ 发布；Issues 只有三去向；回顾必须落到门禁/规范/不采纳 |
| 10 流程分档 | phase / 小循环 / 热修，判据是有无独立交付边界；小循环不省验证证据，热修可跳评审但必须补回归用例 |
| 11 会话组织 | 以 phase 为主维度：两池一评审常驻 + 每 phase 一对话；四种标题格式；新开对话仅三条准入理由；派发必须报对话/角色/phase 三要素 |
| 12 文档结构 | README 与任何单份文档 ≤300 行；简单模块教程写在 README 内，复杂模块 README 只留入口、教程进 `docs/tutorial/` 按主题分文件；分拆按变更原因切；取代"教程一律并入 README" |
| 13 任务粒度 | 小步快跑：一个任务一个交付物，一轮可完成、单独验证、单独回滚；先红后绿（测试提交先于实现，红证带 `baseline:`）；禁止整模块 / 整 phase 大包；任务清单开工前写死，任一项不可独立验收不许开工，未全部验收不许收口（6.6） |
| 14 版本号 | 产品版本 `MAJOR.MINOR.PATCH`：MINOR 与 phase 一一对应（每 phase +1，多跳与同 phase 二次 +1 均失败），PATCH 与 fix 一一对应（一 fix 一处缺陷）；纯文档 / 注释 / 测试自身的修正不算 fix；代码里的版本字段与工程状态不一致即缺陷，按 fix 处理；**phase 收口必打 annotated tag `v<版本>` 并推送到 origin，fix 不打 tag，分支 push 仍须用户指令**；只对 1.6.0 之后新开的 phase 生效；存量落差走带签字的版本偏离；主规范自己的 `spec-version` 不受此约束（6.7、11.4） |
| 15 落库 | 每版规范必须进入每个纳管项目两处：`AGENTS.md` 生成块（章节索引 + §5.4/§6.4/§6.6/§6.7/§8.3/§11.5 判据摘录，不是全文）与 `docs/spec/ai-coding-workflow.md` 全文副本。判据：块头 version/sha 等于主规范头部与实算值、块体与 `--print` 逐字相同、副本 sha 等于块头、块外三段齐全；手改块内即漂移；未落库即未纳管，G0 失败、不得开新 phase；`AGENTS.md` 的块不计入 300 行（11.5、`g0-block`、DOC-S8） |
