## 2. 包管理器线怎么拆

按「能分别收口」拆成四项。前三项是缺陷，按 D-005 走 patch，不占 phase 号；第四项是删除兼容层，建议从 PH-54 拆出单独立相。

| 序 | phase | 版本位 | 目标 | 独立开工前提 | 退出判据能否现在写成可执行 | 真实依赖 |
| --- | --- | --- | --- | --- | --- | --- |
| P0 | 无（patch） | v0.58.1 | `ct get` 缓存/校验按 `publisher/name` 隔离，不串用不同发布方的同名包 | 无 | **能**：两个发布方各发同名包，先后 `ct get`，缓存目录与 store 必须分离；篡改 origin 必须报错 | 无 |
| P1 | 无（patch） | v0.58.2 | `ct install` 在写 lock 前试解析 import，失败即非零 | 无（S2 的 `-I` / store 已就绪） | **能**：删掉被 import 的包目录后 `ct install` RC≠0 且文案指名 import | 建议在 P0 后（同一文件，避免冲突） |
| P2 | 无（patch） | v0.58.3 | `ct.pkg` 未知键告警，不改变 RC | 无 | **能**：加一个 `foo = 1` 键，stderr 有 warning，RC 不变 | 无 |
| P3 | **PH-63**（建议新立） | v0.63.0 | 删除 `vendor/` 读写，v1 lock 只报错 | 两个 MINOR 兼容期 + S6 errata + 三条判据 | **能**：v1 工程 build 告警、`ct install` 每包告警一次、`ct migrate` 后移走 vendor 仍可 build | 时间门（≥ v0.59.0 / v0.60.0）；不阻塞包仓 |

> 包仓开工时点：**P0 + P1 合入后**。P2 是卫生项，可并行；P3 是兼容期清理，不影响包仓按新规范开发。

## 7. 判断不了的取舍（单列）

1. **PH-60 是否值得做**：目前只有提案，没有确认的消费者。若 SwiftCT 不落地，建议整相跳过，不做「为了占位而做」。
2. **PH-62 与 PH-59 的先后**：两者无相互依赖，但都改 `Emitter` / `Symbols`。按「卡面就绪度」先 PH-59，按「下游痛感」先 PH-62；本序列取前者。
3. **PH-63 的时点**：两个 MINOR 的兼容期从 v0.58.0 起算，最早 v0.60.0 具备条件；是否等满两个 MINOR 再删，取决于包仓迁移登记，但**登记不进 CT 判据**。
