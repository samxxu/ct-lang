# D-023 · 静态映射方法的接收者可变性拼写（SH-60 / D-60-1）

- 日期：2026-11-23
- 状态：**accepted（语言表面）**；实现随 SH-60 同批，不 bump 版本（本轮任务口径）
- 目标：v1.0 之前的 ct-ast 小修，不新增 phase
- 签收：REQ 2026-11-23（owner 交底授权 REQ 裁定，见 SH-60 任务交底）
- 依据：[SH-60](../../issues/selfhost/sh60-mct-signature-types-decorative.md) 2026-11-09 裁决；
  [D-024](D-024.md)（同族「声明点 C 类型证据」决策）
- 决策范围：只定「静态映射方法如何声明会写接收者」及调用点诊断；不动 vtable、
  动态 trait 的 impl 语义、recipe 展开与生成 C

## 1. 决策

1. **拼写**：`int toUpper() mut;` —— 后缀，位于参数表 `)` 与 `;`（或默认体，`.m.ct` 不允许）
   之间。前缀 `mut int toUpper();` **拒绝**，诊断点名后缀写法。
2. **适用范围**：只允许出现在 `.m.ct` 的 `pub trait`（静态 trait）方法上。`.h.ct` / 普通 `.ct`
   的 trait 方法写 `mut` 报 `error: receiver mutability is only valid on a .m.ct trait method`。
3. **语义**：`mut` 是作者声明的一条契约——该方法会写接收者。编译器不据此改变 recipe 展开、
   vtable、mangled 名或任何生成物；它只服务调用点诊断。
4. **调用点诊断**：接收者是**字面量**（字符串 / 数字 / 浮点/字符）或**顶层 `const`** 值时：
   - `ct build` / `ct compile`：`warning: '<method>' writes its receiver, but the receiver is a literal`
     或 `... is a top-level const value`，退出 0；
   - `ct check`：同一条记录打印为 `error:`，退出 1（19.2 / 19.3 的同一严重级策略）。
5. **正例必须安静**：`"abc".len()`（读方法）、`"abc".compare("x")`、`char buf[8]; buf.toUpper()`
   （接收者可写）、`const char *s; s.len()`。
6. **默认不标注 = 今天的行为**：零回退；覆盖率取决于作者标注纪律，编译器不推断。

## 2. 为什么选后缀，不选前缀

| 方案 | 判定 | 理由 |
| --- | --- | --- |
| `int toUpper() mut;`（本决策） | **采纳** | `)` 之后语法位置唯一：只可能是 `{` / `;` / `mut`，零前瞻；与 C 的后置 `const` 成员函数同构；返回类型读取器完全不变 |
| `mut int toUpper();` | 否 | `mut` 落在返回类型位。CT 的类型读取器把未知名字当**不透明 C 拼写**保留（`time_t` / `FILE` 同路），于是 `mut` 被读成返回类型、`int` 被读成方法名，诊断位置与文案都错。要修得加「`mut` + 类型」的两 token 前瞻，或把 `mut` 升为保留字 |
| `mut self`（照抄 Rust） | 否 | CT 的 trait 方法没有显式 `self`（只有 `impl`/recipe 侧隐式接收者），拼写无处可写 |
| 类型键保留顶层 `const`（路线 B） | 否 | 见 SH-60 历史评估：会让今天所有字面量/`const` 接收者的读方法失配，std 大面积回退 |

**`mut` 冲突核查（2026-11-23）**：

```console
$ grep -rn '\bmut\b' --include='*.ct' --include='*.c' --include='*.h' .
examples/tour/12_multiunit/cross_unit_iface/main.ct:29:    printf("mut  %d\n", s.read());
```

全仓 `.ct` / `.c` / `.h` 里 `mut` 只作为该 `printf` 的字符串内容出现，没有任何标识符叫
`mut`；词法器没有关键字表，后缀位置按上下文识别，因此**不新增保留字**，现有代码与
`mut` 作局部名的写法都不受影响。

## 3. 为什么只限静态 trait

- 静态映射的 recipe 是裸 C 文本，编译器无法看方法体，`mut` 是唯一可得的「会不会写」信息；
  SH-60 的 1a/1b 又都发生在 `.m.ct` 的类型宿主上（`char *` 的 `toUpper`）。
- 动态 trait 的 `impl` 方法体是 CT 代码，可以走将来的数据流 / `const` 检查；若也允许 `mut`，
  必须同时定义「trait 声明与 impl 标注必须一致」以及动态派发点的检查，属于另一条语言表面，
  不在本决策内。当前在 `.h.ct` 写 `mut` 会直接报错，避免造出一个无效果的标注。

## 4. 实现落点

- `frontend/sym/Symbols.h.ct`：`struct MethodSig` 增加 `int is_mut`（编译期表，1 个 flag）。
- `frontend/parse/Parser.h.ct`：`parse_trait` 在 `)` 后识别 `mut`（`(void)` 快捷路径同样处理）；
  非 `.m.ct` 报错；方法行初始化 `is_mut = 0`。
- `frontend/parse/Expr.h.ct`：类型宿主点调用与 `Trait::method(recv, …)` 两条有接收者的静态形态
  调用 `recv_mut_check`；接收者判定只看节点种类（字面量）与静态类型前缀（顶层 `const`），
  不做数据流。
- `tool/diag/Diag.h.ct`：新记录类别 `receiver_mutability`（kind 13），文本 / JSON 各一条；
  `ct check` 的既有 `strict == 1` 通道自动把它升为 `error`。

## 5. 生成物不变（判据与证据）

`is_mut` 只存在于编译器的符号表，不进入 `.h` / `.c` / vtable / recipe。实测（2026-11-23）对
`p25_static_argtype/ok`、`map_unit`、`map_unit_type`、`map_unit_varargs`、`map_unit_shim` 五组
既有 fixture 分别用改动前 / 改动后的 ct-ast 跑 `build --emit-c`，产物逐字节相同；
新增 fixture `test/modules/sh60_recv_mut/ok.ct` 也只在字面量/`const` 接收者上产生诊断。

## 6. 被否的替代与遗留

- 命名空间宿主的方法没有接收者，在 `.m.ct` 的 namespace-host trait 上写 `mut` 不会触发诊断，
  也不改变任何东西；本决策不把它升为错误，避免为一个无害误用增加 map 声明期的校验
  （`mut` 的收益只在有接收者的类型宿主上）。
- 若将来要覆盖动态 trait，应另立 decision：trait 声明与 `impl` 两侧标注一致 + 动态派发点检查。
- ct-pkg 的 `std` 需要给 `toUpper` / `toLower` / `copyFrom` 补 `mut`；该仓不在本项目工作树内，
  按 DB-5 只登记、由 ct-pkg 自己的会话执行。
