# D-001 — `ct build --lib` 导出面选择机制

> `status: accepted` 指「本决策记录成立、按此执行」；`verdict: rejected` 指**主张席 A 不成立**（§7.9）。
> 本记录**不是**对 B 的采纳，也**不是**对 C 方案的批准：C 按 §7.10 第 1 项另走单方案评审。
> `spec-claim: none`：本决策不涉及项目 claim，只改 PH-39 卡的 O2 相关判据。

## 争点

`ct build --lib` 的导出面怎么定：**A** 本次构建所有非内建 `.h.ct` 单元的有定义 `pub` 函数，非 C 兼容即硬错 L39-1；**B** 新增显式导出标记/清单（`pub export` 或 `--export` 文件），未标记的 `pub` 不导出也不报错。

立案见 [`battle/p39-1/question.md`](../../battle/p39-1/question.md)（T0）；判决全文见 [`battle/p39-1/verdict.md`](../../battle/p39-1/verdict.md)（T5）；C 方案见 [`battle/p39-1/C-proposal.md`](../../battle/p39-1/C-proposal.md)。

## 判决（rejected）

按 `docs/spec/ai-coding-workflow.md` §7.9：J-1、J-2 未被满足，且反证清单 C2、C3 被证据证实 → 主张不成立 → **`verdict: rejected`**。

- `rejected` **不等于**「反对席的方案成立」：B 在本庭没有主张书、没有 E1–E5，且其 `pub export`/`--export` 撞 `AGENTS.md:469` 而记录中无用户批准 → B 不满足全部判据（至少 J-3）。
- A′（`claim-r2.md` 的「泛型跳过 + 诊断」）**不能作为 A 的合法补丁**：① `claim.md:347` 自定「静默省略 `id`/`max2` 即不是 A」，A′ 属 `counter-r2.md` §5(b) 命名的新机制；② 它要改用户已批的 D39-6（`:60` 逐字含「泛型」）与冻结负例 `p39_export_generic/`（`:194`）；③ 即便批准，J-1 的通用情形仍失败（`claim-r2.md:56` 自认不解决有符号内部 helper）。
- **证据席「`--lib`/L39-1 未实现、E3 预测无法执行」是正当的无法判定理由**（V1；verify.json unreproduced #3）：所有「落地后应 exit≠0 / 不写产物」的断言（`claim.md:335-347`、`claim-r2.md:205-219`、`counter.md:174-181`）记为无法判定，**不作为任何一方胜证**；本判决不建立在这些预测上。
- 卡面自相矛盾（C3）成立：`phase39-draft.md:45`（泛型跳过）与 `:60/:102/:134/:194`（泛型硬错）必须二选一，修法进 C 方案。
- **§7.10 出口**：A 被否、B 不能满足全部判据 → 取第 1 项，产出 [`battle/p39-1/C-proposal.md`](../../battle/p39-1/C-proposal.md)（根单元限定 + 分级处置 + 零新语法），再走一次单方案评审（主张席 = REQ，反对席 = REVIEW，证据席 = VERIFY）。

## 理由（逐条对应判据）

- **J-1 不成立**：判据要求「只导出作者要的、且不把其余判死」。① 导出面定义（`:37`）没有清单/标记/白名单输入，主张席在 `claim-r2.md:56` 自认「A/A′ 确实没有『只导出 C 兼容 `pub` 的真子集』的输入」；② `pub` 是跨单元可见（`language-spec.md:617`），`main.ct:9` 用它服务 CT 消费方（`counter-r2.md` §3），故「`pub` = C ABI 意图」是重定义而非判据满足；③ f3 的 trait 值仍被判死，属 D39-6（用户已批），本庭不能替用户改，但判据文本仍未满足 → 如实记不成立，并把「f3 类单元能否成库」移交 C 的需批准项。f1 的 2/2（V15）不能让整条判据通过。
- **J-2 不成立**：12 个非 C 兼容 `pub` 分散 5 个单元（V5/V6）。硬错 A 下这 5 个单元不改一行不能成库；A′ 下剩 2 个 trait 值单元 + `Str.h.ct` 作根。残余失败由 D39-6 造成，不是选择机制的缺陷，故移交 C 的需批准项，不据此否定机制方向。双方口径各有更正：主张席 A-1「`lib/std` 不能做根」是无条件错误（V8）；反对席 C5-1 按默认路径不成立、只在 `-I vendor` 下成立（V9）；反对席 54 的分母含 `pub extern`（V7，D39-2 明写不进导出面）。
- **J-3 成立**：只新增 `--lib`（卡内已立项并获批），零关键字、零新语法；B 需要 `AGENTS.md:469` 的批准而记录中没有。成立的是 A 的**语言面成本**，不是 A 可行。
- **J-4 成立（设计层）**：2 文件 / ≤80 行；双方独立估算相容；无实现可实测，R2 落地时按 G8 复核。
- **J-5 成立**：硬错路径 `sem_error` 无条件写 `文件:行:列: error:`（`Diag.h.ct:85`）；`ct check` 的 `4:10`（V11）证明格式可行；今天 `--emit-c` 省略 `id` 时零诊断（V2）正是要修掉的静默。风险：`struct Fn` / `struct Node` 只存 `line` 不存 `col`，导出扫描的列号需另取（C §5 给两条路径）；若 R2 拿不到列号，J-5 在该轮转为不成立，须回单方案评审，不得静默降级。

## 失效条件（什么情况下该决定需要重开）

1. `--lib` 落地后，C-proposal §7 的 P-C1…P-C6 任一条不符（含 C 选取的根单元机制未按预测成立）。
2. 用户对 D39-6 的泛型项 / trait 值项作出与本记录不同的批准（B1/B2 的任一方向），J-1/J-2 需按新处置重判。
3. 用户批准 B 的标记/清单（`pub export` 或 `--export`）——本记录的范围收窄，A 可再判一次。
4. 卡面 C3 被按另一方向消解（即泛型保持硬错），J-1/J-2 的失败面回到 A 原文，需重开。
5. 发现 V-id 有误或证据环境不可复现（V9、V14 已按不复现记录；若再有同类发现，按 §7.9 的「重跑不一致」重判）。
6. `--lib` 的实现证明 J-4 的 2 文件 / 80 行上限不成立（C 的取舍规则见 C §5），需按 G8 记偏差并重审。

## C 评审（§7.10 出口 1 的结果）
