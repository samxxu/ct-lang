## 1. 裁定（A/B/C）

| 项 | 争点 | 裁定 |
| --- | --- | --- |
| A | 旧 MAJOR 的 `version-minor-offset` | **d=0 继续**；v0-PH-76 起 MINOR=phase，不新增 offset；迁移不改任何已收口版本号 |
| B | `docs/design/` 还是 `docs/phases/` | **迁移到 `docs/phases/v0-PH-<n>/card.md`**；但在 `v1-PH-0` 开卡前**一次原子迁移**，不逐卡拉锯 |
| C | 旧卡缺顶层 `phase-id:` / `version-minor:` | 迁移脚本一并补；迁移前新卡（v1 起）必须写这两个字段 |

## 2. 执行时点

- 迁移不在本轮执行：v1-pre 刚收口，`v1.0` 尚未开卡；此时做全量重命名会给 88 张卡与
  数百处引用制造无收益的冲突面。
- 执行窗口：**`v1-PH-0` 开卡提交的前一步**（同一天、同一批次）。按 PN-6：
  1. 建 `docs/planning/phase-id-ledger.md`，`window: W0` → `W1`；
  2. 跑单一迁移脚本（PN-6 五条断言），生成 `docs/phases/v0-PH-*` 与账本；
  3. 贴 W2 旧形态负例，推 `window: W2`；
  4. 迁移提交只改目录/文档引用/账本，不动 tag、battle、代码、测试。
- 迁移前**禁止新增裸 `PH-*` 引用**（新文档统一写 `v0-PH-<n>`）。

## 3. 为什么不是现在

1. 本轮 issues 批处理与 v0-PH-85…88 文档改动仍在收尾，迁移会与之冲突；
2. 主规范允许“在 v1.0 前完成”，未要求“立即”；
3. DOC-74 的 blocked-by 是“A/B/C 裁定”，本 decision 解开该 blocker；执行触发条件明确，
   不是无限期挂着。

## 4. 关闭方式

DOC-74 置 `deferred`（REQ），`blocked-by` 改为“执行触发：`v1-PH-0` 开卡前”，
并在 issue 处置段引用本 decision。`v1-PH-0` 开卡时必须先执行迁移，否则 G1/G6 拦截。
