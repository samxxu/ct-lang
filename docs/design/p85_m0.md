# PH-85 S85c M0 粗切（纯搬移，v0.85.0）

> **S85c 交付物**。把 6 组自洽的自由函数从 5 个大单元里搬进 6 个
> `<Subsystem><Role>.h.ct` 单元：函数体逐字节不变，接口从 `static` 变 `pub`，
> 不新增导入环。基线 `10c23c77`（M0 之前）。
> 基线/映射入库：[p85_m0_baseline.json](../../test/probes/p85_m0_baseline.json)、
> [p85_m0_mapping.tsv](../../test/probes/p85_m0_mapping.tsv)；
> 探针：[test/ast/p85_m0.sh](../../test/ast/p85_m0.sh)（`p85_m0`）；
> 依据：[D-017](../decisions/D-017.md) A2/A3/A4、[phase85.md](phase85.md) §1.4。

## 1 判据与实现

| 判据 | 实现 | 机器检查 |
| --- | --- | --- |
| J1 函数体哈希集合不变 | 只搬 `{ … }` 文本，签名行只去掉 `static`、在新单元加一行 `pub` 原型；调用点不动（同命名空间 + 宿主 import 新单元） | `p85_inventory.py m0`：基线 827 个 body-hash 全部仍在，函数数 838 → 842（+4 个是 S85d 新增，见 §4） |
| A2 期望集合基线 + 旧→新映射 | `p85_m0_baseline.json` 冻结 20 个产物；映射 6 行；产物集 = 基线 + 6 个新单元 | 探针 §2/§3 |
| J4 不新增环 | 新单元只依赖**共享**单元（`Symbols`/`Arena` 等），**不** import 宿主；宿主单向 import 新单元 | `p85_inventory.py m0` 的环检查：0 → 0 |
| 机械行白名单 | 每个宿主：新增 1 行 `import`、删除被搬函数/原型/全局；新单元：头注释、`#include`、原样 import、所需 `#define`、`namespace`、无状态 marker、`pub` 原型、搬来的定义 | `git diff -M` 辅助；body-hash 是主判据 |
| 单写者 | 本卡在单分支内一次搬完（C4）；合入窗口 `check-all` 全绿 | 收口记录 |
| 提交自洽（F2） | 三条调用方 import（`Parser`/`TypeCheck` 的 `SymbolsTypeText`、`Driver` 的 `ModuleBoundary`）与搬移同提交；`ct_norm_path` 的 `realpath` 原型也随函数进新单元 | `git archive <M0 提交>` 全链构建 rc=0（卡 §7.7 F2） |

### 1.1 命名与形状

- 单元名 `<Subsystem><Role>.h.ct`，PascalCase、全局唯一：`EmitterText`、
  `ModuleBoundary`、`ExprTypeText`、`SymbolsTypeText`、`StmtRangeText`、`PkgIndex`。
- 每个新单元是无状态单元（`Sh.h.ct` 的先例）：`pub struct <Name> { int unused; }`
  只为满足“单元文件以主类型命名”的 lint；单元里只有自由函数，没有 `use`、没有方法。

### 1.2 为什么不是“整文件搬”

`ct-ast` 的函数体大量使用 `self->`，方法只能在 `impl <Trait> for <Type>` 里；
把方法搬到新单元会让宿主被迫 import 新单元，而新单元又要 import 宿主（类型）——
**必然成环**。M0 因此只搬“不依赖宿主类型、也不被宿主类型签名约束”的自由函数；
宿主剩下方法，调用点仍是 `self->…` 或同名自由函数，行为不变。

## 3 验证（原始输出见探针）

**M0 提交自身**（`git archive 33f06d17`，不含 S85d；允许清单为空文件）：

```
$ python3 tools/p85_inventory.py m0
p85_m0: body hashes preserved (827 bodies, 838 functions, 6 moved units,
        0 declared S85d edits), 26 products, 0 cycles
$ bash test/ast/p85_m0.sh ./.temp/b/ct-ast
p85m0: 4 passed, 0 failed
$ ./.temp/b/ct-ast build --help | grep -c check-level
0
```

**HEAD**（M0 + S85d；允许清单为 11 条 S85d 改动）：

```
$ python3 tools/p85_inventory.py m0
p85_m0: body hashes preserved (827 bodies, 842 functions, 6 moved units,
        11 declared S85d edits), 26 products, 0 cycles
$ bash test/ast/p85_m0.sh <ct-ast>
p85m0: 4 passed, 0 failed
```

- **J1**：827 个基线 body-hash 全部存在；M0 提交是 `838` 个函数，HEAD 是
  `842 = 838 + 4`（4 个 S85d 新增函数，见 §4）。**M0 提交混入的 8 行 S85d 代码
  （`--check-level` help 文本 + `nsem` 提前退出守卫）已移回 S85d 提交**，所以 M0
  提交的允许清单是空集、`--help` 不列出未实现的选项（F2 残留修复）。
- **A2**：产物 20 → 26（新增 6 个 `<base>.c` + `.h`）；旧 20 个仍在。
- **J4**：环 0 → 0。
- **E85-6 第 1 层**：66 个语料文件（`test/cases/*.ct` + `examples/*/*.ct`）的发射
  逐字节等于 M0 之前用基线 ct-ast 生成的 `p85_corpus_sha.tsv`。清单对生成物
  banner 的 `Generated by ct v<X.Y.Z>` 做归一化，因此 v0.84.1 → v0.85.0 的**有意**
  banner 升级不掩盖任何行为差异（banner 以下的字节不变）。
- **自举不动点**：新编译器编译自身两次，产物 `diff -r` 无差异。
- **编译**：L0→L1→L2→ct-ast 全链 `-Wall -Wextra -std=c99` 零警告。

## 4 与 S85d 的交叉（诚实登记）

J1 在 **M0 提交处**成立；S85d（A 机制）随后有意改了 7 个函数体并新增 4 个函数
（`Diag` 的 `type_fail`/`set_types_level`/两个 `ct_*` 门面、`Expr` 的 3 个类型内核、
`Module.build_main`、`Driver.run`）。为让 HEAD 上的 `p85_m0` 仍能区分
“搬移改写了 body”和“后续任务改了 body”，[p85_m0_s85d_edits.tsv](../../test/probes/p85_m0_s85d_edits.tsv)
列了这 11 条；探针要求**每个被搬单元的函数体仍逐字节等于基线**，并只允许这 11 条
出现在“变化/新增”里。

## 5 产物/下游影响（B2）

- 新增 6 个 `.c` + 6 个 `.h` 产物；`--emit-c`/`build` 的产物集合变化已进基线。
- 单元名进生成物的 `#line` 与 banner；ABI 头（`<base>.abi.h`）只受 `pub` 类型影响，
  M0 没有新增 `pub` 类型（marker 是无状态的，不进 ABI）。
- 下游脚本用 `*.c` 通配（`check-ast.sh`、`check-warnings.sh`），无需改路径。
