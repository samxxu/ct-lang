# 第三十四批：增量构建的依赖闭包（2026-10-31）

> 锚点：`0e6d47a`（第三十三批收口），工作树干净。
> 现象来源：第三十三批 spec §4 记录的「增量缓存会产出不自洽的单元组合」。
> 复现（HEAD 可重现，L2）：先完整 `build` 一次多单元工程，改一个较早的单元，再在
> **同一输出目录**重建；某个被重新生成的单元会把导入类型写回源名（`struct Cache`
> 而不是 `struct tool_cache_Cache`），生成的 C 编译失败。

## 1. 现状与根因

- L2 的 `build` 是「一次运行、一张共享符号表」：单元按依赖优先序逐个
  `ct_compile_file`，后编译的单元能看见前面单元注册的类型。
- 缓存判定后，旧代码的编译集合是「第一个脏单元之前的所有单元 + 之后的脏单元」：
  `if (first < 0 || (o > first && !dirty[u])) continue;`
- 这条规则假设「脏单元的干净依赖都在 `first` 之前」，但依赖优先序不保证这一点：
  例如顺序 `A(脏) → B(干净) → C(脏，依赖 A 和 B)`，`first = A`，B 在 `first` 之后
  且干净，被跳过；C 重新编译时找不到 B 的导出类型，`B` 原样写进产物。
- ct-ast 的 `build` 不受影响：它先用 `load_unit` **解析全部单元**、再只重新发射脏
  单元，符号表始终完整（已用同一工程实测）。
- 现象只在 L2 上出现；而 L2 是 `check-ast.sh` 用来构建 ct-ast 的开发链路，全新目录
  构建不会触发，所以九关一直全绿。

## 2. 决策

- **D-1 编译集合改为「脏单元的依赖闭包」**：`need[u] = dirty[u]`，再从 `order` 末尾
  向前遍历，把每个 `need` 单元的依赖标为 `need`（依赖总在 `order` 更早的位置，
  一趟反向传播即可得到传递闭包）。发射循环只问 `need[u]`，删除 `first`。
- **D-2 允许重编译干净的依赖**：为了共享符号表，这是必要的代价；这些单元的产物与
  缓存里的内容逐字节相同（生成是确定的），缓存键也不变，因此不破坏「键与 ct-ast
  逐字节一致」的既有断言。验证方式：改动前后对比全部产物。
- **D-3 只动 `selfhost/l2/driver.ct` 的 `build_main`**：compile 模式、缓存键格式、
  生成物内容、`CTC_VERSION` 都不变。L2 按 D36 冻结为回归 oracle，这里按「bug 修复」
  处理，并在提交正文说明。
- **D-4 回归测试放在 `check-ast.sh` 的缓存一节**：用 L2 构建一个三单元小工程
  （A 脏、B 干净、C 依赖 A 与 B），断言第二次构建后 C 的头文件仍写
  `struct cache_B`，且生成物可零告警编译。

## 3. 边界

- 只影响 `build`（多文件）模式；单文件 `compile` 与缓存键不变。
- ct-ast 的构建逻辑不改：它本来就解析全部单元。
- 不做「只解析不发射」的优化；本批只修正正确性。

## 4. 验证

- `test/ast` 之外的临时工程回归（`check-ast.sh` 新增两条断言）。
- 实测真实链路：用新 L2 构建 ct-ast → 改 `Parser.h.ct` → 同目录重建 → 生成的 C
  零告警编译，`Module.h` 与重建前逐字节一致。
- 三关数字如实记录；`check-all` 九关全绿。
