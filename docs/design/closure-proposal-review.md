# 闭包提案评审：该照做、该改、该砍

> **状态：评审结论**（2026-11-06，基线 `v0.19.1`）。
> 对象：《CT 闭包语法分层设计提案》（自称基于 v0.12.0）。
> 本文只做判断，不复述提案；配套计划见 [phase21.md](phase21.md)。
> 结论均已按仓库现状核实；未核实的只有"提案作者当时怎么想"，那不影响判断。

---

## 0. 一页结论

**总评：方向对，论证有三处不成立，排期要改一处，边界结论可以保留但理由必须换。**

| 定性 | 条目 | 一句话理由 |
| --- | --- | --- |
| **照做** | `(fn, env)` 两词 ABI | 档① 的 `impl` 包装今天就是这个形状；换成打包 struct 立刻失去两档互通 |
| **照做** | 栈上环境、零 `malloc` | 堆环境会把闭包变回"又一个 `own` 对象"，收益归零、风险翻倍 |
| **照做** | 逃逸即硬错误 + hint | 静默悬垂是 `own` 存在的理由；闭包不能退回这个坑 |
| **照做** | 档② = 档① 的自动展开 | 第二套机制会让后端翻倍，并产生两套调试故事 |
| **照做** | 档③ 不进本阶段 | 但**不是"不可能"**，是"暂不值得"（见 §1.1） |
| **改** | 「复用 `own`，闭包是第三类右值」 | 机制是变量中心 + 取消析构 + 泄漏警告；闭包是一对局部 + 硬错误 |
| **改** | 「borrow 阶段一待做，需合并」 | v0.16.0 已实现；只剩抽 `outlives()` |
| **改** | 「两档零改动互通」 | 包装函数是 `static`，互通只在同一翻译单元内 |
| **改** | 「自动展开零风险」 | 运行时零风险成立；可调试性/可读性有实打实的成本（见 §1.2） |
| **改** | 「容器先行」 | 无泛型时闭包省的是调用点样板，不是容器函数数量（见 §1.3） |
| **改** | 「错误码」 | CT 没有错误码体系；契约应是稳定文案 + `note:` |
| **砍** | 方言生成作为档① 通路 | 编译器零感知；方言只能是仓库外实验 |
| **砍** | 万能 `Callable` | 无泛型时一个 trait 只能有一个 `call` 签名 |
| **砍** | 打包 struct 的 ABI 方案 | 只有档② 能填，档① 填不了 |
| **砍** | 跨过程逃逸分析 | 成本远超收益；把经 `void *` 的漏洞明确写进限制即可 |

## 1. 三个重点判断

### 1.1 「只做非逃逸闭包」的边界：结论保留，论证不成立

提案的原话是：无 GC / 无泛型 → 通用逃逸闭包会撞三堵墙——隐藏堆分配与所有权、**闭包类型无处安放**、生成物变形。

逐堵墙核对：

| 提案的墙 | 实际情况 | 判断 |
| --- | --- | --- |
| 闭包类型无处安放 | **假的**。`struct Clo_i2i { int (*fn)(void *, int, int); void *env; }` + `use Drop` 就是完整的逃逸闭包类型；env 是堆上的捕获集，`own` 负责释放。CT 今天没有任何语法障碍 | **只是难看，不是放不下** |
| 隐藏堆分配与所有权 | 只在"语法糖替你 `new`"时成立。写成显式 `own` 的 `Callable` 对象，分配与所有权都在源码里，不隐藏 | 是**糖的成本**，不是语言能力的缺失 |
| 生成物变形 | 档② 同样有 trampoline，同样变形；`#line` 机制已经存在（`Module.line_mode`），可以映射回源码 | **不区分别档②/档③**，不构成砍档③ 的理由 |

三堵墙去掉两堵半，剩下的真实成本只有两条：

1. **按签名一族的结构体样板**：每个 `(参数…, 返回)` 组合要一个闭包结构 + 一个 `Drop` 实现。这是**档① 今天已经在付的成本**。
2. **按引用的捕获需要生命周期表达**：CT 的 `own` / `borrow` 表达不了"借用一个比闭包短的变量"。这才是真正过不去的地方。

所以正确的表述是：

> **档③ 不是"做不到"，而是"能力已经在档① 里，只差一层语法糖；这层糖要配按引用捕获的生命周期，Phase 21 不做。"**

这个区别不是文字游戏，它决定了三件事：

- **hint 的写法**：不能写「不支持逃逸闭包」，要写「Phase 21 只支持非逃逸；逃逸请用显式 `Callable`，可抄的三行如下」。前者把用户推去塞 `void *`，后者把用户导向官方逃生门。
- **文档的口径**：不能把"无 GC 所以不可能"写进教程，否则将来做档③ 时自打脸；应写"按值捕获的逃逸闭包 = 档① 对象；按引用捕获暂不提供"。
- **决策的可逆性**：如果是"不可能"，就没有路线图；如果是"暂不做"，它就进入 backlog，有明确的触发条件（例如出现三个以上重复的 `Callable` 样板）。

**结论：边界保留（Phase 21 只做档②），论证必须替换。** 原论证把一个成本决策包装成物理不可能，会误导排期和用户预期。

### 1.2 「档② 是档① 的自动展开」不是零风险

提案说这是最大优点：不新增运行时。这一半成立——生成物确实只有栈上 env 与 `static` trampoline，没有 `malloc`、没有引用计数、没有 vtable。

但"零风险"不成立。自动展开把风险从**运行时**转移到了**可调试性**：

| 风险 | 具体表现 | 现状 |
| --- | --- | --- |
| 调试器看到合成帧 | 断点停在 `__ct_cl_tramp_3`，栈回溯里是机器名 | `#line` 默认**关闭**（`Driver.h.ct` 的 `line_mode = 0`），只有打开时才映射 |
| 生成 C 的可读性 | 用户读生成物时看到 `__ct_cl_env_v_1`；结构体字段还用源名，但变量名是造的 | tutorial 承诺"生成物可读"，闭包是第一个**名字由编译器造**的局部值 |
| 报错定位 | 闭包体内的错误必须报源行号，不能报 trampoline 行 | 需要 emitter 在 trampoline 前后重新锚定 `#line` |
| profiler / backtrace | 采样里出现匿名函数名 | 只能靠命名可读性缓解，无法消除 |

这条底线**守得住，但要付三笔小账**：

1. trampoline 前后发 `#line`（复用 `Emitter` 现有的 `#line` 重锚定机制），打开调试时断点能落回源码；
2. 无论是否开 `#line`，都在每对生成物前发一行注释 `/* closure at t.ct:4 */`，保证"读生成 C"时能对上；
3. env 字段沿用源变量名，实例名短且带序号；诊断一律指向源位置，绝不出现 `__ct_cl_*`。

如果这三条不做，提案必须**明说**：闭包是"生成物可读"这条底线的第一个例外。我认为不该开这个例外——代价小，守住的价值大。

**结论：展开方案照做；"零风险"改成"运行时零风险、可调试性有明确成本，已用 `#line` + 注释 + 源名兜住"，并把它写进验收判据（探针 80）。**

### 1.3 排期：容器不该先行，闭包应提前

提案的理由是"闭包最大用途是 `map/filter`，所以容器先落地"。没有泛型时算一笔账：

- 容器侧：`VecInt` / `VecStr` 各需要 `map` / `filter` / `each`，共 **6 个包装函数**。有闭包是 6 个，没闭包也是 6 个——**闭包一个都省不掉**，因为元素类型不同，签名不同。
- 调用侧：每个回调点，档① 要写 `struct AddN { int n; }` + `use Callable` + `impl` + 构造，约 **8–10 行**；档② 是 **1 行**。闭包省的是这里。

所以闭包的收益是**按调用点数**增长的，不是按容器数。而它还有一类完全不依赖容器的即时收益：C 回调（`qsort`、事件注册、`atexit`）与就地循环。反过来，如果先冻容器回调签名，很可能把 `env` 顺序、是否打包、arity 展开规则定错，然后再被闭包反过来推翻。

**结论：闭包先于容器完整落地；容器回调约定降级为并行文档（21.0），不阻塞。** 提案的顺序应改成：
`共用判定 → 档② 核心（冻结 ABI）→ 多行/嵌套 ∥ 容器约定 → 官方 Callable → 自举`。

## 2. 提案没意识到的新风险：类型宿主 `map` 的歧义坑

CT 已经有两条 trait 派发通路：`map trait T for instance x`（实例宿主）和
`map trait T for type <ctype>`（类型宿主）。后者的规则是：**接收者由调用点静态类型决定，
struct / 接口方法优先，查找失败才回退到类型宿主，多个候选报歧义**。std 刚踩过
`ambiguous type-host map`，说明这条通路的候选集是**全局按类型聚合**的——任何第三方都能给
`char *` 加方法，从而让别人的调用点变歧义。

闭包会不会掉进同一个坑？**取决于实现方式，不取决于"用不用 trait"：**

| 实现方式 | 是否撞坑 | 原因 |
| --- | --- | --- |
| 闭包调用是**直接调用**（`Var.is_closure` → 已知 trampoline） | **不撞** | 不进入方法派发，候选集不参与 |
| 把闭包 desugar 成 `Callable` 接口值，按类型派发 `call` | **撞** | 每个 `char *` 宿主 map 都进候选集；这正是 std 的坑 |
| 给函数指针类型加 `map trait Callable for type <fnptr>` | **撞得更狠** | 所有闭包与所有普通函数指针共享同一个表面类型，一次映射全局生效 |
| 支持 `closure.call(…)` 语法糖 | **撞** | 走的就是方法派发通路 |

**结论（必须钉死）：**

1. 闭包的调用、传参、逃逸检查**一律不经过 trait / 类型宿主派发**；`Var.is_closure` 是唯一的解析依据。
2. Phase 21 **不提供** `.call()` 方法语法；闭包只能 `c(args)` 直接调用。
3. **禁止**对函数指针类型使用 `map trait … for type`；如果 21.4 要引入官方 `Callable`，它必须是**真实的 struct 类型**（档①），不能是 fnptr 的类型宿主。
4. 官方 trait 名 `Callable` 只作为 trait 名存在，不再叠加一个同名类型宿主。

这条不只是防御：它同时解释了为什么"档② = 档① 展开"必须走**生成 trampoline**，而不是"把闭包塞进 `Callable` 接口再派发"——后者看起来更统一，实际会把 std 的歧义坑复制到每一个闭包调用点。

## 3. 逐条定性

### 3.1 该照做

| # | 条目 | 理由 | 不做会坏在哪 |
| --- | --- | --- | --- |
| A1 | `(fn, env)` 两词 ABI，`env` 第一参数 | 与 `impl` 的 `void *self` 同位；档① 的包装函数可直接填 | 打包 struct 后档① 填不进去，两档退化成两套机制 |
| A2 | 环境在栈上，零 `malloc` / 零引用计数 | 非逃逸的前提就是环境活不过栈帧 | 一旦堆分配，就必须回答所有权、释放、逃逸三个问题，Phase 21 直接失控 |
| A3 | 逃逸即硬错误，不是警告 | 静默悬垂比编译失败危险一个数量级 | 用户会存下闭包，运行期读到已弹出的栈 |
| A4 | 档② = 档① 的自动展开 | 一套 ABI、一套调试故事、一套文档 | 第二套机制 = 后端翻倍 + 两档无法互操作 |
| A5 | 撞墙 hint 必须给可抄的 `Callable` 三行 | 提案自己说对了：没有逃生门，用户会塞 `void *` | 边界会被用户绕过，最终等于没有边界 |
| A6 | `=>` 设为保留字 | 全仓 0 处 CT 标识符使用，破坏面为零 | 用别的符号（如 `->`）会与现有语法/可读性冲突 |
| A7 | 负例 golden + 稳定文案 | CT 没有类型系统兜底，诊断就是契约 | 文案漂移会让编辑器与用户脚本同时失效 |
| A8 | 自举纪律：先支持、后使用 | 否则编译器源码先用了 `=>`，旧编译器编不动自己 | 自举链断裂，发布无法复现 |

### 3.2 该改

| # | 原写法 | 改成 | 为什么原写法不行 |
| --- | --- | --- | --- |
| B1 | 逃逸判定复用 `own`，闭包是"第三类右值" | 新增闭包标记 + 复用 `expr_returns` / `var_scope` / 三个挂载点；逃逸是硬错误 | `own` 是变量中心、取消析构、泄漏警告；闭包是一对局部、必须硬错误。数据结构复用不了 |
| B2 | borrow 阶段一待做，与档② 合并 | 承认已实现（v0.16.0）；只抽 `outlives()` | 阶段一已落地，按原计划会重做一遍并制造第二套语义 |
| B3 | 两档零改动互通 | 同单元互通；跨单元走 vtable / `pub` 包装 | impl 包装是 `static`，跨单元拿不到裸 `fn` |
| B4 | 自动展开零风险 | 运行时零风险；可调试性有成本，用 `#line` + 注释 + 源名兜住 | 默认 `#line` 关闭，断点会停在合成帧；"可读生成物"是既有承诺 |
| B5 | 容器先行 | 闭包先行；容器约定并行、不阻塞 | 无泛型时闭包省的是调用点样板（8–10 行/处），不是容器函数数量（6 个不变） |
| B6 | 命名 `__cl_env_N` / `__cl_tramp_N` | `__ct_cl_env_N` / `__ct_cl_tramp_N` / `__ct_cl_env_v_N`，单元内单调、不复用、`static`、只进 `.c` | 原前缀不在保留命名空间里，可能与用户标识符或既有 `__ct_retN` 家族冲突 |
| B7 | 错误码 | 稳定英文文案 + `note:` hint 通道 | CT 没有错误码体系；新增一套码比闭包本身还大 |
| B8 | 官方 `Callable` | 按签名一族（`Callable0` / `Callable1i` …），不是单个万能 trait | 无泛型时一个 trait 只能有一个 `call` 签名 |
| B9 | 语法用 `auto add = …` | `int (*add)(int x) = (int x) => …` | CT 没有 `auto`，也没有类型推断；引入推断是另一个语言特性 |
| B10 | 档③ "撞三堵墙，不可能" | "能力已在档①，缺的是语法糖；按引用捕获需要生命周期，Phase 21 不做" | 类型有地方放，堆分配可显式，生成物变形对档② 同样成立；把成本决策说成物理限制不可逆 |

### 3.3 该砍

| # | 砍掉什么 | 损失 | 值不值 |
| --- | --- | --- | --- |
| C1 | 档③ 的语法糖（不是能力） | 逃逸闭包要手写 `Callable`，约 8–10 行/处；按引用捕获完全没有 | **值**。能力已在档①；按引用捕获要生命周期，不是本阶段能付的价 |
| C2 | 方言生成作为档① 官方通路 | 少一条"用 DSL 生成闭包"的实验路径 | **值**。编译器零感知，方言只能在仓库外；把它写成官方逃生门会误导用户 |
| C3 | 打包 struct 的 ABI 备选 | 无损失 | **值**。档① 填不进去，纯粹是退路 |
| C4 | 万能 `Callable` | 用户要记几个按签名的 trait 名 | **值**。无泛型下本来就不可能；假装万能只会在派发处炸 |
| C5 | 跨过程逃逸分析 | 经 `void *` 交给不透明 C 函数后由对方保存，检测不到 | **值**。这是整个 CT 的既有边界；为它做可达性分析的成本远超闭包 |
| C6 | 容器先行的排期约束 | 无能力损失，只是顺序 | **值**。容器约定可以并行，且应先看闭包 ABI 再定容器签名 |

## 4. 提案 §11 十项：直接给倾向

| # | 事项 | 倾向 | 一句话理由 |
| --- | --- | --- | --- |
| 1 | `=>` 完整语法 | `ret (*name)(params) = (params) => expr`；多行 `=> { … }`；无显式捕获列表；返回类型取左侧声明 | 复用现有函数指针声明，零新类型语法；`auto` 不存在 |
| 2 | 捕获按值还是按引用 | **按值**、创建点求值、捕获名只读；指针浅拷贝；禁止捕获 `own` / `borrow` | 按引用要生命周期；只读避免"写了不生效"的静默错误 |
| 3 | 命名与去重 | `__ct_cl_env_N` / `__ct_cl_tramp_N` / `__ct_cl_env_v_N`，共享 N，单元内单调，`static`，只进 `.c` | 与 `__ct_ret%d` 同风格；嵌套天然不撞 |
| 4 | 传参 ABI | 两参数、`env` 第一；闭包实参在相邻 `(fn, env)` 参数对上展开为两参 | 打包 struct 断掉档① |
| 5 | 逃逸扩展点 | E1–E8（return / 更长寿命存储 / 字段元素 / 捕获 own-borrow / 捕获名写入 / 普通函数指针 / 同层拷贝放行 / goto 记录） | 形态只增不减；同层拷贝安全 |
| 6 | 共用检查与诊断 | 抽 `outlives()`；无错误码，稳定文案 + `note:` | borrow 已落地，只差抽取 |
| 7 | `Callable` 签名 | 按签名一族；`use Callable` 不强制 `use Drop`，只有堆对象才需要 | 无泛型；栈对象析构无意义 |
| 8 | namespace 交互 | 不加前缀 | `static` + 一单元一 `.c`，跨单元不可见 |
| 9 | golden 用例 | 70–79（另加 80 `#line` 映射、81 类型宿主不参与） | 覆盖正面、负例、漏洞记录、跨单元、调试 |
| 10 | 对照最新源码 | **已完成**（本文 §1、§3 与 phase21 §3） | v0.19.1 实测，5 处偏差已在 phase21 §3 记录 |

## 5. 对 [phase21.md](phase21.md) 的修订要求

计划已按本文结论落笔，以下是对照检查项：

1. §2 非目标：把"档③ 不做"的理由从"不可能"改为"能力在档①、缺的是糖、按引用捕获需生命周期"。
2. §4.3：命名统一为 `__ct_cl_*`；明确 `__ct_` 保留前缀检查。
3. §4.3 / §4.6：增加 trampoline 的 `#line` 重锚定 + `/* closure at … */` 注释；诊断只指向源位置。
4. §4.4：写明"跨单元只能走 vtable / `pub` 包装"。
