# 容器选型：`std::map` / `hashmap` / `dict`

> 本文是决策与需求记录，不含实现。实现全部落在同级 `ct-pkg` 仓库：
> `std` 保持不变，新增 `hashmap`、`dict` 两个包。ct 仓库只保留本文作为选型依据。

---

## 1. 结论

三个容器并存，各自对应一种明确的取舍；**不做统一抽象层**，用"场景向导"代替"统一接口"。

| # | 容器 | 归属 | 一句话定位 |
| --- | --- | --- | --- |
| A | `std::map` | `ct-pkg/std`（已有，**保留**） | 有界、`init` 一次定容、之后不增长；内存可预测 |
| B | `hashmap` | `ct-pkg/hashmap`（新增） | 动态增长、**拷贝**键值、单文件、MIT |
| C | `dict` | `ct-pkg/dict`（新增） | 增量 rehash、**存指针**、面向大表 |

选型标准不是"哪个更强"，而是"哪个的取舍匹配你的场景"。三者的差异里有两条是**调用方可见的语义**，不是实现细节：键值是拷贝还是借用、扩容是否会造成长停顿。

---

## 2. 背景与边界

- ct 没有泛型，容器只能手写具体类型；这一点三个实现都一样，换库不会消除组合爆炸。
- `std::map` 的形态是已确认决策 D17-7（[phase17.md](phase17.md)）：单态类型为主、有界开放寻址、`*_clear` / `free_fn`、不用 `delete`、不做第三方 binding。**本次不推翻它。**
- **三者都不是线程安全的**，包也不提供锁；并发由调用方负责。
- 三个容器都**不提供 `Drop` 自动释放**：内建 `Drop` 的发射函数是 `static`，跨单元不可用，包单元无法销毁调用方的值。三者统一使用显式 `release()` / `free()` / `clear()` + `free_fn`。

---

## 3. 三个实现

### A. `std::map`（保留）

| 维度 | 事实 |
| --- | --- |
| 结构 | 有界开放寻址；`init` 一次定容（向上取 2 的幂），`put` 满即失败 |
| 增长 | 从不 rehash、从不增长 |
| 键值所有权 | 键按指针存，**不拷贝**，必须比条目活得久 |
| 删除 / 遍历 | 无单条 `delete`；`clear` 全清（`MapIntPtr` 可配 `free_fn`）；v1 无遍历 |
| 依赖 | 无（纯 ct 类型，无 mapping、无 shim） |
| 固定成本 | 每个对象多 8 字节 vptr，每次调用一次间接跳 |
| 形态 | `MapStrInt`（`char *`→`int`）、`MapIntPtr`（`int`→`void *`） |

### B. `hashmap`（新增，基于 tidwall/hashmap.c）

| 维度 | 事实 |
| --- | --- |
| 结构 | 罗宾汉开放寻址，`key_size` / `value_size` 在创建时固定 |
| 增长 | 动态增长、自动扩容 |
| 键值所有权 | **按字节拷贝进表**；`put` 返回后调用方可以立即释放自己的键值 |
| 删除 / 遍历 | `delete`、`scan`、`iter` 齐全 |
| 依赖 | 单个 `.c` + `.h`，MIT；无其它依赖 |
| 固定成本 | 每个条目多一次拷贝；创建时必须传 `sizeof` |
| 失败模型 | `set` 返回被替换的旧值；OOM 需要单独查询（`hashmap_oom`） |

> 具体函数签名与默认 hash/compare 行为，以引入版本的官方头文件为准；S1 定稿时逐条核对。

### C. `dict`（新增，基于 Redis 7.2.x 抽取）

| 维度 | 事实 |
| --- | --- |
| 结构 | 链式桶 + 两张表，增量 rehash |
| 增长 | 渐进扩容：每次操作搬一点，**不会出现长停顿** |
| 键值所有权 | 只**存指针**，不拷贝；需要拷贝时由 `dictType` 的 `keyDup` / `valDup` 决定 |
| 删除 / 遍历 | safe iterator 允许遍历中删除当前元素；`dictScan` 用于安全全量扫描 |
| 依赖 | 需抽离 `zmalloc`、`siphash`、`serverassert`，并初始化 hash seed |
| 固定成本 | 代码面最大；每种键值形状需要一份 `dictType` + shim |
| 许可 | **Redis 7.2 及更早为 BSD-3-Clause**；7.4 起为 RSALv2 / SSPLv1；8.0 起另可选 AGPLv3。只能用 7.2.x 快照 |

## 4. 场景向导

### 4.1 决策树

1. **容量能在 `init` 时确定**，并要求 `put` 路径不再分配、行为完全可预测？→ **A `std::map`**
2. 需要动态增长，且希望键值被**拷贝**（`put` 之后调用方可以立刻释放）？→ **B `hashmap`**
3. 规模到十万级以上，扩容不能有长停顿，或需要边遍历边删？→ **C `dict`**
4. 只是少量键值、生命周期短、想少一个依赖？→ **A `std::map`**

### 4.2 对照表

| 场景 | A `std::map` | B `hashmap` | C `dict` |
| --- | --- | --- | --- |
| 嵌入式 / 内存受限 | ✅ 首选 | ⚠️ 会增长 | ❌ 代码面过大 |
| 实时性 / 禁止 put 分配 | ✅ 唯一选择 | ❌ | ❌ |
| 容量可预估的小表 | ✅ | ✅ | ⚠️ 过度 |
| 通用业务表（规模未知） | ❌ 会满 | ✅ 首选 | ✅ |
| 键值由调用方管理生命周期 | ✅ 借用 | ✅ 拷贝 | ✅ 借用 |
| 键值需要被容器持有 | ❌ | ✅ | ⚠️ 需配 dup |
| 百万级 / 扩容平滑 | ❌ | ⚠️ 全量扩容有停顿 | ✅ 首选 |
| 遍历中删除 | ❌ 无遍历 | ⚠️ 需查该版本约束 | ✅ safe iterator |
| 零第三方依赖 | ✅ | ✅ 单文件 | ❌ |
| 代码审查面 | 最小 | 小 | 最大 |

### 4.3 调用形态（示意，S1/S2 定稿）

三者都是**显式调用**，不做链式：

- A：`m->init(n)` / `m->put(k, v)` / `m->get(k, &out)` / `m->clear()`
- B：`h->init(sizeof k, sizeof v, n)` / `h->put(&k, &v)` / `h->get(&k)` / `h->del(&k)` / `h->free()`
- C：`d->init(type)` / `d->put(k, v)` / `d->get(k)` / `d->del(k)` / `d->release()`

差异集中在两个地方，文档必须反复强调：**B 的键值会被拷贝，C 只存指针。**

## 5. 为什么不做统一 `Map` trait

1. **所有权语义不同**：B 拷贝、C 借用。统一接口只有两种写法，都会牺牲一边——要么让 C 强制 dup（丢掉它"零拷贝指向你自己的结构体"的优势），要么让 B 假装借用（做不到）。
2. **"统一接口 / 零开销 / 运行时可切换"三角，只能取两个**：要统一接口又要运行时可切换，就会产生 vtable 与间接调用，不再是零成本；要零成本就必须在编译期选定后端。
3. **无泛型**：统一接口只能是 `void *`，反而丢掉 A 现有的类型安全。

因此本文只提供选型向导，不提供抽象层。若将来真的出现"同一段代码需要在两种后端上跑"的需求，再单独设计，不在本次范围内。

## 6. 实施规划

### S0 · 文档入库（本文）

- 产出：本文件。
- 验收：`test/docs/check-docs.py` 通过；不改代码、不改 `std`。

### S1 · `ct-pkg/hashmap`

范围：
- `.h.ct` 定义句柄类型（按值包裹的指针，避免与其它 `void *` 宿主冲突）；
- `.m.ct` 放 mapping；`sizeof`、默认 hash/compare、OOM 查询、旧值返回由 shim 收口；
- 首批两种形状与 `std` 对齐：`str→int`、`int→ptr`；
- 文档：与 `std::map` 的差异、拷贝语义、失败模型。

验收：
- put/get/del/len/遍历全部有断言；
- 扩容后旧值仍可读；键值在 `put` 后立即释放不影响读取（验证拷贝语义）；
- OOM 可被调用方检测；
- 包自带断言，不新增 ct 硬门禁。

### S2 · `ct-pkg/dict`

范围：
- 抽取 `dict.c` / `dict.h` + 最小 `zmalloc` + `siphash` + `serverassert`，并初始化 hash seed；
- 保留上游版权头与 `LICENSE`，记录来源 commit 与版本（7.2.x）；
- 每种键值形状一份 `dictType` shim；`dictGetKey` / `dictGetVal` 宏进 shim；
- 暴露显式 `release()`；不提供自动析构。

验收：
- 增量 rehash 过程中读写正确；
- safe iterator 遍历中删除当前元素正确；
- 大表（十万级）插入/查找/删除有基准数据；
- 许可与出处可追溯。

### S3 · 向导定稿与示例

- 同一任务的三种写法并列示例；
- 场景向导按实测基准校正；
- 明确迁移建议：默认用哪个、什么时候换。

## 7. 明确不做

- 不删除 `std::map`（推翻 D17-7 需要单独决策）。
- 不做统一 `Map` trait / 抽象层。
- 不做 `Drop` 自动释放（包内做不到，只有调用方单元自己写 `impl Drop` 才生效）。
- 不做链式调用（与零成本直绑冲突）。
- 不引入 Redis 7.4 及以后版本的任何代码。
- 不新增 ct 仓库的硬门禁；测试留在各包内。

---

## 8. 风险与开放问题

1. **三套语义的认知负担**：这是本方案最大的成本。文档必须把"拷贝 vs 借用"和"是否扩容"讲成第一顺位信息。
2. **键值所有权**：最易出错的地方。B 用完后可以释放键值，C 不行；同一个人在两份代码里切换时最容易犯这个错。
3. **shim 数量**：C 的成本是"形状数 × 1 份 `dictType`"；B 是"形状数 × 1 个创建点"。新增一种形状就要改 C 代码。
4. **许可**：只能用 7.2.x；必须保留版权声明与许可文本，且不得以 Redis 名义背书。
5. **命名与 import 路径**：`std::map`、`hashmap`、`dict` 三个包名与命名空间根需要与包命名空间方案一起定。
6. **`ct check` 不支持 `import`**：三个包的单元都无法被语义检查，只能靠各自断言；这是主线带来的限制，不在本方案内解决。
7. **线程安全**：三者都不加锁；`dict` 的 `dict_can_resize` 是进程全局量，多表并发扩容的行为需要单独说明。
