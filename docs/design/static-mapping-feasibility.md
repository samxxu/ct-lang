## 1 链路与职责

```
用户 .ct（模型 + 逻辑）
   │  ct build --emit-model model.json        ← CT 侧唯一新增出口
   ▼
生成器（包内，PHP 等任意语言）
   ├─► generated/*.ct        模型/事件骨架（自由函数）
   ├─► generated/*.c|.h      胶水（不透明句柄 + set_on_* + void *ctx）
   └─► generated/*.swift     holder + @State 镜像 + @convention(c)
   ▼
ct build（CT 侧）+ 包内 bridging header（构建产物）→ Xcode / SPM
```

**CT 侧自有运行时 0 行**：CT 不提供 Swift 运行时、不提供 holder、不提供事件分发器；只提供声明层出口与既有的 `.abi.h`。
`--emit-model` 不是 ABI 面，只是代码模型，零 ABI 影响（提案 §8）。

## 2 已定（6 条）

### 2.1 bridging header 判为构建产物

| 项 | 裁定 |
| --- | --- |
| 性质 | **构建产物**，不是用户维护的源文件 |
| 产出方 | 与 `.abi.h` **同源**：由生成器从模型导出 + `.abi.h` 派生，随包分发 |
| 用户可见性 | 用户**不写**、也**不该看见**；不计入「用户样板」 |
| 对 CT 的要求 | `.abi.h` 必须自足到可被机械包裹（不透明前置声明 + 导出原型 + `ABI_VERSION`/`ABI_HASH`）；**不要求** CT 直接产 Swift 可用的头 |
| 依据 | 若 bridging header 由消费者维护，则每加一个模型都要人改一次，直接击穿「用户只写 `.ct`」的口径 |

**边界**：`@main`、App 生命周期、平台适配仍在 Swift 侧；bridging header 自动化不等于「不需要 Swift」。
**未定细节（不影响本条成立）**：由生成器产 `.h` 还是产 `.modulemap`，以及是否复用 `.abi.h` 的 `ABI_HASH` 作版本戳——见 §3.2 与 Phase 59 卡的任务边界。

### 2.2 模型导出全字段

| 项 | 裁定 |
| --- | --- |
| 导出范围 | struct 的**全部字段**，含非 `pub` 字段；不按可见性过滤 |
| 字段顺序 | 与源码声明顺序（即内存布局）一致 |
| `visibility` | LANG-9 落地前一律 `"unknown"`；落地后填 `"pub"` / `"private"` |
| 对消费方的约束 | `unknown` = **未判定**，不得据此过滤字段或推断私有 |
| 依据 | CT 布局不分公开私有；漏字段会让生成器还原的结构体与 `.abi.h` 对不上，比「多导出」危险得多 |

本条与提案 §4.1 一致，已在提案内登记为「已定，2026-11-15」；此处作为链路级决策再记一次，避免两处口径漂移。

### 2.3 首版范围：无 import 的单单元端到端

| 项 | 裁定 |
| --- | --- |
| 首版范围 | **只做无 `import` 的单单元端到端**：一个 `.ct` 单元 → `--emit-model` → 生成器 → 编译运行 |
| 多单元 | 列为**第二里程碑**，等 CT 的 **SH-79（0.53.8）** 落地后接上；不阻塞首版 |
| 禁止的绕过 | 首版**不做**「生成器自己拼模型图」——多单元不靠包侧遍历补，靠 SH-79 修好出口 |
| 依据 | 单单元已足以验证「声明层出口 → 生成器 → 编译」这条链；先在包侧自拼模型图会把 CT 的出口缺陷固化进包，日后难拆 |

**SH-79 的两个 facet 正是多单元前置**：`--lib` 提前收口导致 `--emit-map` 不落文件、`file` 字段固定写 `units[0].prog`。二者不修，多单元模型必错。详见 [open-items-routing §8.1](../planning/open-items-routing.md)。

### 2.4 异步 / 流式 / 动态增删：首版一律非目标

| 项 | 裁定 |
| --- | --- |
| 范围 | 异步数据、流式推送、运行时增删节点，首版**一律列入非目标** |
| 钩子 | **不留半成品钩子**：schema 不预留 `async`，不预留「稳定 id + 整子树替换」这类本期不实现的字段 |
| 判据 | 与「最小样例」判据分开表述：最小样例只验同步单向链路，非目标不设判据、也不设「已预留」断言 |
| 依据 | 预留字段会被当成已支持，生成器按它写代码后再改就要破契约；等有真实消费者再按实际用例立需求 |

### 2.5 首版类型集含枚举

| 项 | 裁定 |
| --- | --- |
| 范围 | 首版 `kind` 含 `enum`，并导出**成员名与成员值** |
| Swift 映射 | 带 `rawValue` 的 `enum`（整型底层），不做字符串枚举 |
| 判据要求 | 最小样例必须**包含一个枚举字段**，不能只在文档里写支持 |
| 依据 | 枚举是 UI 状态机与选项集的常见形态；首版不含会让生成器第一版就撞墙，后续补又要动 schema |

### 2.6 字段级位置回指必带

| 项 | 裁定 |
| --- | --- |
| 范围 | `fields[]` **必带** `loc{file,line,col}`，指向字段声明处 |
| 依赖 | **PH-58**（字段级位置，[routing §3.4/7c](../planning/open-items-routing.md)）；PH-58 本来就排在 PH-59 之前 |
| 滑期降级 | PH-58 若滑期，降级为「只带 `line`」并在卡内显式标注缺 `col`；不得退回到「不写该键」 |
| 判据要求 | 必须有一条能真红的断言：`loc` 存在且指向声明行/列；golden 用**字段级**定位，不许停在 struct 级 |
| 依据 1 | 提案自己的 schema 规则：字段从「可缺席」变「必有」属于改义，按定义要 +1 大版本——那就等于 PH-59 出厂即欠一次大版本 |
| 依据 2 | 原 J1–J10 没有一条断言位置，golden 停在 struct 级也能全绿，等于「回指」这个卖点没有判据 |

## 3 待定（无）

原「字段级回指」已按 §2.6 转「必带」；异步/流式/动态增删已按 §2.4 转非目标；多单元已按 §2.3 转 M2。
与映射相关的待定项已清零。剩余的**版本位冲突**不属于映射决策，登记在 [Phase 59 卡](phase59.md) §8。

> §2 六条即当前全量裁定，Phase 59 只实现这六条的范围。
