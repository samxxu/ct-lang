## 2. 拆分依据（CT 内部逻辑）

### 2.1 什么必须同相：语义闭环

- **错误出口类型契约**（PH-43）与 `?`（PH-44）是两件事，不是一相的上下半场：前者约束的是既有的
  `return err:`，后者引入新语法与新临时量。但后者依赖前者，否则 `?` 的失败分支会把同一条静默坏 C
  放大成语法级隐患。
- **`?` 的语法、语义、发射、Drop 失效化**必须同相：只做解析不做发射会留下「能过语法检查但生成坏 C」的
  中间态，正是本方案要消灭的形态。
- **ADT 的声明、构造、`match`、穷尽检查**必须同相：只交付 tagged union 而不做穷尽检查，等于把一个
  半成品语法交给用户，且后续再补穷尽会改诊断面与夹具，属于「先应付、后面再补」，本方案明确禁止。

### 2.2 什么有硬前置

- **PH-44 → PH-43**：`?` 的失败分支语义是 `return err: <外层 Result>::err(t.err)`；PH-43 之前，
  `return err:` 的载荷类型不被检查。若先上 `?`，用户仍可用显式写法制造静默坏 C，而 `?` 的展开又依赖
  该检查来保证 E 是否一致。故 43 必先。
- **PH-46 → 前置无**：ADT 不依赖 43/44 的代码路径，但它改 Parser/Emitter 的公共面，必须独占时间窗。

### 2.3 什么互相独立

- **PH-45 ABI 校验**：只新增 CLI 子命令与导出面重算，不引入新语法、不改类型系统。它与 43/44 的唯一
  实质交集是 `Emitter.h.ct` 里的哈希算法（见 §5，S0 决定是否提取共享助手）。
- **PH-43 与 45** 可任意先后；把 43 放前面是因为它修正确性缺口。

### 2.4 工量是否落在单相可交付区间

以已收口相的实测/卡面估算校准（`docs/design/phase38-draft.md:9` 合计 410–790；
`phase40-draft.md:8` 合计 460–750；`phase42-draft.md:8` 合计 590–1030；PH-40 实际编译器改动
`git diff --stat v0.39.0 v0.40.0 -- selfhost/ct-ast/` = 3 文件 +271/−14）：

- 43、45 落在「单相可交付」的小区间（<700）；
- 44 与 PH-40/PH-42 同量级；
- 46 明显超出单相历史区间，因此必须用**切片数**控制风险（S1–S10），而不是把能力砍半。

## 3. PH-43 错误出口类型契约

**一句话**：让 `return err: <expr>` 的载荷类型在所有模式下被检查；判出不一致就是编译期硬错，不再依赖
`ct check --types` 才发现。

**现状（S0 必须逐条核对并写入相卡）**

- `return err:` 的语法标记：`selfhost/ct-ast/frontend/parse/Stmt.h.ct:1388-1400`（`err_ahead`）、
  `:1941-1947`（`return` 分支消费 `err` `:`）。
- 载荷类型检查：`Stmt.h.ct:1993-2012` 整段被 `self->ex->types_mode && *self->ex->types_mode` 包住，
  因此默认编译路径完全不检查；`ct check --types` 才走 `chk_type` / `chk_assignable`。
- 判据文档：`docs/language-spec.md:2177-2203`（§4.53），其中 `:2180-2182` 明确「不带 `--types` 的
  `ct check`、以及 `ct build` / `ct compile` 的输出、诊断和 golden 逐字节不变」。
- 能力声明：`README.md:65`、`README.en.md:64` 仍写「默认编译路径的类型检查」属于明确不做。
- 既有用例密度：全仓 `return err:` 共 12 处 / 9 文件，`break err:` + `continue err:` 共 7 处（本轮实测
  `grep -rn`），迁移面小。

**范围（闭环）**

1. `return err: expr;`：`expr` 的静态 C 类型必须可由既有内核判定，且可赋给当前函数的返回类型。
2. `return err:;`（void）与 `return err: expr;`（非 void）的既有诊断（`an error return needs a value`、
   `a void function cannot return a value`）保持不变。
3. `break err:;` / `continue err:;` 无载荷，不在本相范围内（行为不变）。
4. 规则在 `ct build` / `ct compile` / `ct check` / `ct check --types` 四种入口一致生效；`--types` 不得
   重复报告同一条。
5. 复用既有判定内核与文案 `return: expected '<T>', got '<U>'`，不新增第二套类型规则；判不出（数组、
   闭包、函数指针、`sizeof`、宏等，见 `docs/language-spec.md:2186-2187`）仍跳过，交给 `cc`。
6. 覆盖接口返回值的既有行为：`--types` 今天对普通 `return` 已经跑同一条检查，PH-43 只是去掉
   `types_mode` 门槛，接口槽位的行为以现有 `--types` 回归为准。

**完整性边界**

| 维度 | 内容 |
| --- | --- |
| 交付后能写 | 任何返回类型的函数都可写 `return err: expr`；载荷与返回类型一致时编译通过并保持原有清理语义 |
| 不能写 | 载荷与返回类型不一致（`Result<int, char *>` 函数里 `return err: <char *>` 之外的类型、struct↔标量、不同 struct 互赋） |

| 明确仍不判 | 数组、闭包、函数指针、`sizeof` / `_Generic` / 宏等类型内核判不出的形态，仍交由 `cc`；这是 §4.53 的既有边界，列入 §10 的后续项，不在本相偷偷放宽 |

## 4. PH-44 `?` 错误传播运算符

**一句话**：后缀 `?` 对 `Result<T,E>` 做同 E 传播：失败则构造外层 `Result` 的 Err 并走 `return err:` 的
清理语义，成功则取 `value`；与三目运算符确定性消歧。

**现状（S0 必须核对）**

- 三目：`selfhost/ct-ast/frontend/parse/Expr.h.ct:2879-2893`，遇到 `?` 后无条件读表达式并 `expect(":")`。
- 后缀层：`parse_postfix` / `parse_unary`（`Expr.h.ct:3301-3468`）；一元集合为 `++ -- - ! ~ & *`，
  **没有一元 `+`**，这是消歧规则可判定的前提。
- 返回类型保存：`selfhost/ct-ast/frontend/sym/Symbols.h.ct:522`（`char ret_type[160]`），赋值点见
  `Parser.h.ct:282-294`、`:1643`、`:3060`、`:3214`、`:3581`。S0 必须实测 `Result<int, char *>` 在该字符串里
  的规范形态（决定 E 比较与实例名还原），判不出来的先做 S1 归一化，不带着猜测开工。
- `Result`：`lib/std/Result.h.ct:24-28`（`int ok; T value; E err;` + `use Drop`），`ok`/`err`/`is_err` 见
  `:33`/`:42`/`:53`。
- 规范：`docs/language-spec.md:2264-2270`（§4.58），`:2270` 明确把 `?` 列入「不做」（开放项 T40-1）。

**范围（闭环）**

1. **非 void**：函数返回 `Result<U,E>` 时，`expr?` 要求 `expr` 的类型可判为 `Result<T,E>`，E 与外层
   **同一 C 类型**（不做任何转换）；失败分支等价于
   `if (__t.is_err()) return err: Result<U,E>::err(__t.err);`。
2. **void**：函数返回 `void` 时，`expr?` 要求 `expr` 为 `Result<_,E>`，失败即 `return err:;`（触发
   errdefer，丢弃载荷）。E 不做跨函数比较。
3. **链式 / 嵌套**：`f()? + g()?`、`h(f()?)`、`v.set(i, f()?)`、`o.m(f()?)` 全部支持；求值顺序与 C 的
   从左到右一致，临时量在语句边界内按出现顺序展开。
4. **出现位置**：表达式语句、声明初值、赋值右值、`return` 表达式、函数/方法实参内部（含任意嵌套）。
5. **消歧规则（确定性、单 token 前瞻）**：`?` 之后跳过空白/注释，若下一个字符**不能**开始表达式，
   则为后缀 `?`；否则按三目解析。能开始表达式的字符：字母、`_`、数字、`"`、`'`、`(`、`-`、`!`、`~`、
   `&`、`*`、`++`（即 `+` 后紧跟 `+`）。因此：
   - `f(a?)`、`x = a?;`、`f(a?, b)`、`(a?) + 1`、`a? + 1` 是后缀；
   - `a ? b : c`、`a ? -1 : 0`、`a ? (b) : c` 是三目；
   - `a? * p` 会被当作三目并在 `p` 处报 `expected ':'`，用户写 `(a?) * p` —— 这条要写进教程。
6. **与 `return err:` 的衔接**：失败分支走既有错误出口，因此 errdefer / defer 单栈 LIFO、`own` 泄漏分析、
   `retire_before_return` 全部复用，不新增清理路径。
7. **Drop 与移动**：`Result` 带 `use Drop`；成功取值后临时量必须失效化（参照
   `Stmt.h.ct:2034` 的 `return_reads_autodrop` 调用点（定义在 `:355`）），否则载荷被释放两次。`T` 作为载荷的复制/移动
   规则沿用现有泛型 struct 字段语义。
8. **类型内核边界**：操作数类型判不出时**保守硬错**（L44-3），不允许「判不出就当成功」静默发射。

**完整性边界**

| 维度 | 内容 |
| --- | --- |
| 交付后能写 | 有返回值函数里的同 E 传播、void 函数里的失败传播、链式/嵌套/实参位置、任意深的 `?` 组合 |

## 5. PH-45 ABI 消费端校验

**一句话**：`ABI_HASH` 今天只发射不校验；新增只读子命令，重算导出面哈希并与 `.abi.h` 比对，让「有度量」
变成「有门禁」。

**现状（S0 必须核对）**

- 发射：`selfhost/ct-ast/backend/emit/Emitter.h.ct:5336-5337`（`<BASE>_ABI_VERSION 1`、`<BASE>_ABI_HASH`）。
- 规范：`docs/language-spec.md:2254-2262`（§4.57），导出面只取根 `.h.ct` 的 `pub` 函数，泛型模板不导出
  （L39-1w），按值 struct / 接口值 / 容器 / `own` 拒绝（L39-1）。
- 唯一消费点：`test/modules/p39_lib/r3_probe.sh:22`，只断言「宏存在」，不比对数值。
- 名字占用：`selfhost/ct-ast/main.ct:116-117` 的 `verify` 已派发给 `tool::pkg::ct_pkg_verify`

**范围（闭环）**

## 6. PH-46 非泛型 ADT + `match` + 穷尽检查

**一句话**：带载荷的枚举值 + 构造 + 判别 + 穷尽式 `match`，作为一个完整语言特性交付；不做「先上 tagged
union、穷尽以后再说」的半成品。

**现状（S0 必须核对）**

- `pub enum` 今天是 **C 枚举常量集合**（`docs/language-spec.md:711-747`），无载荷、无标签联合。
- 无 `match` 关键字、无值级模式；Phase 33 的 pattern 是 impl 类型 pattern（`docs/language-spec.md:2220-2228`）。
- `Option`/`Result` 是普通泛型 struct，不是 enum（`docs/language-spec.md:2153-2161`；`docs/glossary.md:84`）。
- 仓库自估：`docs/modern-oo-gap.md:170` D2「枚举带载荷 + 模式匹配」= 1,500–3,000 行，难度 L。
- 自举约束：新 AST 节点必须能过 `check-ast.sh` 的自举 fixpoint（编译器编译自身）。

**范围（闭环）**

1. **声明**：`enum Name { A(int), B(char *, int), C }`；有载荷成员即 ADT，无载荷成员作为纯标签成员共存。
   既有「全无载荷」的 `enum` 保持 C 枚举语义不变（D46-1，S0 冻结）。
2. **构造**：`Name::A(1, p)`、`Name::C`；参数个数/类型按成员声明检查。
3. **判别**：`match (expr) { case A(x): …; case B(p, n): …; case C: …; }`，支持 `default:` 兜底。
4. **穷尽**：无 `default` 时，缺失成员即硬错并列出缺失项；有 `default` 时不做缺失检查。
5. **可达性**：重复 case、被 `default` 或前序 case 完全覆盖的 case 报错。
6. **绑定**：每个 case 的绑定个数与成员声明一致；绑定类型即载荷类型；绑定在 case 体内只读（赋值/取址
   明确禁止，理由见 non-goals）。
7. **载荷约束**：载荷类型必须可平凡复制（标量/指针/无 Drop 的 struct）；含 `Drop` 的类型暂不允许作载荷，
   给硬错而不是静默复制（D46-2）。
8. **布局与发射**：`struct Name { int tag; union { … } u; }`；构造/判别/取值全部静态生成，无运行时反射、
   无间接层；不改变既有 C 枚举的发射形态。
9. **与 `switch` 的关系**：`match` 是新语法，不改 `switch` 语义；`match` 只接受 ADT 值。

**完整性边界**

| 维度 | 内容 |
| --- | --- |
| 交付后能写 | 任意非泛型带载荷枚举；构造；穷尽 `match`；`default` 兜底；纯标签成员；按值传递/返回（平凡复制） |
| 不能写 | 泛型 ADT（`enum Option<T>`）；嵌套构造子模式（`case A(B(x))`）；载荷含 `Drop` 的类型；把 ADT 当 C 枚举常量用；对 C 枚举写 `match` |
| 不能写的反馈 | 全部编译期硬错（见下表）；不存在「少写一个 case 仍能编译」的路径 |
| 为什么载荷先限制平凡复制 | 绑定语义（按值还是按引用）与 Drop 归属是一套独立的拥有权设计，硬塞进本相会把 `own`/Drop 规则改坏。给硬错是诚实的边界，不是静默降级 |

**诊断清单**

| 编号 | 触发 | 文案 |
| --- | --- | --- |
| L46-1 | `match` 的操作数不是 ADT | `match needs an ADT value` |
| L46-2 | 非穷尽且无 `default` | `non-exhaustive match: missing '<A>', '<B>'` |
| L46-3 | 不可达 case | `unreachable case '<A>'` |
| L46-4 | 重复 case | `duplicate case '<A>'` |
| L46-5 | 绑定个数/构造参数个数不符 | `case '<A>': expected <m> bindings, got <n>` |
| L46-6 | 载荷类型含 `Drop` | `'<T>' cannot be an ADT payload (needs Drop)` |
| L46-7 | 成员不存在 / 构造参数类型不符 | `'<X>' is not a member of '<E>'` / `'<E>::<X>': expected '<T>', got '<U>'` |
| L46-8 | 对 case 绑定赋值或取址 | `a case binding is read-only` |

**不做（non-goals）**

| 不做 | 理由 | 后续 |
| --- | --- | --- |
| 泛型 ADT | 与单态化/Drop 交互，需独立设计 | PH-47（未定稿） |
| 嵌套构造子模式 | 需要递归模式 AST 与乘积穷尽分析 | PH-47（未定稿） |
| 迁移 `Option`/`Result` 布局 | 破坏已发布 struct 布局与 Drop 胶水契约 | PH-47 且需版本化迁移规则 |
| 载荷含 `Drop` 的拥有权语义 | 与 `own`/Drop 规则耦合 | PH-47 |
| 模式守卫（`case A(x) if x > 0`） | 会让穷尽判定变成不可判定问题 | 不做 |
| 零载荷 ADT | 与既有 C 枚举不可区分，保持原语义 | 不做 |

**任务切分**

| 切片 | 内容 | 边界 |
| --- | --- | --- |

## 9. 完成定义与流程（每相通用）

### 9.1 四件套 DoD（缺一不算完成，即使测试全绿）

1. **实现面**：§范围 的每一条都生效，无 TODO、无「暂不支持」分支；自举链与 fixpoint 通过。
2. **诊断面**：§诊断清单 的每条都有负例夹具、精确文案断言与位置断言；特性面内不存在「能判却静默」的用法；
   若确有判不出的形态，已写进 non-goals 并注明后续相号。
3. **文档面**：`docs/language-spec.md` 对应章节、`docs/tutorial.md` 示例、`README.md` / `README.en.md` 能力
   一览与「明确不做」行、`docs/glossary.md` 术语（涉及标准库时 `lib/std/README.md`）全部更新；旧的
   「不做」条目已删除；`python3 test/docs/check-docs.py` 绿；文档中的能力描述与实现逐条对得上。
4. **门禁面**：新增夹具全部进入 `check-all.sh` 实际运行的脚本（`test/run.sh` / `check-ast.sh` /
   `check-sanitizers.sh` 之一）；`bash selfhost/check-all.sh` 11 道全绿；红证按 T-7 提交（`test(...)` 提交是
   实现提交的父提交，正文含 `baseline: <sha>` 与原始输出）。

### 9.2 每相第一个任务是「核现状」

S0 必须只读核对：该特性在 `docs/language-spec.md`、`docs/tutorial.md`、`README.md` / `README.en.md`、
`docs/glossary.md`、`docs/roadmap.md` 里**现在是怎么写的**，以及实现代码的真实行为。输出写进相卡的
「现状与缺口」段，作为该相冻结输入。任何相卡若缺这一段，不予评审。

### 9.3 节奏

- 每片 ≤150 行、≤3 文件；先红后绿；仓库随时可构建。
- 全量 `check-all.sh` 只在整相收口时跑；单片只跑相关门禁。
- 收口时在同一次动作里完成版本 bump（五处 `CTC_VERSION` + 两处 README + 受影响 golden 重生成），
  版本号取相号次版本；tag 与 push 需用户单独授权。
- 每相一个专属会话，禁止跨相复用。

## 11. 建议先立哪一相

**PH-43**，理由按权重排序：

1. **正确性优先**：它修的是「编译器判得出、却静默发射非法 C」。仓库的底线是「禁发射坏 C、禁吞错」，
   这类缺口优先级高于任何语法糖。
2. **它是 `?` 的硬前置**：`?` 的失败分支就是 `return err:`；先建契约再加糖，避免把同一条缺口放大成
   语法级隐患，也避免 `?` 的 E 校验变成第二套类型规则。
3. **它最小、可在一相内把四件套流程跑通**：实现面只有一处门槛改动，风险可控；用它把「S0 现状核查 →
   红证 → 实现 → 文档同步 → 门禁接入」的模板固定下来，后续相照抄。
4. **`?` 的收益大但只晚一相**：不是长期绕路，且 `?` 的消歧规则与 `ret_type` 形态需要单独冻结，放在
   43 之后评审质量更高。
