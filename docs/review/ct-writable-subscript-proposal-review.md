# 研判记录 · 容器下标可写与嵌套链提案（语法糖口径）

- 日期：2026-11-15
- 对象：[ct-writable-subscript-proposal](../proposals/ct-writable-subscript-proposal.md)
- 证据基线：HEAD `v0.53.1` 重建 `ct-ast`（`/tmp/cthead`）
- 形式：逐条反证（主张 → 反证 → 裁定）
- 结论：**按「下标是 get/put/set 的糖」通过方向**，作为 **PH-62** 立项；吸收 PH-61，不单独先发；
  `Vec::set` 改为「补齐再写」是本提案的前置；本轮不排 phase 卡、不改 `selfhost/**`

## 1 主张席

- JSON 写回需要 `doc["server"]["host"] = "..."`；今天单层写被拒、嵌套链发坏 C。
- `m[k]` / `v[i]` 已经是 `get` 的糖：取不到就是 0 / 零值，**不存在「越界」概念**。
- 因此 `m[k] = v` 只能是 `put` 的糖，`v[i] = x` 只能是 `set` 的糖；糖本身不另造语义。
- 唯一冲突是 `set` 在 `i >= len` 时静默 no-op；这是底层函数行为不对，应由 `set` 修正，
  而不是让语法糖另加「越界处理」。

## 3 裁定

- **定性**：语法糖（B）；`m[k]`/`v[i]` 是 `get`，`m[k]=v` 是 `put`，`v[i]=x` 是 `set`；
  嵌套链逐层套用。朴素嵌套读的「静默坏 C」是可独立止血的 A 类子项。
- **`set` 结论**：改为「补齐再写」——`i >= len` 时 `len = max(len, i+1)`，`[old_len, i)` 填零值，
  再写 `v[i]`；`i < len` 覆盖且 `len` 不变；同位置连续写 `len` 不增；空 Vec 写 0 位 `len` 变 1。
- **洞的语义**：零值元素、密集存储、无 bitmap；`get` 零值、`has` 真、`at` 有指针、`foreach` 访问；
  容器释放跳过全零元素。
- **嵌套写**：Map 缺键建空 Map；Vec 下标不存在按 `set` 补齐；两者都是各自底层函数的行为。
- **通过条件**：
  1. 只做语句级赋值，读类型不变（`Map -> V*`、`Vec -> T`）；
  2. `set` 先改，且 `len = max(len, i+1)` 条款进验收；
  3. 嵌套读零值传播；嵌套写按 Map/Vec 规则补齐；
  4. 物化必须用槽指针；自动创建句柄 release；洞释放跳过；
  5. 吸收 PH-61，废止其「不放开 `v[i] = x`」非目标；
  6. 更新 `test/ast/142_vec_api` 与 `Vec::set` 注释/规范条款。
- **落点**：**PH-62**；PH-61 作为 S1 切片，不再单独占号；本轮不排 phase 卡。
- **建议切片**：S0 读物化/诊断位置 → S1 `v[]=x` → S2 `set` 补齐/len/洞释放 →
  S3 单层写 → S4 嵌套读/写/补齐 → S5 所有权与 golden。

## 4 未决问题

1. `i < 0`：保持不写（提案暂按此）还是改硬错/abort；
2. `set` 分配失败：abort（推荐）还是 no-op；
3. `m[k]=v` 的 `put` 返回 0（NULL 键 / 分配失败）：忽略（纯糖）还是 abort；
4. 洞释放跳过全零元素：统一在 `__ct_elem_release` 还是各容器 `release`；
5. 巨大下标是否设上限/诊断；
6. 是否顺手修 `1:-3788` 负行号诊断（建议单独 patch）；
7. 嵌套写是否覆盖 `Vec` 元素 struct 的字段写（`v[i].f = x`；建议后续单列）。
